Azure.

You already know a cloud. This sheet does not teach you cloud computing again — it teaches you the delta. Most of Azure is AWS with different nouns, and for those parts a translation table is enough. Four things are genuinely different and will catch you out: resource groups, the split between Entra ID and Azure RBAC, the trigger/binding model in Functions, and KQL. Budget one week, not eight.

The same deployment, drawn twice

Sheet 07 put BadgeDesk on AWS. Here is that exact deployment next to its Azure equivalent, tier for tier. Read the pairs left to right, then read the notes — the notes are where the mapping stops being a rename and starts being a different design.

1
Edge: two AWS services collapse into one. Route 53 is Azure DNS and CloudFront is Azure Front Door — but Front Door is CloudFront, Global Accelerator and AWS WAF bundled into a single resource with a single anycast IP. Azure also has Azure CDN, which is the closer like-for-like to CloudFront and which you should ignore: for a new build, Front Door Standard is the answer. The genuinely different bit is that Front Door terminates TLS at the edge and does layer-7 routing globally, so it partially overlaps the next tier down.
2
Load balancing is split three ways, not one. The ALB maps to Application Gateway (regional, layer 7, WAF, path and header rules). The NLB maps to Azure Load Balancer (regional, layer 4). Front Door is the global layer-7 option, which AWS only approximates with CloudFront plus Lambda@Edge. Picking the wrong one of the three is the classic first-week mistake: if you need host- or path-based routing inside one region, you want Application Gateway, and Azure Load Balancer will simply not do it.
3
AKS is EKS with the bill moved. Same Kubernetes API, same manifests, same Helm charts, same images — your Sheet 09 deployment YAML runs unchanged. The differences that matter: the AKS control plane has a Free tier with no SLA (EKS always charges roughly $0.10 per hour per cluster), AKS has explicit node pools where a system pool runs CoreDNS and metrics-server, and identity is wired through workload identity rather than IRSA. Ingress: AKS gives you the Application Gateway Ingress Controller or the newer app-routing add-on instead of the AWS Load Balancer Controller.
4
Postgres: the HA model is the real difference. RDS Multi-AZ keeps a synchronous standby you cannot read from and fails over by moving a DNS name. Flexible Server does the same thing but you choose zone-redundant or same-zone HA explicitly, and it ships PgBouncer inside the service at no extra cost — on RDS you pay for RDS Proxy or run PgBouncer yourself. Flexible Server also has a genuine stop/start, which makes a dev database cost almost nothing overnight.
5
Blob Storage has one more level of nesting than S3. An S3 bucket name is globally unique and holds objects. On Azure the globally unique name is the storage account, and inside it you create containers which hold blobs. So s3://badgedesk-photos/e-902.jpg becomes https://badgedeskprod.blob.core.windows.net/photos/e-902.jpg. The storage account is also the unit of firewalling, private endpoints, redundancy (LRS/ZRS/GRS) and throughput limits — which is why you do not put every workload in one account.
6
Key Vault replaces two services. Secrets Manager (rotating secrets), Parameter Store (config) and KMS (keys) are one resource on Azure, with three object types: secrets, keys and certificates. The trap: Key Vault has two permission models — legacy access policies and Azure RBAC. Always choose RBAC on a new vault, because access policies are per-vault and invisible to every RBAC report you will ever run.
7
Workload identity: same idea, different plumbing. On EKS you annotate a service account, the pod gets a projected OIDC token, and the SDK calls sts:AssumeRoleWithWebIdentity to get temporary credentials for an IAM role. On AKS you create a user-assigned managed identity, federate it to the cluster's OIDC issuer plus a namespace and service-account name, and give it role assignments. There is no AssumeRole step and no policy document attached to the identity — permissions live on the resource side as a role assignment at a scope. That inversion is the single biggest mental shift on this sheet.
8
Monitoring is one product with three names. CloudWatch Logs plus CloudWatch Metrics plus X-Ray becomes Azure Monitor as the umbrella, a Log Analytics workspace as the single store everything queries, and Application Insights as the APM front end that writes into that workspace. You query all of it — platform metrics, container stdout, traces, custom events — with one language, KQL. This is the part of Azure that is genuinely better than the AWS equivalent, and it is also the part with the steepest learning curve.
Why this sheet exists at all

Roughly 30–35% of enterprise cloud spend is Azure, and it is overwhelmingly concentrated in companies that already bought Microsoft 365 — banks, telcos, insurers, government, and almost every large Indian enterprise IT estate. The realistic scenario is not “you become an Azure engineer”. It is “your AWS-shaped team acquires a company running on Azure”, or “the job description says Azure and you have three days’ notice”. One week of deliberate translation work makes you useful in that room. Eight weeks of Azure study when you already know AWS is a waste of eight weeks.

Red pencil — the two-cloud CV

Do not write “AWS and Azure” on your CV with equal weight when you have done one week of Azure. Interviewers probe the second cloud precisely because they expect it to be thin, and “I deployed a container to Azure once” delivered as if it were production experience costs you credibility on the first cloud too. The honest, strong framing is in section 11 — learn it as a sentence and use it verbatim.

The resource hierarchy

This is the first thing that will confuse you and the most frequently asked Azure question in an interview, because it is the one place where the AWS model does not have a slot for what Azure requires. Azure has one more mandatory level than AWS: the resource group.

What a resource group actually is

A resource group is not a tag, not a folder for tidiness, and not a network boundary. It is three things at once, and all three have consequences:

Property 01A lifecycle boundary

az group delete deletes every resource inside it in one dependency-ordered operation. That is the intended use: things that are created together and destroyed together share a group. It is also why a database in the same group as a test cluster is a resignation letter waiting to happen.

Property 02A permission boundary

Role assignments at resource-group scope are the normal unit of Azure RBAC. “The provisioning-worker identity may write blobs” is a role assignment on rg-badgedesk-prod-data, and it automatically covers every storage account you later add to that group.

Property 03A cost and inventory unit

Cost Management reports by resource group for free, with no tagging discipline required. This is the single most practical reason to align groups with something a finance person recognises — a service, an environment, a team.

Resources in different resource groups can talk to each other freely. A resource group has no effect on networking, no effect on latency, and it is not a security perimeter in the way a VPC or a subscription is. A resource group also has a location, which only stores the group's own metadata — you can absolutely put a centralindia VM in a westeurope resource group, and it works. Do not, because if that metadata region has an outage you cannot manage the group's contents.

Red pencil — the classic resource-group mistake

Two mistakes, and everybody makes one of them. One giant group called badgedesk holding prod and non-prod, the database and the ephemeral cluster: now nobody can be given permission to redeploy the app without also being able to delete the Postgres server, and no cost report is useful. One group per resource, the over-correction: forty groups, no lifecycle meaning, and every deployment touches a dozen of them. The working rule is one resource group per environment per lifecycle: rg-badgedesk-prod-core (things that get redeployed — AKS, App Gateway, Container Apps, ACR-adjacent config), rg-badgedesk-prod-data (things that must never be deleted — Postgres, storage accounts, Key Vault), and rg-badgedesk-prod-net (VNet, NSGs, private DNS zones, private endpoints). Then put a delete lock on the data group.

terminal — the resource-group layout for BadgeDesk, with a lock
# Log in and pick the subscription. Everything after this is scoped to it.
az login
az account set --subscription "badgedesk-prod"
az account show --query "{sub:name, id:id, tenant:tenantId}" -o table

# Three groups, three lifecycles. Location here is metadata only.
az group create -n rg-badgedesk-prod-net  -l centralindia --tags env=prod owner=platform
az group create -n rg-badgedesk-prod-data -l centralindia --tags env=prod owner=platform
az group create -n rg-badgedesk-prod-core -l centralindia --tags env=prod owner=platform

# The lock that saves your job. CanNotDelete blocks deletion but allows updates.
az lock create --name no-delete-data --lock-type CanNotDelete \
  --resource-group rg-badgedesk-prod-data

# Prove it. This fails with a LockedResource error rather than deleting Postgres.
az group delete -n rg-badgedesk-prod-data --yes
# (LinkedAuthorizationFailed) ... scope '/subscriptions/.../rg-badgedesk-prod-data'
# cannot perform delete operation because following scope(s) are locked

# What is actually in a group, and what it costs you to look:
az resource list -g rg-badgedesk-prod-core -o table
az group show -n rg-badgedesk-prod-core --query "properties.provisioningState"

Subscriptions are the AWS account

If you take one sentence from this section: an Azure subscription plays the role an AWS account plays. It is the billing boundary, the quota boundary (vCPU limits per region are per-subscription, exactly as AWS service quotas are per-account) and the practical blast-radius boundary. Multi-account AWS designs translate directly into multi-subscription Azure designs: one per environment, one for shared services, one for sandbox.

The part that does not translate: identity. In AWS, every account has its own IAM, and cross-account access means a trust policy and an AssumeRole. In Azure, one Entra ID tenant sits above all your subscriptions and the same user object exists in all of them. Granting an engineer Contributor on three subscriptions is three role assignments for one identity — there is no role-chaining, no credential swap, and no per-subscription user directory. This is why Azure feels more convenient and is easier to over-permission.

Entra ID and RBAC versus IAM

The deepest conceptual difference on this sheet. AWS puts a policy document on the principal. Azure puts an assignment on the resource scope that names a principal and a role. Once that inversion clicks, every Azure permission question becomes easy.

The split: directory versus authorisation

IAM is one service doing two jobs: it stores identities (users, roles) and it decides what they may do (policies). Azure splits those jobs across two products that are administered separately, often by different teams:

Microsoft Entra ID — who you are

A corporate directory. Holds users, groups, app registrations (an application's identity definition), service principals (the instance of an app registration inside one tenant) and managed identities. Issues OAuth 2.0 / OIDC tokens. Owns MFA, Conditional Access, guest (B2B) accounts and every Microsoft 365 login in the company.

Knows nothing about Azure resources. An Entra Global Administrator has, by default, zero permission on your VNet.

Azure RBAC — what you may do

An authorisation layer inside Azure Resource Manager. Holds role definitions (lists of allowed operations) and role assignments (principal + role + scope). Evaluated by ARM on every single control-plane and RBAC-aware data-plane call.

Knows nothing about people. It only ever sees an object ID that came from Entra.

A role assignment is a triple

Every permission in Azure is exactly three things bolted together. If you can name all three, you can grant, audit or revoke anything.

terminal — granting the core service read/write on badge photos, correctly
# The principal: a user-assigned managed identity for the core service.
az identity create -g rg-badgedesk-prod-core -n id-badgedesk-core -l centralindia

PRINCIPAL_ID=$(az identity show -g rg-badgedesk-prod-core -n id-badgedesk-core \
  --query principalId -o tsv)

# The scope: one storage account, not the resource group, not the subscription.
SCOPE=$(az storage account show -g rg-badgedesk-prod-data \
  -n stbadgedeskprodcin001 --query id -o tsv)

# The role: a built-in DATA-plane role. "Contributor" would let it manage the
# account and rotate keys but would NOT let it read a single blob. This catches
# every AWS engineer exactly once.
az role assignment create \
  --assignee-object-id "$PRINCIPAL_ID" \
  --assignee-principal-type ServicePrincipal \
  --role "Storage Blob Data Contributor" \
  --scope "$SCOPE"

# Audit: everything this identity can do, anywhere, including inherited rows.
az role assignment list --assignee "$PRINCIPAL_ID" --all -o table

# Audit the other direction: everyone who can touch the photos account.
az role assignment list --scope "$SCOPE" --include-inherited -o table
Red pencil — control plane versus data plane

Azure has two completely separate permission surfaces and the built-in roles do not overlap them. Contributor on a storage account lets you delete the account, change its firewall and read its access keys — but GET /photos/e-902.jpg with a bearer token returns 403 AuthorizationPermissionMismatch, because reading a blob needs Storage Blob Data Reader. The same split exists for Key Vault (management operations versus “Key Vault Secrets User”), Service Bus, Event Hubs and Cosmos DB. In AWS, s3:GetObject and s3:DeleteBucket are actions in the same policy language, so there is no equivalent trap and no equivalent instinct to fall back on. When something returns 403 on Azure and you are “sure” the permission is there, this is the reason nine times out of ten.

Built-in versus custom roles

Azure ships roughly 500 built-in roles. Use them. The three you will see constantly are Owner (everything, including granting access), Contributor (everything except granting access) and Reader. Contributor is the default over-grant: it can delete your production database, so it belongs on a resource group at most, never on a subscription for an application identity.

Write a custom role only when no built-in role fits and you can name the specific operations. A custom role is a JSON document with Actions (allowed control-plane operations), NotActions (subtracted from those — not a deny, just a subtraction), DataActions and AssignableScopes (where the role is even allowed to be assigned, which has no IAM equivalent).

Managed identities — the IAM role for a workload

A managed identity is a service principal in Entra ID whose credentials Azure creates, rotates and hands to your compute at runtime. It is the direct equivalent of an EC2 instance profile or an IRSA role: the point is that no secret exists anywhere — not in an env var, not in Key Vault, not in the image.

System-assignedTied to one resource, dies with it

Created by flipping a switch on the VM, App Service or Container App. Its lifecycle is the resource's lifecycle: delete the app and the identity and every role assignment referencing it are gone. Simple, and the right default for a single-resource workload. Closest AWS analogue: a role you created for exactly one instance.

User-assignedA standalone resource you attach

Created as its own resource in a resource group, then attached to one or many compute resources. Role assignments survive redeployment, which matters enormously: with a system-assigned identity, every terraform destroy and rebuild produces a new object ID and every grant must be re-created. Use user-assigned for anything managed by IaC or by CI.

Interviewers ask

“How does a pod in AKS get permission to read a blob, with no secret in the container?” The full answer in five beats: a user-assigned managed identity exists as its own resource; a federated identity credential on it trusts the cluster's OIDC issuer URL for one specific namespace and service-account name; the pod's service account is annotated with the identity's client ID and AKS projects a short-lived signed token into the pod at a well-known path; the Azure SDK swaps that projected token at Entra ID for an access token for storage.azure.com; and Blob Storage checks whether a role assignment grants the identity's object ID .../blobs/read at that scope or any ancestor. Service endpoints versus private endpoints

AWS has one concept (VPC endpoints, in gateway and interface flavours). Azure has two products that sound similar and behave completely differently. This is the most commonly asked Azure networking question, and the answer is short: private endpoints, always, for anything new.

Service endpoint — the old answer

A flag on the subnet. Traffic to the PaaS service keeps using the service's public DNS name and public IP, but leaves via the Azure backbone and arrives carrying your subnet identity, so the storage account firewall can allow “requests from snet-aks”.

Free. Configured in one line. No DNS changes. Zero extra resources.

But: the resource still has a public endpoint. It does not work from on-premises over ExpressRoute or VPN. It is per-service, not per-resource — you allow a subnet to reach Storage, and the per-account firewall is the only thing narrowing it. And it does nothing about data exfiltration to someone else's storage account.

Private endpoint — the modern answer

A real NIC, in your subnet, with an address from your CIDR (10.20.2.4), mapped to one specific sub-resource of one specific PaaS instance. You then turn public network access off on the resource entirely.

Works from on-premises over ExpressRoute/VPN, because it is just an address in your address space. Scoped to one resource. Survives an audit.

But: it costs roughly $7–8 per endpoint per month plus data processing, it consumes addresses, and it only works if DNS is right — you must link a privatelink.* Private DNS Zone to every VNet that needs to resolve it.

Compute and containers

The one area where Azure has products AWS genuinely lacks. If you translate “we run containers” straight to AKS because EKS was the answer on AWS, you will build and operate a Kubernetes cluster that BadgeDesk does not need.

App Service and Container Apps — the two AWS does not have

App Service is a fully managed web-app host that predates containers and is still the default way enterprises run HTTP workloads on Azure. You point it at a Git repo, a zip, or a container image; it gives you TLS, custom domains, autoscale, deployment slots (a real staging slot with an atomic swap — the cleanest blue/green primitive in either cloud), and Easy Auth, which puts an Entra ID login in front of your app with no code at all. It is Kubernetes underneath and you never see it.

In production

The scale rule in step 5 is the difference between a demo and a system. BadgeDesk's provisioning worker is idle most of the day and then gets 800 requests when a site onboards a contractor cohort. With --min-replicas 0 and a Service Bus scaler, that costs nothing overnight and 20 replicas at 09:05, with no cluster to keep warm. The same behaviour on AKS means installing KEDA, running nodes that can absorb 20 pods, and paying for them all night. This is the concrete argument for Container Apps and it is worth being able to state with numbers.

Red pencil — scale to zero has teeth

--min-replicas 0 on an HTTP service means the first request after an idle period pays a cold start: a 3–15 second wait while the platform pulls and starts the container. That is fine for the worker and fatal for the gateway. Set --min-replicas 1 on anything a human waits for, and keep zero for queue- and schedule-driven work. The second trap: in-memory state. A revision that scales to zero loses everything, so the idempotency keys and the distributed lock stay in Redis where Sheet 04 put them.

Blob Storage versus S3, and SAS versus presigned URLs

The structural difference from the hero drawing again, because it changes your code: storage account → container → blob, where S3 has bucket → object. The account is the globally unique name, the firewall, the redundancy setting (LRS, ZRS, GRS, RA-GRS) and the throughput ceiling, so one account per workload per environment is the sane default.

Access tiers map closely: Hot is S3 Standard, Cool is Standard-IA, Cold is close to Glacier Instant Retrieval, and Archive is Glacier Deep Archive with a rehydration delay measured in hours. Lifecycle management rules read almost identically to S3's.

Signed URLs differ more than they look. An S3 presigned URL is a signature computed from your credentials — there is no server-side object. A SAS token is a query string with explicit permissions (sp=r), a start and expiry, an optional IP range and protocol restriction, and one of three signing mechanisms: the account key (avoid), a stored access policy on the container (revocable, which presigned URLs are not), or a user delegation key obtained from Entra ID (the right answer, because it requires no account key to exist at all).

def photo_read_url(employee_id: str, minutes: int = 15) -> str:
    """A short-lived, read-only URL for one badge photo.

    Uses a USER DELEGATION KEY, signed by Entra ID on behalf of the managed
    identity. No account key exists on this storage account -- we disabled
    shared-key auth entirely -- so this is the only way to mint a SAS, and the

    # Cache this: it is valid for up to 7 days and each call is an HTTP round trip.
    delegation_key = service.get_user_delegation_key(
        key_start_time=now - timedelta(minutes=5),
        key_expiry_time=now + timedelta(hours=1),

        container_name=CONTAINER,

        start=now - timedelta(minutes=5),           # clock skew allowance
        expiry=now + timedelta(minutes=minutes),
        protocol="https",                           # spr=https
    )
    return f"{ACCOUNT_URL}/{CONTAINER}/{employee_id}.jpg?{sas}"

Cosmos DB, honestly

Cosmos DB is a globally distributed, multi-model database with a genuinely excellent set of guarantees: single-digit-millisecond reads, five well-defined consistency levels (strong, bounded staleness, session, consistent prefix, eventual) rather than DynamoDB's two, multi-region writes, and change feed. It is also the service most often chosen for the wrong reasons and the one whose bill most often surprises people.

The reason is the Request Unit, and there is no AWS analogue to reason from. An RU is a normalised unit of throughput covering CPU, IOPS and memory. A point read of a 1 KB document costs 1 RU. A write of that document costs about 5 RUs. A query that touches ten documents costs the sum of what it read, plus more if it crosses partitions, plus more again if it cannot use an index. You provision RU/s — manually, or autoscale between 10% and 100% of a ceiling — and you are billed for the provisioned number, not the used number. Exceed it and you get 429 TooManyRequests with a x-ms-retry-after-ms header, and the SDK retries silently until it gives up.

Red pencil — when Cosmos DB is the wrong answer

Cosmos is wrong for BadgeDesk's access_requests: they are relational (a request has approvals, an approval has an approver), they need transactions across entities, and they are queried every way a manager can filter a table. That is Postgres, and putting it in Cosmos costs you joins and gains you nothing. Cosmos is also usually wrong as a “cheap document store”: the minimum practical provisioned throughput on a shared database is 400 RU/s, which is roughly $24 per month before storage, per database, forever — a serverless account or Postgres jsonb is cheaper for low traffic. Cosmos is right for the access_events stream: high write volume, a natural partition key, per-vendor document shapes, TTL-based expiry, and a change feed that Sheet 11's consumers can read. Say “write-heavy, key-based access, schema varies, needs global distribution” and you have justified it; say “it is our NoSQL database” and you have not.

Serverless and messaging

Functions is the one service where you cannot get away with a translation table, because the programming model is different rather than the names. Messaging splits into three products where AWS has three different ones, and the mapping is not one-to-one.

Azure Functions versus Lambda: triggers and bindings

A Lambda handler receives an event dictionary and does everything else itself: construct a boto3 client, read the object, write the row, publish the message, handle the retries. An Azure Function declares a trigger (what invokes it, the same idea as a Lambda event source) plus zero or more input bindings and output bindings — declarations that tell the runtime to fetch data before your code runs and to write data after it returns. Your function becomes a pure transformation.

Red pencil — the concurrency assumption you carried over from Lambda

Lambda gives each execution environment exactly one concurrent invocation, so a module-level counter, a mutable cache or a non-thread-safe client is safe by construction. Azure Functions runs many invocations concurrently in one worker process. Global mutable state is now shared state, a requests.Session without a lock will interleave, and your “this is fine on Lambda” instincts produce a race that only shows up under load. Reuse clients (you should — creating a BlobServiceClient per invocation is the classic performance bug) but make them thread-safe and keep per-invocation state local.

Service Bus versus SQS and SNS

AWS separates the queue (SQS) from the fan-out (SNS). Azure puts both in Service Bus, plus a set of enterprise features that AWS mostly does not have, and then adds Event Grid for the lightweight push-webhook case.

QueuePoint to point, like SQS

One consumer group competing for messages. Peek-lock (the default) is SQS's visibility timeout with a name that describes it better: you receive with a lock, you complete(), abandon() or dead_letter(). maxDeliveryCount is the redrive policy and the dead-letter subqueue is created for you rather than being a second queue you provision.

Topic + subscriptionFan-out, but durable

This is the real difference from SNS. A Service Bus subscription is a durable queue with its own filter (a SQL-like rule or a correlation filter) and its own dead-letter queue. A subscriber that is down for an hour finds its messages waiting. An SNS subscriber that is down loses the message unless you put an SQS queue behind it — which is exactly what the Azure model gives you by default.

Event Hubs and Event Grid

Event Hubs is the Kinesis equivalent, and it matters to you for one reason: it exposes a Kafka-compatible endpoint on Standard tier and above. The Kafka producer and consumer you write on Sheet 11 connect to it by changing three settings — no code change, no different client library. An Event Hub is a partitioned log with a retention window, consumer groups that each track their own offsets, and capture-to-blob; the mental model from Sheet 11 transfers completely. The differences: partition count is fixed at creation on lower tiers (no adding partitions later), retention is 1–7 days on Standard rather than indefinite, throughput is bought in Throughput Units, and there is no log compaction.

Red pencil — nothing is collected until you say so

ARM, Bicep and Terraform

ARM templates are the substrate. Every Azure deployment — portal click, CLI command, Terraform apply — ends up as a request to Azure Resource Manager, and an ARM template is a JSON description of what you want. They are the CloudFormation equivalent and, like early CloudFormation JSON, they are unpleasant to write by hand: string-concatenation functions, no types, 400-line files for three resources. You should be able to read one and never need to author one.

Bicep is a typed DSL that transpiles one-to-one to ARM JSON. It is first-party, has no state file (ARM already knows the state of your resource group), gives you real editor completion for every resource type, and every new Azure feature is available on day one. az deployment group create deploys it directly.

Terraform with the azurerm provider is what you already know from Sheet 10. Same HCL, same state file, same plan/apply loop, different resource names. If your team is already on Terraform for AWS, use Terraform for Azure — one tool, one state discipline, one review process is worth more than Bicep's marginal ergonomic advantage. Use Bicep when the shop is Microsoft-only, or when you need a feature the provider has not shipped yet.

Drill — hierarchy and identity
What is a resource group, and what is it actually for?

A mandatory container that every Azure resource belongs to exactly one of. It is three things: a lifecycle boundary (az group delete removes everything inside in one dependency-ordered operation), a permission boundary (the normal scope for RBAC role assignments), and a cost and inventory unit (Cost Management reports by group without any tagging). It is not a network or security perimeter — resources in different groups talk freely. There is no AWS equivalent; the closest analogy is a CloudFormation stack that is also an IAM scope. Practical rule: one group per environment per lifecycle, so the database that must never be deleted is not in the same group as the cluster you rebuild weekly. Expect the follow-up: “how many would you create for BadgeDesk?” — three: core, data, net, plus a delete lock on data.

How does a pod in AKS get permission to read a blob, with no secret in the container?

Workload identity federation. A user-assigned managed identity exists as its own resource. A federated identity credential on it trusts the AKS cluster's OIDC issuer for one exact subject, system:serviceaccount:badgedesk:core-sa. The service account is annotated with the identity's client ID and the pod template carries azure.workload.identity/use: "true", so a mutating webhook projects a short-lived signed token into the pod. The Azure SDK exchanges that token at Entra ID for an access token scoped to storage.azure.com, and Blob Storage authorises the call by checking whether a role assignment grants that object ID .../blobs/read at that scope or an ancestor. The AWS equivalent is IRSA, and the one structural difference is that AWS finishes with AssumeRoleWithWebIdentity handing back credentials for a different principal, whereas Azure never swaps identity — the token is the identity and RBAC decides at the target.

How do managed identities work, and when would you pick user-assigned over system-assigned?

A managed identity is a service principal in Entra ID whose credential the platform holds and rotates; your code gets a token from a local endpoint (IMDS at 169.254.169.254 for VMs, a projected token file for AKS) and never sees a secret. System-assigned is created and destroyed with one resource — simplest, and fine for a single long-lived app. User-assigned is a standalone resource you attach to one or many compute resources; pick it whenever infrastructure is managed by Terraform or CI, because a system-assigned identity gets a new object ID on every destroy-and-recreate and every role assignment referencing it breaks. It also lets the gateway and the core service share one identity if that is what you want, and it lets you create the role assignments before the compute exists, which removes a chicken-and-egg problem from your pipeline.

I gave the service Contributor on the storage account and it still gets 403 reading a blob. Why?

Control plane versus data plane. Contributor grants management operations — delete the account, change the firewall, read the access keys — but not Microsoft.Storage/.../blobs/read, which lives in DataActions and is granted by Storage Blob Data Reader or Storage Blob Data Contributor. The same split applies to Key Vault, Service Bus, Event Hubs and Cosmos DB. AWS has no equivalent distinction — s3:GetObject and s3:DeleteBucket are both just actions — which is exactly why AWS engineers hit this once and remember it forever. Also check propagation: a new role assignment can take a couple of minutes, and cached tokens can be up to an hour stale.

Drill — networking, compute and data
What is the difference between an NSG and a security group?

Both are stateful allow-lists, so the return traffic is automatic in both. Three differences. First, placement: a security group attaches to an ENI, an NSG attaches to a subnet, a NIC, or both — and when both apply, inbound is evaluated subnet-then-NIC and outbound the reverse, so debugging means checking two objects. Second, semantics: NSG rules have numbered priorities from 100 to 4096 with first-match-wins and support explicit Deny, which security groups cannot express at all. Third, references: a security group can name another security group as a source; NSGs cannot, so you use an Application Security Group as a named tag for NICs, or hard-code CIDRs. Bonus point for mentioning service tags — AzureMonitor, Storage.centralindia — as rule sources, which is cleaner than anything AWS offers.

Private endpoint or service endpoint — which and why?

Private endpoint for anything new. A service endpoint is free and is one flag on the subnet, but the PaaS resource keeps its public endpoint and public IP, it does not work from on-premises over ExpressRoute or VPN, and it is scoped to a whole service type rather than one resource. A private endpoint creates a real NIC in your subnet with an address from your CIDR, mapped to one sub-resource of one instance, which lets you set publicNetworkAccess: Disabled and survive an audit; it works from on-premises because it is just an address in your space. The costs are roughly $8 per endpoint per month, some IP consumption, and a hard dependency on DNS — you must link the matching privatelink.* Private DNS Zone to every VNet whose clients resolve the name, which is where almost every failure comes from.

When would you pick Container Apps over AKS for BadgeDesk?

Now, and I would need a specific reason to move. BadgeDesk is four HTTP services, one queue consumer and a nightly job, run by one team with no Kubernetes specialist. Container Apps gives me KEDA scaling on Service Bus queue depth with min-replicas 0, revision-based traffic splitting for canaries, managed ingress and certificates, and a Jobs mode for the reconciler — with no nodes, no upgrades and no idle spend overnight. AKS earns its cost when I need Kubernetes itself: operators such as cert-manager or a Postgres operator, a service mesh with mTLS, DaemonSets, node-level tuning, or a shared multi-team cluster with a platform team to run it. The honest framing is that AKS is a permanent operational commitment and Container Apps is not, so I would start on Container Apps and treat the move to AKS as a decision with a trigger rather than a default.

What is a request unit?

Cosmos DB's normalised currency for throughput, bundling CPU, IOPS and memory into one number. A point read of a 1 KB document is 1 RU; writing it is about 5 RUs; a query costs the sum of what it read plus penalties for cross-partition fan-out and for anything the index cannot serve. You provision RU/s per container or per database — fixed or autoscaling between 10% and 100% of a ceiling — and you are billed on the provisioned figure, not the used one. Exceed it and you get 429 TooManyRequests with x-ms-retry-after-ms, which the SDK retries silently until it gives up. There is no DynamoDB equivalent: RCUs and WCUs are separate and much coarser. The practical consequences are that you log x-ms-request-charge in development, you choose the partition key for even distribution and for the query you actually run, and you remember the 400 RU/s minimum makes it a poor choice for a low-traffic document store.

How does Azure Functions' programming model differ from Lambda's, and why does that matter?

Lambda hands you an event dictionary and you write every SDK call yourself. A Function declares a trigger plus input and output bindings, so the runtime fetches the blob before your body runs and writes the Cosmos document and the queue message after it returns — your function becomes a pure transformation with no clients and no credentials. That is less code and harder unit tests, and it hides retry semantics, which is why many teams use the trigger and then the SDK. Two other differences bite in practice: hosting plan choice determines whether you can reach a VNet at all (Consumption cannot, Flex and Premium can), and a Function worker runs many invocations concurrently in one process, unlike Lambda's one-at-a-time execution environment — so global mutable state that was safe on Lambda is now a race.

Where does the Azure design differ from the AWS one in a way that changes the diagram, not just the labels?

Four places. Subnets are regional, not zonal, so a two-AZ AWS layout with four subnets collapses to two subnets with --zones 1 2 3 on the workloads — the diagram genuinely loses boxes. Resource groups add a level that has to appear somewhere, and I would draw them as the boundaries they are.
