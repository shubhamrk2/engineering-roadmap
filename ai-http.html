One request, end to end

Before any library: what happens between client.get(url) and a Python dict. Every later section is a decision about one box in this drawing.

1
Your code only sees a function call. client.get(url, params=..., headers=...) hides everything to its right. When something goes wrong in production, the bug is almost always in a box you cannot see from this line, which is why this sheet opens the boxes.
2
Connecting is not free and can fail on its own. The name is looked up (DNS), a TCP connection is opened, and for https the two sides agree encryption (TLS). Each can fail before a single byte of your request is sent. The connect timeout bounds exactly this step.
3
A request is plain text. A method, a path, headers, a blank line, an optional body. Section 2 shows one byte for byte.
4
The server is a black box with its own slow parts. It may call a database or, as in BadgeDesk-style integrations, a slow vendor system. The read timeout is how long you will tolerate silence from it, not how long you will tolerate its total work.
5
A response always has a status line. A 404 or a 503 is a perfectly valid HTTP answer; nothing has “gone wrong” at the network level. Whether it is an error for you is a decision your code makes.
6
Classify, then act. Three outcomes only: it worked, it might work if you try again, or trying again cannot help. Getting this classification right is most of what makes a client trustworthy; sections 7 and 8 are about it.
Interviewers ask

“What happens when you call an API from your code?” Name the stages in order: resolve the name, open a TCP connection, negotiate TLS, send the request (method, path, headers, body), wait for the server, read the response (status, headers, body), then decide what the status means. Then add the point that gets you hired: each wait can hang, so each needs a timeout, and a failure at one stage is handled differently from a failure at another.

Request and response anatomy

HTTP is a text protocol over a connection. If you can read these few lines you can debug any API from a log.

The messages, byte for byte

Watch one happen

The block below starts a real HTTP server inside your program (Python’s standard library http.server, on port 0 so the operating system picks a free one), calls it with httpx, and prints exactly what the server received. There is no internet involved. A Handler class with a do_GET method is how http.server decides what to do for a GET; self.headers and self.requestline are the request, send_response and send_header build the response. Daemon threads end when the main program ends.

see_the_wire.py
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer

import httpx


class Echo(BaseHTTPRequestHandler):
    def do_GET(self):
        # self.requestline is the first line of the request, exactly as it arrived
        print("REQUEST LINE :", self.requestline)
        for name in ("Host", "Accept", "X-Request-Id", "User-Agent"):
            print(f"HEADER {name:<11}:", self.headers.get(name))
        body = b'{"items": [], "count": 0}'
        self.send_response(200)                          # status line: HTTP/1.1 200 OK
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()                               # blank line: headers are finished
        self.wfile.write(body)

    def log_message(self, *args):                        # silence the default access log
        pass


server = HTTPServer(("127.0.0.1", 0), Echo)              # port 0: the OS picks a free port
threading.Thread(target=server.serve_forever, daemon=True).start()
base = f"http://127.0.0.1:{server.server_port}"

r = httpx.get(f"{base}/v1/requests", params={"status": "pending", "limit": 2},
              headers={"Accept": "application/json", "X-Request-Id": "req-demo-1"})
print("STATUS       :", r.status_code, r.reason_phrase)
print("CONTENT-TYPE :", r.headers["content-type"])
print("BODY (text)  :", r.text)
print("BODY (parsed):", r.json())
server.shutdown()

Red pencil — the body is text until you parse it

r.text is a string. r.json() is a dict or list. Mixing them up produces TypeError: string indices must be integers, which looks baffling until you remember that "{...}"["id"] is indexing a string. Methods, URLs, status codes, JSON

The vocabulary. A method says what you want done, a status code says what happened, and two properties — safe and idempotent — decide what a client may do automatically.

Methods: safe and idempotent

Safe means the request is not supposed to change anything on the server (it only reads). Idempotent means that sending it once or ten times leaves the server in the same state. These two words decide whether you may retry automatically, so learn the table.

Red pencil — “idempotent” is about server state, not about the response

The second DELETE /v1/requests/req-1 returns 404 instead of 204, yet the method is still idempotent: after one call or ten, the request is gone. Interviewers like this one. The dangerous method is POST: retrying “create a badge” after a timeout can create two badges, because a timeout does not tell you whether the server did the work. Section 12 shows how an idempotency key fixes that.

Interviewers ask

“What is the difference between 401 and 403?” 401 means the server does not know who you are (missing, expired or wrong credentials), so the fix is to authenticate. 403 means it knows exactly who you are and the answer is no, so the fix is permissions. “And 502 versus 504?” Both come from a gateway or proxy in front of the real server: 502 is a bad or empty reply, 504 is no reply in time. In both cases the work behind the gateway may or may not have happened, which is why POST is dangerous to retry.

JSON and content types

JSON is text with six types: object, array, string, number, true/false, null. Content-Type tells the receiver how to read the body. The most common client mistake is sending form-encoded data when the API wants JSON. The block asks a fake server to report back what it was sent, so you can see the three ways to send a body.

bodies_and_content_types.py
import json
import httpx

def echo(request: httpx.Request) -> httpx.Response:
    """A fake server: report back what it was sent."""
    return httpx.Response(200, json={
        "content_type": request.headers.get("content-type"),
        "length": request.headers.get("content-length"),
        "body": request.content.decode(),
    })

client = httpx.Client(transport=httpx.MockTransport(echo), base_url="https://api.example.test")
payload = {"employee_id": "e-902", "site_id": "BLR-01", "reason": "client visit"}

print(client.post("/v1/requests", json=payload).json())     # json=  -> JSON body + Content-Type set for you
print(client.post("/v1/requests", data=payload).json())     # data=  -> HTML-form encoding (NOT JSON)
print(client.post("/v1/requests", content=json.dumps(payload),
                  headers={"Content-Type": "application/json"}).json())   # content= -> raw bytes you built

# JSON is text with six types. Python objects map onto it, and some do not fit.
print(json.dumps({"ok": True, "n": None, "xs": [1, 2.5, "x"]}))   # {"ok": true, "n": null, "xs": [1, 2.5, "x"]}
try:
    json.dumps({"when": __import__("datetime").date(2026, 11, 29)})
except TypeError as err:
    print("TypeError:", err)                                  # dates are not JSON: send an ISO string yourself

Predict — then reveal
A vendor API says “send JSON”. You write client.post(url, data={"site_id": "BLR-01"}). What does the server most likely answer, and why is the message confusing?

Usually 400 or 415 Unsupported Media Type, or 422 from a framework like FastAPI saying the body is missing. data= sends site_id=BLR-01 with a form content type, so a JSON parser sees no JSON at all. The message is confusing because it reports a missing field while you can see you sent one. The fix is the argument name: json=. When an API claims a field is missing that you are sure you sent, print the request you actually made (headers and body) before doubting the server.

Calling APIs from Python with httpx

One Client, configured once, used for many calls. The same four moves every time: build the request, send it, check the status, parse the body.

Why httpx, and why a Client

httpx is a third-party HTTP library with a requests-like interface that also supports async and HTTP/2 and has a built-in way to fake the network (MockTransport, used throughout this sheet). The module-level httpx.get(...) is a convenience that opens and closes a connection each time. A Client keeps a pool of open connections, so repeated calls skip the DNS/TCP/TLS set-up, and it holds settings you want on every call: base URL, headers, timeout, authentication. The word you will hear is “session”; in httpx the object is httpx.Client and it does the same job.

The four moves

Read this block slowly: it contains the vocabulary of the whole day. with ... as client is the context manager from Sheet 23: it closes the connection pool when the block ends. MockTransport plays the server; in real code you delete that one line and give the client a real base_url.

client_basics.py
import httpx

DB = {"req-1": {"id": "req-1", "employee_id": "e-902", "site_id": "BLR-01", "status": "pending"}}

def fake_api(request: httpx.Request) -> httpx.Response:
    if request.headers.get("authorization") != "Bearer test-key":
        return httpx.Response(401, json={"error": "missing or bad key"})
    rid = request.url.path.rsplit("/", 1)[-1]
    if rid in DB:
        return httpx.Response(200, json=DB[rid])
    return httpx.Response(404, json={"error": f"no request {rid}"})

with httpx.Client(
    transport=httpx.MockTransport(fake_api),       # real code would omit this line
    base_url="https://api.example.test",
    headers={"Authorization": "Bearer test-key", "Accept": "application/json"},
    timeout=httpx.Timeout(10.0, connect=3.0),
) as client:                                       # `with` closes the connection pool for you
    r = client.get("/v1/requests/req-1")
    r.raise_for_status()                           # 2xx: returns quietly
    data = r.json()                                # body text -> dict
    print(data["id"], data["status"])              # req-1 pending

    r = client.get("/v1/requests/req-404")
    print(r.status_code, r.is_success)             # 404 False   <- no exception yet: a 404 is a valid HTTP answer
    try:
        r.raise_for_status()                       # NOW it raises
    except httpx.HTTPStatusError as err:
        print(type(err).__name__, err.response.status_code, err.request.url)
        print(err.response.json())                 # the error body often says what was wrong

Red pencil — a 404 is not an exception until you ask for one

client.get(...) returns normally for a 404 or a 503, because the server did answer. Forgetting raise_for_status() is the classic bug: the code carries on, calls .json() on an error body, and reads data["items"] from {"error": "not found"}, which fails three lines later with a KeyError that points nowhere near the cause. Check the status immediately, in the same place, every time. Better still: wrap it once, in a client class (the lab does this).

Interviewers ask

“Why use a Session or Client object instead of calling get() each time?” Connection reuse (no repeated TCP and TLS set-up, which is often most of a small call’s latency), shared configuration such as base URL, headers and timeout in one place, and one place to attach authentication, logging and test doubles. Timeouts: the setting that prevents the 3 a.m. hang

A network call with no limit on how long it may take is a call that can wait forever. A worker that waits forever holds a thread, a connection and a queue slot, and eventually everything behind it stops.

Why “no timeout” means “hang”

TCP will happily keep a connection open for as long as both ends exist. If the server is overloaded, a firewall silently drops packets, or a vendor system stalls half-way through a response, your client waits for data that never comes. Nothing raises. The program just stops making progress. Libraries differ in their defaults: httpx applies a default of 5 seconds to each phase (per the httpx timeouts page), the popular requests library has no default at all, and curl has no overall limit unless you pass --max-time. Do not rely on a default you have not read. Set it, in the code, where the next person will see it.

Predict — then reveal
The client has read=1.0. Server A says nothing for 3 s, then answers. Server B sends one byte every 0.4 s for 3.2 s. Which call raises ReadTimeout, and after how long?

Only A. It raises after about 1.0 s, not 3 s. B never raises: each byte arrives well inside the 1 s window, and the timer resets on every read, so the call succeeds after about 3 s with no timeout at all. This is the difference between a limit on silence and a limit on duration. For a hard cap you need your own deadline, shown as the third part of the block.

import threading, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

import httpx


class Slow(BaseHTTPRequestHandler):
    def do_GET(self):
        try:
            if self.path == "/silent":              # accepts the request, then says nothing for 3 s
                time.sleep(3)
                self.send_response(200); self.send_header("Content-Length", "2"); self.end_headers()
                self.wfile.write(b"ok")
            elif self.path == "/ping":
                self.send_response(200); self.send_header("Content-Length", "0"); self.end_headers()
            elif self.path == "/drip":              # sends 1 byte every 0.4 s, 8 bytes in total
                self.send_response(200); self.send_header("Content-Length", "8"); self.end_headers()

        except OSError:                             # the client gave up and closed the socket: expected here

        pass

def get_with_deadline(url, total=1.5):
    deadline = time.monotonic() + total
    with client.stream("GET", url) as resp:
        chunks = []
        for chunk in resp.iter_bytes():
            chunks.append(chunk)
            if time.monotonic() > deadline:
                raise TimeoutError(f"total deadline of {total}s exceeded")
        return b"".join(chunks)

t0 = time.monotonic()
try:

In production — picking the numbers

Do not guess. Find the vendor’s documented response time, or measure the 95th and 99th percentile of real calls, and set the read limit slightly above the 99th. A limit tighter than normal latency causes self-inflicted failures; a limit of five minutes is no limit at all. Then work backwards from the person or process waiting: if a web request must answer in 5 s, a call that retries three times with 10 s read limits is a bug no matter how resilient it looks. The total deadline is a product decision, not a technical one.

Interviewers ask

“What happens when the server takes 30 seconds to answer?” (This is Saturday’s question.) With no timeout your call blocks for 30 s and ties up a worker, so ten slow calls can starve a pool of ten. With a 10 s read timeout the call fails at 10 s with ReadTimeout. Whether you retry depends on the method: a GET can be retried, a POST that may already have taken effect needs an idempotency key. The user sees either a spinner for 30 s or a clear message after a bounded wait, and you pick the second. Add that the server may still be working after you give up, which is why the work itself must be safe to repeat.

Error handling: a taxonomy

“The call failed” is not one thing. Four different failures need four different responses, and the status code alone does not separate them.

Four families

Family 1 · retryTransport failures

DNS failure, connection refused, connection reset, TLS error. The request may never have reached the server. httpx.TransportError and its children (ConnectError, ReadError, RemoteProtocolError). Usually retryable; for POST ask whether it could have been processed.

Family 2 · retry, carefullyTimeouts

httpx.TimeoutException. The worst case, because you do not know whether the server did the work. Safe to retry for GET, PUT, DELETE. For POST, only with an idempotency key.

Family 3 · depends on the codeHTTP status errors

The server answered. 408, 429, 500, 502, 503, 504: transient, retry. 400, 401, 403, 404, 409, 422: the request or your permission is wrong, retrying changes nothing. httpx.HTTPStatusError, only after you call raise_for_status().

Family 4 · do not retryBody and logic errors

A 200 whose body is not JSON, a missing field, a schema that changed. Retrying a deterministic failure just repeats it. Fail loudly, log the status and a trimmed body, and alert a human. Includes your own bugs: a TypeError is never a reason to retry.

Retries, backoff, jitter, budgets

A retry is a bet that the next attempt will succeed. Placed well it hides a blip. Placed badly it turns one slow server into a dead one.

Exponential backoff with a cap

Waiting a fixed second between attempts hammers a struggling server at a steady rate. Exponential backoff doubles the wait each time (1 s, 2 s, 4 s, 8 s), giving the server room to recover. A cap stops the wait growing without limit (210 seconds is 17 minutes). The formula for wait number i, counting from 0, is min(cap, base × 2i).

Jitter: why randomise

If a vendor blips and a thousand workers all fail at once, plain exponential backoff has all thousand retry again at exactly the same instant, then again, in synchronised waves. Jitter multiplies each wait by a random number so the retries spread out. “Full jitter” (wait a random time between 0 and the computed delay) is the simple, effective version, and is the one the AWS Architecture Blog measured. This block simulates 1000 clients with a seeded random source so the output is the same every run:

jitter_simulation.py
import random
from collections import Counter

def retry_times(clients, attempts, base, cap, jitter, rng):
    """When does each client's retry land? All clients failed together at t=0."""
    times = []
    for _ in range(clients):
        t = 0.0
        for i in range(attempts):
            wait = min(cap, base * 2 ** i)
            t += wait * rng.random() if jitter else wait     # "full jitter": uniform in [0, wait]
            times.append(t)
    return times

rng = random.Random(7)                                        # seeded: the same output every run
for jitter in (False, True):
    times = retry_times(clients=1000, attempts=4, base=1.0, cap=30.0, jitter=jitter, rng=rng)
    windows = Counter(int(t * 10) for t in times)             # bucket arrivals into 0.1-second windows
    peak = max(windows.values())
    print(f"jitter={jitter!s:<5}  busiest 0.1 s window: {peak:>4} requests   (1000 clients, 4 retries each)")

retry_by_hand.py
import random, time

def backoff(attempt, base=0.5, cap=30.0):
    """Wait before retry number `attempt` (0, 1, 2 ...): grows 2x each time, never above cap, randomised."""
    return random.uniform(0, min(cap, base * 2 ** attempt))

calls = []
def flaky():
    calls.append(time.monotonic())
    if len(calls) < 3:                       # fails twice, then works
        raise ConnectionError("vendor reset the connection")
    return "badge provisioned"

for attempt in range(5):                     # at most 5 tries
    try:
        print(flaky())
        break
    except ConnectionError as err:
        wait = backoff(attempt, base=0.05)   # tiny base so this demo takes a fraction of a second
        print(f"attempt {attempt + 1} failed ({err}); sleeping {wait:.3f}s")
        time.sleep(wait)
else:
    raise RuntimeError("gave up after 5 attempts")
You must be able to explain this

Three lines of this block are interview material. 2 ** attempt: why the wait grows. min(cap, ...): why it stops growing. random.uniform(0, ...): why the random part goes after the cap. And the for ... else: the else branch runs only if the loop finished without a break, that is, only if every attempt failed. It is a Python idiom you will not see in C++.

Retry-After, budgets and what must not be retried

Rule 01The server’s number wins

A 429 or 503 may carry Retry-After: either whole seconds (120) or an HTTP date (Wed, 21 Oct 2026 07:28:00 GMT). It knows its own recovery time better than your formula. Cap it so a hostile or buggy value of 86400 does not park your worker for a day. The lab has you parse both forms.

Rule 02Budget the retries

Three attempts per call is fine for one caller. For a thousand callers it triples the load exactly when the server is weakest. A retry budget caps retries as a share of traffic (for example, at most 10 percent extra requests over a minute) or as a total per job, so a bad hour cannot multiply into an outage. Limit retries at one layer, not at every layer: three layers each retrying three times is 27 calls.

Rule 03Idempotency before retry

Retrying a POST that already succeeded creates a duplicate. Either the call is naturally idempotent, or you send a unique Idempotency-Key so the server recognises the repeat and returns the first result. Section 12 shows the mechanism; not every vendor supports it, so find out before the first retry ships.

Retry or not: a comparison

Retry

Transport errors, timeouts, 408, 429, 500, 502, 503, 504, on idempotent calls or with an idempotency key. The failure is a property of the moment, not of your request. Bounded attempts, capped and jittered backoff, Retry-After honoured, the last error raised.

Do not retry

400, 401 (after one refresh), 403, 404, 409, 422, a body that will not parse, any exception from your own code, and a non-idempotent POST with no key. The failure is a property of the request or of you. Repeating it burns quota and delays the real fix.

Red pencil — retries that cause the outage

The classic incident: a database slows down, every client times out at 5 s and retries immediately three times, the database now receives four times the traffic, slows further, and never recovers even after the original fault is fixed. The cure is the set above: backoff, jitter, a cap on attempts, a retry budget, and a total deadline so abandoned work stops. A client you cannot make stop retrying is an attack on your own infrastructure.

OAuth2 client-credentials: the enterprise reality

Most enterprise vendors do not hand out a permanent key. You register an application, receive a client id and client secret, and exchange them at a token endpoint for a short-lived bearer token (commonly valid for about an hour). That is the client-credentials grant of OAuth 2.0, defined in RFC 6749 section 4.4. It is the flow for a service acting as itself, with no human logging in. You have used it already, even if it was hidden inside a Power Platform connector or a Microsoft Entra app registration: the connector held the secret and fetched and refreshed the token for you. Now you are the one writing that part.

The block implements it as an httpx.Auth object, which httpx calls around every request. The token is cached, refreshed 30 s before it expires, and the clock is injected so the demo can move time forward instantly. It runs against a fake vendor, so it shows the mechanism; every real vendor adds its own details (extra parameters such as scope or audience, the token endpoint URL, sometimes credentials in the body instead of Basic auth). Read the vendor’s documentation for those; do not assume.

    """OAuth2 client-credentials: swap a client id + secret for a short-lived bearer token,
    cache it, and refresh before it expires."""

    def __init__(self, token_client, token_url, client_id, client_secret, clock=time.monotonic):
        self.token_client, self.token_url = token_client, token_url
        self.client_id, self.client_secret = client_id, client_secret
        self.clock, self._token, self._expires_at = clock, None, 0.0

    def _fetch(self):
        r = self.token_client.post(self.token_url, data={"grant_type": "client_credentials"},
                                   auth=(self.client_id, self.client_secret))
        r.raise_for_status()
        body = r.json()
        self._token = body["access_token"]
        self._expires_at = self.clock() + body["expires_in"] - 30     # refresh 30 s early: latency and clocks drift

    def auth_flow(self, request):
        if self._token is None or self.clock() >= self._expires_at:
            self._fetch()
        request.headers["Authorization"] = f"Bearer {self._token}"
        response = yield request
        if response.status_code == 401:                               # revoked early: fetch once more, retry once
            self._fetch()
            request.headers["Authorization"] = f"Bearer {self._token}"
            yield request

Pagination: offset versus cursor

An API will not return a million rows in one response, and you would not want it to. It returns a page and tells you how to get the next. The way it tells you decides whether you lose or duplicate data.

Why page at all

One huge response costs memory on both ends, risks hitting a timeout, and fails as a whole if anything goes wrong at the last byte. Pages are small, bounded and individually retryable. The price is that your client must loop, and that the data may change while you loop. Two designs exist, and they behave very differently under change.

offset_vs_cursor.py
# A "database" of 6 requests, newest first. A new one arrives between the client's two page fetches.
rows = [f"req-{n}" for n in range(6, 0, -1)]          # ['req-6', ..., 'req-1']

def page_by_offset(offset, limit):
    return rows[offset:offset + limit]

seen = page_by_offset(0, 3)                            # the client fetches page 1
print("offset page 1:", seen)                          # ['req-6', 'req-5', 'req-4']
rows.insert(0, "req-7")                                # <-- a new request is created meanwhile
page2 = page_by_offset(3, 3)                           # the client fetches page 2
print("offset page 2:", page2)                         # ['req-4', 'req-3', 'req-2']   req-4 AGAIN
print("duplicates   :", set(seen) & set(page2))        # {'req-4'}; and req-1 is never reached by page 2

# Cursor: "give me the 3 items after THIS one". A new row at the front cannot shift it.
rows = [f"req-{n}" for n in range(6, 0, -1)]
def page_after(cursor, limit):
    start = 0 if cursor is None else rows.index(cursor) + 1
    chunk = rows[start:start + limit]
    next_cursor = chunk[-1] if start + limit < len(rows) else None
    return {"items": chunk, "next_cursor": next_cursor}

p1 = page_after(None, 3)
rows.insert(0, "req-7")                                # the same interference
p2 = page_after(p1["next_cursor"], 3)
print("cursor page 1:", p1["items"])                   # ['req-6', 'req-5', 'req-4']
print("cursor page 2:", p2["items"], p2["next_cursor"])   # ['req-3', 'req-2', 'req-1'] None

Red pencil — the cursor loop that never ends

The loop is “ask, append, follow next_cursor until it is empty”. If a server bug returns the same cursor forever, or you accidentally compare against the wrong field, that loop runs until memory is gone and your job never finishes. Production loops carry two guards: remember every cursor seen and stop (with an error) on a repeat, and cap the number of pages. The lab’s fetch_all requires both, and its tests deliberately feed it a server that loops. Also check what “empty” means for the specific API: an empty list of items with a non-null cursor is legal on some APIs, so stop on the cursor, not on the list.

Rate limits: 429, Retry-After, throttling yourself

Every serious API caps how fast you may call it. You can find out the limit the hard way, with 429s, or the polite way, by never exceeding it.

What a limit looks like

When you exceed it the API answers 429 Too Many Requests, usually with a Retry-After header giving seconds or a date. Many APIs also send headers that report your budget on every response so you can slow down before hitting the wall. Those headers are not standardised: you will meet X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset (the JSONPlaceholder response earlier carried exactly these three) and other spellings. Read the vendor’s page; never hard-code a guess. Limits may also be per key, per user, per IP, per endpoint, or per second, minute or day.

A token bucket, with a clock you control

A token bucket holds up to capacity tokens and refills at rate tokens per second. Each request spends one token; with none left you must wait. It allows short bursts while enforcing an average. The clock is passed in as a function so the demo (and a test) can move time forward without sleeping. This shows the idea for one process; it is not a distributed rate limiter, and take() only reports a wait, it does not reserve the slot.

token_bucket.py
import time


class TokenBucket:
    """Client-side throttle: at most `rate` requests per second on average, bursts up to `capacity`."""

    def __init__(self, rate, capacity, clock=time.monotonic):
        self.rate, self.capacity, self.clock = rate, capacity, clock
        self.tokens, self.last = float(capacity), clock()

    def take(self):
        """Return 0.0 if a request may go now, otherwise how many seconds to wait first."""
        now = self.clock()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)   # refill for the time that passed
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return 0.0
        return (1 - self.tokens) / self.rate


t = [0.0]                                       # a fake clock: the demo runs instantly and is repeatable
bucket = TokenBucket(rate=2, capacity=3, clock=lambda: t[0])   # 2 per second, burst of 3

print([bucket.take() for _ in range(5)])        # [0.0, 0.0, 0.0, 0.5, 0.5]  burst of 3 passes, then you must wait
t[0] += 1.0                                     # one second passes: 2 tokens refill
print([bucket.take() for _ in range(3)])        # [0.0, 0.0, 0.5]
In production — shared quotas

Five workers each throttling to 10 requests per second is 50 per second against a vendor that allows 10. A client-side bucket is per process. For a shared limit you need shared state (often Redis in a bigger system), or you divide the budget by the number of workers, or you funnel calls through one queue-fed worker. And a vendor’s limit is frequently per account, so another team’s job can consume yours: that is why handling 429 correctly is not optional even when you throttle.

Idempotency keys: making POST safe to retry

The server remembers the Idempotency-Key of every create it has processed. A repeat with the same key does not create anything: it returns the stored answer. The client picks a key tied to its own unit of work (here, the request id) and reuses the same key on every retry. That is the standard defence against the “timeout, did it happen?” problem. The header name and the rules (how long keys are remembered, what happens when the body differs) vary by vendor; this block shows the idea with a fake server.

idempotency_key.py
import httpx

created = {}                                     # the fake server: idempotency key -> the answer it first gave

def server(request):
    key = request.headers.get("idempotency-key")
    if key is None:
        return httpx.Response(400, json={"error": "Idempotency-Key header required for POST"})
    if key in created:                           # seen before: replay the stored answer, create nothing
        return httpx.Response(200, json=created[key], headers={"Idempotent-Replay": "true"})
    body = {"id": f"badge-{len(created) + 1}", "employee_id": "e-902"}
    created[key] = body
    return httpx.Response(201, json=body)

c = httpx.Client(transport=httpx.MockTransport(server), base_url="https://vendor.example.test")
key = "req-1-provision"                          # derived from YOUR request id: stable across retries

first = c.post("/v1/badges", json={"employee_id": "e-902"}, headers={"Idempotency-Key": key})
print(first.status_code, first.json())           # 201 {'id': 'badge-1', 'employee_id': 'e-902'}
# ... imagine the connection dropped before the response was read. The client cannot tell whether the
# badge was made, so it sends the SAME request with the SAME key:
again = c.post("/v1/badges", json={"employee_id": "e-902"}, headers={"Idempotency-Key": key})
print(again.status_code, again.json(), again.headers["idempotent-replay"])   # 200 {'id': 'badge-1', ...} true
print("badges created:", len(created))           # 1, not 2
Red pencil — a new key per attempt defeats the point

Generating a fresh random key inside the retry loop gives every attempt a different key, so the server treats each as a new request and you create duplicates anyway. The key must be created once, before the first attempt, from something stable, and stored with the work item so a restarted worker uses the same one.

Enterprise APIs: the reality

Public tutorial APIs are fast, consistent and free of surprises. The ones you will integrate for money are none of those.

What I mean, kept generic on purpose

This section describes patterns from the kind of work you have done, with no product, tenant or client specifics, and you should keep it that way in interviews: say what you built and learned, never the confidential detail. Everything below is also true of public APIs you can name freely.

Pattern 01Slow and bursty

A ticketing or access-control vendor may answer in 200 ms at 10:00 and 20 s at 10:05 when a nightly job runs on their side. Read-timeouts chosen from a good day cause failures on a bad one. Measure the tail, not the average.

Pattern 02Quirks are the norm

Dates in three formats. A 200 whose body says "success": false. Pagination by page number in one endpoint and by cursor in the next. An id that is a string in one place and a number in another. Wrap each quirk in one adapter function, comment why, and test it, so the rest of the code sees clean data.

Pattern 03Expiring credentials

Object stores and many SaaS APIs use short-lived signed URLs or tokens. A long upload that outlives its token fails halfway with a 403, and it looks like a permissions bug. Refresh before expiry (as in the OAuth block), and check the clock on your machine.

Pattern 04Throttling you did not cause

The quota is shared per account or per tenant. Another job, another team, the vendor’s own UI can burn it. Handle 429 properly even if you throttle, and log the remaining budget on each response so you can see it fall.

Pattern 05Duplicates and replays

Webhooks are delivered at least once, so you will see the same event twice. Your retries cause duplicates on their side. Everything that writes needs an idempotency story: a key, a natural unique id, or a check-then-write that is itself safe.

Pattern 06The contract drifts

Vendors add fields (harmless) and occasionally change or drop one (not). Parse tolerantly, validate the fields you depend on, and alert when one is missing, rather than letting None flow into a database.

Red pencil — “it worked in the sandbox”

Vendor sandboxes are usually fast, empty and lenient. They rarely reproduce rate limits, slow tails, pagination over thousands of rows, or expiring tokens. A client proven only against a sandbox has not been tested against the thing that fails in production. Build the failure cases yourself with fakes (the next section), and treat the first week in production as part of the testing.

Drill — HTTP and API clients
What is the difference between a safe method and an idempotent method? Give an example of each that is not the other.

Safe means the request does not change server state (GET, HEAD). Idempotent means repeating it leaves the same final state as doing it once (GET, PUT, DELETE). Every safe method is idempotent, but not the reverse: DELETE is idempotent and not safe. POST is neither, which is why a blind retry of a POST can create duplicates. Follow-up: “the second DELETE returns 404, so is it not idempotent?” It is: idempotency is about server state, which is the same, not about the response code.

Why must every HTTP call from a service have a timeout, and what are the different kinds?

With no limit a stalled server or a dropped connection makes the call wait forever, which ties up a worker, a connection and a queue slot until the service stops. In httpx there are four limits: connect (opening the connection), read (silence between chunks of response), write (sending the body) and pool (waiting for a free connection). There is no built-in total, so a slow-drip response can outlast every per-read limit; I enforce a total deadline myself. Follow-up: “what number?” From measured latency: slightly above the 99th percentile for read, a few seconds for connect.

The server takes 30 seconds to answer. Walk me through what your client does.

With a 10 s read timeout it raises ReadTimeout at 10 s, not 30. If the call is a GET I retry after a capped, jittered backoff, within a total deadline set by whoever is waiting. If it is a POST I only retry with an idempotency key, because the server may have finished the work behind my back, otherwise I check the resource’s state first. The user gets a bounded wait and a clear message instead of a hang, and I log the timeout with the call, not the credentials. If it keeps happening I stop retrying and alert.

Which failures should you retry and which should you not? Why?

Retry transient ones: network errors, timeouts, 408, 429, 500, 502, 503, 504, on calls that are safe to repeat. Do not retry 400, 401 (beyond one token refresh), 403, 404, 409 or 422, or a body that will not parse, or any exception from my own code, because the same request fails the same way and retrying burns quota and hides the bug. A POST needs an idempotency key before it joins the retry list. Follow-up: “what about 500?” Usually transient, so a few attempts, but a deterministic 500 on one input should be caught by a low attempt limit and reported.

Explain exponential backoff with jitter. Why not a fixed delay, and why add randomness?

A fixed delay keeps hitting a struggling server at a steady rate. Exponential backoff doubles the wait each attempt (min(cap, base times 2 to the i)), giving it room to recover, and the cap stops the wait growing without limit. Without randomness, a thousand clients that failed together all retry at the same instant and form waves; jitter (a random wait between 0 and the computed delay) spreads them. And if the server sends Retry-After I use that instead, capped. Follow-up: “what is a retry budget?” A limit on retries as a share of total traffic so retries cannot multiply load during an outage.

How do you make a POST safe to retry?

Send an idempotency key: a unique id the client generates once, from a stable source such as the work item id, before the first attempt, and reuses on every retry. The server stores the result against the key and replays it on a repeat instead of creating a second resource. If the vendor has no such feature I make the operation naturally idempotent (a PUT to a known id, or a lookup by my own reference before creating), or accept at-least-once and deduplicate afterwards. A fresh key per attempt defeats the whole mechanism.

401 versus 403, and authentication versus authorisation.

Authentication is proving who you are; authorisation is what that identity may do. 401 means the server does not know who you are (missing, expired or wrong credentials): refresh or fix the credential. 403 means it knows you and refuses: change permissions or scopes, because retrying with the same identity cannot help. A valid token can still return 403. Follow-up: “what do you do on a 401 with an OAuth token?” Fetch a new token once and retry once; a second 401 is a configuration failure, so fail loudly.

Where do secrets live, and what are the ways they leak?

In the process environment (environment variables, or a secrets manager), read once at start-up, failing immediately if missing. For local development a .env file that is in .gitignore before the first commit, plus a .env.example with fake values. They leak through source code and Git history, URLs and query strings, log lines and error messages, and screenshots. If one leaks, revoke and rotate it at once, since deleting it from the latest commit does not remove it from history.

Offset versus cursor pagination: which would you pick to copy all records from a vendor, and what can go wrong with the loop?

Cursor, because the data changes while I read it, and offset then repeats or skips rows when something is inserted or deleted between pages, and gets slower on deep pages. The cost is that I can only go forward. The loop can run forever if the server repeats a cursor, so I remember cursors I have seen and stop with an error on a repeat, and I cap the page count. I also stop on the cursor being absent, not on an empty list, since some APIs return empty pages with a valid cursor.

You get a 429 with Retry-After: 30. What do you do, and how do you stop it happening again?

Wait the 30 seconds (capped by my maximum so a huge value cannot park a worker), then retry, within my attempt budget and total deadline. The header may also be an HTTP date, so I parse both forms. To stop earning 429s I throttle on the client side with a token bucket below the documented limit, share the budget across workers (it is per account, so division or shared state), batch or cache to make fewer calls, and log remaining-quota headers if the vendor sends them. I still handle 429, because someone else can use up the quota.

How do you test code that calls a flaky third-party API?

I inject the things that are slow, random or remote: the transport (httpx.MockTransport with a handler that returns scripted responses or raises timeouts), the sleep function, the clock and the jitter source. Then I can reproduce 503 then 200, a 429 with Retry-After, a timeout, a repeating cursor and invalid JSON in milliseconds, and assert both on results and on the requests that were sent. The limit is that a mock only encodes my assumptions, so I keep recorded real responses as fixtures and run a few contract checks against the vendor’s sandbox.
