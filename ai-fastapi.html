FastAPI and Pydantic.

A web API is a function with a contract bolted to the front and the back. Pydantic is the contract: it turns type hints into checks on everything that comes in and a filter on everything that goes out. FastAPI is the machinery that reads your hints, runs the checks, calls your function and writes the answer. Both portfolio projects (the knowledge assistant and the operations assistant) are exactly this shape, so this week is the one the rest of the roadmap leans on.

One request, end to end

Every behaviour on this sheet (404, 405, 422, 401, 403, 201, your own error shape) happens at a specific box on this path. Learn the path and the rest is looking things up.

1
uvicorn speaks HTTP so your code does not have to. It owns the socket, parses the bytes, and calls your application through a tiny standard interface called ASGI. FastAPI never touches a network connection.
2
Middleware wraps the whole app like layers of an onion. It sees the request first and the response last, so it is the right place for things that apply to every route: CORS headers, a request id, timing, logging. The last middleware you add is the outermost.
3
The router matches a path and a method before any of your code runs. No path matches: 404. The path exists but not for that method: 405. Both are produced by the framework, in its own shape, until you override it.
4
FastAPI reads your function signature once, at start-up. Each parameter becomes a rule: this one comes from the path, that one from the query string, this one from the JSON body, this one is a Depends. Per request it gathers those values, validates them with Pydantic, and runs your dependencies. Any failure follows the red arrow.
5
Your function runs only with valid, typed inputs. That is the whole payoff: no if "days" not in body at the top of every handler. A plain def is run in a worker thread; async def runs on the event loop (see sync versus async).
6
The response model is a second check, pointed outwards. Whatever you return is validated against it and everything not declared is dropped. A field you stored (an internal note, a password hash) cannot leak unless you declared it.
Why this sheet teaches the mechanism first

In an interview, “I used FastAPI” means nothing; “a request with days=abc never reaches my handler because FastAPI validates against the signature and returns 422 with a field-level body, and I replaced that body with our standard error shape” means you understand it. Each section writes the mechanism by hand where that is short (raw ASGI, a hand-signed token, a hand-written validation loop), then shows the library, then says when the library is the wrong choice.

The four layers: ASGI, uvicorn, Starlette, FastAPI

Four names that blur together on day one. Each does one job; knowing which job tells you where to look when something breaks.

You do not have to take the claim that FastAPI is “just an ASGI callable” on trust. The block below is a complete ASGI application with no framework at all, called through Starlette’s test client.

raw_asgi.py
from starlette.testclient import TestClient

async def app(scope, receive, send):         # the entire ASGI contract: three arguments
    assert scope["type"] == "http"           # scope: who is calling (method, path, headers...)
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/plain")]})
    await send({"type": "http.response.body", "body": b"hello from raw ASGI"})

r = TestClient(app).get("/anything")
print(r.status_code, r.text)                 # 200 hello from raw ASGI
# FastAPI(...) instances are exactly this kind of callable. uvicorn does not know or care which one it was given.
Interviewers ask

“What is the difference between FastAPI, Starlette and uvicorn?” uvicorn is the server: it owns the socket and speaks HTTP. Starlette is the toolkit that provides routing, middleware and request/response objects. FastAPI sits on Starlette and adds type-hint based parameter handling, Pydantic validation, dependency injection and generated OpenAPI docs. ASGI is the interface that lets the server call the app. Follow-up they will ask: “why not run it with python main.py?” Because a FastAPI object is not a server; something must listen on a port, and that something is uvicorn (or another ASGI server).

Route decorators and path operations

FastAPI calls each (method, path, function) triple a path operation. The decorator names the HTTP method; the function is the handler. Methods carry meaning that clients, caches and retry logic rely on, so choose them on purpose.

DecoratorMeaningSafe?Idempotent?Typical status
@app.getRead. Must not change state.yesyes200
@app.postCreate, or run an action.nono201 (created), 200/202
@app.putReplace a whole resource.noyes200, 204

Routes are matched in the order you declare them. This is the classic first bug: a general pattern declared before a specific one swallows it.

route_order.py
from fastapi import FastAPI
from fastapi.testclient import TestClient

app = FastAPI()

@app.get("/requests/{request_id}", tags=["requests"], summary="Fetch one request")
def by_id(request_id: str):
    return {"matched": "by_id", "id": request_id}

@app.get("/requests/mine")                   # declared SECOND: never reached
def mine():
    return {"matched": "mine"}

c = TestClient(app)
print(c.get("/requests/mine").json())        # {'matched': 'by_id', 'id': 'mine'}   <- the trap

# Fix: declare the fixed path first. Rebuild to prove it.
app2 = FastAPI()

@app2.get("/requests/mine")
def mine2():
    return {"matched": "mine"}

@app2.get("/requests/{request_id}")
def by_id2(request_id: str):
    return {"matched": "by_id", "id": request_id}

c2 = TestClient(app2)
print(c2.get("/requests/mine").json())       # {'matched': 'mine'}
print(c2.get("/requests/req-1").json())      # {'matched': 'by_id', 'id': 'req-1'}
Red pencil — GET that changes state

A GET /requests/{id}/approve is a bug waiting for a link-preview bot, a browser prefetch or a crawler to approve things by looking at them. Anything that changes state is POST, PUT, PATCH or DELETE. Put the verb in the method, not only in the URL.

Parameters: path, query, header, body

FastAPI decides where each argument comes from by looking at its name and its type. Get the four sources straight and the automatic 422 stops being mysterious.

from typing import Annotated
from fastapi import FastAPI, Header, Path, Query
from fastapi.testclient import TestClient
from pydantic import BaseModel

app = FastAPI()

class Note(BaseModel):                                   # a model type => read from the JSON body
    text: str

@app.post("/sites/{site_id}/requests/{request_id}/notes")
def add_note(
    site_id: Annotated[str, Path(pattern=r"^[A-Z]{3}-\d{2}$")],   # PATH, with a pattern
    request_id: int,                                              # PATH, converted to int
    note: Note,                                                   # BODY
    urgent: bool = False,                                         # QUERY: has a default, so optional
    limit: Annotated[int, Query(ge=1, le=50)] = 10,               # QUERY with bounds
    x_trace_id: Annotated[str | None, Header()] = None,           # HEADER: x_trace_id <-> X-Trace-Id
):
    return {"site": site_id, "id": request_id, "text": note.text,
            "urgent": urgent, "limit": limit, "trace": x_trace_id}

           json={"text": "badge printed"}, headers={"X-Trace-Id": "t-1"})

Predict, then reveal

You add a parameter tags: list[str] = [] to a GET handler and send ?tags=a&tags=b. What happens?

Open the answer

FastAPI treats a plain list[str] as a body, not a query parameter, so the query string is ignored and a GET would be expecting a JSON body. To read repeated query values you must mark it explicitly: tags: Annotated[list[str], Query()] = []. The rule to remember: scalars default to query, collections default to body, and Query() overrides the guess.

Typed parameters and the automatic 422

Type hints are not decoration here. request_id: int means “convert to an integer or reject the request”. The rejection is a 422 Unprocessable Content (older docs say “Unprocessable Entity”): the request was well-formed HTTP but its content broke the contract. Your function is never called. Contrast the others you will see:

Reading the validation error body

The default 422 body is a JSON object with one key, detail, holding a list of every problem at once, not just the first. Learn to read it; you will do it daily.

read_422.py
import json
from typing import Annotated
from fastapi import FastAPI, Query
from fastapi.testclient import TestClient

app = FastAPI()

@app.get("/requests/{request_id}")
def one(request_id: int, limit: Annotated[int, Query(ge=1, le=50)] = 10):
    return {"id": request_id, "limit": limit}

c = TestClient(app)
r = c.get("/requests/abc?limit=0")
print(r.status_code)                         # 422
print(json.dumps(r.json(), indent=1))
# {
#  "detail": [
#   {"type": "int_parsing",            "loc": ["path", "request_id"], "msg": "Input should be a valid integer, unable to parse string as an integer", "input": "abc"},
#   {"type": "greater_than_equal",     "loc": ["query", "limit"],      "msg": "Input should be greater than or equal to 1", "input": "0", "ctx": {"ge": 1}}
#  ]
# }

# A reader for humans and logs: field path, then message.
for err in r.json()["detail"]:
    where = ".".join(str(part) for part in err["loc"])   # loc is a list: where the value came from, then the field
    print(f"{where}: {err['msg']}")
# path.request_id: Input should be a valid integer, unable to parse string as an integer
# query.limit: Input should be greater than or equal to 1
KeyWhat it tells you
locThe address of the bad value. First element is the source (path, query, header, body), the rest is the path inside it: ["body", "attachments", 1, "size_kb"] means the second attachment’s size.
typeA stable machine-readable code (int_parsing, missing, string_too_short). Branch on this, never on msg.
msgA human sentence. Wording can change between versions.
inputWhat the client actually sent. Useful in debugging; do not echo it back or log it for sensitive fields.
ctxThe limits that were violated (ge: 1, pattern…), when there are any.
Red pencil — the 422 you did not expect

Two classic causes. (1) You send JSON but forget the Content-Type: application/json header from a hand-rolled client, so the body arrives as a plain string and FastAPI answers model_attributes_type with loc ["body"] (checked here with a text/plain header). (2) You declared a body model and your client sends the fields as query parameters, or the other way round. Read loc: it says body or query, which tells you which side is wrong in ten seconds. Also check the JSON itself: a malformed document gives a json_invalid error with loc pointing into body.

Pydantic v2: the contract

Pydantic checks data against a class made of type hints, and tells you exactly what is wrong. It works on its own, with no web server, which is how you will test it on day 38.

What it replaces: validation by hand

Write the checks yourself once, so you know what you are buying. Even for two fields it is long, and it stops at the first thing you remembered to check.

by_hand_vs_pydantic.py
import re
from pydantic import BaseModel, Field, ValidationError

def check_by_hand(data):
    errors = []
    emp = data.get("employee_id")
    if not isinstance(emp, str) or not re.fullmatch(r"e-\d+", emp):
        errors.append("employee_id must look like e-902")
    try:
        days = int(data.get("days"))
    except (TypeError, ValueError):
        errors.append("days must be a whole number")
    else:
        if not 1 <= days <= 30:
            errors.append("days must be between 1 and 30")
    return errors

class Visit(BaseModel):                                  # the same rules, declared
    employee_id: str = Field(pattern=r"^e-\d+$")
    days: int = Field(ge=1, le=30)

bad = {"employee_id": "902", "days": "abc"}
print(check_by_hand(bad))
# ['employee_id must look like e-902', 'days must be a whole number']

try:
    Visit.model_validate(bad)                            # model_validate: dict in, validated object out
except ValidationError as e:
    print(e.error_count(), [(x["loc"], x["type"]) for x in e.errors()])
    # 2 [(('employee_id',), 'string_pattern_mismatch'), (('days',), 'int_parsing')]

v = Visit.model_validate({"employee_id": "e-902", "days": "5"})
print(v, type(v.days))                                   # employee_id='e-902' days=5 <class 'int'>   (the string "5" became 5)

BaseModel, Field constraints, validators

A BaseModel subclass is a schema. Annotations give types; Field(...) adds constraints, defaults and descriptions; validators add rules a constraint cannot express. In v2 the decorators are field_validator (one field) and model_validator (several fields together). The v1 names validator and root_validator are the ones to distrust when an old tutorial shows them.

ticket_model.py
from datetime import date
from enum import Enum
from pydantic import BaseModel, Field, ValidationError, field_validator, model_validator

class Priority(str, Enum):                               # str mixin: serialises as the plain string
    LOW = "low"
    HIGH = "high"
    URGENT = "urgent"

class TicketIn(BaseModel):
    title: str = Field(min_length=3, max_length=80)      # constraints live on the field
    priority: Priority = Priority.LOW                    # a default makes it optional
    assignee: str | None = None                          # may be None AND has a default
    due: date | None = None

    @field_validator("title")                            # runs after the type check, on this field only
    @classmethod
    def tidy_title(cls, v: str) -> str:
        v = " ".join(v.split())                          # collapse runs of whitespace
        if not v:
            raise ValueError("title must not be blank")
        return v                                         # whatever you return becomes the stored value

    @model_validator(mode="after")                       # runs when ALL fields are valid; sees the whole object
    def urgent_needs_owner(self):
        if self.priority is Priority.URGENT and self.assignee is None:
            raise ValueError("urgent tickets need an assignee")
        return self

t = TicketIn(title="  Badge   reader   offline ", priority="high")   # keyword args work like model_validate
print(repr(t.title), t.priority)                         # 'Badge reader offline' Priority.HIGH

try:
    TicketIn(title="ok", priority="urgent")              # title too short AND urgent without assignee
except ValidationError as e:
    for err in e.errors():
        print(err["loc"], err["type"])
    # ('title',) string_too_short        <- field errors stop the model validator from running
try:
    TicketIn(title="Gate stuck", priority="urgent")
except ValidationError as e:
    print(e.errors()[0]["loc"], e.errors()[0]["type"])   # () value_error   (loc is empty: the whole model)
    print(e.errors()[0]["msg"])                          # Value error, urgent tickets need an assignee
You must be able to explain this

Why did the first failure report only the title error, and not the “urgent needs an assignee” rule as well? Because a mode="after" model validator runs on a fully built object, which only exists when every field passed. If you need cross-field rules to report alongside field errors, you have to use mode="before" and work on the raw dictionary. Say this in an interview and you have shown you have actually read a ValidationError.

Validation, serialisation, and strict versus lax

Two directions, two verbs. Validation (model_validate, model_validate_json, or just calling the class) turns untrusted input into a trusted object. Serialisation (model_dump, model_dump_json) turns the object back into plain data for a response, a file or a log line. By default validation is lax: it converts sensibly ("5" to 5, "2026-12-07" to a date, "yes" to True). Strict mode refuses to convert.

lax_strict_dump.py
from datetime import date
from pydantic import BaseModel, ConfigDict, Field, ValidationError

class Reading(BaseModel):
    count: int
    seen_on: date
    ok: bool = False

# LAX (the default): the usual JSON-ish inputs are converted
r = Reading.model_validate({"count": "3", "seen_on": "2026-12-07", "ok": "yes"})
print(r)                                       # count=3 seen_on=datetime.date(2026, 12, 7) ok=True
try:
    Reading.model_validate({"count": 3.5, "seen_on": "x"})      # lax still refuses lossy conversions
except ValidationError as e:
    print([x["type"] for x in e.errors()])     # ['int_from_float', 'date_from_datetime_parsing']

# STRICT: no conversion from Python values
class StrictReading(BaseModel):
    model_config = ConfigDict(strict=True)
    count: int
    seen_on: date
try:
    StrictReading.model_validate({"count": "3", "seen_on": "2026-12-07"})
except ValidationError as e:
    print([(x["loc"], x["type"]) for x in e.errors()])   # [(('count',), 'int_type'), (('seen_on',), 'date_type')]
# ...but JSON has no date type, so strict mode accepts an ISO string when the input IS a JSON document:
print(StrictReading.model_validate_json('{"count": 3, "seen_on": "2026-12-07"}'))   # count=3 seen_on=datetime.date(2026, 12, 7)

# SERIALISATION: python mode keeps rich types, json mode produces JSON-safe ones
print(r.model_dump())                          # {'count': 3, 'seen_on': datetime.date(2026, 12, 7), 'ok': True}
print(r.model_dump(mode="json"))               # {'count': 3, 'seen_on': '2026-12-07', 'ok': True}
print(r.model_dump_json(exclude={"ok"}))       # {"count":3,"seen_on":"2026-12-07"}

# Aliases: JSON in camelCase, Python in snake_case (the pairing from the BadgeDesk-style APIs)
class Visitor(BaseModel):
    model_config = ConfigDict(populate_by_name=True)
    employee_id: str = Field(alias="employeeId")
v = Visitor.model_validate({"employeeId": "e-902"})
print(v.employee_id, v.model_dump(by_alias=True))        # e-902 {'employeeId': 'e-902'}
Red pencil — lax is a feature until it is a bug

With the default lax mode, a client that sends "days": "5" or "active": "no" is accepted and converted, which is friendly for form-style input and dangerous when a type matters (an id that must stay a string, a boolean flag where "false" must not be truthy-guessed). When correctness beats friendliness, set strict=True on the model or a single field, and test the rejection. Do not assume either mode; run the one line that proves which you have.

Nested models, enums, Optional, default_factory

nested_models.py
from datetime import date
from enum import Enum
from pydantic import BaseModel, Field, ValidationError

class Kind(str, Enum):
    PDF = "pdf"
    PNG = "png"

class Attachment(BaseModel):
    name: str
    kind: Kind
    size_kb: int = Field(ge=0)

class Ticket(BaseModel):
    title: str
    attachments: list[Attachment] = Field(default_factory=list)   # a NEW empty list per object
    due: date | None = None                                       # nullable, optional
    reviewer: str | None                                          # nullable but REQUIRED (no default!)

a = Ticket(title="One", reviewer=None)
b = Ticket(title="Two", reviewer=None)
a.attachments.append(Attachment(name="x.pdf", kind="pdf", size_kb=10))   # "pdf" becomes Kind.PDF
print(len(a.attachments), len(b.attachments))                 # 1 0   (not shared)

try:
    Ticket(title="Three")                                     # reviewer omitted
except ValidationError as e:
    print(e.errors()[0]["loc"], e.errors()[0]["type"])        # ('reviewer',) missing

try:
    Ticket(title="Four", reviewer="r", attachments=[
        {"name": "ok.pdf", "kind": "pdf", "size_kb": 3},
        {"name": "bad.exe", "kind": "exe", "size_kb": -1},    # two problems in the SECOND item
    ])
except ValidationError as e:
    for err in e.errors():
        print(err["loc"], err["type"])
    # ('attachments', 1, 'kind') enum
    # ('attachments', 1, 'size_kb') greater_than_equal

# None versus missing: matters for PATCH
t = Ticket(title="Five", reviewer=None)
print(t.model_fields_set)                                     # {'title', 'reviewer'}  (a set, so order varies; only what the caller passed)
print(t.model_dump(exclude_unset=True))                       # {'title': 'Five', 'reviewer': None}
Red pencil — Optional does not mean optional

reviewer: str | None says the value may be None. It does not say the key may be absent; with no default it is required. Write str | None = None for “may be absent and may be null”. And for PATCH endpoints, model_fields_set / exclude_unset=True is how you tell “the client sent null” from “the client said nothing”.

Request bodies, response models, status codes

Two models per resource: one for what a client may send, one for what you are willing to reveal. The gap between them is where internal fields stay internal.

A body model on POST

Declare a parameter whose type is a Pydantic model and FastAPI reads the JSON body into it, validated. By the time your function starts, body is a real object with real types.

response_model, and why it hides internal fields

Real storage rows carry fields no client should see: an internal note, a cost centre, a password hash, a soft-delete flag. If your handler returns the stored row, everything in it goes out unless something filters it. response_model is that filter: FastAPI validates the return value against the model and serialises only the declared fields.

ticket_api.py
from fastapi import FastAPI, Response, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

    title: str = Field(min_length=3, max_length=80)
    priority: str = "low"

    id: int
    title: str
    priority: str

Red pencil — the leak that response_model prevents

Remove response_model=TicketOut from the POST above and the client gets internal_note and reporter_email too. Declare an output model on every route that returns stored data, and write one test that asserts the exact set of keys in the response (the lab does this). Errors: HTTPException, handlers, one consistent shape

Clients write code against your error bodies. If a 404 looks different from a 422 which looks different from a 500, every caller needs three parsers. Pick one shape and make every failure use it.

Where errors come from

HTTPException, domain errors, and one shape

Raise HTTPException(status_code, detail) from anywhere in a handler or dependency and FastAPI stops and answers with it. Good code goes one step further: the business logic raises a domain error that knows nothing about HTTP, and one handler maps it to a status code. Then register handlers so that 404, 405, 409, 422 and the unexpected 500 all share one body.

error_shape.py
from fastapi import FastAPI, HTTPException, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from fastapi.testclient import TestClient
from pydantic import BaseModel
from starlette.exceptions import HTTPException as StarletteHTTPException

class ConflictError(Exception):                    # a DOMAIN error: no status codes, no HTTP in here
    def __init__(self, message: str):
        self.message = message

def error_body(code: str, message: str, details=None) -> dict:
    body = {"error": {"code": code, "message": message}}
    if details is not None:
        body["error"]["details"] = details
    return body

app = FastAPI()

@app.exception_handler(ConflictError)              # domain error -> HTTP, in ONE place
async def on_conflict(request: Request, exc: ConflictError):
    return JSONResponse(error_body("conflict", exc.message), status_code=409)

@app.exception_handler(StarletteHTTPException)     # Starlette's class, NOT FastAPI's: see the trap below
async def on_http(request: Request, exc: StarletteHTTPException):
    return JSONResponse(error_body("http_" + str(exc.status_code), str(exc.detail)),
                        status_code=exc.status_code, headers=getattr(exc, "headers", None))

@app.exception_handler(RequestValidationError)     # replace the default {"detail": [...]} body
async def on_invalid(request: Request, exc: RequestValidationError):
    details = [{"field": ".".join(str(p) for p in e["loc"]), "message": e["msg"]} for e in exc.errors()]
    return JSONResponse(error_body("validation_error", "request failed validation", details), status_code=422)

@app.exception_handler(Exception)                  # last resort: hide the stack trace from the client
async def on_crash(request: Request, exc: Exception):
    return JSONResponse(error_body("internal_error", "unexpected error"), status_code=500)

class Approve(BaseModel):
    days: int

@app.post("/tickets/{ticket_id}/approve")
def approve(ticket_id: int, body: Approve):
    if ticket_id == 404:
        raise HTTPException(status_code=404, detail="ticket not found")
    if ticket_id == 409:
        raise ConflictError("ticket is already approved")
    if ticket_id == 500:
        raise RuntimeError("database password is hunter2")   # must never reach the client
    return {"ok": True}

Red pencil — two traps in that file

1. Register Starlette’s HTTPException, not FastAPI’s. FastAPI’s class is a subclass of Starlette’s. A handler registered for the subclass never sees the 404 and 405 that the router raises (those are Starlette’s own, checked here), so unknown URLs keep the framework’s default body and your “one consistent shape” has a hole in it. Registering the parent catches both. The third print above is the proof. 2. TestClient re-raises server errors by default. With the catch-all handler registered, a plain TestClient(app) still raises the RuntimeError in your test (checked), so you cannot see the 500 body. raise_server_exceptions=False shows what a real client would get. Also notice what the 500 body does not contain: the string hunter2. Log the traceback server-side; send the client a code and a sentence.

In production

Teams often add a request_id to this body and log the same id, so a customer can quote it and you can find the exact trace. Another recognised convention is RFC 9457 “problem details” (application/problem+json). The point is not which shape; it is that there is exactly one, that the code is stable and machine-readable, and that the message is safe to show.

Dependencies: Depends

A dependency is a function FastAPI calls for you before your handler and whose result it passes in. It is how shared logic, a database session and authentication stay out of every route.

Shared logic

Anything repeated across routes (pagination parameters, “load this record or 404”, “who is calling”) becomes a dependency. A dependency may itself declare parameters, and they are validated and documented exactly like a route’s.

shared_deps.py
from typing import Annotated
from fastapi import Depends, FastAPI, HTTPException, Query
from fastapi.testclient import TestClient

app = FastAPI()
TICKETS = {1: {"id": 1, "title": "Gate stuck"}, 2: {"id": 2, "title": "Badge reader offline"}}

def page(limit: Annotated[int, Query(ge=1, le=50)] = 10,      # its OWN parameters: validated, shown in /docs
         offset: Annotated[int, Query(ge=0)] = 0) -> dict:
    return {"limit": limit, "offset": offset}

def load_ticket(ticket_id: int) -> dict:                      # a dependency may read the path too
    ticket = TICKETS.get(ticket_id)
    if ticket is None:
        raise HTTPException(status_code=404, detail="ticket not found")
    return ticket

Page = Annotated[dict, Depends(page)]                         # an alias: write the dependency once, reuse the name
Ticket = Annotated[dict, Depends(load_ticket)]

@app.get("/tickets")
def list_tickets(p: Page):
    rows = list(TICKETS.values())
    return rows[p["offset"]: p["offset"] + p["limit"]]

@app.get("/tickets/{ticket_id}")
def show(ticket: Ticket):                                     # the 404 logic is not in this function at all
    return ticket

@app.delete("/tickets/{ticket_id}", status_code=204)
def remove(ticket: Ticket):                                   # ...nor in this one
    del TICKETS[ticket["id"]]

c = TestClient(app)
print(c.get("/tickets?limit=1").json())        # [{'id': 1, 'title': 'Gate stuck'}]
print(c.get("/tickets?limit=99").status_code)  # 422   (the dependency's own Query rule applied)
print(c.get("/tickets/9").status_code)         # 404

The database-session pattern: yield

A dependency that yields is a setup and teardown pair: code before yield runs before the handler, the yielded value is injected, and code after it (in finally) runs once the response is on its way. That is the pattern for a database session, a file, or any resource with a lifetime of one request. Week 7 plugs a real PostgreSQL session into exactly this shape.

session_dep.py
from typing import Annotated
from fastapi import Depends, FastAPI, HTTPException
from fastapi.testclient import TestClient

EVENTS = []                                         # a log, so we can SEE the order things happen

class FakeSession:                                  # stands in for a DB session; week 7 swaps in a real one
    def __init__(self):
        EVENTS.append("open")
    def close(self):
        EVENTS.append("close")

def get_session():
    session = FakeSession()
    try:
        yield session                               # the handler runs while we are suspended here
    finally:
        session.close()                             # runs after the handler, even if it raised

Session = Annotated[FakeSession, Depends(get_session)]
app = FastAPI()

@app.get("/ok")
def ok(session: Session):
    EVENTS.append("handler")
    return {"fine": True}

@app.get("/missing")
def missing(session: Session):
    EVENTS.append("handler")
    raise HTTPException(status_code=404, detail="no such ticket")

c = TestClient(app)
c.get("/ok"); print(EVENTS)                         # ['open', 'handler', 'close']
EVENTS.clear()
print(c.get("/missing").status_code, EVENTS)        # 404 ['open', 'handler', 'close']   closed despite the error

# The same dependency in a test: swap it, no handler changes
class StubSession(FakeSession):
    pass
app.dependency_overrides[get_session] = lambda: StubSession()
EVENTS.clear(); c.get("/ok"); print(EVENTS)         # ['open', 'handler']   the stub has no cleanup: overrides replace the whole function
Red pencil — the dependency you cannot test

If a handler creates its own session or reads os.environ inside the function body, a test cannot replace it. Put anything with a side effect or an environment (database, clock, vendor client, settings) behind a Depends and the test swaps it with app.dependency_overrides[original] = replacement. The key is the original function object, not its name. This is also the main reason to prefer dependencies over module-level globals.

Interviewers ask

“What is dependency injection and why does FastAPI have it?” A function declares what it needs (a session, the current user, pagination numbers) and the framework supplies it, instead of the function constructing or fetching it. The gains: shared logic written once, validated parameters for free, and test doubles by overriding one entry. Follow-up: “when does the code after yield run?” After the handler returns or raises, as part of finishing the request; so a database session is always released.

Authentication in an API: keys, bearer tokens, 401 versus 403

Authentication answers “who are you?”; authorisation answers “may you do this?”. The two failures have different status codes and the difference is a favourite interview question.

An API key header dependency

The simplest scheme: the caller sends a secret in a header, your dependency checks it and returns who it belongs to. It suits server-to-server calls and internal tools. Because the check is a dependency, every protected route opts in with one parameter, and a test can replace it.

api_key_auth.py
import secrets
from typing import Annotated
from fastapi import Depends, FastAPI, Header, HTTPException
from fastapi.testclient import TestClient

KEYS = {"key-emp": "employee", "key-mgr": "manager"}    # in real life: hashed, stored, from settings. Never in source.

def current_role(x_api_key: Annotated[str | None, Header()] = None) -> str:
    if x_api_key is None:
        raise HTTPException(status_code=401, detail="missing API key",
                            headers={"WWW-Authenticate": "ApiKey"})
    for key, role in KEYS.items():
        # compare_digest takes the same time however many characters match; encode so non-ASCII input cannot crash it
        if secrets.compare_digest(x_api_key.encode(), key.encode()):
            return role
    raise HTTPException(status_code=401, detail="invalid API key", headers={"WWW-Authenticate": "ApiKey"})

def require_role(*allowed: str):                         # a dependency FACTORY: returns a dependency
    def check(role: Annotated[str, Depends(current_role)]) -> str:
        if role not in allowed:
            raise HTTPException(status_code=403, detail=f"requires one of {allowed}")
        return role
    return check

app = FastAPI()

@app.get("/tickets")                                     # any known caller
def list_tickets(role: Annotated[str, Depends(current_role)]):
    return {"role": role}

@app.post("/tickets/1/approve")                          # managers only
def approve(role: Annotated[str, Depends(require_role("manager"))]):
    return {"approved_by": role}

c = TestClient(app)
print(c.get("/tickets").status_code)                                           # 401   (no key: unknown caller)
print(c.get("/tickets", headers={"X-API-Key": "nope"}).status_code)            # 401   (key does not match)
print(c.post("/tickets/1/approve", headers={"X-API-Key": "key-emp"}).status_code)  # 403   (known caller, wrong role)
print(c.post("/tickets/1/approve", headers={"X-API-Key": "key-mgr"}).json())   # {'approved_by': 'manager'}
print(c.get("/tickets").headers["www-authenticate"])                           # ApiKey
Red pencil — the 401/403 mix-up and the key in the URL

Returning 403 for a missing key tells a client “logging in will not help” when it will; returning 401 for a wrong role makes a well-behaved client retry credentials that were fine. Order matters in code too: the role check depends on the identity check, which is why require_role declares Depends(current_role): without a key you reach 401 first. And never accept the key as a query parameter: URLs end up in browser history, proxy logs and access logs. Headers do not. In production, store hashes of keys, not the keys.

OAuth2 bearer tokens and JWT, explained by building one

An API key proves “whoever holds this string”. A bearer token is a string sent as Authorization: Bearer <token>, issued after a login, that expires. OAuth2 is the family of rules for how a client gets such a token (the user logs in with an identity provider, the app receives an access token and often a longer-lived refresh token). A JWT (JSON Web Token) is one common format for the token: three base64url parts joined by dots, header.payload.signature. The payload is readable by anyone; the signature proves it was not altered. Build the signing yourself once and the mystery goes away. The signing function below is checked against the well-known example token from the JWT introduction page.

jwt_by_hand.py
import base64, hashlib, hmac, json, time

def b64(raw: bytes) -> str:
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()          # base64url, no padding

def unb64(text: str) -> bytes:
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))

def sign(claims: dict, secret: bytes) -> str:
    header = b64(json.dumps({"alg": "HS256", "typ": "JWT"}, separators=(",", ":")).encode())
    payload = b64(json.dumps(claims, separators=(",", ":")).encode())
    mac = hmac.new(secret, f"{header}.{payload}".encode(), hashlib.sha256).digest()   # HMAC-SHA256 over "header.payload"
    return f"{header}.{payload}.{b64(mac)}"

def verify(token: str, secret: bytes, now: float | None = None) -> dict:
    try:
        header_b64, payload_b64, sig_b64 = token.split(".")
        header = json.loads(unb64(header_b64))
    except ValueError:
        raise ValueError("malformed token")
    if header.get("alg") != "HS256":                                    # PIN the algorithm: never trust the token's own claim
        raise ValueError("unexpected algorithm")
    good = hmac.new(secret, f"{header_b64}.{payload_b64}".encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(good, unb64(sig_b64)):
        raise ValueError("bad signature")
    claims = json.loads(unb64(payload_b64))
    if claims.get("exp", 0) <= (time.time() if now is None else now):
        raise ValueError("token expired")
    return claims

# Proof the signing is the real standard: the example token from the JWT introduction page.
known = sign({"sub": "1234567890", "name": "John Doe", "iat": 1516239022}, b"your-256-bit-secret")
print(known.endswith("SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c"))   # True

secret = b"dev-only-secret"
token = sign({"sub": "e-902", "role": "employee", "exp": 2000}, secret)
print(verify(token, secret, now=1000))                                 # {'sub': 'e-902', 'role': 'employee', 'exp': 2000}

for label, t, now in [("expired", token, 3000),
                      ("wrong secret", sign({"sub": "x", "exp": 2000}, b"other"), 1000)]:
    try:
        verify(t, secret, now=now)
    except ValueError as e:
        print(label, "->", e)                                          # expired -> token expired / wrong secret -> bad signature

# Tampering: change the payload to role=manager but keep the old signature
head, sig = token.split(".")[0], token.rsplit(".", 1)[1]
forged = f"{head}.{b64(json.dumps({'sub': 'e-902', 'role': 'manager', 'exp': 2000}, separators=(',', ':')).encode())}.{sig}"
try:
    verify(forged, secret, now=1000)
except ValueError as e:
    print("forged ->", e)                                              # forged -> bad signature

print(json.loads(unb64(token.split(".")[1])))                          # anyone can READ the payload: it is encoded, not encrypted

Now wire the verifier into FastAPI the way the OAuth2 pattern does: a dependency pulls the bearer token out of the Authorization header with HTTPBearer (which also puts the lock icon in /docs), verifies it, and returns the identity.

bearer_dependency.py
import base64, hashlib, hmac, json, time
from typing import Annotated
from fastapi import Depends, FastAPI, HTTPException
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from fastapi.testclient import TestClient

SECRET = b"dev-only-secret"

def b64(raw): return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()
def unb64(s): return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))
def sign(claims):
    h = b64(b'{"alg":"HS256","typ":"JWT"}'); p = b64(json.dumps(claims).encode())
    return f"{h}.{p}.{b64(hmac.new(SECRET, f'{h}.{p}'.encode(), hashlib.sha256).digest())}"
def verify(token):                                      # condensed from the previous block
    h, p, s = token.split(".")
    if not hmac.compare_digest(hmac.new(SECRET, f"{h}.{p}".encode(), hashlib.sha256).digest(), unb64(s)):
        raise ValueError("bad signature")
    claims = json.loads(unb64(p))
    if claims["exp"] <= time.time():
        raise ValueError("expired")
    return claims

bearer = HTTPBearer()                                   # reads "Authorization: Bearer ..."; missing header -> 401 automatically

def current_user(creds: Annotated[HTTPAuthorizationCredentials, Depends(bearer)]) -> dict:
    try:
        return verify(creds.credentials)
    except (ValueError, KeyError):                      # malformed, forged or expired: all 401, say nothing more
        raise HTTPException(status_code=401, detail="invalid or expired token",
                            headers={"WWW-Authenticate": "Bearer"})

app = FastAPI()

@app.get("/me")
def me(user: Annotated[dict, Depends(current_user)]):
    return {"sub": user["sub"], "role": user["role"]}

c = TestClient(app)
good = sign({"sub": "e-902", "role": "employee", "exp": time.time() + 60})
old = sign({"sub": "e-902", "role": "employee", "exp": time.time() - 1})
print(c.get("/me").status_code)                                                  # 401  no header at all

Red pencil — four JWT mistakes that become incidents

1. Believing the token’s own alg. Pin the accepted algorithm on the server (the verify above does); older libraries had a hole where alg: none skipped the check. 2. Secrets in the payload. The payload is base64, not encryption; the last print above shows anyone can read it. 3. No expiry, or days of it. The hand-written code here is for understanding and was only exercised against the tests above. Do not write the login screen. For this roadmap the API-key dependency is enough to build and test; know the bearer story well enough to explain it. A version note worth checking

With the installed FastAPI, a missing Authorization header on an HTTPBearer dependency returned 401 with WWW-Authenticate: Bearer (checked). Tutorials written for older releases describe it as 403. If a test of yours disagrees with a blog post, the installed version is right; look at your own output, and pin the expectation in a test so an upgrade that changes it is noticed.

Interviewers ask

“401 or 403?” 401 means unauthenticated: no credential, or an invalid or expired one. 403 means authenticated but not permitted. Follow-up: “Is a JWT encrypted?” No. A normal JWT is signed, not encrypted: anyone can read it, nobody can change it without detection. “How do you log a user out of a JWT system?” You cannot cancel a token already issued; you keep expiry short, rotate refresh tokens, and keep a deny-list for emergencies.

Sync versus async: when it matters

FastAPI accepts both def and async def handlers. The choice is not “fast versus slow”; it decides which thread your code runs on, and one wrong combination freezes the whole server.

What each one does

def handlerasync def handler
Runs onA worker thread from a pool (40 threads by default in the installed stack: checked)The single event-loop thread, shared with every other request
A slow blocking call (time.sleep, requests.get, a sync DB driver)Occupies one thread; other requests carry onFreezes the loop: nothing else is served until it returns
Waiting on I/O with awaitNot possibleCheap: thousands of waiting requests on one thread
CPU-heavy workCompetes for the interpreter lock; slow either wayBlocks the loop; use a process pool or a worker queue
Right whenYou use ordinary blocking libraries (most database drivers, requests, file I/O)Every slow call inside is awaitable (httpx.AsyncClient, an async driver)

First prove the thread claim, then the freeze.

freeze_demo.py
import asyncio, time

# Five "requests" arrive together. Each handler needs 0.2 s of waiting.
async def blocks_the_loop(n):
    time.sleep(0.2)                       # async def + a blocking call: the loop cannot switch away

async def awaits(n):
    await asyncio.sleep(0.2)              # async def + an awaitable: the loop serves others meanwhile

async def sync_in_thread(n):              # roughly what FastAPI does for a plain `def` handler
    await asyncio.to_thread(time.sleep, 0.2)

async def burst(handler):
    start = time.perf_counter()
    await asyncio.gather(*(handler(i) for i in range(5)))
    return time.perf_counter() - start

for handler in (blocks_the_loop, awaits, sync_in_thread):
    print(f"{handler.__name__:<16} {asyncio.run(burst(handler)):.1f} s")
# blocks_the_loop  1.0 s      5 x 0.2, one after another
# awaits           0.2 s      all five waited at once
# sync_in_thread   0.2 s      five threads, five waits at once (0.3 s is normal: starting threads costs a little)
# (timings are about these on an idle machine; the ordering is what matters)
Red pencil — async def is not a speed switch

The commonest mistake: writing async def everywhere because it sounds modern, then calling a blocking library inside. The server now handles one request at a time while looking fine on a laptop with one user. If you are unsure, use plain def: FastAPI runs it safely in a thread. Use async def only when you await something. In an Applied AI service the usual slow calls (a vendor API, an LLM, a vector store) are I/O waits, so an async HTTP client inside async def scales well; a blocking SDK inside async def does not. Also remember that the thread pool is finite: 40 slow def requests in flight and the 41st queues.

Interviewers ask

“What happens if I call requests.get inside an async def endpoint?” It blocks the event loop for the duration of the call, so every other request on that worker waits. Fix: make the handler a plain def, use an async client such as httpx.AsyncClient with await, or push the call to a thread with asyncio.to_thread. Follow-up: “does async make one request faster?” No. It lets one process hold many waiting requests at once.

Middleware, CORS and background tasks

Things that apply to every request belong in middleware. Things that must happen after the response is sent belong in a background task, until they matter enough to need a real queue.

Middleware and CORS

Middleware wraps the whole application: code before call_next runs on the way in, code after it on the way out. CORS is the browser rule that a page served from one origin (http://localhost:3000, your Next.js dev server) may not read responses from another origin (your API on port 8000) unless the API says so with Access-Control-Allow-* headers. The browser enforces it; curl, a server or a test client never does.

middleware_cors.py
import time, uuid
from fastapi import FastAPI, Request
from fastapi.middleware.cors import CORSMiddleware
from fastapi.testclient import TestClient

app = FastAPI()

@app.middleware("http")                              # runs for EVERY request
async def request_id_and_timing(request: Request, call_next):
    rid = request.headers.get("x-request-id") or uuid.uuid4().hex[:8]
    started = time.perf_counter()
    response = await call_next(request)              # everything inside (router, deps, handler) happens here
    response.headers["X-Request-Id"] = rid
    response.headers["X-Elapsed-Ms"] = f"{(time.perf_counter() - started) * 1000:.1f}"
    return response

app.add_middleware(                                  # added LAST => outermost: sees the request first
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],         # a list of exact origins; avoid "*" for anything with credentials
    allow_methods=["GET", "POST"],
    allow_headers=["X-API-Key", "Content-Type"],
)

@app.get("/health")
def health():
    return {"status": "ok"}

c = TestClient(app)
r = c.get("/health", headers={"X-Request-Id": "abc123"})
print(r.headers["x-request-id"], "x-elapsed-ms" in r.headers)       # abc123 True

# The browser's PREFLIGHT: an OPTIONS request it sends before a "non-simple" request
pre = c.options("/health", headers={"Origin": "http://localhost:3000",
                                    "Access-Control-Request-Method": "GET",
                                    "Access-Control-Request-Headers": "X-API-Key"})
print(pre.status_code, pre.headers["access-control-allow-origin"])  # 200 http://localhost:3000

bad = c.options("/health", headers={"Origin": "http://evil.example",
                                    "Access-Control-Request-Method": "GET"})
print(bad.status_code, "access-control-allow-origin" in bad.headers)  # 400 False
Red pencil — the CORS error is not an API error

“CORS error” in the browser console while curl works means the API is fine and the headers are missing or wrong for that origin. Adding allow_origins=["*"] to make it go away is the fix that fails security review; list the exact origins. Two more: a request that fails with a 500 can look like a CORS error because the error response lacks the CORS headers (look at the server log, not the browser message), and CORS never protects your API from non-browser callers, so it is not authentication.

Pagination, versioning and idempotency

Three decisions that are cheap on day one and expensive after a client depends on you.

Pagination parameters

Never return an unbounded list: one big table and one careless GET /tickets becomes an outage. Take limit and offset (or a cursor), cap the limit, and say how many there are in total.

paging_versioning.py
from typing import Annotated
from fastapi import APIRouter, FastAPI, Query
from fastapi.testclient import TestClient

ROWS = [{"id": n, "title": f"Ticket {n}"} for n in range(1, 8)]      # ids 1..7

v1 = APIRouter(prefix="/v1")                                          # the version lives in the URL prefix
v2 = APIRouter(prefix="/v2")

@v1.get("/tickets")
def list_v1(limit: Annotated[int, Query(ge=1, le=50)] = 3, offset: Annotated[int, Query(ge=0)] = 0):
    return {"items": ROWS[offset: offset + limit], "total": len(ROWS), "limit": limit, "offset": offset}

@v2.get("/tickets")                                                    # v2 changes the shape: a BREAKING change, so a new version
def list_v2(after_id: int = 0, limit: Annotated[int, Query(ge=1, le=50)] = 3):
    page = [r for r in ROWS if r["id"] > after_id][:limit]             # keyset (cursor) paging
    return {"items": page, "next_after_id": page[-1]["id"] if len(page) == limit else None}

app = FastAPI()
app.include_router(v1)
app.include_router(v2)

c = TestClient(app)
print(c.get("/v1/tickets?limit=3&offset=3").json())
# {'items': [{'id': 4, 'title': 'Ticket 4'}, {'id': 5, 'title': 'Ticket 5'}, {'id': 6, 'title': 'Ticket 6'}], 'total': 7, 'limit': 3, 'offset': 3}
print(c.get("/v1/tickets?limit=500").status_code)                      # 422   the cap is enforced, not advisory
print(c.get("/v2/tickets?after_id=6").json())                          # {'items': [{'id': 7, 'title': 'Ticket 7'}], 'next_after_id': None}

Versioning basics

A change is additive (a new optional field, a new endpoint: safe in place) or breaking (a renamed field, a changed type, a removed route: needs a new version). The simplest scheme that works is the one above: a version prefix in the path (/v1). Header-based versioning is neater in theory and harder to test, cache and read in a log. Keep the old version running until every caller has moved, and say how long.

Idempotency, and what this week deliberately leaves unfixed

A client times out on POST /tickets, does not know whether it worked, and retries. Without protection you now have two tickets. An idempotency key is a client-chosen header; the server stores the result against it and replays that result for a repeat. The version below is deliberately naive so you can see the idea.

idempotency_naive.py
from typing import Annotated
from fastapi import FastAPI, Header
from fastapi.testclient import TestClient

app = FastAPI()
TICKETS: list[dict] = []
SEEN: dict[str, dict] = {}                           # key -> the response we gave the first time

@app.post("/tickets", status_code=201)
def create(title: str, idempotency_key: Annotated[str | None, Header()] = None):
    if idempotency_key and idempotency_key in SEEN:
        return SEEN[idempotency_key]                 # replay: same answer, no second row
    ticket = {"id": len(TICKETS) + 1, "title": title}
    TICKETS.append(ticket)
    if idempotency_key:
        SEEN[idempotency_key] = ticket
    return ticket

Testing with TestClient

The test client calls your app in-process: no server, no port, no network, and a failing test points at one function. It is also how you prove the 401, 403, 404 and 422 paths that you never hit by hand.

from typing import Annotated
from fastapi import Depends, FastAPI, Header, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

# ---- a small app under test (in a real project this is `from desk.main import create_app`)
class TicketIn(BaseModel):
    title: str = Field(min_length=3)

class Clock:
    def now(self) -> str:
        return "real-time"

def get_clock() -> Clock:
    return Clock()

def create_app() -> FastAPI:
    app = FastAPI()
    rows: dict[int, dict] = {}

    def require_key(x_api_key: Annotated[str | None, Header()] = None):
        if x_api_key != "k":
            raise HTTPException(status_code=401, detail="invalid API key")

    @app.post("/tickets", status_code=201, dependencies=[Depends(require_key)])
    def create(body: TicketIn, clock: Annotated[Clock, Depends(get_clock)]):
        row = {"id": len(rows) + 1, "title": body.title, "created": clock.now()}
        rows[row["id"]] = row
        return row

    @app.get("/tickets/{ticket_id}", dependencies=[Depends(require_key)])
    def read(ticket_id: int):
        if ticket_id not in rows:
            raise HTTPException(status_code=404, detail="not found")
        return rows[ticket_id]

    return app

Drill — FastAPI and Pydantic
What is the difference between FastAPI, Starlette, uvicorn and ASGI?

uvicorn is the server: it owns the socket and parses HTTP. ASGI is the interface it uses to call the application, an async callable taking scope, receive and send. Starlette is the toolkit on top that provides routing, middleware, request and response objects. FastAPI adds parameter extraction from type hints, Pydantic validation, dependency injection and generated OpenAPI docs. Follow-up: “why does python main.py not serve anything?” A FastAPI object is not a server; something must listen on a port.

A client sends limit=abc. What happens, and how do you read the response?

FastAPI cannot convert it to the declared int, never calls the handler, and returns 422 with a body {"detail": [...]}. Each entry has loc (the source and field, such as ["query","limit"]), a stable type (int_parsing), a human msg and the offending input. All errors are reported at once. Branch on type, not on msg. Follow-up: “how do you change the shape?” Register a handler for RequestValidationError.

Why use response_model when the handler already returns the right dict?

It is an output filter and a second validation. FastAPI keeps only the declared fields, so stored internal data (a note, an email, a hash) cannot leak even if a developer returns the whole row; it also feeds the OpenAPI schema so docs match behaviour. Without it nothing errors and the leak is silent. I back it with a test that asserts the exact set of response keys. Follow-up: “should the input and output model be the same class?” No: the client could then set server-owned fields.

Validation versus serialisation in Pydantic: which methods, and what is lax versus strict?

Validation turns untrusted input into a typed object: model_validate for a dict, model_validate_json for a JSON string, or calling the class. Serialisation turns the object back into plain data: model_dump (python types) and model_dump(mode="json") or model_dump_json (JSON-safe, dates as strings). Lax mode, the default, converts sensibly ("5" to 5, "yes" to True); strict mode refuses. Choose strict where a silent conversion would hide a client bug, and test the rejection.

What is wrong with reviewer: str | None in a model?

Nothing is wrong, but it does not mean what people think: it allows the value None yet has no default, so the key is still required. For “may be omitted and may be null” write str | None = None. For PATCH endpoints, model_dump(exclude_unset=True) or model_fields_set distinguishes “client sent null” from “client said nothing”. Related trap: mutable defaults; use Field(default_factory=list).

When would you pick a Pydantic model over a dataclass?

At any trust boundary: HTTP bodies, config, files, queue messages, LLM output, because a model checks and converts types, enforces constraints, parses nested JSON and produces a schema. A dataclass does none of that at runtime, but it is cheaper and in the standard library, so it suits small internal value objects built from data you already validated. Follow-up: “do type hints on a dataclass stop days="abc"?” No; they are documentation until something enforces them.

401 or 403 for a valid user without permission? And what if no key is sent?

No key, an invalid key or an expired token is 401, with a WWW-Authenticate header: I do not know who you are, and logging in can fix it. A known caller who lacks the role or scope is 403: I know who you are and the answer is no. Authentication runs first, so the role check depends on the identity check. For objects the caller should not know exist, return 404 instead of 403. Follow-up: “order in code?” require_role declares Depends(current_user), so 401 is reached before 403.

What does Depends give you, and how does yield change it?

A function declares what it needs and FastAPI supplies it: shared logic (paging, load-or-404, the current user) is written once, its own parameters are validated and documented, and tests replace it with app.dependency_overrides[original] = fake. A dependency that yields is setup and teardown: code before the yield runs first, the handler runs, and the code in finally runs after, even if the handler raised. That is the shape of a database session per request. The override key is the original function object.

What happens if you call requests.get inside an async def endpoint?

It blocks the event loop, so every other request on that worker waits for the call to finish; the server looks fine with one user and stalls under load. Options: make the endpoint a plain def (FastAPI runs it in a thread pool, 40 threads by default), use an async client such as httpx.AsyncClient with await, or call asyncio.to_thread. Follow-up: “does async make a request faster?” No; it lets one process hold many waiting requests.

Why register a handler for Starlette’s HTTPException rather than FastAPI’s, and what is “one consistent error shape”?

FastAPI’s class subclasses Starlette’s. The router raises Starlette’s own for unknown paths (404) and wrong methods (405), so a handler on the subclass misses them and those responses keep the framework default. Registering the parent covers both. One consistent shape means every failure (401, 403, 404, 409, 422, 500) returns the same JSON structure, such as {"error": {"code", "message", "details"}} with a stable machine code, so a client needs one parser, and the 500 hides internals.

When is BackgroundTasks enough, and when do you need a queue?

Enough for small, quick, loss-tolerable follow-ups after the response, like a log line or a notification you could drop. It runs in the same process, so a crash or deploy loses it, there are no retries, no visibility and it shares the API’s CPU. Anything that must happen (provisioning a badge, a payment, calling a flaky vendor) belongs on a real queue with retries and a dead-letter path, plus an idempotent consumer. The honest status code for queued work is 202.

Is a JWT encrypted? How do you invalidate one? What would you not hand-write?

A normal JWT is signed, not encrypted: anyone can read the payload, but cannot change it without invalidating the signature, so never put secrets in it. A token already issued cannot be cancelled; keep access tokens short (minutes), use rotating refresh tokens, and keep a deny-list for emergencies. Pin the accepted algorithm on the server. I would not hand-write the signing and verification in production, nor the login system: use a maintained library and an identity provider, and verify with its public keys.
