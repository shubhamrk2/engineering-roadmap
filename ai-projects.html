The two projects and how they connect

Architecture: components, data flow, failure points

1
The chunker decides retrieval quality. A chunk is the unit that gets embedded, retrieved and cited. Too big and the vector blurs; too small and the answer is split across chunks. It is configuration, not a constant.
2
The repository is the seam. Ingest and ask depend on three methods only (add_chunks, search, count), so SQLite, in-memory and pgvector are interchangeable and tests need no server.
3
The gate is where you earn trust. It compares the best score to a threshold you chose from data. Below it, you refuse and never call the model.
4
The LLM is a replaceable part. A complete(prompt) -> str interface lets a fake, a local model, or later a hosted one slot in without changing anything else.
5
List failures before you write code. Each red item becomes a test name in stage 6 and stage 7. Writing them down on day 78 is cheaper than discovering them on day 90.

Red pencil — the vector size is part of the schema

vector(384) means every embedding must have exactly 384 numbers. Change the embedding model and every stored vector is the wrong size or, worse, the right size but a different meaning, so similarity scores become meaningless without any error. Store the model name with the data (a settings or meta table) and refuse to start if it differs.

The repository interface and its in-memory double

You must be able to explain this: a Protocol describes a shape without inheritance (compare a C++ concept or an abstract base class); the key (doc_id, ordinal, content_hash) is what makes re-ingest safe.

app/adapters/repository.py
# app/repository.py : the interface you design FIRST. Everything above it (ingest, ask) depends on this shape only.
import math
from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class Chunk:
    doc_id: str
    ordinal: int          # position of the chunk inside its document
    text: str
    content_hash: str     # hash of the text: lets re-ingest detect "same chunk again"


@dataclass(frozen=True)
class Hit:
    chunk: Chunk
    score: float          # cosine similarity, -1.0 .. 1.0


class ChunkRepository(Protocol):          # a Protocol is a C++-style "concept": any class with these methods fits
    def add_chunks(self, chunks: list[Chunk], vectors: list[list[float]]) -> int: ...   # returns NEW rows only
    def search(self, vector: list[float], k: int) -> list[Hit]: ...
    def count(self) -> int: ...


def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    na, nb = math.sqrt(sum(x * x for x in a)), math.sqrt(sum(y * y for y in b))
    return dot / (na * nb) if na and nb else 0.0


class InMemoryRepo:
    """The test double. Postgres/pgvector later implements the SAME three methods."""
    def __init__(self) -> None:
        self._rows: dict[tuple[str, int, str], tuple[Chunk, list[float]]] = {}

    def add_chunks(self, chunks, vectors):
        added = 0
        for c, v in zip(chunks, vectors, strict=True):
            key = (c.doc_id, c.ordinal, c.content_hash)     # the idempotency key
            if key not in self._rows:
                self._rows[key] = (c, v)
                added += 1
        return added

    def search(self, vector, k):
        hits = [Hit(c, cosine(vector, v)) for c, v in self._rows.values()]
        return sorted(hits, key=lambda h: h.score, reverse=True)[:k]

    def count(self):
        return len(self._rows)


repo: ChunkRepository = InMemoryRepo()
a = Chunk("leave-policy", 0, "Staff may carry over 5 days.", "h1")
b = Chunk("vpn-guide", 0, "Reset the VPN token in the portal.", "h2")
print(repo.add_chunks([a, b], [[1.0, 0.0], [0.0, 1.0]]))      # 2
print(repo.add_chunks([a, b], [[1.0, 0.0], [0.0, 1.0]]))      # 0  (re-running ingest adds nothing)
print(repo.count())                                           # 2
best = repo.search([0.9, 0.1], k=1)[0]
print(best.chunk.doc_id, round(best.score, 3))                # leave-policy 0.994
assert repo.count() == 2 and best.chunk.doc_id == "leave-policy"
Predict: what does the second add_chunks print, and why?

It prints 0. Both chunks already exist under the same key, so nothing is added. If you had used a list with append the count would be 4 and a second ingest would double your index, which then returns every passage twice.

A fake model

Every test of /ask uses this. It records the prompts it received, so a test can assert on what you sent, which is the part you control.

tests/fakes.py
# tests/fakes.py : a deterministic stand-in for any model. Rs 0, no network, same answer every run.
from typing import Protocol


class LLM(Protocol):
    def complete(self, prompt: str) -> str: ...


class FakeLLM:
    def __init__(self, rules: dict[str, str], default: str = "I cannot find that in the documents.") -> None:
        self.rules = rules                 # "substring of the prompt" -> canned reply
        self.default = default
        self.prompts: list[str] = []       # every prompt it saw: tests can assert on what was SENT

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        for needle, reply in self.rules.items():
            if needle in prompt:
                return reply
        return self.default


llm: LLM = FakeLLM({"carry over": "Up to 5 days [leave-policy#0]."})
print(llm.complete("Context: Staff may carry over 5 days.\nQ: carry over?"))   # Up to 5 days [leave-policy#0].
print(llm.complete("Q: what is the canteen menu?"))                           # I cannot find that in the documents.
assert len(llm.prompts) == 2
assert "[leave-policy#0]" in llm.complete("carry over")

The app-factory pattern

The factory takes its collaborators as arguments, so a test builds an app around fakes without patching anything. The production main.py passes the real repository and model. The threshold logic is inline here only to keep the fragment short; your ask service lives in services/ask.py.

app/main.py (shortened) and a test using fakes
# app/main.py : the app-factory pattern. create_app() takes its collaborators as arguments, so a test can hand in fakes.
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field


class AskRequest(BaseModel):
    question: str = Field(min_length=3, max_length=500)      # reject junk at the edge (OWASP API4: resource consumption)


class Source(BaseModel):
    doc_id: str
    ordinal: int


class AskResponse(BaseModel):
    answer: str | None
    answerable: bool
    sources: list[Source]


def create_app(retrieve, llm, min_score: float = 0.35) -> FastAPI:
    app = FastAPI(title="Knowledge Assistant")

    @app.get("/health")
    def health() -> dict:
        return {"status": "ok"}

    @app.post("/ask", response_model=AskResponse)
    def ask(req: AskRequest) -> AskResponse:
        hits = [h for h in retrieve(req.question) if h["score"] >= min_score]     # the refusal threshold
        if not hits:
            return AskResponse(answer=None, answerable=False, sources=[])
        prompt = "Answer ONLY from the passages.\n" + "\n".join(h["text"] for h in hits) + f"\nQ: {req.question}"
        return AskResponse(answer=llm(prompt), answerable=True,
                           sources=[Source(doc_id=h["doc_id"], ordinal=h["ordinal"]) for h in hits])

    return app

Interviewers ask

Why does an unanswerable question return 200 and not 404? The request was valid and the system worked; “I do not know” is a normal answer, not a missing resource. A 404 would make clients treat it as an error and retry. The answerable flag and reason code are the machine-readable part.

This is the file your stage 5 reads. It is small on purpose: an id, a question, whether the documents can answer it, which documents should be retrieved, and the facts the answer must contain. # eval/questions.json (inline here so the block is self-contained). One list of cases, a validator, one metric.
import json

RAW = """
[
  {"id": "q01", "question": "How many leave days can I carry over?",
   "answerable": true,  "expected_doc_ids": ["leave-policy"], "expected_facts": ["5 days"]},
  {"id": "q02", "question": "How do I reset my VPN token?",
   "answerable": true,  "expected_doc_ids": ["vpn-guide"],    "expected_facts": ["portal"]},
  {"id": "q03", "question": "What is the canteen menu on Friday?",
   "answerable": false, "expected_doc_ids": [],               "expected_facts": []}
]
"""


def load_cases(raw: str) -> list[dict]:
    cases = json.loads(raw)
    seen = set()
    for c in cases:
        missing = {"id", "question", "answerable", "expected_doc_ids", "expected_facts"} - c.keys()
        if missing:
            raise ValueError(f"{c.get('id', '?')}: missing {sorted(missing)}")
        if c["id"] in seen:
            raise ValueError(f"duplicate id {c['id']}")
        seen.add(c["id"])
        if c["answerable"] and not c["expected_doc_ids"]:
            raise ValueError(f"{c['id']}: answerable but no expected_doc_ids")
        if not c["answerable"] and c["expected_doc_ids"]:
            raise ValueError(f"{c['id']}: unanswerable but lists expected_doc_ids")
    return cases


def recall_at_k(cases: list[dict], retrieve, k: int) -> float:
    """Of the ANSWERABLE cases, the share where at least one expected doc is in the top k ids."""
    scored = [c for c in cases if c["answerable"]]
    hit = sum(1 for c in scored if set(c["expected_doc_ids"]) & set(retrieve(c["question"], k)))
    return hit / len(scored) if scored else 0.0


cases = load_cases(RAW)
fake_retrieve = lambda q, k: ["leave-policy"] if "leave" in q else ["handbook"]   # a deliberately imperfect retriever
print(len(cases), recall_at_k(cases, fake_retrieve, k=3))      # 3 0.5
assert recall_at_k(cases, fake_retrieve, 3) == 0.5

try:
    load_cases('[{"id": "x", "question": "?", "answerable": true, "expected_doc_ids": [], "expected_facts": []}]')
except ValueError as e:
    print("rejected:", e)                                        # rejected: x: answerable but no expected_doc_ids
Predict

The imperfect retriever returns handbook for the VPN question. What is recall@3 over the answerable cases, and why is the unanswerable case not in the denominator?

Answer

0.5: one of the two answerable questions (leave) finds its expected document, the VPN one does not. The unanswerable question has no expected document, so retrieval recall is undefined for it; it is measured separately as refusal accuracy. Mixing them would let easy refusals hide poor retrieval.

Drill — Project 1 implementation
Walk me through what happens between POST /ask and the response.

Validate the question (length), embed it with the same embedder used at ingest, search the repository for the top k chunks, drop those under the score threshold. If none remain, return answerable=false without calling the model. Otherwise build a prompt with each passage labelled by its ID, call the LLM interface, verify every cited ID is among the hits, and return the answer plus sources taken from the hits. Follow-up: where can it fail? Embedder timeout, database down, model timeout, invalid citation; each has a defined response.

Why did you choose that chunk size and overlap, and how would you find a better one?

I started with paragraph-aware chunks around 800 characters and 100 overlap because the documents are short policies. The honest answer is that I measured, not guessed: I varied size and overlap and compared recall@k on my 20-question set. Too small loses context, too large dilutes the embedding and wastes the prompt budget. The caveat is that the set is synthetic and small, so differences of one question are noise.

How do you make ingestion idempotent?

Each chunk has a key of document id, ordinal and a hash of its text, with a UNIQUE constraint in the database and an insert that ignores duplicates. Re-running adds nothing. If a document changes, chunks with that document id whose hash is not in the new set are deleted in the same transaction as the inserts, so readers never see a half-updated document.

What does your similarity threshold actually do, and what are its limits?

It rejects questions whose best chunk scores below a cutoff, so the model is never asked to answer from irrelevant text. I chose it by comparing score ranges for answerable and unanswerable questions. Limits: the ranges overlap, so some refusals are wrong in both directions, and near-miss questions on a related topic can score high. A second check or a better embedding model improves it; I recorded the cases it still gets wrong.

How do you know the citations are real?

I do not trust the model for that. The prompt labels each passage with an ID; after the model replies I check that every ID it cites is in the retrieved set, and I return sources built from my own hits, not from the model's text. A test feeds a fake model that cites a non-existent ID and asserts it is flagged. What I cannot verify automatically is whether the cited passage really supports the sentence; that needs a human or a judge, and the judge is fallible.

Why a repository interface instead of calling Postgres directly?

Three methods behind a Protocol let tests use an in-memory or SQLite implementation with no server, and let me swap in pgvector without touching the ingest or ask code. The cost is one layer of indirection and the discipline of running the same contract tests against every implementation. Without it, every test needs Docker and my feedback loop slows down.

What does your evaluation measure, and what does it not?

It measures recall@k and reciprocal rank for retrieval, whether expected facts appear in answers, whether citations are valid, and whether unanswerable questions are refused. It does not measure real-world quality: the documents and questions are synthetic and written by me, so I may have unconsciously written questions my system passes. It also does not measure tone, latency under load or behaviour with a real model unless I ran one, which the report states.

Pgvector or an in-memory index: when would you use which?

In-memory (or SQLite with a brute-force scan) is fine for thousands of chunks and for tests; the scan is linear but trivial at that size. pgvector gives persistence, filtering with SQL, and approximate indexes (HNSW or IVFFlat) once the corpus is large enough that scanning is too slow. Approximate indexes trade a little recall for speed, so I would re-run the evaluation after adding one.

How do you protect against prompt injection in a document?

I cannot fully prevent it. I reduce it: retrieved text is delimited and labelled as data, the instruction says to ignore commands inside it, output is validated and citations verified, and the system has no tools that could act on a hijacked answer. I tested one injected document and wrote down what happened. The strongest defence is architectural: a read-only assistant has little to lose if it is steered.

What do you log, and what do you deliberately not log?

Request id, a hash of the question, top score, number of hits, outcome and latency. Never the question text, chunk text, secrets or stack traces in responses. A test asserts that a captured log stream contains none of the planted sentences. Stack traces go to the server log only, never to the client.

The model times out. What does the user see?

A 504 style JSON error with a request id and a retry hint; no partial answer, no stack trace. The timeout is set on the client call so it truly stops. I do not retry silently more than once because retries multiply load during an incident. The failure is logged with the request id and the latency, and a test uses a fake model that raises the timeout exception.

How would you add a PDF loader safely?

Behind the same loader interface, with a size limit, a page limit and a timeout, since PDFs can be huge or malformed. Extraction can yield garbled text or nothing for scanned pages, so I would count extracted characters and refuse documents that yield almost none instead of ingesting empty chunks. Tests use a tiny synthetic PDF plus a corrupted file.

Your tests pass offline. How is that useful if the real model behaves differently?

They prove my code is correct given a model that behaves as specified: prompt construction, threshold logic, citation checks, error handling. They say nothing about model quality. That is deliberate: deterministic tests for my code, a separate evaluation for model behaviour, and a manual check against a local model, each labelled for what it proves.

What would break first at 100 times the data?

Ingest time and the search scan. I would move to an approximate vector index, batch embeddings, make ingest a background job with progress rather than a request, and add metadata filtering so a query searches only relevant documents. I would also revisit the refusal threshold, since score distributions shift as the corpus grows.

What did an AI assistant write in this project and how did you validate it?

I answer from my ownership note: which files I wrote from a blank page, which an assistant suggested and I rewrote, which were generated and kept, and the validation for each (tests I wrote first, breaking the code on purpose to see tests fail, reading every line I cannot explain). I can modify any line live. If I cannot explain a line, it is not in the repository.

Why is your refusal path not just 'ask the model to say it doesn't know'?

Because a model may answer confidently from nothing, and because skipping the call is cheaper and deterministic. When retrieval finds nothing relevant, my code refuses without invoking the model, so the behaviour is testable and cannot be talked out of it by a clever question.

Architecture: components, data flow, failure points

1
Extract. Failure points: model returns malformed JSON, wrong shape, or a service that does not exist. Response: one retry, then needs_info. No guessing.
2
Retrieve. Failure points: nothing above the threshold, store unavailable. Response: say so in the recommendation; never invent a runbook.
3
Recommend. Failure points: proposes a tool not on the list, cites evidence that was not retrieved, wrong target service. Response: validator rejects.
4
Approval gate. Failure points: self-approval, wrong role, expired, replayed. Response: reject and record. Checked again at execution time.
5
Execute. Failure points: timeout (unknown outcome for a write), error response, duplicate request. Response: failed with a note; idempotency key; no blind retry of writes.
6
Record. Failure point: the audit write fails. Response: the status change rolls back with it, so the system never moves forward without a record.

The lifecycle as a state machine

1
The pause is a status, not a thread. awaiting_approval is a row in the database. The process can restart and the issue is still waiting.
2
One incoming edge. executed is reachable only from approved. The block below asserts that property, so it cannot be broken silently by a later edit.
3
Missing information is a state. A vague issue goes to needs_info and comes back; it does not trigger a guess.
4
Everything ends in closed. Success or failure, there is one terminal state, so “what happened to issue X” always has an answer in the audit log.

# app/workflow/states.py : the lifecycle of one issue, as DATA. Illegal jumps are impossible, not merely unlikely.
ALLOWED = {
    "received":          {"extracted", "needs_info", "failed"},
    "needs_info":        {"extracted", "closed"},
    "extracted":         {"recommended", "failed"},
    "recommended":       {"awaiting_approval", "closed"},      # read-only advice may close without approval
    "awaiting_approval": {"approved", "rejected", "expired"},
    "approved":          {"executed", "failed"},
    "executed":          {"closed"},
    "rejected":          {"closed"},
    "expired":           {"closed"},
    "failed":            {"closed"},
    "closed":            set(),
}


class IllegalTransition(Exception):
    pass


def transition(current: str, target: str) -> str:
    if target not in ALLOWED.get(current, set()):
        raise IllegalTransition(f"{current} -> {target}")
    return target


s = "received"
for nxt in ["extracted", "recommended", "awaiting_approval", "approved", "executed", "closed"]:
    s = transition(s, nxt)
print(s)                                                        # closed

try:
    transition("recommended", "executed")                       # skipping approval
except IllegalTransition as e:
    print("blocked:", e)                                        # blocked: recommended -> executed

reachable_executed = [k for k, v in ALLOWED.items() if "executed" in v]
assert reachable_executed == ["approved"]                       # the ONLY way to executed is through approved
Predict: if you add an edge "recommended": {"executed"} to be “quick for read-only issues”, what happens?

The final assertion fails, which is the point. A read-only issue should close from recommended (already allowed) without ever being executed; if some action really is read-only and runs a tool, that is a separate flag on the tool, still gated by validation. Never loosen the one-incoming-edge rule for convenience.

from pydantic import BaseModel, ConfigDict, ValidationError


class ToolRejected(Exception):
    pass


class GetServiceStatus(BaseModel):
    model_config = ConfigDict(extra="forbid")        # unknown argument names are an error, not ignored
    service: str


class RestartService(BaseModel):
    model_config = ConfigDict(extra="forbid")
    service: str
    reason: str


# name -> (argument model, is it consequential?)
REGISTRY = {
    "get_service_status": (GetServiceStatus, False),
    "restart_service": (RestartService, True),
}
ALLOWED_SERVICES = {"payments-api", "auth-api"}       # allow-list: the model cannot invent a target


def prepare_call(name: str, raw_args: dict, approval_id: str | None = None) -> BaseModel:
    if name not in REGISTRY:
        raise ToolRejected(f"unknown tool {name!r}")
    model, consequential = REGISTRY[name]
    try:
        args = model(**raw_args)
    except ValidationError as e:

        raise ToolRejected(f"service {args.service!r} is not on the allow-list")
    if consequential and not approval_id:
        raise ToolRejected("consequential tool needs an approval id")
    return args

Mock APIs with scripted failures

A failure that happens randomly cannot be tested. A script of outcomes can. Notice that the retry helper retries a read; a write needs a different rule.

tests/mock_apis.py
# tests/mock_apis.py : a mock enterprise API with SCRIPTED failures, so a failure test is repeatable.
class ApiTimeout(Exception):
    pass


class ApiServerError(Exception):
    pass


class FlakyBackend:
    def __init__(self, script: list[str]) -> None:
        self.script = list(script)       # e.g. ["timeout", "500", "ok"]: one outcome per call, in order
        self.calls = 0

    def get_status(self, service: str) -> dict:
        self.calls += 1
        outcome = self.script.pop(0) if self.script else "ok"
        if outcome == "timeout":
            raise ApiTimeout(service)
        if outcome == "500":
            raise ApiServerError(service)
        return {"service": service, "state": "degraded"}


def call_with_retry(fn, attempts: int = 3):
    """Retry ONLY what is safe to repeat (a read). A consequential write needs an idempotency key, not blind retries."""
    last = None
    for _ in range(attempts):
        try:
            return fn()
        except (ApiTimeout, ApiServerError) as e:
            last = e
    raise last


b = FlakyBackend(["timeout", "500", "ok"])
print(call_with_retry(lambda: b.get_status("payments-api")), b.calls)     # {'service': 'payments-api', 'state': 'degraded'} 3
b2 = FlakyBackend(["timeout"] * 5)
try:
    call_with_retry(lambda: b2.get_status("auth-api"), attempts=3)
except ApiTimeout:
    print("gave up after", b2.calls, "calls")                              # gave up after 3 calls
assert b.calls == 3 and b2.calls == 3
Red pencil — the retry that restarts a service twice

A write times out. You retry. The first request had actually succeeded, and the service restarts again. Retrying is only safe when repeating the request has the same effect as sending it once (idempotency) or when the operation is a read. For consequential tools: send an idempotency key the downstream system honours, or do not retry and mark the outcome unknown. See Sheet ai-reliability.

import re

PATTERNS = [
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "[EMAIL]"),
    (re.compile(r"\b(?:sk|tok|key)[-_][A-Za-z0-9]{12,}\b"), "[SECRET]"),

]


def redact(text: str) -> str:
    for rx, repl in PATTERNS:
        text = rx.sub(repl, text)
    return text

Red pencil — a regex net has holes

This catches email-shaped strings, a few key-shaped tokens, password=... pairs and ten-digit numbers. It misses names, postal addresses, an API key in an unusual format and numbers written with spaces. Say so in the README. Redaction reduces exposure; it is not proof that nothing sensitive remains.

# tests/test_expiry_pattern.py : the pattern for testing anything that depends on time. Never sleep in a test.
from datetime import datetime, timedelta, timezone

import pytest


class FakeClock:
    def __init__(self, now: datetime) -> None:
        self.now = now

    def advance(self, **kw) -> None:
        self.now += timedelta(**kw)


class Grant:
    """Stand-in for an approval: valid for `ttl` after it was issued. Your Approval class applies the same idea."""
    def __init__(self, clock: FakeClock, ttl: timedelta) -> None:
        self.clock, self.expires = clock, clock.now + ttl

    def is_valid(self) -> bool:
        return self.clock.now < self.expires


@pytest.fixture
def clock():
    return FakeClock(datetime(2027, 2, 24, 9, 0, tzinfo=timezone.utc))


def test_grant_valid_before_expiry(clock):
    g = Grant(clock, timedelta(minutes=15))
    clock.advance(minutes=14, seconds=59)
    assert g.is_valid()


def test_grant_expired_at_exact_expiry(clock):          # the boundary is the bug-prone case
    g = Grant(clock, timedelta(minutes=15))
    clock.advance(minutes=15)
    assert not g.is_valid()

Workflow, agent, LangGraph, MCP: deciding where each is justified

1
Start from the steps, not the framework. Project 2’s six steps are fixed, so a state table plus functions is the honest design.
2
Pause and resume is the real LangGraph question. Checkpointed state and interrupts are what it gives you that plain code makes you write yourself. Read its current docs (links in the stage 5 resources): the API changes.
3
MCP is about reuse, not about capability. It lets other clients call your tools through a standard protocol. It does not remove the need for validation and approval on your side.
Workflow (what Project 2 uses)
You wrote the steps and the order. The model fills in a step (extract, recommend) but never chooses what runs next. Behaviour is repeatable, testable and auditable.
Agent loop
The model chooses the next tool, observes the result and decides again until it says it is done. Flexible, harder to bound, harder to test, and every step is a chance for a bad choice.

Trade-offs and known limitations (write yours; start from these)

  • Identity is a header mapped to a role. A leaked key is a full takeover of that role; real SSO and per-user authorisation are missing.
  • The enterprise APIs are mocks that behave more politely than real ones: no rate limits, no partial failures beyond the scripted ones, no schema drift.
  • Regex redaction is best-effort and misses names and unusual formats.
  • With a fake or small local model, evaluation measures plumbing, not model quality. The report must say which one ran.
  • An unknown outcome after a write timeout is recorded and escalated to a human; there is no automatic reconciliation against the real system.
  • No concurrency testing: two approvers racing on the same approval is guarded by a transaction but was not load tested.
  • One-host design: no queue, no workers; a long tool call blocks a request.
  • Where an agent was not justified: the six steps are fixed, so a model choosing the next step would add risk without adding capability. (If you used LangGraph, name exactly what it bought you.)

Interview questions about this implementation

Drill — Project 2 implementation
Why did you use a fixed workflow rather than an autonomous agent?

The steps (extract, retrieve, recommend, approve, execute, record) are known in advance, and an auditable system benefits from a state table that makes illegal jumps impossible. An agent loop chooses the next step by model, which adds nondeterminism and risk. I would use one where the next step genuinely cannot be enumerated, such as open-ended investigation across many unknown tools, and I would still keep approval and validation outside the model.

Where did you use LangGraph and was it justified?

Answer from your actual decision. A defensible version: I built the workflow as plain functions and a persisted state table first. LangGraph was justified only for checkpointed pause and resume at the approval step, because it gives persistence and interrupts without me writing them. If I did not need that, I say so and name what I would use it for. The wrong answer is using it because it is popular.

How do you stop the model calling a tool it should not?

The model only proposes. My registry decides: unknown tool names are rejected, arguments are validated by a Pydantic model that forbids extra fields, targets must be on an allow-list, and consequential tools need a valid approval id. Each rejection is recorded. The model's text never reaches a tool unvalidated.

Explain your approval design and how it can be bypassed.

An approval has a requester, a different approver, a decision and an expiry, is single-use, and is checked again at execution time. Bypass routes I tested: self-approval, wrong role, expired, replayed. Remaining weaknesses: authentication is a simulated API key, so identity is only as strong as that key, and a compromised approver account approves anything. Production would need real SSO and a separation of duties policy.

What happens if the restart tool times out after approval?

The outcome is unknown: the restart might have happened. I record the call with outcome timeout, move the issue to failed with a note to verify manually, and do not retry blindly. If the downstream API supports idempotency keys I send one so a later retry cannot double-execute. Reads can be retried a bounded number of times; writes cannot.

How do you validate the model's structured output?

Parse JSON in a try block, validate with Pydantic (types, ranges, required fields, extra forbidden), then run business checks: evidence must reference retrieved passages, the tool must be registered, the service must match the extracted one. On failure I retry once with the error appended and then fall back to needs-info. Model output is untrusted input, handled like a request from the internet.

How do you keep secrets and personal data out of logs and prompts?

Secrets come from the environment only, per-tool least-privilege credentials, redaction applied at the boundaries (logger filter, prompt builder, storage of raw text), and a test that plants fake secrets then scans captured logs and prompts. Regex redaction is best-effort: it misses names and free-form data, which I state as a limitation.

Why does the audit log write happen in the same transaction as the status change?

So the two can never disagree. If the audit insert fails the status change rolls back, which is the safe direction: the system refuses to move forward without a record. If they were separate writes, a crash between them would leave an executed action with no trace.

How do you test time-dependent logic like approval expiry?

With an injected clock. The code under test takes a clock object, the test controls it, and I test both sides of the boundary: one second before expiry is valid, exactly at expiry is not. Sleeping in tests makes them slow and flaky, and reading the system time directly makes them untestable.

What is idempotency and where did you need it?

Doing the same request twice has the same effect as doing it once. I needed it for duplicate issue submissions (key from content hash and requester with a UNIQUE constraint), for the restart tool (an idempotency key sent downstream), and for approvals (single-use). Retries are only safe when the operation is idempotent.

How is Project 2 coupled to Project 1?

Through one narrow port: search(query, k) returning passages with ids and scores. Project 2 never imports Project 1's API or database code. In tests a fake implements the port. If the port needed more than a string and a number, the boundary would be wrong.

Would you expose these tools over MCP?

The read-only tools, yes, if other assistants should reuse them: one implementation, many clients. The consequential tool, not unless the approval check lives on the server side of the MCP boundary, because an MCP client is not trusted to say that approval happened. Transport and authentication of the MCP server then become part of the threat model.

Which OWASP risks did you map, and give one concrete test for each of two.

Excessive agency (LLM06): test that a proposed consequential tool without a valid approval is rejected. Broken function-level authorisation (API5): test that a non-approver calling the decide endpoint gets 403. I also mapped prompt injection, sensitive information disclosure, improper output handling and unbounded consumption, each with a file and a test in the checklist.

How did you evaluate the assistant and what is the key metric?

A suite of 15 scenarios with expected tool, approval requirement and final status. The metric that must be zero is unsafe executions (an action without valid approval); I made it a test. Tool-choice accuracy and failure-handling pass rate are reported with the caveat of which model ran. Failures are committed, not hidden.

What are the biggest limitations of this project?

Simulated identity, mock APIs that are friendlier than real ones, regex redaction, synthetic data so evaluation numbers do not transfer, no rate limiting beyond basics, no real concurrency testing, and a small local or fake model. I list each with what fixing it would cost. None of this is production-ready and I say so in the README.

What would you change to run this for a real team?

Real authentication (SSO), per-user authorisation on issues, secrets in a manager, rate limiting and quotas, durable background execution with a job queue, structured tracing, a reviewed approval policy, and tests against real vendor sandboxes. I would also run the evaluation on real, sanitised incidents and have operators review the recommendations before trusting any score.

A reviewer says 'the AI wrote this'. What do you say?

I show the ownership note: what I wrote, what was generated, how I validated each part, and I explain or modify any line on request. Using an assistant for explanation and review is honest and common; claiming ownership of what I cannot explain is not. The git history shows the incremental build and the tests I wrote first.

Extend it

  • Expose the two read-only tools as an MCP server and call them from a second client; keep approval outside it.
  • Adopt LangGraph for the approval pause and compare: lines of code, test effort, and what failed during resume.
  • Replace the API-key header with real token validation (JWT) and per-user object checks.
  • A background worker and a queue so a slow tool does not hold a request; then re-test the failure scenarios.
  • Reconcile unknown outcomes: a status check after a timed-out write that settles failed or executed with evidence.
  • Rate limits per key and a lockout after repeated rejected approvals.
  • Run the scenario suite against one small local model and compare it with the scripted fake, reporting the difference honestly.

Drill — building and presenting portfolio projects
Why write the tests before the code when the model is a fake?

The test states the behaviour I want before I know how to build it, so a green result means I met that statement and not that my code agrees with itself. The fake makes the test deterministic, so a failure is a bug in my code, not model noise. It does not tell me how a real model behaves; that needs a separate evaluation. Follow-up: “what if the fake is wrong?” Then my tests prove my code against a wrong model, which is why I also run one manual check against a local model.

Your tests are all green. What have you proved, and what not?

That the code handles the cases I listed. Not that it is correct for other inputs, safe, or good with a real model. The next bug is in a case nobody wrote down, which is why failure scenarios and an evaluation set exist, and why I add a test for every bug I find.

How do you handle the question “did an AI write this?”

Answer from the ownership note: what I wrote from a blank file, what an assistant suggested and I changed, what was generated, and how I validated each. Then offer to modify any file live. The honest account with a validation story is stronger than a claim I cannot defend.

A secret was committed three commits ago and removed. Are you safe?

No. It remains in history and any clone has it. Rotate the secret first (treat it as exposed), then remove it from history by the documented method, and check forks and caches. Prevention: .env in .gitignore from the first commit, .env.example with empty values, and a pre-publish scan.

Why must approval be checked again at execution time?

Time passes between approval and execution. The approval may have expired, been consumed by another request, or the issue may have changed. Checking only when the approval is granted leaves a window where an old approval authorises a new action. Check validity and mark it consumed in the same transaction that records the execution.

When would you use LangGraph, and when would you not?

When I need durable pause and resume (checkpoints, interrupts) and do not want to write that persistence myself, or when the control flow is genuinely a graph that changes over time. Not when the steps are fixed and a state table plus functions is clearer and easier to test. Either way, validation and approval stay in my code. I can name what it bought me, or I do not use it.

Your evaluation gives 100%. Do you believe it?

Not without checking how it was produced. If I wrote the questions after the system, or the fake model was scripted to pass, 100% measures my plumbing. I would look for cases that should fail, add near-miss and adversarial questions, read some results by hand, and report failures. A report with two honest failures is better evidence than a perfect score.

How do you decide what goes in “known limitations”?

Anything a reviewer would discover by trying: no real authentication, mock backends, synthetic data, regex redaction gaps, no load testing, what I did not execute. Each gets a sentence on impact and what fixing it would cost. If I did not know a limitation existed until an interviewer found it, that is the one that hurts.

What is the single most important test in Project 2?

That no consequential action executes without a valid approval from a different person: the unsafe-execution count across all scenarios is zero, asserted in a test and backed by a state machine where executed has one incoming edge. Everything else is a supporting property of that sentence.
