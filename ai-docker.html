The one idea: a clean clone that runs

Everything on this sheet exists to remove the sentence “it works on my machine” from your portfolio. The test is brutal and simple: delete the folder, clone again, follow only the README.

1
The repo is the product. A reviewer sees files, not your laptop. Everything needed to run the project must be in the clone, or named in the README as a prerequisite.
2
Config lives outside the image and outside git. .env.example is committed (fake values, every variable listed). .env is private and git-ignored. That split is the twelve-factor idea (section 6).
3
One command. docker compose up --build builds what is missing and starts everything, in order. “In order” is the subtle part: section 5 shows that depends_on alone does not do it.
4
Containers find each other by service name. Inside the network the API connects to db:5432, not localhost. Inside the API container, localhost is the API container itself.
5
Only published ports reach your host. 8000:8000 exposes the API. The database has no ports line on purpose, so it is reachable only from inside the network.
6
Each failure has a cheap guard. You will build all five guards on this sheet. A project that has them can be cloned by a stranger; one that lacks them works for you and nobody else.

Why containers, honestly

A container is a normal Linux process that has been given its own view of files, processes and network. It is not a small computer. Knowing that one sentence answers most interview questions.

Container versus virtual machine

Virtual machine
A full guest operating system, with its own kernel, running on a hypervisor. Strong isolation, minutes to boot, gigabytes of disk. You patch the guest OS yourself.
Container
Your process plus its files, sharing the host’s kernel. Starts in about a second, images are often tens to hundreds of megabytes. Isolation is real but thinner: a kernel bug is shared by every container on the host.
DimensionVirtual machineContainer
What is insideWhole OS, kernel includedApp, libraries, a minimal userland; no kernel of its own
Start timeTypically tens of seconds to minutesTypically about a second (check on your machine, it varies)
Disk sizeGigabytesTens to hundreds of MB for a slim Python image
IsolationStrong: separate kernelsWeaker: shared kernel, so a kernel flaw affects all of them
Best atRunning a different OS; hard multi-tenant isolationPackaging one app so it runs the same everywhere
On your Windows laptopHyper-V, VirtualBoxLinux containers actually run inside a small Linux VM (WSL2 or Hyper-V), because Windows has no Linux kernel
Typical mistakeTreating it as a pet to hand-patchTreating it as a VM: SSH-ing in, editing files by hand, expecting them to survive

Pick a container to ship an application; pick a VM when you need a different kernel or a strong security boundary. Note the honest Windows detail in the table: on your laptop a “container” is a Linux process inside a hidden Linux VM, so containers are cheap, but Docker on Windows is never free of that VM’s memory cost.

The writable layer of a container disappears when you remove the container. That single fact is why volumes exist (section 4). Docker Hub is the default registry; GitHub also hosts one (ghcr.io). You will only pull in this roadmap. Pushing to a registry is a deployment step you do not need for a portfolio, and registries have their own storage and pull-rate terms: check them yourself before you push anything.

Interviewers ask

“What is the difference between a container and a VM?” A VM virtualises hardware and runs its own kernel; a container isolates a process using kernel features (namespaces for what it can see, cgroups for what it can use) and shares the host kernel. So containers are lighter and faster to start but isolate less strongly. Follow-up: “then how does Docker run Linux containers on Windows?” Inside a lightweight Linux VM (WSL2 or Hyper-V), so there is a VM underneath after all.

The Dockerfile

A Dockerfile is a recipe of instructions; each one that changes the filesystem becomes a layer. We build a synthetic ticket API: a tiny FastAPI service that checks its database.

The app we are packaging

Two endpoints, deliberately different. /health is liveness: the process is alive, and it never touches the database. /ready is readiness: the service can do real work, so it checks Postgres. Containers and orchestrators ask these two questions separately, and mixing them is a classic bug (a database blip would make every instance look dead and get restarted). The block below ran on Python 3.14.7 with the versions in the “Tested with” panel. The Postgres half could not run here (no database), so the test replaces db_ping with a fake.

app/main.py — executed; the database call itself was not (no Postgres here)
import os
from fastapi import FastAPI, HTTPException

app = FastAPI(title="ticket-api")          # a synthetic service: tickets, no real data


def db_ping() -> bool:
    """True if Postgres answers SELECT 1. psycopg is imported inside the function so
    the module imports (and /health works) even where the driver is not installed."""
    import psycopg
    with psycopg.connect(os.environ["DATABASE_URL"], connect_timeout=2) as conn:
        conn.execute("SELECT 1")
    return True


@app.get("/health")                        # liveness: "the process is up". Never touches the database.
def health():
    return {"status": "ok"}


@app.get("/ready")                         # readiness: "I can do real work". Checks the database.
def ready():
    try:
        db_ping()
    except Exception as exc:               # broad on purpose: any failure means "not ready"
        raise HTTPException(status_code=503, detail=type(exc).__name__)
    return {"status": "ready"}


# ---- checks for this sheet; in a real repo these live in tests/test_health.py ----
if __name__ == "__main__":
    from fastapi.testclient import TestClient
    client = TestClient(app)
    assert client.get("/health").json() == {"status": "ok"}

    os.environ.pop("DATABASE_URL", None)               # no database configured
    r = client.get("/ready")
    print(r.status_code, r.json())                     # 503 {'detail': 'KeyError'}
    assert r.status_code == 503

    db_ping = lambda: True                             # a fake database that always answers
    r = client.get("/ready")
    print(r.status_code, r.json())                     # 200 {'status': 'ready'}
    assert r.status_code == 200
    print("ok")
You must be able to explain this line

raise HTTPException(status_code=503, ...) inside except Exception. The broad except is acceptable here because this is a top-level boundary: any failure means “not ready”, and we return the exception type (not its message, which could contain the connection string). Compare with Sheet 23’s red-pencil on bare except:: the rule was never “never catch broadly”, it was “do not swallow errors silently”.

.dockerignore, secrets and size

When you run docker build ., the folder . is sent to Docker as the build context. Anything in it is available to COPY. A .dockerignore keeps junk and secrets out of the context, so they cannot be copied into a layer by accident.

Red pencil — the .dockerignore that breaks your build

A .dockerignore entry makes a file invisible to COPY. If you add tests to it, COPY tests ./tests in the test stage fails with a “not found” style error, because the folder never reached the build. I expect that; I could not run it. The general lesson holds: “file not found” during a build usually means “ignored”, not “missing”. The reverse also bites: forgetting to ignore .venv sends hundreds of megabytes to Docker on every build.

Red pencil — secrets baked into an image

Any of these puts a secret into the image, where anyone who can pull it can read it, and deleting it in a later layer does not help because the earlier layer still holds it: ENV API_KEY=abc123, COPY .env ., a RUN that downloads with a token in the URL, and (visible in docker history) build arguments passed with --build-arg. Pass secrets at run time: docker run -e API_KEY ... (value taken from your shell, never typed in the command), --env-file .env, or Compose environment: with ${API_KEY}. Docker also has build-time secret mounts for the rare case you need a secret during the build (search for “RUN --mount=type=secret” in the Docker docs; I did not test it). If a real key ever lands in an image or a git commit, rotate it: treat it as published.

Multi-stage builds, slim images and non-root

The Dockerfile above already uses stages to keep test tools out of the runtime image. The other classic use is to keep build tools out. You build in one stage that has compilers, then copy only the result into a clean stage.

Interviewers ask

“Why do you COPY requirements.txt before the rest of the code?” Because of layer caching. A layer is reused only if its inputs and all layers above it are unchanged. Dependencies change rarely and code changes constantly, so copying and installing dependencies first means a code edit reuses the slow pip install layer. Follow-up: “what invalidates that cache anyway?” Editing requirements.txt, changing the base image tag, or building with --no-cache.

Running containers: commands, ports, environment, volumes, networks

Building an image changes nothing on your machine. docker run is what starts a process, and every flag on it answers one question: what can this container see, and what can see it?

Typing those flags by hand is how people leak secrets and mistype ports. The lab builds the command as a list of strings, which is also how you should call it from any program: a list is passed to the operating system as separate arguments, so spaces and quotes in values cannot change the command’s meaning. This block ran.

run_cmd.py — executed; it only builds and prints the command, it does not call Docker
import shlex

def docker_run(image, name, ports, env_names):
    cmd = ["docker", "run", "-d", "--name", name]
    for host, container in sorted(ports.items()):
        cmd += ["-p", f"{host}:{container}"]
    for key in env_names:              # name only: Docker copies the value from YOUR shell
        cmd += ["-e", key]
    return cmd + [image]

cmd = docker_run("ticket-api:dev", "api", {8000: 8000}, ["DATABASE_URL", "API_KEY"])
print(cmd)
print(shlex.join(cmd))                 # the same thing as one shell-safe string, for README or logs
assert cmd[-1] == "ticket-api:dev"
assert "API_KEY=" not in shlex.join(cmd)   # the secret VALUE never appears
# To really run it:  subprocess.run(cmd, check=True)   (a list, never a string with shell=True)

Ports, environment variables and logs

Ports. -p HOST:CONTAINER. The container side is fixed by the app (uvicorn listens on 8000). The host side is yours to change when 8000 is taken: -p 8080:8000 then browse localhost:8080. Another trap: inside a container the server must bind 0.0.0.0, not 127.0.0.1. Bound to loopback, the app is reachable only from inside its own container, so the published port appears to connect and then hangs or resets.

Environment variables. -e KEY=value, -e KEY (take it from my shell), or --env-file .env (one KEY=value per line; read the Docker docs for how quotes and comments are treated, as they are not identical to a shell). Logs. A container should log to stdout and stderr and nothing else; Docker collects them, so docker logs works and so does any log tool later. Do not write a log file inside the container: it vanishes with the container.

Use a named volume for Postgres data and a bind mount for code you are actively editing. Never use a bind mount as the way your project is meant to run for a stranger; they will not have your path.

Networks

Containers on the same Docker network can reach each other by service name, because Docker runs a small DNS server for that network. The Compose docs say it creates one default bridge network per project and every service joins it. Two numbers in a ports line mean two different things: the left is for traffic from your host, the right is the container port that other containers use.

Red pencil — “connection refused” to localhost:5432 inside a container

The single most common first-week Docker bug. Your DATABASE_URL says localhost because that is what worked on your laptop. Inside the API container localhost is the API container, where nothing listens on 5432. The fix is the service name: postgresql://app:...@db:5432/app. The mirror-image bug: from your host, the name db does not resolve; use localhost and a published port.

Interviewers ask

“Your container exited immediately. How do you debug it?” docker ps -a for the exit code, docker logs for the last output, then run it again with docker run -it --entrypoint sh IMAGE to poke around. Exit 0 with no logs often means the command finished (a script, not a server); exit 1 is an app error; 137 is a kill. Follow-up: “and if it runs but the browser cannot connect?” Check the port is published, and the server is bound to 0.0.0.0.

depends_on does not wait for readiness

Plain depends_on: [db] means “start db first”. It does not mean “wait until db accepts connections”. The Compose docs say it directly: Compose does not wait until a container is “ready”, only until it is running. Postgres takes a few seconds after the container starts to initialise and accept connections, so an API that connects on start-up crashes with “connection refused” on a fresh volume. There are three fixes, in order of preference:

FixHowTrade-off
Healthcheck + condition: service_healthyAs in the file aboveCompose handles it. You maintain a correct healthcheck
Retry in the appTry to connect N times with a short sleep, then fail loudlyAlso protects you in production when the database restarts. Best done in addition
restart: on-failureLet it crash and be restarted until the database is upNoisy logs, and hides real crashes behind restarts. A last resort
Red pencil — service_healthy with no healthcheck

condition: service_healthy needs the target service to define a healthcheck. Without one, there is nothing to become healthy. The lab’s validate_compose catches exactly this. And a healthcheck that is too eager (no start_period, tiny retries) marks a slow-starting database unhealthy and blocks the start; give it a start period and several retries.

Postgres, volumes and pgvector

The database files live in a named volume, so docker compose down keeps your data and docker compose down -v deletes it. The mount path /var/lib/postgresql/data is correct for the postgres:16 image as I remember it; newer major versions of the official image may use a different data directory layout, so when you change the major version, read that image’s Docker Hub page about where to mount. Also note: the POSTGRES_* variables are read only the first time, when the volume is empty. Change the password in .env later and nothing happens until you delete the volume, a favourite source of “password authentication failed”.

pgvector. The vector extension is not in the plain postgres image. Running tests in a container

The test stage and the tests service exist for one reason: “the tests pass” should mean “they pass in the same environment a stranger will have”, not “in my virtualenv with the package I installed last Tuesday and forgot”. docker compose run --rm tests builds the test stage, waits for a healthy database, runs pytest -q once and removes the container. check_compose.py — executed (needs pip install pyyaml); the same idea the lab asks you to generalise
import yaml   # PyYAML; yaml.safe_load turns YAML text into dicts and lists

COMPOSE = """
services:
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
"""

def unhealthy_dependencies(doc):
    """Services that wait for service_healthy on something with no healthcheck."""
    services = doc["services"]
    problems = []
    for name, spec in services.items():
        deps = spec.get("depends_on", {})
        if isinstance(deps, list):                 # short form: ["db"] has no conditions
            continue
        for target, cfg in deps.items():
            if cfg.get("condition") == "service_healthy" and "healthcheck" not in services[target]:
                problems.append(f"{name} waits for {target}, which has no healthcheck")
    return problems

doc = yaml.safe_load(COMPOSE)
print(unhealthy_dependencies(doc))                 # []
del doc["services"]["db"]["healthcheck"]
print(unhealthy_dependencies(doc))                 # ['api waits for db, which has no healthcheck']
assert unhealthy_dependencies(doc)

Readiness: should it receive traffic right now? The database check belongs in readiness.

Twelve-factor configuration

The twelve-factor app rule for config is: store it in environment variables, strictly separate from code. Concretely: one variable per setting, no config files with secrets committed, a default only where a wrong default is harmless (LOG_LEVEL, PORT), and no default at all for anything secret or environment-specific. A missing required setting should stop the program at start-up with an error naming the setting, not fail ten minutes later with NoneType. Environment variables are always strings, so parsing is your job, and bool("false") is True. This block ran.

config_by_hand.py — executed
import os

class ConfigError(Exception):
    """A setting is missing or invalid. The message names the setting."""

def required(name, env=os.environ):
    value = env.get(name, "").strip()      # missing and blank both count as unset
    if not value:
        raise ConfigError(f"{name} is required")
    return value

def as_bool(text):
    t = text.strip().lower()
    if t in ("1", "true", "yes", "on"):
        return True
    if t in ("0", "false", "no", "off"):
        return False
    raise ConfigError(f"not a boolean: {text!r}")

def redact(url):
    """postgresql://app:secret@db/app -> postgresql://app:***@db/app"""
    import re
    return re.sub(r"(://[^:/@]+):[^@/]*@", r"\1:***@", url)

env = {"DATABASE_URL": "postgresql://app:s3cret@db:5432/app", "DEBUG": "false", "PORT": "8080"}
print(bool(env["DEBUG"]))                  # True   <-- the trap: any non-empty string is truthy
print(as_bool(env["DEBUG"]))               # False  <-- what you meant
print(int(env.get("PORT", "8000")) + 1)    # 8081   (convert once, at start-up)
print(redact(required("DATABASE_URL", env)))   # postgresql://app:***@db:5432/app
try:
    required("API_KEY", env)
except ConfigError as err:
    print("start-up stopped:", err)        # start-up stopped: API_KEY is required
You must be able to explain this line

env.get(name, "").strip() then if not value. Compose and shells often give an empty string for an unset variable rather than a missing key, so a check for None alone lets an empty API_KEY through. Treating blank as unset is the safer rule, and the lab tests it. Also: the redact function exists because the database URL embeds the password, and a print(settings) in a log line is how secrets reach a log aggregator.

Secrets in Actions, caching and what not to do

Secrets. Add them in the repository settings, then reference them as ${{ secrets.NAME }} and pass them to the one step that needs them through env:. Per the GitHub docs on secrets: secrets are not passed to workflows triggered from forks (except the automatic GITHUB_TOKEN); an unset secret evaluates to an empty string; you cannot use a secret directly in an if:; avoid passing secrets on a command line because other users may see process lists, so prefer environment variables. GitHub masks registered secret values in logs, but masking is a last line of defence, not permission to print.

step fragment — NOT RUN; right and wrong ways to use a secret
# RIGHT: scoped to one step, passed through the environment, never printed
- name: Smoke-test against the real service
  env:
    API_KEY: ${{ secrets.API_KEY }}
  run: python scripts/smoke.py          # the script reads os.environ["API_KEY"]

# WRONG: prints the secret (masking may hide it, but a transformed value is NOT masked)
- run: echo "key is ${{ secrets.API_KEY }}"
- run: echo ${{ secrets.API_KEY }} | base64        # the base64 text is a different string: it will not be masked
# WRONG: debug step left in
- run: env | sort

The two WRONG lines are my own illustration of why masking is not a plan. I did not run them; the docs warn that GitHub cannot redact values you transform or print in unusual forms, and the safe habit does not depend on that detail.

Red pencil — CI green, laptop red

Or the reverse. The usual causes: a file that is in git-ignore but your code needs; a package you installed by hand and never added to requirements.txt; tests that depend on order or on today’s date; a secret that exists in your shell but not on the runner; a different Python version. This is exactly why CI exists: when it fails, it found a real reproducibility bug. Read the log from the first red line, not from the bottom. And a cache can lie: if a build behaves oddly, re-run with the cache cleared before blaming your code.

Interviewers ask

“What is the difference between CI and CD?” CI runs build and tests on every change so integration problems appear within minutes. CD takes a passing build and delivers it (continuous delivery: ready to release by a click) or releases it automatically (continuous deployment). CI is about confidence, CD about release. Follow-up: “where do secrets go?” In the CI system’s secret store, injected as environment variables to the one step that needs them, never in the repository or in logs. Drill — Docker, Compose and CI
What is the difference between an image and a container?

An image is a read-only stack of layers plus metadata (default command, environment, ports): the template. A container is a running or stopped instance of an image, with a thin writable layer on top that is lost when the container is removed. You can start many containers from one image. Follow-up: “where should data that must survive go?” In a volume, not the container’s writable layer.

Why copy requirements.txt before the application code?

Layer cache. A layer is reused only if its instruction and inputs are unchanged and every layer above it was reused. Dependencies change rarely, code changes constantly. Copy and install dependencies first so a code edit leaves that slow layer cached; copy code last. Follow-up: what busts the cache anyway? Changing requirements, changing the base tag, --no-cache, or an earlier COPY . ..

CMD versus ENTRYPOINT?

CMD is the default command and is replaced entirely by arguments to docker run IMAGE .... ENTRYPOINT is the fixed executable and run-time arguments are appended to it. Together, an exec-form ENTRYPOINT plus exec-form CMD makes the CMD the default arguments. Use exec (JSON array) form; shell form runs under /bin/sh -c and the Dockerfile reference notes it does not pass signals, so docker stop cannot shut the app down cleanly.

Your API in a container cannot reach Postgres at localhost:5432. Why, and what is the fix?

Inside the API container, localhost is the API container itself. Containers on a Compose network reach each other by service name, so use db:5432. From the host, you would use localhost and a published port instead. Follow-up: “should the db publish a port?” Not unless you need host access; leaving it unpublished keeps it reachable only from inside the network.

Does depends_on wait for the database to be ready?

No. By default it only controls start order: Compose waits until the dependency is running, not ready. To wait for readiness give the database a healthcheck (for Postgres, pg_isready) and use depends_on with condition: service_healthy. Also make the app retry its first connection, which also helps when the database restarts in production.

Named volume or bind mount, and for what?

Named volume: Docker-managed storage, portable via the compose file, best for database files. Bind mount: a host folder mapped into the container, best for editing source during development, but it depends on a host path and can have ownership and speed problems. Follow-up: “what does docker compose down -v do?” It also deletes the named volumes, so you lose the database.

How do you keep secrets out of an image and out of git?

Never ENV or COPY a secret; list .env in both .gitignore and .dockerignore; commit a .env.example with fake values; pass real values at run time via -e, --env-file or Compose ${VAR} with ${VAR:?message} to fail fast. In CI use the secret store. If one leaks, rotate it, because deleting a layer or commit does not un-publish it.

Why run as a non-root user, and what is the catch?

If the app is compromised, the attacker is not root inside the container, limiting what they can change. It does not make the container a security boundary by itself, since the kernel is shared. The catch is file ownership: files copied as root may not be writable by the app user, so use COPY --chown or write only to directories the user owns.

Liveness versus readiness: which one should check the database?

Readiness. Liveness asks “should this process be restarted?” and should not depend on external services, or a database outage would trigger pointless restarts of every instance. Readiness asks “can it serve traffic now?” and may check dependencies. Our /health is liveness, /ready is readiness; the container HEALTHCHECK uses /health.

Walk me through a GitHub Actions workflow that tests a Python project.

The on key sets triggers (push to main, pull requests). One job on ubuntu-latest runs steps: actions/checkout, actions/setup-python with a version and cache: pip, a run step to install requirements, and a run step for pytest. A non-zero exit fails the step and job and shows a red cross. Secrets come from ${{ secrets.X }} into one step’s env, never echoed. Follow-up: “does a green check prove it works?” Only that the tests passed on that environment.

The tests pass locally and fail in CI. What do you check?

Differences between the two environments: Python version, a dependency installed by hand but missing from requirements, a file excluded by git-ignore that the code needs, a secret or env var set only locally, test order or date dependence, case-sensitive file names (CI is Linux, you may be on Windows). Read the log from the first failure and reproduce it in a fresh clone or the test container. Do not “fix” it by re-running until it passes.

Your project needs hosting for a portfolio but you have no budget. What do you do?

Make it reproducible instead: docker compose up from a clean clone, a README with expected outputs, a recorded demo, and CI on a public repository. If I consider any hosted option I read that provider’s current free-tier terms the same day, check whether a card is needed and what happens at the limit, and set spending alerts. I do not assume anything is free from memory.
