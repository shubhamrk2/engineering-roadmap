The build ladder

Each project adds one layer and reuses everything below it. By Week 12 you are not presenting a portfolio of exercises; you are presenting one system and can talk about any layer of it.

1
Project 6 is the one that changes your interviews. Almost every candidate has built a CRUD application. Very few have provisioned the network it runs on, written the pipeline that deploys it, and torn it all down and rebuilt it from code. That is the difference between “I have used AWS” and “here is my VPC, and here is why the database has no route to the internet”.
2
Project 9 is not optional padding. Nobody clones your repository. They read the README, look at one diagram, and decide in ninety seconds whether to talk to you. An excellent system with no write-up is invisible; a modest system explained clearly gets the call.
Rules for every project

Ship it before you polish it. Working and ugly beats elegant and unfinished, every time. Write the README as you go, not at the end when you have forgotten why you chose things. Commit small and often, with messages that explain why. Write down every problem that took you more than an hour — those notes become your behavioural answers on Sheet 14. And timebox: a project that overruns by a week costs you the next project, not just the time.

Project 1 — one spec, three languages

Weeks 01–02. The fastest way to actually learn a language is to solve the same problem in it that you already solved in another.

the specification — identical for all three implementations
badgedesk-validate  --input access-requests.csv  --sites sites.json  --out report.json

Reads a CSV of bulk access requests and validates each row.

Columns:  employee_id, site_id, starts_on, ends_on, reason

Rules:
  R1  employee_id matches ^e_\d{5}$
  R2  site_id exists in sites.json
  R3  starts_on and ends_on are ISO dates, and ends_on >= starts_on
  R4  the window is at most 365 days
  R5  reason is between 20 and 500 characters
  R6  no duplicate (employee_id, site_id) pair with an overlapping window
       - within the file, AND against an existing-requests file

Output: JSON with per-row results, an error code and message per failure,
        and a summary. Exit code 0 if all rows valid, 1 otherwise.

Must:   stream the file rather than loading it into memory - it must handle
        a 500 MB input on a laptop with 8 GB of RAM
        report ALL errors on a row, not just the first
        be covered by tests, including the overlap edge cases

Projects 2 to 5 — building the product

Weeks 03–04 · Sheet 03 Project 2 — BadgeDesk web

Next.js App Router. Request list, request detail, new-request form, approve action. Server components fetch; only the button and the filter bar are client components. Filter and page number live in the URL. Tailwind for styling.

Done when: a manager can list, filter, open and approve a request using only a keyboard; the back button works; and it is usable at 360 px wide. Data comes from a mocked module with real TypeScript types — Project 3 replaces the implementation, not the types.

Stretch: optimistic UI on approve, with rollback on failure.

Weeks 05–06 · Sheets 04, 05 Project 3 — core service

FastAPI over PostgreSQL. Full CRUD for access requests, the approve and reject transitions, Pydantic validation mirroring every client-side rule, cursor pagination, RFC 9457 errors with a trace id, and Idempotency-Key backed by Redis.

Done when: the OpenAPI schema generates the TypeScript types the web app compiles against, firing the same request twice creates one record, and the integration tests run against a real Postgres in Docker.

Stretch: row-level security so a site admin can only see their own site.

Week 06 · Sheet 05 Project 4 — gateway, notifier, webhooks

A NestJS GraphQL gateway in front of core, with a per-request DataLoader, a depth limit and complexity scoring. An Express notifier. An inbound webhook receiver with HMAC verification, a timestamp window and delivery-id deduplication.

Done when: you can demonstrate the N+1 problem with query logging on, then show it fixed; and a tampered webhook body is rejected while a replayed delivery returns 2xx without acting twice.

Stretch: outbound webhooks to a fake partner, with retry, jitter and a dead letter store.

Week 07 · Sheet 06 Project 5 — make it fast

Seed a million access requests. Find the slow queries, read the plans, add the right composite indexes, and record before-and-after EXPLAIN ANALYZE output. Add cache-aside for the site directory with jittered TTL and stampede protection. Store door events in MongoDB and write the aggregation pipeline.

Done when: the request list p99 is under 50 ms at a million rows, and you have a written record of each optimisation with its measured effect.

Stretch: reproduce a deadlock deliberately, then fix it with consistent lock ordering.

In production — the habit worth building here

Project 5 is the first time you will have numbers. Keep a PERFORMANCE.md in the repository with a row per change: what was slow, what you measured, what you changed, what it became. It costs five minutes per entry and it turns “I optimised some queries” into “the request list was 813 ms because it was sequentially scanning ten million rows to keep forty-three thousand; a composite index on site, status and created-at took it to 0.14 ms”. Interviewers remember the second answer.

Project 6 — ship it

Weeks 08–10. The highest-value fortnight on the entire drawing set.

Projects 7 and 8 — the senior differentiators

Week 11 · Sheet 11 Project 7 — event-driven provisioning

Replace the synchronous vendor call with Kafka. core writes an outbox row inside the approval transaction; a relay publishes access.approved; a consumer group calls the fake CCure API with retry and backoff and publishes access.provisioned. Failures go to a dead letter topic.

Done when: you can stop the vendor entirely and the system keeps accepting approvals, then drains the backlog when it returns; and replaying a message twice provisions once.

Why it matters: the transactional outbox is a genuine senior-level pattern, and being able to explain why you cannot write to a database and a queue atomically separates candidates immediately.

Week 11 · Sheet 12 Project 8 — the policy assistant

RAG over invented access-policy documents. Chunk on headings, embed into pgvector, hybrid search with rank fusion, cross-encoder reranking, citations verified against what you actually sent. A golden set of thirty questions scored on every change.

Done when: you can show a question that vector search alone gets wrong and hybrid search gets right, with recall@5 measured before and after; and an injected instruction in a document fails to make the assistant leak anything.

Why it matters: almost every AI project in a portfolio is a thin wrapper around a chat API. Retrieval measurement and an evaluation suite are what make this engineering.

Project 9 — the write-up

Week 12. Ninety seconds of a reader's attention is all you get. Design for that.

the decisions section — the format that works
## Engineering decisions

### GraphQL at the edge, REST between services
The web and mobile clients need different shapes of the same data, and the
alternative was a growing set of `?include=` parameters that were becoming a
query language by accident. Internally there are two known callers who want
HTTP caching, plain URLs in logs and `curl` during an incident, so REST stays.

**Rejected:** GraphQL everywhere. It would have cost the caching and tooling
we get free from REST, for no benefit at two internal callers.
**Would revisit if:** a third and fourth internal consumer appeared with
genuinely different data needs.

### Transactional outbox instead of publishing directly to Kafka
You cannot write to Postgres and Kafka atomically. Publishing first risks an
event for an approval that then rolls back; committing first risks an approval
that is never provisioned. The outbox commits the event with the approval and a
relay publishes it, which makes delivery at-least-once - so every consumer is
idempotent on the event id.

**Rejected:** two-phase commit, which is operationally miserable, and
"publish then commit and hope", which loses approvals silently.
**Cost:** roughly 200ms of extra latency and one more moving part to monitor.

If you want variety

BadgeDesk is the recommended path because depth beats breadth. But if you genuinely need a second domain for a specific role, these use the same stack against a different problem.

Data-heavyLog analytics pipeline

Ingest logs over Kafka, aggregate in a consumer, store rollups in Postgres and raw events in S3, query with a FastAPI service, chart in Next.js. Exercises messaging, time-series schema design, partitioning and cost-aware storage tiering.

Real-timeCollaborative shift planner

WebSockets, presence, optimistic UI with conflict resolution, Redis pub/sub for fan-out across instances. Exercises the hardest part of frontend state and the stateful-service scaling problem.

Integration-heavyVendor sync service

Pull from three fake external APIs with different auth schemes, rate limits and pagination styles; reconcile into one model; expose webhooks outbound. Exercises resilience patterns, backoff, circuit breaking and reconciliation.

Choose at most one, and only after Project 6 is deployed. A second system before the first one ships is how portfolios end up as a collection of promising starts.

Deploy a slice, not the whole system

You do not need all eleven services live to have a demo. Deploy the front end plus the core API plus Postgres — the request-submit-approve path — and let the README and the three-minute recording cover the rest. A reviewer clicks the link, submits a badge request, sees it appear, and closes the tab. That is the entire job of the deployed instance. The Kafka worker and the reconciler Lambda are more convincing as a diagram plus a passing test suite than as an idle deployment you are paying to keep warm.

Red pencil — free hosting still leaks secrets

Every platform above wants environment variables through a dashboard, and the temptation is to paste your real values into the first box you see. Two rules carry over from Sheet 01 unchanged: generate separate credentials for the demo — a Neon connection string that only the demo uses, so rotating it breaks nothing — and seed the demo with fabricated data only. A public URL with a login form is a public URL: put fake employees behind it, rate-limit the endpoints, and assume someone will try the obvious injection. If the demo is compromised it should be an inconvenience, not an incident.

In production — what the free tier teaches you anyway

Render spinning down after fifteen minutes is a cold start; Neon scaling to zero is a connection pool problem; Upstash’s 10,000 commands a day forces you to notice how often you actually hit the cache. Every constraint on that table is a scaled-down version of a real production concern, and being able to say “the demo cold-starts because the free tier suspends idle containers, here is how I would fix that with a warm pool” is a better answer than a demo that never had a constraint.

Drill book

The project conversation opens most interviews. These are the questions that follow “tell me about something you have built”.

Talking about your work
Tell me about a project you are proud of.

Ninety seconds, in this order: the problem and who had it, the shape of the solution in two sentences, the one interesting engineering decision, and one number. “BadgeDesk manages building access requests across three sites. It is a Next.js front end over a FastAPI service and a NestJS GraphQL gateway, on ECS behind an ALB, all in Terraform. The interesting part was making provisioning asynchronous through Kafka with a transactional outbox, because the vendor API was slow and unreliable and we could not let their latency become our timeouts. The request list went from 813 milliseconds to 0.14 after indexing.” Then stop and let them choose where to dig.

What was the hardest problem you hit?

Pick something genuinely technical with a real diagnosis, not “time management”. Structure it as symptom, investigation, root cause, fix, prevention — the investigation is the part they are assessing. Duplicate access requests appearing under poor mobile connectivity, traced by correlating client retries with server logs, root cause being a non-idempotent POST, fixed with client-generated idempotency keys in Redis, prevented by making it a requirement in the API guidelines and a test in the suite.

What would you do differently?

Answer honestly and specifically, because a candidate with no criticisms of their own work has not looked hard. “I introduced MongoDB for the door events when a jsonb column in Postgres would have handled the volume and removed a whole database from the estate. I chose it partly to learn it, which is fine for a personal project and would have been the wrong call at work.” That answer demonstrates judgement about judgement, which is what a senior interview is looking for.

How do you know it works?

Layered: unit tests for the validation and business rules, integration tests against a real Postgres and Redis in Docker so the tests exercise the actual queries, contract checks that the generated OpenAPI schema still matches, smoke tests against staging after every deploy, and alarms on the four golden signals in production. Plus the deliberate failure exercises — I killed a task mid-request and confirmed no request was dropped, and rebooted RDS with failover to check the pool reconnected without a redeploy.

How would you scale it to a hundred times the traffic?

Measure first, because the bottleneck is rarely where you guess. Then in likely order: read replicas and more aggressive caching for the read path, which dominates; more Fargate tasks behind the existing load balancer, since the services are stateless; more Kafka partitions and consumer instances for provisioning throughput; and only then partitioning the access-request table by site or by date. The part that would actually break first is the connection pool arithmetic, and the part that would cost the most is CloudWatch Logs ingestion.

You built this alone. How do we know you can work in a team?

Point at the artefacts that only exist for other people: the README and architecture document written for a reader, decision records with the rejected options and the trade-offs, small reviewable commits, branch protection with required checks, and an API contract defined before either side was written. Then give a concrete example from your actual job of a disagreement resolved and what you changed your mind about. The project shows habits; the job story shows collaboration.
