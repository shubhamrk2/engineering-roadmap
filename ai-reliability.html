The map: one integration, six places it can go wrong

A badge request leaves your code, crosses a trust boundary, and comes back as a webhook. Each numbered point below is a section of this sheet and a question an interviewer will ask.

1
Authenticate, then authorise, at the edge. Authentication answers “who are you”; authorisation answers “may you do this to this object”. Mixing them up produces 401/403 mistakes and the number-one API vulnerability (see section 1 and the OWASP walk-through).
2
Validate everything that crosses a boundary. Types, lengths, allowed values, unknown fields. Your own database is trusted; the request body, the vendor response and the webhook payload are not.
3
Credentials live outside the code. The worker reads its vendor credential from a secret store at run time. If one leaks you rotate it; you do not “delete the commit”.
4
The write and the message commit together. Saving the request and queuing the vendor call in one transaction (the outbox) means a crash cannot lose the work or invent it. The worker then calls the vendor with a timeout and an idempotency key so a retry is harmless.
5
Record what happened, without recording secrets. An audit row per attempt and outcome is how you answer “did the badge get created?” three weeks later. Redact personal data on the way in.
6
Inbound webhooks are an unauthenticated public door. Verify the signature over the raw body, reject old timestamps, answer 200 quickly, and drop event ids you have already seen.
Why this sheet matters for the roles you want

Applied AI and forward-deployed roles are mostly integration work with a model in the middle: a model calls a tool, the tool calls a flaky enterprise API, the answer comes back late or twice. Anyone can make the happy path work in an afternoon. The person who gets hired is the one who can say “the call timed out, so I do not know if it happened; I retried with the same idempotency key; the vendor deduplicated; the audit table shows two attempts and one badge”. You already think like this from real integration work. This week you make it provable with tests, and you learn the vocabulary to say it.

Red pencil — the one-line version that fails interviews

“I would add retries.” Retries without a timeout hang forever, retries without backoff hammer a struggling vendor, retries without jitter synchronise every client into a storm, and retries without idempotency create duplicates. A good answer names all four. This sheet is those four, plus the security basics that sit around them.

1. Authentication, authorisation, tokens and OAuth

Who are you, and what may you do? Then: how do you prove it on every request without sending your password every time?

Authentication versus authorisation

Authentication (authn) establishes identity: this request really comes from hr-sync or from employee e-902. Authorisation (authz) decides permission: may this identity read this access request? An authenticated caller can still be unauthorised. The HTTP codes are named confusingly: 401 Unauthorized really means “unauthenticated” (no or bad credential); 403 Forbidden means “I know who you are, and no”.

authz_demo.py — 401 vs 403 vs the object-level check
# API keys are looked up by hash in real systems; plain dict keeps the idea visible.
API_KEYS = {
    "key-hr-sync": {"client": "hr-sync",   "scopes": {"requests:read"}},
    "key-admin":   {"client": "admin-bot", "scopes": {"requests:read", "requests:write"}},
}
REQUESTS = {
    "req-1": {"owner": "hr-sync",   "site_id": "BLR-01"},
    "req-2": {"owner": "other-team", "site_id": "HYD-01"},
}

def authenticate(headers):
    """Who is calling? Returns a principal dict or None (-> 401)."""
    key = headers.get("X-Api-Key")
    return API_KEYS.get(key)

def get_request(headers, request_id):
    principal = authenticate(headers)
    if principal is None:
        return 401, {"error": "unauthenticated"}                 # no or unknown credential
    if "requests:read" not in principal["scopes"]:
        return 403, {"error": "missing scope requests:read"}     # known caller, wrong permission
    record = REQUESTS.get(request_id)
    if record is None or (record["owner"] != principal["client"] and "requests:write" not in principal["scopes"]):
        return 404, {"error": "not found"}                       # object-level check: never confirm others' ids exist
    return 200, record

assert get_request({}, "req-1")[0] == 401
assert get_request({"X-Api-Key": "nope"}, "req-1")[0] == 401
assert get_request({"X-Api-Key": "key-hr-sync"}, "req-1")[0] == 200
assert get_request({"X-Api-Key": "key-hr-sync"}, "req-2")[0] == 404   # someone else's object
assert get_request({"X-Api-Key": "key-admin"}, "req-2")[0] == 200
print("401, 403, 404 and 200 all behave")
Interviewers ask

“What is the difference between 401 and 403, and what is BOLA?” 401: I do not know who you are. 403: I know, and you may not. BOLA (broken object level authorisation, OWASP API1) is when the scope check passes but the code never checks that this record belongs to this caller, so changing req-1 to req-2 in the URL reads someone else’s data. The fix is an ownership check on every object access, and a test that asks for another caller’s id. Returning 404 instead of 403 for other people’s objects avoids confirming they exist; say which you chose and why.

A JWT is just three base64 strings: build and break one

Concept before library. An HS256 JWT is base64url(header) . base64url(payload) . base64url(HMAC-SHA256(header.payload)). Writing the verifier by hand shows exactly what must be checked. You must be able to explain every check in verify: each one closes a real attack.

jwt_by_hand.py — HS256 signing and the checks that matter
import base64, hashlib, hmac, json

def b64(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def unb64(text: str) -> bytes:
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))   # put the padding back

def issue(secret: bytes, claims: dict) -> str:
    header = {"alg": "HS256", "typ": "JWT"}
    signing_input = b64(json.dumps(header).encode()) + "." + b64(json.dumps(claims).encode())
    sig = hmac.new(secret, signing_input.encode(), hashlib.sha256).digest()
    return signing_input + "." + b64(sig)

class InvalidToken(Exception):
    pass

def verify(secret: bytes, token: str, *, audience: str, issuer: str, now: int) -> dict:
    try:
        h64, p64, s64 = token.split(".")
        header = json.loads(unb64(h64))
        claims = json.loads(unb64(p64))
    except Exception:
        raise InvalidToken("malformed")
    if header.get("alg") != "HS256":                       # YOU choose the algorithm; never trust the header
        raise InvalidToken("unexpected alg")               # blocks alg=none and algorithm-confusion tricks
    expected = hmac.new(secret, (h64 + "." + p64).encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(expected, unb64(s64)):      # constant-time compare
        raise InvalidToken("bad signature")
    if claims.get("iss") != issuer:
        raise InvalidToken("wrong issuer")
    if claims.get("aud") != audience:                      # a token minted for another API must not work here
        raise InvalidToken("wrong audience")
    if now >= claims.get("exp", 0):
        raise InvalidToken("expired")
    return claims

SECRET = b"demo-secret-not-for-real-use-0123456789"
claims = {"iss": "https://idp.example", "aud": "badge-api", "sub": "e-902",
          "scope": "requests:read", "exp": 1_000_300}
token = issue(SECRET, claims)
print(verify(SECRET, token, audience="badge-api", issuer="https://idp.example", now=1_000_000)["sub"])   # e-902

def rejects(tok, **kw):
    args = dict(audience="badge-api", issuer="https://idp.example", now=1_000_000); args.update(kw)
    try:
        verify(SECRET, tok, **args); return False
    except InvalidToken as e:
        return str(e)

print(rejects(token, now=1_000_300))            # expired
print(rejects(token, audience="other-api"))     # wrong audience
h, p, s = token.split(".")
forged = b64(json.dumps({**claims, "scope": "requests:write"}).encode())
print(rejects(h + "." + forged + "." + s))      # bad signature (payload edited, signature not)
none_header = b64(json.dumps({"alg": "none"}).encode())
print(rejects(none_header + "." + p + "."))     # unexpected alg
Red pencil — a JWT is signed, not encrypted

Anyone can base64-decode the payload and read it. Never put secrets or unnecessary personal data in claims. And “it decodes fine” proves nothing: decoding is not verifying. The three classic failures are accepting alg: none, trusting the algorithm named in the token, and skipping aud/exp. In production use a maintained library (for example PyJWT), pin the allowed algorithms, and require exp, aud and iss. The hand-written version above is for understanding, not for shipping.

Token storage, lifetime, refresh and revocation

The worker in drawing 28-B must not request a new token for every call (that hammers the identity provider) nor keep using one past its expiry. The usual shape: cache the token, refresh a little early, and on a 401 refresh once and retry once. The code injects the HTTP call and the clock so you can test expiry without waiting an hour.

token_cache.py — cache, refresh early, recover from one 401
class TokenProvider:
    def __init__(self, fetch_token, clock, skew=60):
        self._fetch, self._clock, self._skew = fetch_token, clock, skew
        self._token, self._expires_at = None, 0.0
        self.fetches = 0

    def get(self, force=False):
        if force or self._token is None or self._clock() >= self._expires_at - self._skew:
            body = self._fetch()                       # POST /token in real life
            self.fetches += 1
            self._token = body["access_token"]
            self._expires_at = self._clock() + body["expires_in"]
        return self._token

def call_with_token(provider, send):
    status, body = send(provider.get())
    if status == 401:                                  # expired or revoked mid-flight
        status, body = send(provider.get(force=True))  # refresh ONCE; never loop on 401
    return status, body

now = [1000.0]
issued = []
def fake_token_endpoint():
    issued.append(f"tok-{len(issued) + 1}")
    return {"access_token": issued[-1], "expires_in": 3600}

provider = TokenProvider(fake_token_endpoint, clock=lambda: now[0])
valid = {"tok-1"}
def vendor(token):
    return (200, "ok") if token in valid else (401, "expired")

assert call_with_token(provider, vendor) == (200, "ok") and provider.fetches == 1
assert call_with_token(provider, vendor) == (200, "ok") and provider.fetches == 1     # cached
now[0] += 3600 - 59                                    # inside the 60 s refresh window
valid.add("tok-2")
assert call_with_token(provider, vendor) == (200, "ok") and provider.fetches == 2     # refreshed early
valid.discard("tok-2")                                 # the vendor revokes it; our cache does not know
valid.add("tok-3")
assert call_with_token(provider, vendor) == (200, "ok") and provider.fetches == 3     # 401 -> refresh once -> ok
print("fetches:", provider.fetches)                    # fetches: 3

In production

Access tokens are short (minutes to an hour) so that a leak has a small blast radius; refresh tokens last longer and are stored more carefully and rotated on use. Revocation is the awkward part for self-contained JWTs: the resource server checks the signature, not a database, so a revoked token keeps working until it expires. Teams either keep lifetimes short, or add token introspection (ask the issuer “is this still valid?”) for high-risk operations. The same idea applies to MCP and tool calls from an AI assistant: give the tool a token with only the scope that one tool needs, and expect to refresh it.

Scopes, permissions model and least privilege

A scope is a named slice of permission carried by a token (requests:read, badges:write). Design scopes around actions on resources, not around people. Least privilege means every credential gets the minimum set that its job needs, and nothing more: the nightly reconciler reads from the vendor, so it has badges:read and cannot create or delete anything. If its key leaks, the worst case is a read.

ModelDecision is based onGood forCost
ScopesWhat the token was grantedThird-party and service-to-service accessCoarse; does not say which objects.
Roles (RBAC)The caller’s role: employee, manager, site-adminInternal apps with few stable job typesRole explosion over time.
Ownership / attributesRelationship: this request belongs to this caller, same siteObject-level rules (stops BOLA)Must be coded and tested per object type.

Real systems layer them: a scope lets you in the door, a role picks the endpoint, an ownership check picks the row. A deny by default posture (nothing allowed unless a rule says so) is the safe starting point.

Interviewers ask

“A worker needs to call a vendor API on behalf of no user. Which OAuth flow, and what do you store?” Client credentials. Store the client id and secret in a secret store, not in the repo; request only the scope the job needs; cache the access token in memory, refresh slightly before expiry, and on a 401 refresh once and retry once. Follow-up: “what if the user is a human?” Authorisation code with PKCE, because a browser or mobile app cannot keep a client secret, and the verifier proves the app that started the login is the one finishing it.

2. Secrets management

A secret is anything that, in the wrong hands, lets someone act as you: API keys, client secrets, signing keys, database passwords, webhook secrets, tokens. The rule is short; the habit is what is hard.

secrets_hygiene.py — load from the environment, never print it, keep it out of logs
import logging, os, re

class Secret:
    """Wraps a value so that print(), f-strings, repr() and logging show a placeholder."""
    def __init__(self, value: str):
        self._value = value
    def reveal(self) -> str:             # the ONE explicit way to get the value out
        return self._value
    def __repr__(self):
        return "Secret(****)"
    __str__ = __repr__

def require_secret(name: str) -> Secret:
    value = os.environ.get(name)
    if not value:
        raise RuntimeError(f"environment variable {name} is not set")   # name it; never print the value
    return Secret(value)

os.environ["VENDOR_CLIENT_SECRET"] = "s3cr3t-demo-value"                # only for this demo
vendor_secret = require_secret("VENDOR_CLIENT_SECRET")
print(vendor_secret)                           # Secret(****)
print(f"using {vendor_secret!r}")              # using Secret(****)
assert "s3cr3t" not in f"{vendor_secret}"

# A logging filter is a safety net for the day someone logs a header by accident.
class RedactFilter(logging.Filter):
    PATTERN = re.compile(r"(?i)(authorization|api[-_]?key|secret|token)(['\"]?\s*[:=]\s*['\"]?)([^\s'\",]+)")
    def filter(self, record):
        record.msg = self.PATTERN.sub(r"\1\2[REDACTED]", str(record.getMessage()))
        record.args = ()
        return True

lines = []
class Collect(logging.Handler):
    def emit(self, record):
        lines.append(self.format(record))

log = logging.getLogger("vendor")
log.setLevel(logging.INFO)
handler = Collect()
handler.addFilter(RedactFilter())
log.addHandler(handler)
log.info("calling vendor with headers Authorization: Bearer abc123 and api_key=zzz999")
print(lines[0])      # calling vendor with headers Authorization: [REDACTED] abc123 and api_key=[REDACTED]

Look at that last line when you run it. The filter redacted the word after Authorization: (which is Bearer) but not the token itself, so the secret still leaked. Pattern-based redaction is a safety net full of holes, not a control. The real fix is upstream: never put the header into a log message at all, and wrap secrets (as Secret does) so that accidental formatting is harmless.

Red pencil — “I will add it to .gitignore later”

Add .env to .gitignore before the first commit. Deleting a secret in a later commit leaves it in history: git log -p still shows it, and a public repo has been scraped long before you notice. Also: committing a .env.example with fake values is good practice and tells the next person which variables exist.

Rotation, and what to do the moment one leaks

Rotation means replacing a secret on a schedule (and on demand) so a stolen copy expires. It only works if the system can accept two valid secrets for a short overlap (old and new), otherwise rotating is an outage. Design for the overlap from the start: webhook secrets, API keys and signing keys all benefit from a “current and previous” pair.

A leak, in order

1. Revoke or rotate first — the secret is burnt the moment it left your control; every minute counts more than cleaning up. 2. Find the blast radius — what could this credential do, and check the vendor’s and your own audit logs for use you do not recognise. 3. Replace it in the secret store and redeploy. 4. Remove it from the repo (history rewrite with git filter-repo, then force-push) — but understand this is tidying, not safety. 5. Say so: tell your security contact, write a short note of cause and prevention. Skipping step 1 to “fix the commit first” is the classic mistake. Prevention: a secret scanner (for example gitleaks, free) in a pre-commit hook.

Interviewers ask

“You find an API key in a public repo. Walk me through it.” Revoke it and issue a new one before anything else, then check usage logs for the exposure window, deploy the replacement from the secret store, then clean the history and add a scanner so it cannot recur. Follow-up: “why not just delete the commit?” Because forks, clones, caches and bots already have it; only revocation makes the old value useless.

Four different tools get called “encryption”. Choosing the wrong one is how teams end up with reversible passwords and signatures that prove nothing.

HMAC: a keyed hash for “did the vendor really send this?”

A plain hash can be recomputed by anyone, so it proves nothing about origin. HMAC mixes a secret into the hash, so only holders of the secret can produce the tag. Two details decide whether it is secure: compare with hmac.compare_digest (constant time, so an attacker cannot learn the tag byte by byte from response timing), and sign the raw bytes you received, not a re-serialised copy.

hmac_demo.py — runnable, standard library only
import hashlib, hmac

secret = b"whsec_demo_not_a_real_secret"
body = b'{"event_id":"evt-1","request_id":"req-1","status":"provisioned"}'

tag = hmac.new(secret, body, hashlib.sha256).hexdigest()
print(tag[:16], len(tag))                         # first 16 hex chars, 64 total

def verify(secret, body, received_tag):
    expected = hmac.new(secret, body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received_tag)       # NOT  expected == received_tag

assert verify(secret, body, tag)
assert not verify(secret, body + b" ", tag)       # one extra byte: rejected
assert not verify(b"other-secret", body, tag)     # wrong key: rejected

# A hash alone is NOT authentication: an attacker can compute this for any body they like.
forged_plain_hash = hashlib.sha256(b'{"event_id":"evt-9"}').hexdigest()
assert not verify(secret, b'{"event_id":"evt-9"}', forged_plain_hash)
print("hmac checks pass")

Authenticated encryption with AES-GCM

Old advice said “encrypt, then add a MAC”. Modern practice uses AEAD (authenticated encryption with associated data) modes such as AES-GCM, which encrypt and produce an authentication tag in one operation. The idea: ciphertext cannot be changed without the tag failing, and you can bind extra associated data (for example the request id) that is authenticated but not hidden. The one rule that matters: never reuse a (key, nonce) pair. With GCM, reuse leaks plaintext relationships and lets an attacker forge messages. A fresh random 96-bit nonce per message is the standard approach for modest volumes.

aesgcm_demo.py — needs: python -m pip install cryptography
import os

Red pencil — rolling your own

Never invent a cipher, a padding scheme or a “secure” XOR trick. Use a maintained library’s high-level AEAD (cryptography’s AESGCM, or Fernet for simple cases). Never use ECB mode, never reuse a nonce, never hard-code a key, and never put a decrypted result into a response before the authentication tag has been checked (the library does this for you: it raises instead of returning bad plaintext). Also: base64 and ROT13 are encodings, not encryption.

Digital signatures: public verification

With HMAC the verifier holds the same secret as the signer, so a verifier could also forge. A signature uses a private key to sign and a public key to verify, so you can hand the public key to every partner. This is how JWTs signed with RS256 or EdDSA let many services verify tokens that only the identity provider can create.

Passwords: slow, salted hash; never encryption

If you can decrypt passwords, so can whoever steals the key and the database. A password store should be one-way, salted (a random per-user value so equal passwords hash differently and rainbow tables fail) and deliberately slow and memory-hard so that guessing billions of passwords per second is not possible. Use Argon2id, scrypt or bcrypt. Python’s standard library has hashlib.scrypt.

password_hash.py — scrypt from the standard library
import hashlib, hmac, os

N, R, P = 2**14, 8, 1            # cost parameters: raise N as hardware allows; store them with the hash

def hash_password(password: str) -> str:
    salt = os.urandom(16)                                   # unique per user
    digest = hashlib.scrypt(password.encode(), salt=salt, n=N, r=R, p=P, dklen=32)
    return f"scrypt${N}${R}${P}${salt.hex()}${digest.hex()}"   # everything needed to verify later

def check_password(password: str, stored: str) -> bool:
    _, n, r, p, salt_hex, digest_hex = stored.split("$")
    digest = hashlib.scrypt(password.encode(), salt=bytes.fromhex(salt_hex),
                            n=int(n), r=int(r), p=int(p), dklen=32)
    return hmac.compare_digest(digest, bytes.fromhex(digest_hex))

Key management, TLS in transit, encryption at rest

The key is the secret, not the algorithm. Key management is where real systems fail: keys beside the data they protect, keys in code, keys never rotated. The standard answer is envelope encryption: encrypt each file with a fresh data key, then encrypt (“wrap”) that data key with a long-lived key-encryption key (KEK) that lives in a key management service. Rotating the KEK means re-wrapping a few dozen bytes per file, not re-encrypting terabytes.

envelope_demo.py — needs: cryptography
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def wrap(kek: bytes, data_key: bytes) -> bytes:
    nonce = os.urandom(12)
    return nonce + AESGCM(kek).encrypt(nonce, data_key, b"data-key")

def unwrap(kek: bytes, wrapped: bytes) -> bytes:
    return AESGCM(kek).decrypt(wrapped[:12], wrapped[12:], b"data-key")

def encrypt_file(kek: bytes, plaintext: bytes) -> dict:
    data_key = AESGCM.generate_key(bit_length=256)          # a fresh key per file
    nonce = os.urandom(12)
    return {"wrapped_key": wrap(kek, data_key),             # stored WITH the file: useless without the KEK
            "nonce": nonce,
            "ciphertext": AESGCM(data_key).encrypt(nonce, plaintext, None)}

def decrypt_file(kek: bytes, blob: dict) -> bytes:
    data_key = unwrap(kek, blob["wrapped_key"])
    return AESGCM(data_key).decrypt(blob["nonce"], blob["ciphertext"], None)

kek_v1 = AESGCM.generate_key(bit_length=256)                # in production: lives in a KMS, never in the app
blob = encrypt_file(kek_v1, b"nightly audit export, 4 MB of rows")
assert decrypt_file(kek_v1, blob) == b"nightly audit export, 4 MB of rows"

# Rotate the KEK: re-wrap only the small data key. The big ciphertext is untouched.
kek_v2 = AESGCM.generate_key(bit_length=256)
old_ciphertext = blob["ciphertext"]
blob["wrapped_key"] = wrap(kek_v2, unwrap(kek_v1, blob["wrapped_key"]))
assert blob["ciphertext"] is old_ciphertext
assert decrypt_file(kek_v2, blob) == b"nightly audit export, 4 MB of rows"

4. Data validation at the boundary

Inside your service you can trust your own types. Everything that arrives from outside, and everything the vendor sends back, is a string someone else wrote.

Reject early, say exactly why, trust nothing from the other side

Validate at every boundary: the incoming request, the vendor’s response, a webhook body, a row read from a file. Check type, presence, length, range, allowed values, and unknown fields. Prefer an allow-list (“site_id must be one of these three”) to a deny-list (“must not contain a semicolon”), which is always incomplete. Return all the problems at once with field names, so the caller can fix them in one go. In a FastAPI service Pydantic does this from type hints (you meet it in the FastAPI weeks); the hand-written version shows what it is doing.

validate_request.py — boundary validation with an error list
from datetime import date

SITES = {"BLR-01", "BLR-02", "HYD-01"}                    # allow-list
ALLOWED_FIELDS = {"employee_id", "site_id", "starts_on", "ends_on", "reason"}
MAX_REASON = 200

def validate_access_request(payload) -> tuple[dict, list[str]]:
    """Return (clean_data, errors). Never raises on bad input; bad input is the normal case."""
    errors = []
    if not isinstance(payload, dict):
        return {}, ["body must be a JSON object"]
    extra = set(payload) - ALLOWED_FIELDS
    if extra:                                              # unknown fields: reject, do not silently store (mass assignment)
        errors.append(f"unknown fields: {sorted(extra)}")

    emp = payload.get("employee_id")
    if not (isinstance(emp, str) and emp.startswith("e-") and emp[2:].isdigit() and len(emp) <= 12):
        errors.append("employee_id must look like e-902")
    if payload.get("site_id") not in SITES:
        errors.append(f"site_id must be one of {sorted(SITES)}")

    dates = {}
    for field in ("starts_on", "ends_on"):
        try:
            dates[field] = date.fromisoformat(payload.get(field))   # TypeError for None, ValueError for junk
        except (TypeError, ValueError):
            errors.append(f"{field} must be an ISO date like 2027-01-04")
    if len(dates) == 2 and dates["ends_on"] < dates["starts_on"]:
        errors.append("ends_on must not be before starts_on")

    reason = payload.get("reason", "")
    if not isinstance(reason, str) or len(reason) > MAX_REASON:
        errors.append(f"reason must be text of at most {MAX_REASON} characters")

    if errors:
        return {}, errors
    return {"employee_id": emp, "site_id": payload["site_id"], **dates, "reason": reason}, []

assert errs == [] and ok["starts_on"] == date(2027, 1, 4)

Red pencil — validating only at the front door

Teams validate the browser form and then trust the vendor’s JSON, the CSV a partner uploaded, or the webhook body. A vendor that renames a field or sends null will crash a worker at 3 a.m.; a malicious payload with an extra is_admin field may get saved if you bind the whole body to a model (mass assignment, OWASP API3). Parse the vendor response with the same discipline as user input, and fail with a clear error that names the field. Also cap sizes: unbounded bodies and unbounded lists are a denial-of-service door (API4).

5. File processing for integrations

Integration work is often files: a partner sends an encrypted export, you decrypt it, process it row by row, and ship a ZIP back. The failure modes are memory, corruption and leftovers on disk.

Stream, do not load: chunking and checksums

path.read_bytes() puts the whole file in memory. That is fine for 20 KB and an out-of-memory crash for 5 GB (or for fifty 200 MB files processed at once). Streaming reads a fixed-size chunk, handles it, and discards it, so memory stays flat no matter how big the file is. A checksum (SHA-256) computed while streaming lets the receiver confirm that what arrived is what was sent; it detects accidents and truncation, but it is not authentication unless the checksum itself travels over a trusted channel or is signed.

stream_vs_load.py — flat memory, proven with tracemalloc
import hashlib, os, tempfile, tracemalloc
from pathlib import Path

def sha256_streaming(path, chunk_size=64 * 1024) -> str:
    digest = hashlib.sha256()
    with open(path, "rb") as f:
        while chunk := f.read(chunk_size):         # walrus: assign and test in one line; b"" at EOF ends the loop
            digest.update(chunk)
    return digest.hexdigest()

def sha256_loading(path) -> str:
    return hashlib.sha256(Path(path).read_bytes()).hexdigest()   # whole file in memory

with tempfile.TemporaryDirectory() as folder:      # deleted when the block ends, even on error
    big = Path(folder) / "export.bin"
    with open(big, "wb") as f:
        for _ in range(64):                        # 64 x 128 KiB = 8 MiB of random bytes
            f.write(os.urandom(128 * 1024))

    tracemalloc.start()
    a = sha256_streaming(big)
    _, peak_stream = tracemalloc.get_traced_memory()
    tracemalloc.stop()

    tracemalloc.start()
    b = sha256_loading(big)
    _, peak_load = tracemalloc.get_traced_memory()
    tracemalloc.stop()

assert a == b                                      # same answer
print("stream peak under 1 MiB:", peak_stream < 1024 * 1024)      # True
print("load peak over 8 MiB:   ", peak_load > 8 * 1024 * 1024)    # True

Decrypt-then-process, in chunks, with tamper detection

Encrypting a large file with one AES-GCM call needs it all in memory and has size limits. The usual design is chunked authenticated encryption: split into chunks, encrypt each with its own nonce, and bind each chunk to its position so an attacker cannot reorder, drop or truncate chunks without detection. The block below does that: nonce = random 8-byte prefix + 4-byte chunk counter, and the associated data marks the final chunk, so cutting the file short makes the last remaining chunk fail authentication. Run it and read the three checks at the end.

chunked_aead.py — needs: cryptography
import io, os, struct
from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

CHUNK = 64 * 1024

def encrypt_stream(key: bytes, src, dst, chunk_size: int = CHUNK) -> None:
    aes, prefix, counter = AESGCM(key), os.urandom(8), 0
    dst.write(prefix)
    chunk = src.read(chunk_size)
    while True:
        nxt = src.read(chunk_size)                     # look ahead one chunk to know whether this one is last
        last = not nxt
        nonce = prefix + struct.pack(">I", counter)     # 12 bytes, unique per chunk
        ct = aes.encrypt(nonce, chunk, b"\x01" if last else b"\x00")
        dst.write(struct.pack(">I", len(ct)) + ct)
        if last:
            return
        chunk, counter = nxt, counter + 1

def decrypt_stream(key: bytes, src, chunk_size: int = CHUNK):
    """Generator: yields plaintext chunks. Raises InvalidTag on tampering, reordering or truncation."""
    aes = AESGCM(key)
    prefix = src.read(8)
    if len(prefix) != 8:
        raise InvalidTag()
    counter = 0
    header = src.read(4)
    while header:
        if len(header) != 4:
            raise InvalidTag()
        ct = src.read(struct.unpack(">I", header)[0])
        next_header = src.read(4)
        last = not next_header                          # no further chunk header: this must be the final one
        nonce = prefix + struct.pack(">I", counter)
        yield aes.decrypt(nonce, ct, b"\x01" if last else b"\x00")
        counter, header = counter + 1, next_header

key = AESGCM.generate_key(bit_length=256)
data = os.urandom(200_000)                              # about 3 chunks of 64 KiB
enc = io.BytesIO()
encrypt_stream(key, io.BytesIO(data), enc)
blob = enc.getvalue()

plain = b"".join(decrypt_stream(key, io.BytesIO(blob)))
assert plain == data                                     # 1. round trip

def fails(mutated: bytes) -> bool:
    try:
        b"".join(decrypt_stream(key, io.BytesIO(mutated)))
        return False
    except InvalidTag:
        return True

flipped = bytearray(blob); flipped[100] ^= 1
assert fails(bytes(flipped))                             # 2. a flipped bit is caught
one_chunk = 4 + CHUNK + 16
assert fails(blob[: 8 + one_chunk])                      # 3. truncation at a chunk boundary is caught
print("round trip ok; tamper and truncation both detected")
Red pencil — decrypt, then trust

Decrypting successfully (authenticated) proves the bytes are unchanged since encryption; it does not prove the contents are valid. Process in the right order: verify the authentication tag, then validate the content (schema, row counts, checksum from the manifest), then use it. And do not stream plaintext onward to a customer before the end-of-file check has passed, or a truncated file will have been half-delivered. Where the format cannot detect truncation, write to a temporary name and rename only after the full check.

ZIP creation, temp-file hygiene and zip-slip

Build ZIPs by streaming each member from disk, not by joining everything in memory. Put intermediate files in a TemporaryDirectory so they are removed even on exceptions; decrypted plaintext on disk is itself sensitive data, so it should live briefly in a private directory and never in the shared output folder. When reading a ZIP from someone else, remember zip-slip: a member named ../../etc/cron.d/x can escape the extraction folder. Check every resolved path.

zip_pipeline.py — stream, checksum, zip, extract safely, clean up
import hashlib, json, shutil, tempfile, zipfile
from pathlib import Path

def write_rows(path: Path, n: int) -> None:
    with open(path, "w", encoding="utf-8") as f:
        for i in range(n):
            f.write(json.dumps({"request_id": f"req-{i}", "site_id": "BLR-01"}) + "\n")

def process_lines(path: Path) -> int:
    """Streams the file line by line: constant memory however long it is."""
    count = 0
    with open(path, encoding="utf-8") as f:
        for line in f:
            json.loads(line)               # validate each row; a bad row raises with its line context in real code
            count += 1
    return count

def build_zip(out_zip: Path, members: dict) -> None:
    with zipfile.ZipFile(out_zip, "w", compression=zipfile.ZIP_DEFLATED) as zf:
        for arcname, source in members.items():
            with open(source, "rb") as src, zf.open(arcname, "w") as dst:
                shutil.copyfileobj(src, dst, length=64 * 1024)   # streamed, not read_bytes()

def safe_extract(zip_path: Path, dest: Path) -> list[str]:
    dest = dest.resolve()
    names = []
    with zipfile.ZipFile(zip_path) as zf:
        for info in zf.infolist():
            target = (dest / info.filename).resolve()
            if dest != target and dest not in target.parents:     # zip-slip check
                raise ValueError(f"unsafe path in archive: {info.filename}")
            names.append(info.filename)
        zf.extractall(dest)
    return names

6. Timeouts, retries, backoff, circuit breakers and bulkheads

The vendor takes 30 seconds. Or answers 503. Or does not answer at all. What your code does next decides whether one slow dependency becomes your outage.

Timeouts first: every network call needs one

Most HTTP clients have no timeout by default (Python’s urllib and requests wait indefinitely unless told). A hung vendor then holds a worker thread forever; fifty hung calls and your worker pool is empty and your service is down. Set a connect timeout (can I reach them: seconds) and a read timeout (are they answering: sized to the endpoint’s real p99), and set a total deadline for the whole operation including retries. The demo below uses a real local server on your loopback interface that answers after one second, with a 0.2 s client timeout.

timeout_demo.py — a slow vendor on 127.0.0.1, no internet needed
import threading, time, urllib.error, urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class SlowVendor(BaseHTTPRequestHandler):
    def do_GET(self):
        time.sleep(1.0)                          # scaled-down "the vendor takes 30 seconds"
        try:
            self.send_response(200); self.end_headers(); self.wfile.write(b"ok")
        except OSError:
            pass                                 # the client already gave up
    def log_message(self, *args):
        pass

server = ThreadingHTTPServer(("127.0.0.1", 0), SlowVendor)      # port 0 = any free port
threading.Thread(target=server.serve_forever, daemon=True).start()
url = f"http://127.0.0.1:{server.server_address[1]}/badges/bdg-1"

started = time.monotonic()
try:
    urllib.request.urlopen(url, timeout=0.2)     # THE line that matters: without timeout= this waits a full second (or forever)
except (TimeoutError, urllib.error.URLError) as exc:
    elapsed = time.monotonic() - started
    print("gave up long before the vendor's 1 s reply:", elapsed < 0.8, type(exc).__name__)   # True TimeoutError
    assert elapsed < 0.8
finally:
    server.shutdown(); server.server_close()

class Deadline:
    """One budget for the whole operation. Each attempt gets what is left, never more than its own cap."""
    def __init__(self, total, clock=time.monotonic):
        self._clock, self._end = clock, clock() + total
    def remaining(self):
        return max(0.0, self._end - self._clock())
    def timeout_for_attempt(self, per_attempt):
        return min(per_attempt, self.remaining())

t = [0.0]
d = Deadline(10, clock=lambda: t[0])
print(d.timeout_for_attempt(4))      # 4
t[0] = 8
print(d.timeout_for_attempt(4))      # 2.0   only 2 s of budget left
t[0] = 11
print(d.timeout_for_attempt(4))      # 0.0   out of budget: stop retrying, return an error now
Interviewers ask

“The vendor takes 30 seconds to respond. What do you do?” First, I do not let my user or my worker wait 30 seconds: I set a timeout shorter than that, sized from the vendor’s measured p99, and return or queue instead of hanging. A timeout means I do not know whether it happened, so the retry must be safe: an idempotency key, or a status lookup before re-sending. For a user-facing request I accept the work, return 202 with a status URL, and finish it in a background job. If the vendor stays slow, a circuit breaker stops me from piling more calls onto it, and an alert fires on error rate and latency. Follow-up: “how long should the timeout be?” Just above the vendor’s normal worst case, and always less than the caller’s own timeout, otherwise the caller gives up first while you keep working.

Retry, exponential backoff and jitter

Retry only what might succeed next time: timeouts, connection resets, HTTP 429 and 502/503/504. Never retry 400, 401, 403, 404 or 422: the answer will be the same. And retry only operations that are safe to repeat (next section). Exponential backoff doubles the wait each time (0.5 s, 1 s, 2 s…) so a struggling vendor gets room to recover; a cap stops it growing forever. Jitter randomises each wait. Without it, 1,000 clients that failed together retry together, again and again, in synchronised waves. “Full jitter” picks a random delay between zero and the current ceiling. This is exactly what the lab’s retry_with_backoff does.

backoff_jitter.py — why jitter matters, measured
import random

def ceiling(attempt, base=0.5, cap=8.0):
    return min(cap, base * 2 ** (attempt - 1))

def retry_times(n_clients, jitter, seed=7, attempts=3):
    """When does each of n clients (all failed at t=0) make its retries? Returns a list of times."""
    rng = random.Random(seed)                    # seeded: the numbers below are repeatable
    times = []
    for _ in range(n_clients):
        t = 0.0
        for attempt in range(1, attempts + 1):
            wait = rng.random() * ceiling(attempt) if jitter else ceiling(attempt)
            t += wait
            times.append(t)
    return times

def busiest_100ms(times):
    buckets = {}
    for t in times:
        buckets[int(t * 10)] = buckets.get(int(t * 10), 0) + 1
    return max(buckets.values())

plain = busiest_100ms(retry_times(1000, jitter=False))
jittered = busiest_100ms(retry_times(1000, jitter=True))
print("no jitter, busiest 100 ms:", plain)             # 1000   every client hits the vendor at the same instant
print("full jitter, busiest 100 ms:", jittered)        # 303   the same 3000 retries, spread out
assert plain == 1000 and jittered < plain / 2

# The call loop itself. Time and randomness are INJECTED so a test needs no real waiting.
class TransientError(Exception): pass

def call_with_retries(fn, *, max_attempts=4, sleep, rand):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts:
                raise                                  # out of attempts: let the caller decide
            sleep(rand() * ceiling(attempt))

waits, results = [], iter([TransientError, TransientError, "ok"])
def flaky():
    r = next(results)
    if r is TransientError:
        raise TransientError("503")
    return r

print(call_with_retries(flaky, sleep=waits.append, rand=lambda: 1.0), waits)    # ok [0.5, 1.0]
Red pencil — retries are a load multiplier

If every layer retries three times (browser, gateway, service, worker), one failure becomes 3 x 3 x 3 x 3 = 81 calls at the bottom, exactly when the vendor is struggling. Retry at one layer, use a retry budget (for example, give up if more than 10% of recent calls are retries), respect the vendor’s Retry-After header when it sends one, and keep the total deadline from the previous section. Also: except Exception: retry retries bugs. Retry only the exceptions you classified as transient.

A circuit breaker you can read in one minute

Retries help with a blip; they hurt during an outage. A circuit breaker notices that a dependency is failing and stops calling it for a while, failing fast instead of burning threads on doomed calls and giving the vendor air to recover. After the wait it lets one probe through. This version has a different shape from the lab’s (three small methods instead of call): in the lab, close this sheet and write yours from the specification, then compare.

breaker_demo.py — closed, open, half-open, driven by a fake clock
class CircuitOpenError(Exception):
    pass

class Breaker:
    def __init__(self, threshold=3, reset_after=30.0, clock=None):
        self.threshold, self.reset_after, self.clock = threshold, reset_after, clock
        self.state, self.failures, self.opened_at = "closed", 0, 0.0

    def before_call(self):
        if self.state == "open":
            if self.clock() - self.opened_at >= self.reset_after:
                self.state = "half_open"               # time is up: allow a probe
            else:
                raise CircuitOpenError("failing fast")

    def on_success(self):
        self.state, self.failures = "closed", 0

    def on_failure(self):
        self.failures += 1
        if self.state == "half_open" or self.failures >= self.threshold:
            self.state, self.opened_at = "open", self.clock()

def guarded(breaker, fn):
    breaker.before_call()
    try:
        result = fn()
    except Exception:
        breaker.on_failure()
        raise
    breaker.on_success()
    return result

now = [0.0]
b = Breaker(clock=lambda: now[0])
vendor_up = [False]
calls = []
def vendor():
    calls.append(now[0])
    if not vendor_up[0]:
        raise TimeoutError("vendor down")
    return "ok"

log = []
for second in range(0, 70, 5):
    now[0] = float(second)
    if second == 35:
        vendor_up[0] = True                           # the vendor recovers at t=35
    try:
        guarded(b, vendor); log.append((second, "ok", b.state))
    except CircuitOpenError:
        log.append((second, "fast-fail", b.state))
    except TimeoutError:
        log.append((second, "timeout", b.state))
for row in log:
    print(row)
fast = sum(1 for _, outcome, _ in log if outcome == "fast-fail")
print(fast, "calls failed fast without touching the vendor")    # 5 calls failed fast without touching the vendor
assert b.state == "closed" and fast == 5 and len(calls) == len(log) - fast

Bulkheads: stop one dependency eating every thread

A ship’s bulkheads stop one flooded compartment sinking the whole hull. In software: give each dependency its own small pool (threads, connections, semaphore permits), so a slow vendor can exhaust only its share. Calls beyond the limit are rejected immediately instead of queueing behind hung ones. Combined with a timeout, a breaker and a fallback (a cached answer, a queued job, a clear error), this is how services degrade gracefully instead of falling over.

bulkhead_demo.py — a bounded permit pool per dependency
import threading

class BulkheadFull(Exception):
    pass

class Bulkhead:
    def __init__(self, name, max_concurrent):
        self.name = name
        self._permits = threading.BoundedSemaphore(max_concurrent)

    def run(self, fn):
        if not self._permits.acquire(blocking=False):     # do not wait in line behind hung calls
            raise BulkheadFull(f"{self.name}: no free slots")
        try:
            return fn()
        finally:
            self._permits.release()

vendor_pool = Bulkhead("badge-vendor", max_concurrent=2)
release = threading.Event()
started = threading.Barrier(3)                            # 2 workers + this main thread

def slow_call():
    started.wait()
    release.wait(timeout=5)                               # simulates two hung vendor calls
    return "done"

workers = [threading.Thread(target=lambda: vendor_pool.run(slow_call)) for _ in range(2)]
for w in workers:
    w.start()
started.wait()                                            # both permits are now held by hung calls

try:
    vendor_pool.run(lambda: "third call")
except BulkheadFull as e:
    print("rejected immediately:", e)                     # rejected immediately: badge-vendor: no free slots

other_pool = Bulkhead("directory-service", max_concurrent=2)
print(other_pool.run(lambda: "unaffected"))               # unaffected: a different dependency still works

release.set()
for w in workers:
    w.join()
print(vendor_pool.run(lambda: "slots free again"))

7. Idempotency and delivery guarantees

A timeout does not tell you the request failed. It tells you that you do not know. Idempotency is how you make “do it again” safe.

Why a retried POST duplicates work

An operation is idempotent if doing it twice has the same effect as doing it once. GET, PUT and DELETE are idempotent by definition in HTTP; POST (create a badge) is not. The dangerous case is the lost reply: the vendor created the badge, the response never reached you, you time out and retry, and now there are two badges. Drawing 28-D shows the fix: the client sends the same idempotency key on every attempt, and the server remembers the result per key.

Idempotency keys, natural keys and the dedupe table

Where does the key come from, and where is it checked?

  • Generated key: the client invents a UUID once per logical operation and reuses it on every retry (Stripe’s model). The server stores key → (request fingerprint, response).
  • Natural key: something already unique in the business: request_id in provision:req-1. Better than a random key when you have one, because a different process or a re-run after a crash derives the same key without remembering anything.
  • Dedupe table / unique constraint: the database enforces it. A UNIQUE (request_id) index makes the second insert fail no matter how buggy the application code is. The database is the last line of defence.
idempotency_table.py — claim a key, replay results, reject mismatches (sqlite3)
import json, sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE idempotency (
    key         TEXT PRIMARY KEY,
    fingerprint TEXT NOT NULL,                    -- what the first request asked for
    status      TEXT NOT NULL,                    -- in_progress | done
    response    TEXT
);
CREATE TABLE badges (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    request_id  TEXT NOT NULL UNIQUE,             -- natural key: the database refuses a second badge
    employee_id TEXT NOT NULL
);
""")

def create_badge(key: str, body: dict):
    fingerprint = json.dumps(body, sort_keys=True)
    with db:                                      # one transaction: commit or roll back together
        cur = db.execute("INSERT INTO idempotency(key, fingerprint, status) VALUES (?, ?, 'in_progress') "
                         "ON CONFLICT(key) DO NOTHING", (key, fingerprint))
        claimed = cur.rowcount == 1               # exactly one caller can win the claim
    if not claimed:
        stored_fp, status, response = db.execute(
            "SELECT fingerprint, status, response FROM idempotency WHERE key = ?", (key,)).fetchone()
        if stored_fp != fingerprint:
            return 422, {"error": "idempotency key reused with a different request"}
        if status == "in_progress":
            return 409, {"error": "original request still processing; retry shortly"}
        return 200, json.loads(response)          # replay: same answer, no second side effect
    with db:
        cur = db.execute("INSERT INTO badges(request_id, employee_id) VALUES (?, ?)",
                         (body["request_id"], body["employee_id"]))
        result = {"badge_id": f"bdg-{cur.lastrowid}"}
        db.execute("UPDATE idempotency SET status = 'done', response = ? WHERE key = ?",
                   (json.dumps(result), key))
    return 201, result

Red pencil — the stuck “in_progress” key

If the process crashes after claiming the key but before finishing, the row stays in_progress forever and every retry gets 409. Real implementations store a lease (claimed_at) and treat a claim older than the longest legitimate run time as abandoned, or they do the claim and the local work in one database transaction so a crash rolls both back. Also decide how long keys live: Stripe’s API v1 may prune keys once they are at least 24 hours old; your reconciliation window must be shorter than your key lifetime or a very late retry becomes a duplicate.

“Exactly-once delivery” over an unreliable network is a myth: after a timeout the sender can never know whether to resend. What systems actually offer is effectively-once processing = at-least-once delivery + an idempotent consumer. Send duplicates freely; make duplicates harmless. (Some platforms advertise “exactly-once” inside their own boundary, using exactly this trick plus transactions; it does not extend to a third-party HTTP API.)

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE processed_events (event_id TEXT PRIMARY KEY);
CREATE TABLE badge_status (request_id TEXT PRIMARY KEY, status TEXT NOT NULL);
""")

class Boom(Exception):
    pass

def handle(event: dict, fail_once: list | None = None) -> str:
    try:
        with db:                                                    # BEGIN ... COMMIT, or ROLLBACK on exception
            db.execute("INSERT INTO processed_events(event_id) VALUES (?)", (event["event_id"],))
            if fail_once:
                fail_once.pop()
                raise Boom("crash after marking, before the effect finished")
            db.execute("INSERT OR REPLACE INTO badge_status VALUES (?, ?)", (event["request_id"], event["status"]))
        return "applied"
    except sqlite3.IntegrityError:
        return "duplicate ignored"                                   # event id already recorded

e = {"event_id": "evt-1", "request_id": "req-1", "status": "provisioned"}
try:
    handle(e, fail_once=[True])                                      # first delivery crashes mid-way
except Boom:
    print("crashed; marker rolled back too")
print(handle(e))                                                     # applied        (redelivery works: nothing was recorded)
print(handle(e))                                                     # duplicate ignored
print(db.execute("SELECT * FROM badge_status").fetchall())           # [('req-1', 'provisioned')]
Interviewers ask

“Can you guarantee exactly-once delivery?” No, and anyone who says yes is describing something narrower. After a timeout the sender cannot distinguish “lost request” from “lost reply”, so it must choose between possible loss (at-most-once) and possible duplicates (at-least-once). I choose at-least-once and make the consumer idempotent: an idempotency key or natural key on the call, a unique constraint or processed-events table on my side, and the dedupe record written in the same transaction as the effect. Follow-up: “what if the vendor does not support idempotency keys?” Then I do a status lookup by my own reference before retrying (read-before-write), and a reconciliation job to catch the duplicates anyway.

8. Webhooks: receiving and sending

A webhook is an HTTP POST from someone else’s server to a public URL of yours. That URL accepts requests from the whole internet, so treat the body as hostile until proven otherwise.

Receiving: verify, check the clock, acknowledge fast, process later, dedupe

Five rules, in this order:

  1. Verify the signature over the raw bytes with a shared secret (HMAC-SHA256), using a constant-time compare. Parse the JSON only after it passes. If your framework parses the body for you, capture the raw body before it does: re-serialised JSON has different whitespace and the signature will not match.
  2. Check the timestamp, which is inside the signed message, and reject anything older than a tolerance (five minutes is common). Otherwise anyone who captured one valid request can replay it forever.
  3. Acknowledge fast with a 2xx once the event is safely stored. Vendors time out after a few seconds and then retry, which creates duplicates. Do the slow work later.
  4. Process asynchronously from a queue or an inbox table, so a slow handler or a crash cannot cause the vendor to resend.
  5. Deduplicate on event id. The vendor will deliver at-least-once, and your own 5xx will cause more resends. Return 200 for a duplicate: it was received, so stop retrying.
webhook_receiver.py — a complete receiver with an inbox table (standard library only)
import hashlib, hmac, json, sqlite3

def sign(secret: bytes, body: bytes, ts: int) -> str:
    mac = hmac.new(secret, str(ts).encode() + b"." + body, hashlib.sha256).hexdigest()
    return f"t={ts},v1={mac}"                                  # same shape as several real providers use

def parse_header(header: str):
    try:
        parts = dict(p.split("=", 1) for p in header.split(","))
        return int(parts["t"]), parts["v1"]
    except (KeyError, ValueError):
        return None

def verify(secrets, body: bytes, header: str, now: int, tolerance: int = 300) -> bool:
    parsed = parse_header(header)
    if parsed is None:
        return False
    ts, received = parsed
    if abs(now - ts) > tolerance:                               # too old (replay) or from the future
        return False
    for secret in secrets:                                     # (current, previous): rotation without downtime
        expected = hmac.new(secret, str(ts).encode() + b"." + body, hashlib.sha256).hexdigest()
        if hmac.compare_digest(expected, received):
            return True
    return False

class Receiver:
    REQUIRED = ("event_id", "request_id", "status")
    def __init__(self, secrets, clock):
        self.secrets, self.clock = secrets, clock
        self.db = sqlite3.connect(":memory:")
        self.db.execute("CREATE TABLE inbox (event_id TEXT PRIMARY KEY, payload TEXT, status TEXT DEFAULT 'new')")
        self.processed = []

    def handle(self, raw_body: bytes, header: str) -> int:
        if not verify(self.secrets, raw_body, header, now=self.clock()):
            return 401                                         # nothing parsed, nothing stored
        try:
            event = json.loads(raw_body)
        except ValueError:
            return 400
        if not isinstance(event, dict) or any(k not in event for k in self.REQUIRED):
            return 400
        with self.db:
            self.db.execute("INSERT OR IGNORE INTO inbox(event_id, payload) VALUES (?, ?)",
                            (event["event_id"], raw_body.decode()))      # duplicate id: silently ignored
        return 200                                             # ACK now; the slow work happens elsewhere

    def work(self) -> None:                                    # a separate worker in real life
        rows = self.db.execute("SELECT event_id, payload FROM inbox WHERE status = 'new'").fetchall()
        for event_id, payload in rows:
            self.processed.append(json.loads(payload)["request_id"])    # the real effect goes here
            with self.db:
                self.db.execute("UPDATE inbox SET status = 'done' WHERE event_id = ?", (event_id,))

Red pencil — four ways receivers fail

Parsing before verifying (a crafted body can exploit your parser). Comparing with == (timing leak). Doing the work inside the request (a 20-second handler makes the vendor retry, which doubles the load you were already struggling with). Returning 5xx for a duplicate (the vendor keeps resending the same event for days). A fifth, subtle one: the timestamp tolerance only helps if the timestamp is inside the signed bytes. If it travels in a separate unsigned header, an attacker simply updates it.

Sending: retry on a schedule, then dead-letter

If you emit webhooks to other systems, you are the unreliable one from their point of view. Sign each delivery, give every event a stable event_id, and retry failures on a growing schedule (for example 1 min, 5 min, 30 min, 2 h, 12 h). Treat 2xx as delivered, 4xx (except 408 and 429) as “stop, the receiver rejected it”, and 5xx or timeouts as “try again later”. After the last attempt, move the event to a dead-letter queue (a parking place that a human can inspect and replay) rather than dropping it. Re-sign with a fresh timestamp on each retry, but keep the same event_id so the receiver can dedupe.

webhook_sender.py — retry schedule and dead-letter queue, with a fake receiver
SCHEDULE = [60, 300, 1800]                 # seconds to wait before retry 1, 2, 3 (a real one runs for hours)

class Outbound:
    def __init__(self, post, sleep):
        self.post, self.sleep = post, sleep
        self.dead_letters = []

    def deliver(self, event: dict) -> str:
        attempts = 0
        for wait in [0] + SCHEDULE:
            if wait:
                self.sleep(wait)
            attempts += 1
            try:
                status = self.post(event, attempt=attempts)    # new timestamp + signature each attempt, same event_id
            except TimeoutError:
                status = 599
            if 200 <= status < 300:
                return f"delivered after {attempts} attempt(s)"
            if 400 <= status < 500 and status not in (408, 429):
                break                                          # the receiver rejected it: retrying cannot help
        self.dead_letters.append({"event_id": event["event_id"], "attempts": attempts})
        return f"dead-lettered after {attempts} attempt(s)"

slept = []
flaky_codes = iter([503, 503, 200])
sender = Outbound(post=lambda e, attempt: next(flaky_codes), sleep=slept.append)
print(sender.deliver({"event_id": "evt-1"}), slept)           # delivered after 3 attempt(s) [60, 300]

down = Outbound(post=lambda e, attempt: 503, sleep=lambda s: None)
print(down.deliver({"event_id": "evt-2"}))                    # dead-lettered after 4 attempt(s)
rejects = Outbound(post=lambda e, attempt: 400, sleep=lambda s: None)
print(rejects.deliver({"event_id": "evt-3"}))                 # dead-lettered after 1 attempt(s)
print(down.dead_letters, rejects.dead_letters)

9. Reliable background jobs: outbox, queues, retries, dead letters

“Save to the database, then call the vendor” has a hole in the middle. The outbox pattern closes it.

The dual-write problem and the outbox pattern

You must do two things: save the access request in your database and tell the worker to provision a badge. Doing them one after the other can fail in the gap. Save first and crash, and a request exists that nobody will ever process. Publish first and the database save fails, and the worker acts on a request that does not exist. No ordering of two separate systems is safe. The transactional outbox: write the request and a row describing the message into an outbox table in the same database transaction. Both commit or neither does. A separate relay reads unpublished outbox rows, sends them to the queue, and marks them published.

1
One transaction, two rows. If either insert fails, both roll back. This is the whole trick; the rest is plumbing.
2
The relay is at-least-once. It publishes, then marks the row. A crash in between republishes, so the pattern gives you at-least-once, never exactly-once.
3
The consumer must be idempotent. The outbox id is a ready-made dedupe key. This links straight back to section 7.
outbox_demo.py — atomic write, relay, crash window, idempotent consumer (sqlite3)
import json, sqlite3

db = sqlite3.connect(":memory:")

CREATE TABLE access_requests (id TEXT PRIMARY KEY, employee_id TEXT NOT NULL, status TEXT NOT NULL);

                     payload TEXT NOT NULL, published_at TEXT);
""")

def create_request(req_id, employee_id, fail_before_outbox=False):

                   (json.dumps({"request_id": req_id, "employee_id": employee_id}),))

def relay(publish, crash_after_publish=False):

Queues, retries, visibility timeout and dead letters

A queue holds messages until a worker handles them. The two concepts to own:

  • Visibility timeout. When a worker receives a message the queue does not delete it; it hides it for N seconds. If the worker finishes it deletes the message. If the worker crashes or is too slow, the timeout expires and the message becomes visible again for another worker. That is how at-least-once works, and why a handler that takes longer than the timeout will see its message processed twice.
  • Dead-letter queue (DLQ). A message that fails repeatedly (a “poison message”: bad data, a bug) would otherwise be retried forever and block progress. After max receives it is moved aside to a DLQ, with an alarm, so a human can look at it and replay it after the fix.
tiny_queue.py — an in-process queue with visibility timeout and a DLQ
class TinyQueue:
    def __init__(self, clock, visibility_timeout=30.0, max_receives=3):
        self.clock, self.visibility, self.max_receives = clock, visibility_timeout, max_receives
        self._messages = {}              # id -> {"body", "receives", "visible_at"}
        self.dead_letters = []
        self._next_id = 1

    def send(self, body):
        self._messages[self._next_id] = {"body": body, "receives": 0, "visible_at": 0.0}
        self._next_id += 1

    def receive(self):
        now = self.clock()
        for msg_id in sorted(self._messages):
            m = self._messages[msg_id]
            if m["visible_at"] > now:
                continue                                       # hidden: another worker is on it
            if m["receives"] >= self.max_receives:             # poison: stop retrying, park it
                self.dead_letters.append(self._messages.pop(msg_id)["body"])
                continue
            m["receives"] += 1
            m["visible_at"] = now + self.visibility            # hide it while we work
            return msg_id, m["body"]
        return None

    def delete(self, msg_id):                                  # the "ack": only after the work succeeded
        self._messages.pop(msg_id, None)

Red pencil — the queue is not exactly-once and not ordered

Standard queues deliver at least once and may reorder. A handler that assumes “approved arrives after requested” will eventually see them swapped. Carry a version or timestamp and ignore stale updates, or design handlers that are correct in any order. Also set the visibility timeout longer than your slowest legitimate handler, otherwise healthy slow work is processed twice in parallel. And alarm on the DLQ depth: a DLQ nobody watches is just a slower way to lose messages.

10. Rate limiting

Two directions: protect your API from callers who send too much, and protect the vendor’s API (and your quota with it) from you.

The token bucket

Imagine a bucket that holds up to capacity tokens and refills at rate tokens per second. Each request takes a token; an empty bucket means “not yet”. Capacity sets the largest burst you allow; the refill rate sets the long-run average. The standard trick is to not run a timer: store the token count and the last-update time, and compute the refill lazily when the next request arrives. The lab asks you to write this with an injected clock; this version adds the Retry-After calculation a 429 response needs.

rate_limit.py — per-client token buckets and a 429 with Retry-After
import math

class Bucket:
    def __init__(self, capacity, per_second, clock):
        self.capacity, self.per_second, self.clock = capacity, per_second, clock
        self.tokens, self.last = float(capacity), clock()

    def take(self):
        """Returns 0 if allowed, otherwise the number of seconds to wait."""
        now = self.clock()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.per_second)   # lazy refill
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return 0
        return math.ceil((1 - self.tokens) / self.per_second)

class Limiter:
    def __init__(self, capacity, per_second, clock):
        self.args, self.buckets = (capacity, per_second, clock), {}

    def check(self, client_id):
        bucket = self.buckets.setdefault(client_id, Bucket(*self.args))     # one bucket PER CLIENT
        wait = bucket.take()
        if wait == 0:
            return 200, {}
        return 429, {"Retry-After": str(wait)}

11. Audit logging, PII and sensitive data

Three weeks later someone asks: “did e-902 get a badge for BLR-01, and who approved it?” The audit log is the only honest answer. It is also a place where personal data goes to be copied for years.

What to record, and what to leave out

RecordNever record
Timestamp (UTC), actor (user or service id), action, object type and id, outcome, reason for failurePasswords, tokens, API keys, signatures, private keys
Correlation / request id, event id, idempotency key, attempt numberFull request or response bodies (they contain whatever the caller sent)

Before/after of security-relevant changes (role granted, badge revoked)Payment or government identifier numbers

Make audit entries append-only and write them in the same transaction as the action where you can, so a change without a record, or a record of a change that rolled back, cannot exist. Keep application logs (for debugging, short retention) separate from the audit trail (for accountability, long retention, restricted access).

Redaction, pseudonyms and minimisation

Personal data (PII: anything that identifies a person, directly or in combination) needs a reason to exist in each place it is stored. Minimise what you collect, redact or mask what you log, and pseudonymise when you need to correlate without revealing: a keyed hash of the employee id gives a stable token that lets you count “the same person” in logs but cannot be reversed without the key. The lab’s redact function is this idea in its simplest form.

pii_helpers.py — mask, pseudonymise, redact
import hashlib, hmac, re

def mask_email(email: str) -> str:
    local, _, domain = email.partition("@")
    return (local[:1] + "***@" + domain) if domain else "***"

PSEUDONYM_KEY = b"demo-pseudonym-key-keep-in-secret-store"      # rotating it changes every token: choose deliberately

def pseudonym(employee_id: str) -> str:
    return "emp_" + hmac.new(PSEUDONYM_KEY, employee_id.encode(), hashlib.sha256).hexdigest()[:12]

PII_FIELDS = {"email", "phone", "name", "photo_url"}

def safe_for_log(record: dict) -> dict:
    out = {}
    for key, value in record.items():
        if key == "employee_id":
            out["employee"] = pseudonym(value)
        elif key in PII_FIELDS:
            out[key] = "[REDACTED]"
        elif isinstance(value, str):
            out[key] = re.sub(r"[\w.+-]+@[\w-]+\.[\w.-]+", "[EMAIL]", value)    # e-mails hiding in free text
        else:
            out[key] = value
    return out

Tamper evidence: a hash chain

If an attacker (or an insider) can edit the audit table, the audit is worth little. Tamper evidence does not stop edits; it makes them detectable. In a hash chain each entry includes the hash of the previous entry, so altering or deleting one in the middle breaks every hash after it. Two honest limits: someone who can rewrite the whole chain can recompute it, and silently chopping entries off the end is invisible unless you store the latest hash somewhere they cannot write (a separate account, write-once storage, or a periodic signed checkpoint). Cloud providers sell this as immutable storage; the idea is just this.

audit_chain.py — append-only log with a verifiable hash chain
import hashlib, json

class AuditLog:
    GENESIS = "0" * 64

    def __init__(self, clock):
        self.clock, self.entries = clock, []

    def append(self, actor, action, obj, outcome, **extra):
        prev = self.entries[-1]["hash"] if self.entries else self.GENESIS
        body = {"ts": self.clock(), "actor": actor, "action": action, "object": obj,
                "outcome": outcome, **extra, "prev": prev}
        digest = hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()
        self.entries.append({**body, "hash": digest})
        return digest

    def verify(self, expected_head=None) -> bool:
        prev = self.GENESIS
        for e in self.entries:
            body = {k: v for k, v in e.items() if k != "hash"}
            if body["prev"] != prev:
                return False
            if hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest() != e["hash"]:
                return False
            prev = e["hash"]
        return expected_head is None or prev == expected_head     # head stored elsewhere catches tail truncation

Red pencil — logging as a leak

The commonest PII breach is not an attacker: it is a developer who logged the whole request body at DEBUG, and the log platform copied it to a search index everyone can read. Rules that prevent this: log identifiers and counts, not payloads; run every dict through one redaction function before it reaches a logger or an audit table (the lab’s redact does this for the audit entries); give logs a retention period; and remember that personal data in a backup or a DLQ is still personal data. Pattern-based redaction misses things (see the Bearer token earlier), so treat it as the second line of defence behind “do not log it”.

12. Failure injection, fakes and integration tests

If you have never seen the timeout path run, you do not know that it works. A fake vendor that you can tell to fail makes every failure a unit test.

Fakes, stubs and mocks

Prefer dependency injection: pass the vendor client, the clock, sleep and the random source into your code instead of importing them globally. Then a test supplies a fake and no patching is needed. Be wary of mocks that merely restate the implementation; a test that says “post was called with these arguments” passes even when the real vendor would reject them. The contract is what you assume the vendor does (status codes, field names, idempotency behaviour): write it down, keep one fake that embodies it, and re-check it against the vendor’s documentation or a sandbox when it changes.

Injecting every failure, over real HTTP on loopback

This fake vendor is a real HTTP server on 127.0.0.1 whose behaviour you script one response at a time: success, a 503, a malformed JSON body, a stall longer than the client timeout. The client under test uses the same timeout and retry code you have seen. No internet, no mocking library.

fake_vendor_http.py — scripted failures against a loopback server
import json, threading, time, urllib.error, urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class FakeVendorServer:
    """script: list of (status, body_bytes, delay_seconds), consumed one per request; then 200 {"badge_id": "bdg-1"}."""
    def __init__(self, script):
        outer = self
        self.script, self.hits = list(script), 0
        class Handler(BaseHTTPRequestHandler):
            def do_POST(self):
                self.rfile.read(int(self.headers.get("Content-Length", 0)))
                outer.hits += 1
                status, body, delay = outer.script.pop(0) if outer.script else (200, b'{"badge_id": "bdg-1"}', 0)
                time.sleep(delay)
                try:
                    self.send_response(status); self.send_header("Content-Length", str(len(body))); self.end_headers()
                    self.wfile.write(body)
                except OSError:
                    pass
            def log_message(self, *a): pass
        self.server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)
        threading.Thread(target=self.server.serve_forever, daemon=True).start()
        self.url = f"http://127.0.0.1:{self.server.server_address[1]}/badges"
    def close(self):
        self.server.shutdown(); self.server.server_close()

class Transient(Exception): pass
class Permanent(Exception): pass

def provision(url, payload, *, attempts=4, timeout=0.3, sleep=lambda s: None):
    """The client under test: timeout, classify, retry only transient failures, validate the response."""
    for n in range(1, attempts + 1):
        try:
            req = urllib.request.Request(url, data=json.dumps(payload).encode(),
                                         headers={"Idempotency-Key": "provision:" + payload["request_id"]})
            with urllib.request.urlopen(req, timeout=timeout) as resp:
                data = json.loads(resp.read())             # may raise ValueError on a malformed body
            if "badge_id" not in data:
                raise Permanent("vendor response missing badge_id")      # validate what the vendor sends back
            return data["badge_id"]
        except urllib.error.HTTPError as e:
            if e.code >= 500 or e.code in (408, 429):
                err = Transient(f"vendor {e.code}")
            else:
                raise Permanent(f"vendor {e.code}")                      # 4xx: retrying cannot help
        except (TimeoutError, urllib.error.URLError, ValueError) as e:
            err = Transient(type(e).__name__)                            # stall, refused connection, junk body
        if n == attempts:
            raise err
        sleep(0.01 * n)

The same idea as a pytest file

In the lab you will write the equivalent with an in-memory FakeVendor. Notice the shape: arrange a scripted failure, act, assert on both the result and the side effects (how many badges exist, how many calls, what was slept). This block runs as a test file.

test_fake_vendor_sketch.py — failure scenarios as tests
import pytest

class VendorTimeout(Exception): pass
class VendorRejected(Exception): pass

class FakeVendor:
    def __init__(self, script):
        self.script, self.calls, self.badges = list(script), [], {}
    def provision(self, request_id, key):
        self.calls.append((request_id, key))
        step = self.script.pop(0) if self.script else "ok"
        if step == "timeout":
            raise VendorTimeout()
        if step == "reject":
            raise VendorRejected()
        self.badges.setdefault(key, f"bdg-{len(self.badges) + 1}")      # honours the idempotency key
        if step == "lost_reply":
            raise VendorTimeout()                                        # created, but we never hear back
        return self.badges[key]

def provision_with_retry(vendor, request_id, sleeps, attempts=3):
    key = "provision:" + request_id                                      # SAME key on every attempt
    for n in range(attempts):
        try:
            return vendor.provision(request_id, key)
        except VendorTimeout:
            if n == attempts - 1:
                raise
            sleeps.append(0.5 * 2 ** n)

def test_timeout_then_success():
    vendor, sleeps = FakeVendor(["timeout"]), []
    assert provision_with_retry(vendor, "req-1", sleeps) == "bdg-1"
    assert len(vendor.calls) == 2 and sleeps == [0.5]

def test_lost_reply_does_not_duplicate():
    vendor = FakeVendor(["lost_reply"])
    assert provision_with_retry(vendor, "req-1", []) == "bdg-1"
    assert len(vendor.badges) == 1                                       # the whole point of the idempotency key

def test_permanent_rejection_is_not_retried():
    vendor = FakeVendor(["reject"])
    with pytest.raises(VendorRejected):
        provision_with_retry(vendor, "req-1", [])
    assert len(vendor.calls) == 1

def test_gives_up_after_the_attempt_budget():
    vendor = FakeVendor(["timeout"] * 5)
    with pytest.raises(VendorTimeout):
        provision_with_retry(vendor, "req-1", [])
    assert len(vendor.calls) == 3

Failure recovery and reconciliation

Even a careful system drifts: a webhook was lost, a retry gave up, someone changed a record in the vendor’s admin console. A reconciliation job runs on a schedule, compares what you believe against what the vendor actually has, and fixes or reports the difference. Because it is itself a retry mechanism, it must be idempotent and safe to run twice. In BadgeDesk this is the nightly audit-reconciler.

reconcile.py — compare local truth with the vendor, plan repairs, never auto-delete
def reconcile(local: dict, vendor: dict, now: float, stuck_after: float = 900.0) -> dict:
    """local: request_id -> {"status", "updated_at"};  vendor: request_id -> {"badge_id"}.
    Returns a plan; applying the plan is a separate, logged step."""
    plan = {"reprovision": [], "mark_provisioned": [], "orphans": [], "ok": []}
    for req_id, row in sorted(local.items()):
        at_vendor = req_id in vendor
        if row["status"] == "approved" and not at_vendor:
            plan["reprovision"].append(req_id)                 # we think it should exist; it does not: provision (idempotent key!)
        elif row["status"] == "provisioning" and now - row["updated_at"] > stuck_after:
            (plan["mark_provisioned"] if at_vendor else plan["reprovision"]).append(req_id)    # stuck: check the vendor, then decide
        else:
            plan["ok"].append(req_id)
    for req_id in sorted(set(vendor) - set(local)):
        plan["orphans"].append(req_id)                         # exists at the vendor, unknown to us: REPORT for a human
    return plan

local = {
    "req-1": {"status": "provisioned",  "updated_at": 0},
    "req-2": {"status": "approved",     "updated_at": 0},      # webhook and retry both lost: vendor never got it
    "req-3": {"status": "provisioning", "updated_at": 100},    # worker died mid-call; vendor DID create it
    "req-4": {"status": "provisioning", "updated_at": 2000},   # in progress right now: leave alone
}
vendor = {"req-1": {"badge_id": "bdg-1"}, "req-3": {"badge_id": "bdg-3"}, "req-9": {"badge_id": "bdg-9"}}
plan = reconcile(local, vendor, now=2100)
print(plan)

assert reconcile(local, vendor, now=2100) == plan              # running it twice changes nothing: idempotent
In production

Reconciliation is the safety net under everything else on this sheet. Webhooks are an optimisation; the nightly comparison is the guarantee. Report orphans (badges at the vendor with no request) rather than deleting them automatically: an automatic delete driven by a bug in your own data is how an access-control outage is made. Record the plan and the outcome in the audit log, alert if the counts jump (a sudden 40% of rows to repair is a sign that something upstream is broken, not that 40% of rows need repair), and keep the job read-only until a human approves the first run in a new environment.

Gate 2: the three-minute explanation

The gate has two parts: the scenario suite passes, and you explain it aloud in under three minutes with no notes. Practise with this skeleton (one sentence each, then say it in your own words):

  1. Trust: the webhook is verified with an HMAC over the raw body and a timestamp window, so forged and replayed requests are rejected with 401 before anything is parsed.
  2. Acknowledge fast: I store the event and return 200; processing happens separately, so a slow vendor cannot cause redelivery.
  3. Dedupe: delivery is at-least-once, so I drop repeated event ids; duplicates are normal, not an error.
  4. Idempotency: the vendor call carries a key derived from the request id, the same on every attempt, so a retry after a lost reply cannot create a second badge.
  5. Timeouts, backoff, jitter: every call has a timeout; only transient errors are retried, with exponential backoff, a cap and jitter; permanent errors are not retried.
  6. Fail visibly: exhausted or permanent failures go to a dead-letter list; every attempt is in the audit log with personal data redacted; a nightly reconciliation catches whatever slipped through.

Scenario round — predict, then reveal
The vendor’s API takes 30 seconds to respond to POST /badges, and your user is waiting. What do you do?

Do not make the user wait: accept the request, store it (with an outbox row in the same transaction), return 202 with a status URL, and let a worker call the vendor with a timeout (say 10 s, from the vendor’s measured p99) and an idempotency key. On timeout the worker retries with backoff and jitter using the same key. If the vendor stays slow a circuit breaker stops new calls and the request waits in the queue. I would alert on the vendor’s latency and the queue age, and I would tell the user “pending”, not “failed”, because I do not know which it is.

A webhook arrives three times, and a fourth copy arrives with a bad signature. What happens?

The three valid copies share an event id: the first is stored in the inbox and processed; the second and third hit the unique constraint, are ignored, and still get 200 so the vendor stops retrying. The fourth fails HMAC verification, gets 401, is never parsed or stored, and I log the source and the reason (not the body). If the bad one is a valid old message replayed, the timestamp check rejects it. I would watch the rate of 401s: a spike means probing or a secret that was rotated on one side only.

The worker times out calling the vendor. How do you know whether the badge was created?

You do not, and that is the point. The call carried an idempotency key, so retrying is safe: if the badge exists the vendor returns it, otherwise it is created. If the vendor has no idempotency support I look the badge up by my own reference (request id) before creating, accepting a small race, and I run reconciliation to find any duplicate. In the audit log the attempt is recorded as “failed: timeout”, not “failed: not created”, because those are different claims.

An engineer pastes a production API key into a ticket. What are your first three actions?

Revoke or rotate the key immediately, since it is now exposed to everyone who can read the ticket; then check the vendor’s access log for use you do not recognise during the exposure window; then redact or delete the ticket content and put the new key in the secret store. After that: note the incident, add a scanner or a reminder, and ask why a person needed to paste it (usually a missing way to share credentials safely).

Your nightly reconciliation reports that 40% of requests need repair. What do you do?

Do not apply the plan. A jump from a normal 0.1% to 40% almost always means a bug or an outage upstream, not 40% genuine drift: perhaps the vendor changed an id format, a webhook secret was rotated, or my own query is wrong. I pause automated repair, sample a few rows by hand against the vendor’s console, compare with yesterday’s counts, and look at the audit log for the first failure. Only after I understand the cause do I run repairs, and they go through the same idempotent provisioning path.

A retry loop you wrote makes an outage worse. How can that happen and how do you prevent it?

Retries multiply load when many clients fail together: without jitter they retry in synchronised waves; with retries at several layers the multiplication compounds (3 x 3 x 3); without a cap or budget they continue for ever. Prevention: a timeout on every call, retry only transient errors, exponential backoff with a cap and full jitter, retries at one layer only, a total deadline, a retry budget, honour Retry-After, and a circuit breaker so that a clearly dead vendor is not called at all.

Drill — reliability, security and integration
What is the difference between authentication and authorisation, and between 401 and 403?

Authentication is proving who you are; authorisation is deciding what that identity may do. 401 means no or invalid credentials (unauthenticated); 403 means the identity is known but not permitted. Follow-up: “and for an object that belongs to someone else?” 403 or 404; 404 avoids confirming that the object exists. Either way the check is per object, not only per endpoint.

When would you use client credentials and when authorisation code with PKCE?

Client credentials when a program acts as itself with no human: a worker calling a vendor. Authorisation code with PKCE when a human signs in and delegates access, especially in browsers and mobile apps that cannot keep a secret; the code verifier proves the app finishing the login is the one that started it. Implicit and password grants are deprecated. Follow-up: “what does OpenID Connect add?” An ID token that says who authenticated.

JWT versus session cookie: how do you choose?

A session cookie keeps state on the server: instant revocation, suited to one first-party web app, CSRF to defend. A JWT carries signed claims verified without a lookup: it suits services behind an identity provider, but cannot be revoked before expiry, so keep it short-lived. A JWT is signed, not encrypted, so no secrets in it. Follow-up: “how do you revoke a JWT?” Short lifetimes, refresh-token rotation, or introspection or a deny-list for sensitive actions.

A secret leaks into a public repository. What do you do?

Revoke or rotate it first, because once public it is compromised regardless of cleanup. Then check the audit logs for misuse during the exposure window, deploy the new secret from the secret store, clean the history (and understand that is tidying), notify the right people and add a scanner to prevent a repeat. Follow-up: “how do you design for rotation?” Accept two valid secrets during an overlap window.

Hash, HMAC, encryption, signature: which do you use to (a) store a password, (b) verify a webhook, (c) protect a file at rest, (d) let many parties verify a token?

(a) A salted slow password hash such as Argon2id or scrypt, never encryption. (b) HMAC-SHA256 with the shared secret over timestamp and raw body, compared in constant time. (c) Authenticated symmetric encryption, AES-GCM, with a unique nonce and a key managed separately (envelope encryption). (d) A digital signature with a private key, so everyone can verify with the public key. Follow-up: “why GCM and not plain AES?” It authenticates as well as encrypts, so tampering is detected.

How do you process a 5 GB encrypted file from a partner without running out of memory?

Stream it in fixed-size chunks: read, decrypt with chunked authenticated encryption (a unique nonce per chunk, position bound into the associated data so reordering and truncation are detected), validate and process each row, update a running SHA-256, and write results to a temporary directory. Compare the checksum with the manifest before delivering anything. Build the ZIP by streaming members. Clean up temp files in a finally or a TemporaryDirectory, and make the whole job re-runnable keyed by file name plus checksum.

Why add jitter to exponential backoff, and what else must a retry policy include?

Without jitter, clients that failed together retry together, producing synchronised waves that keep a recovering service down. Full jitter randomises each wait between zero and the capped exponential ceiling. A retry policy also needs: a timeout per call and a total deadline, a maximum attempt count or budget, retries only for transient errors (not 400/401/403/404), honouring Retry-After, safe repeat (an idempotency key), and a circuit breaker to stop calling a dead dependency.

Explain idempotency keys, and why “exactly-once delivery” is a myth.

An idempotency key identifies one logical operation; the server stores the result under it, so a retry returns the stored result instead of repeating the effect, and a reused key with different parameters is rejected. After a timeout a sender cannot know whether the request arrived, so it must choose possible loss (at-most-once) or possible duplicates (at-least-once). Real systems pick at-least-once and make the consumer idempotent, giving effectively-once processing. Follow-up: “where do the keys live and for how long?” A table with a unique constraint, kept longer than the maximum retry and reconciliation window.

Design a secure, reliable webhook receiver.

HTTPS; verify HMAC over the raw body plus timestamp in constant time; reject stale timestamps; support two secrets for rotation; validate the schema; insert into an inbox table with the event id as primary key and return 200 immediately; process from the inbox asynchronously with retry and a dead-letter state; log event ids and outcomes, not payloads; alert on 401 spikes and inbox age. Follow-up: “the vendor does not sign requests?” Treat the payload as a hint and fetch the authoritative state from the vendor API, and restrict the source network.

What is the outbox pattern, and what guarantee does it give?

Write the business row and a message row in the same database transaction; a relay later publishes unpublished messages and marks them. It removes the dual-write gap, so you cannot save without queueing or queue without saving. It guarantees at-least-once publication, not exactly-once: a crash after publishing and before marking republishes, so consumers dedupe on the outbox id. Follow-up: “alternatives?” Change-data-capture reading the database log, which avoids polling but needs more infrastructure.

How do you test a vendor integration without the vendor?

Inject the client, clock, sleep and random source; use a fake vendor that embodies the contract and can be scripted to time out, return 503, return malformed JSON, reject permanently, or commit and lose the reply. Assert on results and side effects (badge count, call count, sleeps, audit entries). Add a few contract tests against the vendor’s sandbox so the fake does not drift. Follow-up: “what do green tests not prove?” That the vendor really behaves as the fake assumes.
