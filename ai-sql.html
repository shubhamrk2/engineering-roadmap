The one idea: a query is a pipeline that shrinks rows

SQL reads like English, which hides that the database runs it in a fixed order that is not the order you wrote it. Once you can say how many rows are left after each step, joins, grouping and NULLs stop being surprising.

1
FROM / JOIN builds the working set. Joins are where row counts change most: a one-to-many join repeats the “one” side once per match. Section 6 trains you to predict this number.
2
WHERE filters single rows before any grouping. It cannot see aggregates and, in PostgreSQL, cannot see SELECT aliases. Filtering early is also what lets an index help: the rows you never fetch are free.
3
GROUP BY collapses rows into one row per distinct key. After it, you may only mention the grouping columns or aggregate functions (count, sum, …). SQLite quietly lets you break this rule; PostgreSQL refuses, which is the behaviour to learn.
4
HAVING is WHERE for groups. It sees count(*) because the groups now exist. Use WHERE whenever the condition is about a single row; it is cheaper.
5
SELECT shapes the output columns and is where aliases (AS n) are created. Only later steps (ORDER BY) can use them.
6
ORDER BY and LIMIT come last. Without ORDER BY the row order is not defined: it may look sorted today and change after an index or an update. Every example on this sheet that shows rows in a fixed order has an ORDER BY for that reason.

Tables, rows and keys

A relational database is a set of tables. A table has typed columns and any number of rows. Keys are the columns that say which row is which and which rows belong together.

Three kinds of key, all of which you will meet again when you draw the schema (section 10):

Primary keyWhich row is this?

Unique and NOT NULL. access_requests.id. A table has exactly one. It is the thing other tables point at.

Foreign keyWhich row does this belong to?

access_requests.employee_id points at employees.id. The database rejects a request for an employee that does not exist, and (your choice) rejects or cascades a delete of an employee who still has requests.

Unique keyWhich value may appear only once?

employees.email. Not the primary key, but still must not repeat. A table can have many. NULLs are allowed and do not collide (section 4).

Predict, then reveal — keys
What happens if you run INSERT INTO access_requests VALUES ('req-8','e-000','BLR-01','2026-12-01','2026-12-02','pending',NULL) on the seed database?

It fails with a foreign-key error, because there is no employee e-000. SQLite only enforces this when PRAGMA foreign_keys = ON is set on that connection, which the seed does. That detail is a classic surprise: in SQLite, foreign keys are off by default for every new connection. PostgreSQL always enforces them. Section 10 shows the failure in both databases.

Red pencil — “primary key” does not mean “meaningful”

A natural key such as an email or an employee number feels safe until HR renumbers people or someone changes their email, and every row in every child table needs updating. A surrogate key (an identity integer or a UUID that means nothing) never changes. The usual answer: a surrogate primary key plus a UNIQUE constraint on the natural key. This sheet uses text ids like e-902 for readability; real tables for high-volume data use bigint GENERATED ALWAYS AS IDENTITY or uuid.

SELECT, filtering and shaping

The first query you write on any new database is a SELECT with a WHERE. Most of day-to-day SQL is a handful of operators for saying which rows, which columns, in what order, and how to present them.

WHERE: LIKE, IN, BETWEEN, IS NULL, and combining them

Operators you will use weekly. AND binds tighter than OR: a OR b AND c means a OR (b AND c). Put brackets in whenever you mix them. BETWEEN x AND y includes both ends, which matters for dates and is a common off-by-one. LIKE uses % (any run of characters) and _ (exactly one character).

Red pencil — LIKE case rules differ, and OFFSET does not scale

On SQLite 'Training' LIKE 'train%' is true; on PostgreSQL it is false, and you write ILIKE for a case-insensitive match. A search that works on your test database and silently returns nothing in production is usually this. Also, LIMIT 20 OFFSET 100000 still reads and throws away 100,000 rows: for long lists page with “keyset” pagination instead (WHERE id > :last_seen_id ORDER BY id LIMIT 20), which an index on id answers instantly.

CASE, aliases and expressions

CASE is SQL’s if / elif / else, and it is an expression: it produces a value you can select, group by or sort by. An alias (AS name) names a column or table in the output. Table aliases (FROM employees e) are not decoration: once you join a table to itself you cannot write the query without them.

Dates are where the two databases differ most. SQLite has no date type: it stores ISO text ('2026-11-02') and offers functions (date(), julianday(), strftime()). -- date + integer = date; date - date = integer (days).
SELECT id, starts_on + 7 AS next_week, ends_on - starts_on + 1 AS days
FROM access_requests WHERE id <= 2 ORDER BY id;
--   1 | 2026-11-09 | 5
--   2 | 2026-11-16 | 1

-- A month is not 30 days: adding one month to the 30th of November lands on the 30th of December.
-- Time zones: the same instant, shown as UTC.
SELECT date '2026-11-30' + interval '1 month' AS plus_month,
       timestamptz '2026-11-02 09:00+05:30' AT TIME ZONE 'UTC' AS utc;
--   2026-12-30 00:00:00 | 2026-11-02 03:30:00

-- date_trunc cuts a timestamp down to the start of its month: the PostgreSQL way to group by month.
SELECT date_trunc('month', starts_on)::date AS month, count(*) FROM access_requests GROUP BY 1 ORDER BY 1;
--   2026-11-01 | 5
--   2026-12-01 | 2

-- LIKE is case-sensitive in PostgreSQL; ILIKE is not.
SELECT 'Training' LIKE 'train%' AS like_result, 'Training' ILIKE 'train%' AS ilike_result;
--   f | t
Interviewers ask

“What is the difference between timestamp and timestamptz in PostgreSQL?” Despite the name, timestamptz does not store a zone. It stores one absolute instant (UTC internally) and converts to the session’s time zone when it displays it. timestamp stores a wall-clock reading with no zone, so the same value means different instants to different readers. Use timestamptz for anything that happened or will happen (created_at, approved_at); use date for calendar days with no time (starts_on). Follow-up: “how would you store a meeting at 09:00 local time in Bengaluru next year?” The wall-clock time plus the zone name, because the offset rules can change.

NULL and three-valued logic

NULL does not mean zero, empty or false. It means unknown. Every comparison with an unknown is unknown, and a WHERE clause keeps only rows where the answer is definitely true. This one rule explains most “why is my row missing?” questions.

Three answers, not two

In C++ a condition is true or false. In SQL it is TRUE, FALSE or UNKNOWN. site_id = 'BLR-01' is UNKNOWN when site_id is NULL, and so is site_id <> 'BLR-01'. A WHERE clause lets TRUE through and drops FALSE and UNKNOWN. So Neha (no site) appears in neither “is at BLR-01” nor “is not at BLR-01”.

FALSEUNKNOWNFALSEUNKNOWNTRUE
UNKNOWNUNKNOWNUNKNOWNUNKNOWNUNKNOWN

Read the table as “could the answer still go either way?” FALSE AND anything is FALSE, because nothing can rescue it; TRUE OR anything is TRUE for the same reason; everything else stays unknown.

SELECT count(*) FROM employees WHERE site_id IS NULL;         -- 1   the right way
SELECT count(*) FROM employees WHERE site_id <> 'BLR-01';     -- 2   Ravi, Kiran. Neha is UNKNOWN, so dropped

-- count(*) counts rows; count(column) counts NON-NULL values. Two requests have no reason.
SELECT count(*) AS all_rows, count(reason) AS with_reason FROM access_requests;   -- 7 | 5

-- Aggregates other than count(*) skip NULLs: the average of 1, NULL, 3 is 2, not 4/3.
SELECT avg(column1) FROM (VALUES (1), (NULL), (3));           -- 2.0

-- COALESCE: first non-NULL argument. The standard way to give NULL a display value or a default.
SELECT id, COALESCE(reason, '(none)') AS reason FROM access_requests WHERE id IN ('req-2', 'req-3') ORDER BY id;
--   req-2 (none) | req-3 training

-- The classic trap: NOT IN with a NULL inside the list returns NOTHING.
SELECT count(*) FROM access_requests WHERE reason NOT IN ('training', NULL);   -- 0   (expected: the rows with other reasons)
-- Why: reason NOT IN ('training', NULL)  is  reason <> 'training' AND reason <> NULL,
--      and  x <> NULL  is UNKNOWN for every row, so AND can never reach TRUE.
-- The safe form is NOT EXISTS, or filter the NULLs out of the subquery.
SELECT count(*) FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM access_requests r WHERE r.employee_id = e.id);   -- 1   (Neha)

-- NULLs and UNIQUE: two NULLs are not "equal", so a UNIQUE column may hold many NULLs.
CREATE TABLE t (x INTEGER UNIQUE);
INSERT INTO t VALUES (NULL), (NULL), (1);          -- allowed
SELECT count(*) FROM t;                            -- 3

-- Where do NULLs sort? SQLite puts them first when ascending. PostgreSQL puts them LAST. Say it explicitly when it matters.
SELECT id, reason FROM access_requests ORDER BY reason, id LIMIT 3;
--   req-2 NULL | req-6 NULL | req-5 audit

Predict, then reveal — NULL
A table has 10 rows. 4 have status = 'approved', 3 have status = 'pending', 3 have status NULL. How many rows does WHERE status <> 'approved' return?

3, the pending ones. The three NULL rows are UNKNOWN, not TRUE, so they are dropped. To include them: WHERE status IS DISTINCT FROM 'approved' (PostgreSQL), or WHERE status <> 'approved' OR status IS NULL (everywhere). Better still, stop it happening: declare the column NOT NULL DEFAULT 'pending', as the schema in section 10 does.

Why does SELECT count(reason) ... return a smaller number than SELECT count(*) ... on the same table?

count(*) counts rows; count(column) counts rows where that column is not NULL. The difference is the number of NULLs. This is also why count(r.id) (not count(*)) is correct after a LEFT JOIN: the unmatched row is one row but has zero matches (section 6).

Red pencil — NULL in your Python is None, and it disappears the same way

When psycopg or sqlite3 reads a NULL it gives you None; when you pass None as a parameter it writes NULL. So cur.execute("... WHERE site_id = ?", (None,)) sends site_id = NULL, matches nothing, and raises no error. Test for None in Python and switch to IS NULL (or IS NOT DISTINCT FROM ? in PostgreSQL, IS ? in SQLite).

Writing data: INSERT, UPDATE, DELETE

Reading is safe. Writing is where you lose data. Three habits: always name the columns you insert, always look at how many rows a statement changed, and never run an UPDATE or DELETE you have not first run as a SELECT.

The three statements, and what the database tells you back

Every write returns a row count (cursor.rowcount in Python). An UPDATE that matches no row is not an error: it changes nothing and reports 0. That silence is why the repository you write in week 8 checks the count. RETURNING gives back the row you just wrote (including defaults and generated ids) without a second query; PostgreSQL has had it for years and SQLite supports it from 3.35.

    ("req-8", "e-905", "BLR-01", "2026-12-10", "2026-12-11")).fetchone()

cur = con.execute("UPDATE access_requests SET status = 'approved' WHERE id = ?", ("req-999",))
print(cur.rowcount)                          # 0   not an error. Nothing matched, nothing changed.
con.commit()                                 # make the work so far permanent

# The forgotten WHERE: every row changes. Here we undo it with a rollback (section 14).
cur = con.execute("UPDATE access_requests SET status = 'rejected'")
print(cur.rowcount)                          # 8   all rows, including the one we just approved
con.rollback()
print(con.execute("SELECT status FROM access_requests WHERE id = 'req-8'").fetchone())   # ('approved',)

# UPSERT: insert, or update if the key already exists. Same syntax in SQLite and PostgreSQL.
con.execute("INSERT INTO sites VALUES ('BLR-02', 'Bengaluru', 250) "
            "ON CONFLICT (id) DO UPDATE SET capacity = excluded.capacity")
print(con.execute("SELECT capacity FROM sites WHERE id = 'BLR-02'").fetchone())          # (250,)

# DELETE respects foreign keys: Asha still has requests, so she cannot be deleted.
try:
    con.execute("DELETE FROM employees WHERE id = 'e-902'")
except sqlite3.IntegrityError as err:
    print("refused:", err)                       # refused: FOREIGN KEY constraint failed

# A site nobody references can go.
print(con.execute("DELETE FROM sites WHERE id = 'PUN-01'").rowcount)                     # 1

# INSERT ... SELECT copies rows between tables in one statement.
con.execute("CREATE TABLE approved_archive (id TEXT, employee_id TEXT)")
con.execute("INSERT INTO approved_archive SELECT id, employee_id FROM access_requests WHERE status = 'approved'")
print(con.execute("SELECT count(*) FROM approved_archive").fetchone())                   # (4,)
Red pencil — the habits that prevent a bad day

1. Write the WHERE first, run it as SELECT count(*), and only then change the first word to UPDATE or DELETE. 2. Do destructive work inside a transaction and look at the result before you COMMIT. 3. DELETE FROM t without WHERE empties the table; TRUNCATE is the same, faster and in PostgreSQL can be rolled back but takes a table lock. 4. Prefer a deleted_at column (“soft delete”) for anything with an audit obligation, such as access requests: the row stays, queries filter on deleted_at IS NULL.

In production

Identity values are not gap-free. When I ran three failing inserts into access_requests on the PostgreSQL schema on this sheet (a CHECK, a foreign key, another CHECK), the next successful row got id 11, not 8: a failed or rolled-back insert still consumes a number. Never use a sequence id as a “count of rows” or assume ids are consecutive; if you need gap-free numbers (invoice numbers) you generate them under a lock, on purpose.

JOINs

A join pairs rows from two tables whenever a condition is true. Forget the overlapping-circles pictures: think of two lists of rows and lines drawn between the ones that match. Then every join type is a rule about what to do with rows that have no line.

The picture: rows and lines

Two things the picture shows that the Venn pictures hide. First, a join can multiply rows: Asha has two lines, so she appears twice. A join returns one row per pair, not one per employee. Second, RIGHT and FULL only differ from INNER when a row has no partner, which a foreign key forbids. With a proper foreign key from req.emp_id to emp.id, req-9 could not exist, and RIGHT would equal INNER. In practice nearly all the joins you write are INNER and LEFT.

Row-count drill — predict first, then open
1. sites s LEFT JOIN employees e ON e.site_id = s.id: how many rows?

5. Sum of max(1, matches) per site: BLR-01 has two employees (2), BLR-02 one (1), HYD-01 one (1), PUN-01 none (1, with NULL). 2 + 1 + 1 + 1 = 5. Counting the employees per site with count(*) over this join would say 1 for PUN-01; count(e.id) says 0, which is the truth.

2. employees e JOIN access_requests r ON r.site_id = e.site_id (a join on the wrong column). How many rows?

10. It pairs every employee with every request at the employee’s site, which is not a meaningful question: BLR-01 has 2 employees and 3 requests (6 pairs), HYD-01 has 1 employee and 3 requests (3), BLR-02 has 1 and 1 (1), and Neha’s NULL site matches nothing. A join on a non-key column is the usual source of an unexpectedly large result. When a count is bigger than either table, suspect the join condition first.

3. employees e LEFT JOIN access_requests r ON r.employee_id = e.id LEFT JOIN sites s ON s.id = r.site_id: how many rows?

8. The first LEFT JOIN gives 8 rows (7 requests plus Neha). The second adds each request’s site; every request has exactly one site, so it adds no rows and no loss, and Neha’s row has a NULL site_id so it stays with a NULL city. A many-to-one join (many requests to one site) never changes the count; a one-to-many join multiplies it.

4. employees CROSS JOIN sites: how many rows, and when would you ever want that?

20 (5 x 4). Wanted for generating combinations, such as a calendar grid of every employee by every site that you then LEFT JOIN requests onto, so zero-activity cells still show. Unwanted when you forget the ON clause: some databases treat a comma between table names as a CROSS JOIN, which is how a 10,000 x 10,000 accident becomes 100 million rows.

5. You want “every employee and their approved requests, including employees with none”. Where does status = 'approved' go?

In the ON clause, not in WHERE. In WHERE it runs after the join, sees NULL for unmatched employees, and throws them away. The output above shows both versions: 5 rows versus 3.

Interviewers ask

“What is the difference between INNER JOIN and LEFT JOIN? When would you use each?” INNER keeps only rows that have a partner on both sides; LEFT keeps every row from the left table and fills the right side with NULL when there is no partner. Use INNER when a missing partner means the row is irrelevant (an invoice line without an invoice), LEFT when the absence is the information (employees with no requests). The follow-up they always ask: “how would you find rows in A with no match in B?” LEFT JOIN with WHERE b.id IS NULL, or NOT EXISTS; avoid NOT IN if the subquery column can be NULL.

Red pencil — the three join mistakes that make wrong numbers, not errors

1. Fan-out: summing a column from the “one” side after joining to the “many” side (1100 became 1500 above). Aggregate first in a subquery, or sum from the table that owns the number. 2. LEFT JOIN plus a WHERE on the right table silently becomes an INNER JOIN. 3. Joining on the wrong or a non-unique column, which multiplies rows. All three produce plausible, wrong results, which is why you predict the row count first and compare.

WHERE versus HAVING, and what the database refuses

The rule on the drawing, in one sentence: if the condition mentions an aggregate, it must be HAVING; if it mentions only the row’s own columns, it should be WHERE. Putting a row-level condition in HAVING works but makes the database build every group first and discard them afterwards.

The second thing to learn here is a place where SQLite and PostgreSQL disagree, because SQLite is more forgiving than PostgreSQL. After GROUP BY you may select only the grouping columns and aggregates. SQLite will happily return an arbitrary “bare” column; PostgreSQL stops you. The block below runs on SQLite, so it shows both the leniency and the errors it does raise.

Write the query: “sites with more than one pending request”. Which clause holds status = 'pending' and which holds count(*) > 1?

Interviewers ask

“What is the difference between WHERE and HAVING?” WHERE filters individual rows before any grouping and cannot use aggregates; HAVING filters whole groups after GROUP BY and can. Then they ask “can you use HAVING without GROUP BY?” Yes: the whole table is one group, so SELECT count(*) FROM t HAVING count(*) > 5 returns one row or none. And “which is faster?” WHERE, whenever the condition does not need an aggregate, because it reduces the rows before the expensive step.

In production — CTE or subquery, and what PostgreSQL does with them

Before PostgreSQL 12 a CTE was always computed once and could not be optimised into the outer query, so people avoided them in hot paths. From 12, a simple non-recursive CTE that is used once is folded into the outer query like a subquery, unless you write WITH x AS MATERIALIZED (...) (documented on the WITH Queries page). So today: choose the form a colleague can read in a year. Choose a JOIN over a subquery when you need columns from both sides; choose EXISTS when you only need to know whether a match exists.

Predict, then reveal — subqueries
Why does SELECT id FROM sites WHERE capacity = (SELECT capacity FROM sites WHERE city = 'Bengaluru') fail on the seed, and how would you fix it?

The scalar subquery returns two rows (BLR-01 and BLR-02 are both in Bengaluru), and = needs one value. PostgreSQL says “more than one row returned by a subquery used as an expression”; SQLite quietly takes the first row, which is worse because the answer is silently arbitrary. Fix by deciding what you meant: capacity IN (...) for any of them, = (SELECT max(capacity) ...) for one chosen, or a join.

Window functions and set operations

A window function computes something across a set of related rows without collapsing them. GROUP BY gives you one row per group; a window gives you every row plus a number that looks at its neighbours. Set operations stack the results of two queries.

ROW_NUMBER, RANK, SUM OVER, LAG

The shape is always function() OVER (PARTITION BY ... ORDER BY ...). PARTITION BY is the GROUP BY of the window (restart for each employee, say); ORDER BY says what “previous” and “running” mean inside it. Window functions run after WHERE, GROUP BY and HAVING, so you cannot filter on them directly: wrap the query and filter outside.

FunctionGivesTies
ROW_NUMBER()1, 2, 3, … with no repeatsBroken arbitrarily unless your ORDER BY is a total order. Add a tie-breaker such as id.
RANK()1, 2, 2, 4: ties share a rank, then a gapSame value, same rank.
DENSE_RANK()1, 2, 2, 3: no gapsSame value, same rank.

UNION, INTERSECT, EXCEPT

Set operations combine whole result sets that have the same number and type of columns. UNION removes duplicates (and so sorts or hashes: slower); UNION ALL keeps everything and is what you want when you know there are no duplicates or do not mind them. INTERSECT keeps rows in both; EXCEPT keeps rows in the first and not in the second (Oracle calls it MINUS).

Schema design, normalisation and constraints

Queries answer questions; the schema decides which wrong answers are possible. Good design stores each fact once, and uses constraints so the database itself refuses data that makes no sense, whichever application, script or colleague tries to write it.

Normalisation in plain words

Normalisation is a set of rules for not storing the same fact in two places. Start from a “flat” table, the sort of thing you get from a spreadsheet or a Dataverse export, and see what goes wrong:

-- One wide table: every ticket repeats the employee's name and the site's city.

                           site_id TEXT, site_city TEXT);
INSERT INTO tickets_flat VALUES
  ('t-1', 'Badge not working', 'e-902', 'Asha',  'BLR-01', 'Bengaluru'),

When to denormalise on purpose

Normalised is the default; breaking the rules is a decision with a reason you can say aloud. Legitimate reasons:

SnapshotThe fact must NOT follow later edits

An audit row records the approver’s name as it was when they approved. If you only store employee_id and she later changes name, history lies. Copy the value, on purpose.

Read speedA join you run constantly is the bottleneck

A precomputed chunk_count on documents, or a reporting table rebuilt nightly. You accept that you must keep it in step and decide who does that (a trigger, the repository, a job).

Shape variesThe payload really is a document

The raw body an external service sent you, or per-vendor event details: store as jsonb and keep the fields you filter on as real columns (section 19).

WarehouseAnalytics, not transactions

Reporting databases are deliberately wide and flat. Different job, different rules; do not copy that into the system of record.

Constraints: PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL, DEFAULT

A constraint is a rule the database enforces on every write. It is the cheapest, most reliable validation you will ever write, because it cannot be bypassed by a second code path. Each line of the table below is a statement that is now impossible, not merely unlikely.

PRIMARY KEYTwo rows with the same key, or a NULL keyid

Predict, then reveal — schema
You delete a row from documents that has 40 rows in chunks. What happens with (a) no ON DELETE clause, (b) ON DELETE CASCADE, (c) ON DELETE SET NULL on a NOT NULL column?

(a) The default (NO ACTION) refuses the delete with a foreign-key error, because 40 chunks would be orphaned. (b) CASCADE deletes the 40 chunks in the same statement. Right for chunks, which are meaningless without their document; dangerous for anything with its own life, such as employees and their requests. (c) The delete fails with a NOT NULL error, because the database tries to set document_id to NULL and the column forbids it. Pick the behaviour per relationship and write it in the DDL.

Why is answer_sources’s primary key (answer_id, chunk_id) and not a separate id?

The pair is the identity of the fact “this answer cites this chunk”, and a composite primary key also prevents citing the same chunk twice for one answer. A surrogate id would need a separate UNIQUE constraint on the pair anyway. Either design is defensible; the composite key is the smaller, stricter one.

Indexes

An index is a second, sorted copy of one or more columns with pointers back to the rows. It turns “read the whole table to find 400 rows” into “walk three pages”, and it costs you on every write. Almost all of “make the query faster” is deciding which index to have, and having the courage to drop the ones that do not earn their keep.

What a B-tree index is

The default index in PostgreSQL and SQLite is a B-tree: a short, wide tree of sorted keys. Each node is one disk page holding many keys, so even a table of a hundred million rows needs only three or four levels. A lookup starts at the root, follows the one branch whose range contains your key, reaches a leaf, and takes the row pointer to the table. That is why an indexed lookup takes roughly the same time for a thousand rows or a hundred million, and why a B-tree can also answer <, >, BETWEEN, ORDER BY and prefix LIKE 'abc%' (the leaves are sorted and linked), but not LIKE '%abc' or lower(col) = ... unless you index that exact expression.

Seeing an index change the plan (SQLite)

SQLite’s EXPLAIN QUERY PLAN is a small, friendly version of PostgreSQL’s EXPLAIN. The words to look for: SCAN means it reads every row (or every entry of an index); SEARCH ... USING INDEX means it walks the tree. The block builds a 100,000-row table, asks the same question before and after CREATE INDEX, and also shows the traps: composite column order, an expression the index cannot see, a partial index, and the cost of writes.

index_demo.py (Python + SQLite; runs as-is, about 5 seconds)
import sqlite3, time

con = sqlite3.connect(":memory:")
con.executescript("""
CREATE TABLE big_requests (id INTEGER PRIMARY KEY, employee_id TEXT NOT NULL, site_id TEXT NOT NULL,
                           status TEXT NOT NULL, starts_on TEXT NOT NULL);
WITH RECURSIVE n(g) AS (SELECT 1 UNION ALL SELECT g + 1 FROM n WHERE g < 100000)
INSERT INTO big_requests (employee_id, site_id, status, starts_on)
SELECT 'e-' || (900 + g % 500),
       CASE g % 4 WHEN 0 THEN 'BLR-01' WHEN 1 THEN 'BLR-02' WHEN 2 THEN 'HYD-01' ELSE 'PUN-01' END,
       CASE g % 3 WHEN 0 THEN 'pending' WHEN 1 THEN 'approved' ELSE 'rejected' END,
       date('2026-01-01', '+' || (g % 365) || ' days')
FROM n;
""")

def plan(sql, *params):
    return [row[3] for row in con.execute("EXPLAIN QUERY PLAN " + sql, params)]

def ms(sql, *params, n=20):
    start = time.perf_counter()
    for _ in range(n):
        con.execute(sql, params).fetchall()
    return round((time.perf_counter() - start) / n * 1000, 2)

q = "SELECT id FROM big_requests WHERE employee_id = ?"
print(plan(q, "e-950"))            # ['SCAN big_requests']                 reads all 100,000 rows
before = ms(q, "e-950")

con.execute("CREATE INDEX idx_emp ON big_requests (employee_id)")
print(plan(q, "e-950"))            # ['SEARCH big_requests USING COVERING INDEX idx_emp (employee_id=?)']
after = ms(q, "e-950")
print(f"{before} ms -> {after} ms")   # my laptop, one run: 4.16 ms -> 0.07 ms. Yours will differ; the ratio is the point.
assert after < before

# An expression hides the column from the index: lower(employee_id) is not employee_id.
print(plan("SELECT * FROM big_requests WHERE lower(employee_id) = ?", "e-950"))      # ['SCAN big_requests']
con.execute("CREATE INDEX idx_lower ON big_requests (lower(employee_id))")           # index the expression itself
print(plan("SELECT * FROM big_requests WHERE lower(employee_id) = ?", "e-950"))      # ['SEARCH ... USING INDEX idx_lower (<expr>=?)']

# Composite index: column ORDER matters. (site_id, status) helps site_id alone, but not status alone.
con.execute("CREATE INDEX idx_site_status ON big_requests (site_id, status)")
print(plan("SELECT id FROM big_requests WHERE site_id = ? AND status = ?", "BLR-01", "pending"))
#   ['SEARCH big_requests USING COVERING INDEX idx_site_status (site_id=? AND status=?)']
print(plan("SELECT id FROM big_requests WHERE site_id = ?", "BLR-01"))
#   ['SEARCH big_requests USING COVERING INDEX idx_site_status (site_id=?)']          leading column: fine
print(plan("SELECT id FROM big_requests WHERE status = ?", "pending"))
#   ['SCAN big_requests USING COVERING INDEX idx_site_status']                        second column alone: scans the index, no search

# Partial index: only the rows you query. Smaller, cheaper to maintain.
con.execute("CREATE INDEX idx_pending ON big_requests (starts_on) WHERE status = 'pending'")
print(plan("SELECT id FROM big_requests WHERE status = 'pending' AND starts_on > '2026-12-01'"))
#   ['SEARCH big_requests USING COVERING INDEX idx_pending (starts_on>?)']

def load(index_columns):
    c = sqlite3.connect(":memory:")
    c.execute("CREATE TABLE t (id INTEGER PRIMARY KEY, employee_id TEXT, site_id TEXT, status TEXT, starts_on TEXT)")

Red pencil — when an index hurts or does nothing

1. Every index slows writes and takes disk (the 200,000-row test table in the next section is 13 MB; its single-column index is about 1.3 MB). A table that is written all day and read rarely wants few indexes. 2. Low selectivity: an index on a column with three values (status) is useless when a third of the table matches; the planner rightly ignores it. 3. A function or a cast on the column (lower(x), x::text, date(created_at)) disables a plain index. 4. Leading wildcard: LIKE '%abc'. 5. Wrong column order in a composite. 6. Foreign key columns are not indexed automatically in PostgreSQL (the primary side is; the referencing side is not): index employee_id on access_requests, or deleting an employee scans the whole table. 7. Never add an index “just in case”. Add it when EXPLAIN shows a scan on a query that matters.

Interviewers ask

“A query is slow. Do not add indexes by guesswork. The follow-up: “why might the planner ignore your index?” Because a sequential scan is cheaper (low selectivity, a tiny table), because the query hides the column inside a function, or because the statistics are out of date.

Optimisation habits that matter before any tuning

1Fetch less

Name the columns (no SELECT *), filter with WHERE, add LIMIT, and keep embedding vectors and big text out of lists. Moving less data is cheaper than any index.

2Index what you filter and join on

WHERE columns, JOIN columns, foreign keys (PostgreSQL does not index them for you), and the ORDER BY of your hot queries. Verify with EXPLAIN.

3Keep the column bare

WHERE starts_on >= '2026-12-01' uses an index; WHERE date_trunc('month', starts_on) = ... does not. Move the function to the other side of the comparison.

4Avoid N+1 queries

One query per row of an earlier result is the commonest self-inflicted slowdown, and it hides in loops (see below).

5Page by key, not by OFFSET

WHERE id > :last ORDER BY id LIMIT 20 stays fast on page 5,000.

6Measure, then change one thing

Same rule as the debugging loop on sheet 23: reproduce, hypothesise, change one thing, re-measure.

The N+1 problem, counted. Twenty employees and sixty requests; one version asks the database 21 questions, the other asks once. Counting statements with set_trace_callback makes it visible even on a toy database, where the time would hide it. Across a network to a real server, each extra statement adds a round trip, so 21 becomes 21 round trips.

n_plus_one.py (Python + SQLite; runs as-is)
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript("CREATE TABLE e (id TEXT PRIMARY KEY, name TEXT); CREATE TABLE r (id INTEGER PRIMARY KEY, e_id TEXT)")
con.executemany("INSERT INTO e VALUES (?, ?)", [(f"e-{i}", f"name{i}") for i in range(20)])
con.executemany("INSERT INTO r (e_id) VALUES (?)", [(f"e-{i % 20}",) for i in range(60)])

seen = []
con.set_trace_callback(seen.append)            # called with every statement SQLite runs

# N+1: one query for the list, then one more per row.
counts = {}
for (emp_id,) in con.execute("SELECT id FROM e").fetchall():
    counts[emp_id] = con.execute("SELECT count(*) FROM r WHERE e_id = ?", (emp_id,)).fetchone()[0]
print("N+1 statements:", len(seen))            # 21

# One query that asks the database to do the join and the counting.
seen.clear()
joined = dict(con.execute("SELECT e.id, count(r.id) FROM e LEFT JOIN r ON r.e_id = e.id GROUP BY e.id").fetchall())
print("join statements:", len(seen))           # 1
assert counts == joined                        # same answer, one round trip instead of 21

You have an index on (site_id, status). Which of these can use it: (a) WHERE site_id = 'BLR-01', (b) WHERE status = 'pending', (c) WHERE site_id = 'BLR-01' AND status = 'pending', (d) WHERE status = 'pending' AND site_id = 'BLR-01'?

Transactions and ACID

A transaction is a group of statements the database treats as one: all of them take effect together, or none of them do. Without it, a crash or an error between two related writes leaves the data in a state no one intended, and nothing tells you.

BEGIN, COMMIT, ROLLBACK, run

Python’s sqlite3 has a legacy transaction mode that silently opens transactions for you; to see exactly what happens the block uses isolation_level=None, which means “I will write BEGIN and COMMIT myself”. transactions.py (Python + SQLite; runs as-is)
import sqlite3

def fresh():
    con = sqlite3.connect(":memory:", isolation_level=None)       # autocommit: no hidden transactions
    con.executescript("""
    CREATE TABLE quota  (site_id TEXT PRIMARY KEY, seats_left INTEGER NOT NULL CHECK (seats_left >= 0));
    CREATE TABLE grants (id INTEGER PRIMARY KEY, employee_id TEXT NOT NULL, site_id TEXT NOT NULL);
    INSERT INTO quota VALUES ('PUN-01', 0), ('BLR-01', 5);
    INSERT INTO grants (employee_id, site_id) VALUES ('e-901', 'PUN-01'), ('e-902', 'PUN-01'), ('e-903', 'PUN-01');
    """)
    return con

def state(con):
    return (con.execute("SELECT count(*) FROM grants WHERE site_id = 'PUN-01'").fetchone()[0],
            con.execute("SELECT seats_left FROM quota WHERE site_id = 'PUN-01'").fetchone()[0])

def grant_seat(con, employee_id, site_id):
    con.execute("INSERT INTO grants (employee_id, site_id) VALUES (?, ?)", (employee_id, site_id))
    con.execute("UPDATE quota SET seats_left = seats_left - 1 WHERE site_id = ?", (site_id,))   # fails if 0 left

# 1) No transaction: the INSERT is already permanent when the UPDATE fails. A grant exists with no seat behind it.
con = fresh()
try:
    grant_seat(con, "e-904", "PUN-01")
except sqlite3.IntegrityError as err:
    print("failed:", err)                       # failed: CHECK constraint failed: seats_left >= 0
print("no transaction:", state(con))            # (4, 0)   4 grants, 0 seats: the data now contradicts itself

# 2) Explicit transaction: BEGIN, then COMMIT on success or ROLLBACK on any error.
con = fresh()
con.execute("BEGIN")
try:
    grant_seat(con, "e-904", "PUN-01")
    con.execute("COMMIT")
except sqlite3.Error:
    con.execute("ROLLBACK")
print("with rollback:", state(con))             # (3, 0)   the INSERT was discarded with the failed UPDATE

# 3) The success path commits both writes together.
con.execute("BEGIN")
grant_seat(con, "e-905", "BLR-01")
con.execute("COMMIT")
print(con.execute("SELECT count(*) FROM grants WHERE site_id = 'BLR-01'").fetchone(),
      con.execute("SELECT seats_left FROM quota WHERE site_id = 'BLR-01'").fetchone())      # (1,) (4,)

# 4) The same thing with Python's context manager, on a connection in the default mode: commit on success, rollback on exception.
con2 = sqlite3.connect(":memory:")
con2.executescript("""
CREATE TABLE quota  (site_id TEXT PRIMARY KEY, seats_left INTEGER NOT NULL CHECK (seats_left >= 0));
CREATE TABLE grants (id INTEGER PRIMARY KEY, employee_id TEXT NOT NULL, site_id TEXT NOT NULL);
INSERT INTO quota VALUES ('PUN-01', 0);
""")
try:
    with con2:                                   # BEGIN is implicit; leaving the block commits or rolls back
        grant_seat(con2, "e-904", "PUN-01")
except sqlite3.IntegrityError:
    pass
print(con2.execute("SELECT count(*) FROM grants").fetchone())    # (0,)   rolled back by the with-block
Red pencil — transactions are not magic

1. Keep them short. A transaction holds locks until it ends; one that waits on a network call or a user (an HTTP request to the vendor API in the middle of it) blocks everyone who touches the same rows. Do the slow call outside, then write the result in a short transaction. 2. Catching the exception and carrying on without rolling back leaves the transaction open (and in PostgreSQL, aborted: “current transaction is aborted, commands ignored until end of transaction block”). 3. The database rolls back the database, not the world: an email already sent or an API already called stays done. Write the outbox row in the transaction and send afterwards. 4. A transaction does not by itself stop two requests from both reading “1 seat left”: that is the isolation question below.

Interviewers ask

“Explain ACID and give an example where atomicity matters.” Use your own: approving an access request updates the request and appends an audit row; if the audit insert fails and the update has already stuck, there is an approved request with no record of who approved it. Atomicity makes the two writes one unit. Then expect: “what does durable mean?” Once COMMIT returns, the change survives a power cut, because the database flushed its write-ahead log to disk first.

Isolation levels and locks (awareness)

Two transactions running at once can disturb each other in a handful of well-known ways. The isolation level is how many of those the database prevents. You will rarely change the default, but you will be asked which anomaly each level stops, and you will meet a deadlock.

In production — how to choose

Read committed is the right default for most request handlers. When a check-then-write must not race (“1 seat left”), you have three tools, in order of preference: a constraint or a single atomic statement (UPDATE quota SET seats_left = seats_left - 1 WHERE site_id = $1 AND seats_left > 0 and check the row count), an explicit row lock (SELECT ... FOR UPDATE), or serializable with a retry loop. The atomic statement is usually the best: no lock held across round trips, no retry loop.

Locks and deadlocks

A write locks the rows it touches until the transaction ends; another writer to the same row waits. Readers do not block writers in PostgreSQL (each statement reads a consistent snapshot), which is a large part of why it copes with many users. A deadlock is two transactions each holding a lock the other needs: A updated row 1 and wants row 2, B updated row 2 and wants row 1. PostgreSQL detects it after about a second (deadlock_timeout), aborts one of them with deadlock detected (SQLSTATE 40P01), and lets the other continue. I produced one by hand on PostgreSQL 17.6: the error class was psycopg.errors.DeadlockDetected, and which of the two sessions is the victim is not predictable.

locks_postgres.sql (PostgreSQL only)
-- Session A                                   -- Session B
BEGIN;                                         BEGIN;
UPDATE accounts SET balance = balance - 1      UPDATE accounts SET balance = balance - 1
  WHERE id = 'a';                                WHERE id = 'b';
UPDATE accounts SET balance = balance + 1      UPDATE accounts SET balance = balance + 1
  WHERE id = 'b';   -- waits for B               WHERE id = 'a';   -- waits for A: a cycle
-- after about 1 s, one session gets:  ERROR:  deadlock detected     (SQLSTATE 40P01)  and must ROLLBACK and retry.

-- Preventing it: always touch rows in the same order (say, ascending id), keep transactions short,
-- and retry on SQLSTATE 40P01 and 40001 (serialization_failure).

-- Take a lock deliberately: other writers (and other FOR UPDATE readers) wait until you COMMIT.
BEGIN;
SELECT seats_left FROM quota WHERE site_id = 'BLR-01' FOR UPDATE;
-- decide in your application, then:
UPDATE quota SET seats_left = seats_left - 1 WHERE site_id = 'BLR-01';
COMMIT;

-- A job queue that never hands the same row to two workers: skip rows another worker has locked.
SELECT id FROM access_requests WHERE status = 'pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
Predict, then reveal — concurrency
Two requests arrive at the same moment for the last seat at a site. Both run SELECT seats_left, see 1, and both run UPDATE ... SET seats_left = seats_left - 1 in separate transactions at read committed. What happens, and how do you stop it?

With a CHECK (seats_left >= 0) on the column, the second UPDATE waits for the first to commit, re-evaluates against the new value 0, and fails the CHECK: the constraint is the safety net. Without the CHECK you get -1 seats. The cleaner pattern avoids the read entirely: UPDATE quota SET seats_left = seats_left - 1 WHERE site_id = $1 AND seats_left > 0 and treat “0 rows updated” as “sold out”. A read followed by a write based on what you read is the shape of every race condition.

Your code gets psycopg.errors.SerializationFailure or DeadlockDetected. Is that a bug?

No. It is the database telling you the transaction was safe to start but not safe to finish, and that the right response is to roll back and run the whole transaction again (not just the failed statement). A retry loop with a small cap (three attempts) and a little jitter is the standard answer; if it keeps failing, reduce the contention (shorter transactions, consistent lock order).

psycopg_basics.py (psycopg 3 + PostgreSQL)
import os
import psycopg
from psycopg.rows import dict_row

DSN = os.environ["DATABASE_URL"]       # e.g. postgresql://postgres@localhost:5432/badgedesk  (set in your shell, never in code)

# 'with' commits when the block ends normally, rolls back if it raises, and then CLOSES the connection.
with psycopg.connect(DSN, row_factory=dict_row) as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT id, status FROM access_requests WHERE employee_id = %s AND status = %s ORDER BY id",
                    ("e-902", "approved"))                     # values travel separately from the SQL text
        print(cur.fetchall())                                  # [{'id': 1, 'status': 'approved'}]

        # A Python list becomes a PostgreSQL array: WHERE site_id = ANY(...) is the safe way to write IN (...).
        cur.execute("SELECT count(*) AS n FROM access_requests WHERE site_id = ANY(%s)", (["BLR-01", "HYD-01"],))
        print(cur.fetchone())                                  # {'n': 6}

        # RETURNING hands back the generated id and defaults without a second query.
        cur.execute("INSERT INTO access_requests (employee_id, site_id, starts_on, ends_on) VALUES (%s, %s, %s, %s) "
                    "RETURNING id, status", ("e-905", "BLR-01", "2026-12-10", "2026-12-11"))
        print(cur.fetchone())                                  # {'id': 8, 'status': 'pending'}   (8 on a freshly seeded database; ids skip numbers after failed inserts)

        # None becomes NULL. A literal percent sign in SQL text must be doubled when you pass parameters.
        cur.execute("SELECT id FROM access_requests WHERE reason LIKE '%%train%%' AND status = %s ORDER BY id", ("approved",))
        print(cur.fetchall())                                  # [{'id': 3}]

# An exception inside the block rolls everything back.
try:
    with psycopg.connect(DSN) as conn:
        conn.execute("INSERT INTO sites VALUES (%s, %s, %s)", ("MUM-01", "Mumbai", 150))
        raise RuntimeError("something failed after the insert")
except RuntimeError:
    pass
with psycopg.connect(DSN) as conn:
    print(conn.execute("SELECT count(*) FROM sites WHERE id = 'MUM-01'").fetchone())      # (0,)   the insert was rolled back

# conn.transaction(): a block that is its own transaction (or a SAVEPOINT if one is already open).
with psycopg.connect(DSN) as conn:
    try:
        with conn.transaction():
            conn.execute("UPDATE sites SET capacity = capacity + 10 WHERE id = 'BLR-01'")
            conn.execute("INSERT INTO sites VALUES ('BLR-01', 'Duplicate', 1)")    # primary key clash
    except psycopg.errors.UniqueViolation as err:
        print("rolled back:", type(err).__name__)                                   # rolled back: UniqueViolation
    print(conn.execute("SELECT capacity FROM sites WHERE id = 'BLR-01'").fetchone())      # (500,)   the UPDATE was undone too

SQL injection: demonstrated safely, then fixed

SQL injection happens when a program builds SQL text by gluing a value into it. The database cannot tell where your SQL ends and the user’s text begins, so a value containing a quote and some SQL becomes part of the statement. It is old, boring, a standing member of OWASP’s “Injection” category, and the most reliably failed question on a secure-coding interview. Below is the whole attack on a toy table in an in-memory SQLite database, so nothing real is at risk. Notice that the unsafe function works perfectly for the first, honest call.

injection_demo.py (Python + SQLite; runs as-is)
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript("""
CREATE TABLE toy_users (name TEXT, secret TEXT);
INSERT INTO toy_users VALUES ('asha', 'pin-1111'), ('ravi', 'pin-2222'), ('meera', 'pin-3333');
""")

def lookup_unsafe(name):
    sql = f"SELECT name, secret FROM toy_users WHERE name = '{name}'"     # the value is pasted INTO the SQL text
    print("   SQL sent:", sql)
    return con.execute(sql).fetchall()

def lookup_safe(name):
    sql = "SELECT name, secret FROM toy_users WHERE name = ?"             # the SQL text never contains the value
    return con.execute(sql, (name,)).fetchall()

print("honest input")
print(lookup_unsafe("asha"))                  # [('asha', 'pin-1111')]

print("attack 1: make the condition always true")
rows = lookup_unsafe("x' OR '1'='1")          # SQL sent: ... WHERE name = 'x' OR '1'='1'
print(rows)                                   # [('asha', 'pin-1111'), ('ravi', 'pin-2222'), ('meera', 'pin-3333')]   every secret
assert len(rows) == 3

print("attack 2: UNION another query onto this one and read the table list")
rows = lookup_unsafe("zzz' UNION SELECT name, sql FROM sqlite_master --")
print(rows)                                   # [('toy_users', 'CREATE TABLE toy_users (name TEXT, secret TEXT)')]   the schema leaks
assert rows and rows[0][0] == "toy_users"

print("attack 3: a second statement")
try:
    lookup_unsafe("x'; DROP TABLE toy_users; --")
except sqlite3.ProgrammingError as err:
    print("   refused by the driver:", err)  # refused by the driver: You can only execute one statement at a time.
# That refusal is a driver safety net (and psycopg refuses it too when you pass parameters), not a defence:
# executescript() or a driver that allows several statements would have run the DROP. Attacks 1 and 2 already worked.

print("the fix: parameters")
print(lookup_safe("x' OR '1'='1"))            # []   the whole string is just a name nobody has
print(lookup_safe("asha"))                    # [('asha', 'pin-1111')]
con.execute("INSERT INTO toy_users VALUES (?, ?)", ("O'Brien", "pin-4444"))
print(lookup_safe("O'Brien"))                 # [("O'Brien", 'pin-4444')]   apostrophes just work, no escaping by hand

# A placeholder can only stand for a VALUE. Table and column names cannot be parameters:
# if you must choose a column dynamically, choose from an allowlist YOU wrote, never from the user's text.
ALLOWED_SORT = {"id", "starts_on", "status"}
def sort_clause(column):
    if column not in ALLOWED_SORT:
        raise ValueError(f"cannot sort by {column!r}")
    return f"ORDER BY {column}"               # an f-string is acceptable here ONLY because of the allowlist check
print(sort_clause("starts_on"))               # ORDER BY starts_on
try:
    sort_clause("starts_on; DROP TABLE x")
except ValueError as err:
    print(err)                                # cannot sort by 'starts_on; DROP TABLE x'

injection_psycopg.py (psycopg 3 + PostgreSQL)
import os
import psycopg
from psycopg import sql

with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
    conn.execute("CREATE TEMP TABLE toy_users (name text, secret text)")      # TEMP: vanishes when the connection closes
    conn.execute("INSERT INTO toy_users VALUES ('asha', 'pin-1111'), ('ravi', 'pin-2222'), ('meera', 'pin-3333')")

    name = "x' OR '1'='1"
    unsafe = f"SELECT name, secret FROM toy_users WHERE name = '{name}'"      # never write this
    print(len(conn.execute(unsafe).fetchall()))                                # 3   every row came back

    safe = conn.execute("SELECT name, secret FROM toy_users WHERE name = %s", (name,)).fetchall()
    print(safe)                                                                # []

    # Dynamic identifiers: sql.Identifier quotes a column or table name correctly. Still prefer an allowlist.
    column = "name"
    query = sql.SQL("SELECT {col} FROM toy_users ORDER BY {col}").format(col=sql.Identifier(column))
    print(conn.execute(query).fetchall())                                      # [('asha',), ('meera',), ('ravi',)]

I confirmed on PostgreSQL 17.6 that the server receives the query with a $1 placeholder. On older Python, keep using %s. Red pencil — three myths about injection

“I escape the quotes.” Hand-escaping misses encodings and second-order cases (a stored value that is later pasted into another query). Parameters remove the whole class. “It is an internal tool.” The first thing an attacker wants is a place inside; an internal tool with injection is that place. “An ORM makes me safe.” Only if you never use its raw-SQL escape hatch with string formatting, and every ORM has one. The rule is the same everywhere: values go in as parameters; only your own constants go in the SQL text. Including values you think came from your own database.

Interviewers ask

“What is SQL injection and how do you prevent it?” Untrusted input is concatenated into SQL and changes its structure. Prevent it with parameterised queries (the driver sends SQL and values separately, so values are never parsed as SQL), allowlists for identifiers, and a database user with only the permissions the app needs, so the damage of any miss is limited. “Is escaping enough?” No. “Do stored procedures protect you?” Only if they use parameters inside too; a procedure that builds dynamic SQL from its arguments is injectable.

From rows to objects: mapping, the repository layer, connections, migrations

Raw tuples are fine in a script and a liability in an application. The pattern that scales is small: SQL lives in one place (a repository), rows become typed objects at its edge, every request gets its own connection, and schema changes are numbered files, not edits made by hand.

Mapping rows to dataclasses and Pydantic models

A row is a tuple of whatever the driver decided: dates may arrive as str (SQLite) or datetime.date (PostgreSQL), NULL as None. Convert once, at the boundary, so the rest of the code deals in real types. A dataclass is the light choice: you do the conversion, nothing validates. A Pydantic model converts and validates for you, and is what FastAPI will use for requests and responses, so it is a good fit for any row that crosses a trust boundary. (Pydantic is not in the standard library: pip install pydantic; this block was run with Pydantic 2.14.1.)

rows_to_objects.py (Python + SQLite + Pydantic; runs as-is)
import sqlite3
from dataclasses import dataclass
from datetime import date
from typing import Literal, Optional

from pydantic import BaseModel, ValidationError

con = sqlite3.connect(":memory:")
con.row_factory = sqlite3.Row                    # rows you can index by name: row["priority"]
con.executescript("""
CREATE TABLE tickets (id TEXT PRIMARY KEY, employee_id TEXT NOT NULL, priority TEXT NOT NULL,
                      summary TEXT NOT NULL, opened_on TEXT NOT NULL, closed_on TEXT);
INSERT INTO tickets VALUES ('t-1', 'e-902', 'high',   'Badge not working', '2026-11-02', NULL),
                           ('t-2', 'e-903', 'normal', 'Door sensor',       '2026-11-03', '2026-11-05'),
                           ('t-3', 'e-902', 'URGENT!', 'Typo in a bulk import', '2026-11-04', NULL);
""")

# 1) A tuple-ish row: positional, untyped. Easy to get wrong and impossible to read.
row = con.execute("SELECT * FROM tickets WHERE id = 't-1'").fetchone()
print(tuple(row))        # ('t-1', 'e-902', 'high', 'Badge not working', '2026-11-02', None)

# 2) A dataclass: you write the conversion once, in one function.
@dataclass(frozen=True)
class TicketRow:
    id: str
    employee_id: str
    priority: str
    summary: str
    opened_on: date
    closed_on: Optional[date]

def to_ticket_row(r: sqlite3.Row) -> TicketRow:
    return TicketRow(r["id"], r["employee_id"], r["priority"], r["summary"],
                     date.fromisoformat(r["opened_on"]),
                     date.fromisoformat(r["closed_on"]) if r["closed_on"] else None)   # NULL stays None

print(to_ticket_row(row))       # TicketRow(id='t-1', employee_id='e-902', priority='high', ..., opened_on=datetime.date(2026, 11, 2), closed_on=None)

# 3) A Pydantic model: the same conversion, plus validation. 'opened_on' arrives as text and becomes a date.
class Ticket(BaseModel):
    id: str
    employee_id: str
    priority: Literal["low", "normal", "high"]    # only these three values are acceptable
    summary: str
    opened_on: date
    closed_on: Optional[date] = None

ok = Ticket.model_validate(dict(row))             # dict(row) works because of sqlite3.Row
print(ok.opened_on, type(ok.opened_on).__name__)  # 2026-11-02 date
print(ok.model_dump())                            # a plain dict again, e.g. to return as JSON

# Dirty data in the database (t-3 has a priority nobody allowed) is caught at the boundary, not three layers later.
try:
    Ticket.model_validate(dict(con.execute("SELECT * FROM tickets WHERE id = 't-3'").fetchone()))
except ValidationError as err:
    print(err.error_count(), "problem:", err.errors()[0]["loc"], "-", err.errors()[0]["msg"])
    # 1 problem: ('priority',) - Input should be 'low', 'normal' or 'high'

The repository pattern and one connection per request

A repository is a class whose methods are the questions the application asks of one kind of data: add, get, list_open, close. All SQL for tickets lives inside it. Callers pass Python values and receive typed objects; they never see a placeholder, a cursor or a column name. Three payoffs: you can read every query a table is used by in one file; you can test the logic with a fake repository; and the day you change the schema, one file changes. (This is the design you build in the week 8 lab, for access requests, with transactions.) The block below does it for tickets, on a database file, because an in-memory SQLite database exists only inside one connection, which is also the lesson about connection lifecycle.

ticket_repository.py (Python + SQLite; runs as-is)
import sqlite3
import tempfile
from contextlib import closing, contextmanager
from dataclasses import dataclass
from datetime import date
from pathlib import Path
from typing import Iterator, Optional

SCHEMA = """
CREATE TABLE IF NOT EXISTS tickets (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  employee_id TEXT NOT NULL,
  summary TEXT NOT NULL,
  priority TEXT NOT NULL DEFAULT 'normal' CHECK (priority IN ('low', 'normal', 'high')),
  opened_on TEXT NOT NULL,
  closed_on TEXT
);"""

@dataclass(frozen=True)
class Ticket:
    id: int
    employee_id: str
    summary: str
    priority: str
    opened_on: date
    closed_on: Optional[date]

def _to_ticket(row: sqlite3.Row) -> Ticket:
    return Ticket(row["id"], row["employee_id"], row["summary"], row["priority"],
                  date.fromisoformat(row["opened_on"]),
                  date.fromisoformat(row["closed_on"]) if row["closed_on"] else None)

class TicketRepository:
    """The only place that knows tickets are rows. Every query is parameterised."""
    def __init__(self, conn: sqlite3.Connection) -> None:
        self.conn = conn

    def add(self, employee_id: str, summary: str, opened_on: date, priority: str = "normal") -> Ticket:
        cur = self.conn.execute(
            "INSERT INTO tickets (employee_id, summary, priority, opened_on) VALUES (?, ?, ?, ?)",
            (employee_id, summary, priority, opened_on.isoformat()))
        return self.get(cur.lastrowid)

    def get(self, ticket_id: int) -> Optional[Ticket]:
        row = self.conn.execute("SELECT * FROM tickets WHERE id = ?", (ticket_id,)).fetchone()
        return _to_ticket(row) if row else None

    def list_open(self, employee_id: Optional[str] = None) -> list[Ticket]:
        sql, params = "SELECT * FROM tickets WHERE closed_on IS NULL", []
        if employee_id is not None:
            sql += " AND employee_id = ?"
            params.append(employee_id)
        return [_to_ticket(r) for r in self.conn.execute(sql + " ORDER BY id", params)]

    def close(self, ticket_id: int, closed_on: date) -> bool:
        """True if a still-open ticket was closed, False if it was missing or already closed (the rowcount tells)."""
        cur = self.conn.execute("UPDATE tickets SET closed_on = ? WHERE id = ? AND closed_on IS NULL",
                                (closed_on.isoformat(), ticket_id))
        return cur.rowcount == 1

# --- connection lifecycle: one connection per unit of work (an HTTP request), always closed ----------
@contextmanager
def connection(db_path: str) -> Iterator[sqlite3.Connection]:
    """The same shape as a FastAPI dependency that uses yield: open, hand out, commit or roll back, always close."""
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row
    try:
        yield conn
        conn.commit()                       # the request finished normally
    except BaseException:
        conn.rollback()                     # the request failed: undo everything it did
        raise
    finally:
        conn.close()                        # never leak a connection

def handle_request(db_path, work):
    """Pretend HTTP handler: borrow a connection, build a repository on it, run the work."""
    with connection(db_path) as conn:
        return work(TicketRepository(conn))

with tempfile.TemporaryDirectory() as folder:
    db = str(Path(folder) / "badgedesk.db")
    with closing(sqlite3.connect(db)) as setup:
        setup.executescript(SCHEMA)

    t1 = handle_request(db, lambda repo: repo.add("e-902", "Badge not working", date(2026, 11, 2), "high"))
    handle_request(db, lambda repo: repo.add("e-903", "Door sensor", date(2026, 11, 3)))
    print(t1)           # Ticket(id=1, employee_id='e-902', summary='Badge not working', priority='high', opened_on=datetime.date(2026, 11, 2), closed_on=None)

    # A second "request" is a different connection, and sees what the first one committed.
    print([t.id for t in handle_request(db, lambda repo: repo.list_open())])                  # [1, 2]
    print(handle_request(db, lambda repo: repo.close(1, date(2026, 11, 4))))                  # True
    print(handle_request(db, lambda repo: repo.close(1, date(2026, 11, 5))))                  # False   already closed: rowcount 0
    print([t.id for t in handle_request(db, lambda repo: repo.list_open("e-902"))])           # []

    # A failing request leaves nothing behind.
    def doomed(repo):
        repo.add("e-904", "Will be rolled back", date(2026, 11, 6))
        raise RuntimeError("the vendor API call failed")
    try:
        handle_request(db, doomed)
    except RuntimeError:
        pass
    print([t.id for t in handle_request(db, lambda repo: repo.list_open())])                  # [2]   ticket 3 never happened

a.execute("CREATE TABLE x (n INTEGER)")

PostgreSQL, not run by the sheet checker. With PostgreSQL you do not open a brand-new connection per request (that costs a network round trip, authentication and a new server process each time). You keep a small pool of open connections and borrow one for the duration of the request; leaving the with pool.connection() block commits or rolls back and returns the connection to the pool rather than closing it. psycopg ships the pool as a separate package: pip install "psycopg[pool]" (psycopg-pool 3.3.3 here; see the Connection pools page). pool_postgres.py (psycopg_pool + PostgreSQL)
import os
from psycopg_pool import ConnectionPool

# Create ONE pool when the application starts (in FastAPI: in the lifespan handler), not one per request.
pool = ConnectionPool(os.environ["DATABASE_URL"], min_size=1, max_size=4, open=False)
pool.open()
pool.wait()                                    # block until the first connection is ready

def count_requests(site_id: str) -> int:
    with pool.connection() as conn:            # borrow; commit/rollback on exit; return to the pool
        return conn.execute("SELECT count(*) FROM access_requests WHERE site_id = %s", (site_id,)).fetchone()[0]

print(count_requests("BLR-01"), count_requests("HYD-01"))     # 3 3   (two borrows, usually the same underlying connection)
print(pool.get_stats()["pool_size"])                           # 1    one connection served both calls
pool.close()

Red pencil — connection mistakes that take a service down

1. A global connection shared by all requests. Two requests interleave statements in one transaction, and one request’s rollback undoes another’s work. 2. Opening a connection and forgetting to close it (an exception skips your close()): the leaked connections accumulate until PostgreSQL answers “sorry, too many clients already” (the default limit is 100). Use with/try-finally/a pool context, every time. 3. Holding a connection while you call a slow API. A pool of 4 means four such requests starve every other. Borrow late, return early. 4. Connection string in code. It belongs in the environment (DATABASE_URL), and the credentials in git are the ones that get scraped.

Migrations: the schema is code too

Your tables change over a project’s life: a new column, a new index, a new table. A migration is a numbered, never-edited-afterwards script that moves the schema from version N to N+1, and the database records which versions it has applied. Run the same scripts in the same order on your laptop, in CI and in production, and the schemas cannot drift apart. In Python the tools are Alembic (with SQLAlchemy), Flyway or dbmate (plain SQL files); the mechanism below is what all of them do underneath.

migrations.py (Python + SQLite; runs as-is)
import sqlite3

MIGRATIONS = [                                  # (version, description, SQL). Append only: NEVER edit an applied migration.
    (1, "create tickets",   "CREATE TABLE tickets (id INTEGER PRIMARY KEY, employee_id TEXT NOT NULL, summary TEXT NOT NULL)"),
    (2, "add closed_on",    "ALTER TABLE tickets ADD COLUMN closed_on TEXT"),                 # nullable first: safe on existing rows
    (3, "index by employee", "CREATE INDEX tickets_employee_idx ON tickets (employee_id)"),
]

def migrate(con):
    con.execute("CREATE TABLE IF NOT EXISTS schema_migrations (version INTEGER PRIMARY KEY, description TEXT NOT NULL)")
    done = {v for (v,) in con.execute("SELECT version FROM schema_migrations")}
    applied = []
    for version, description, ddl in MIGRATIONS:
        if version in done:
            continue                            # idempotent: running twice changes nothing
        con.execute("BEGIN")
        try:
            con.execute(ddl)                    # SQLite and PostgreSQL can roll back DDL; MySQL cannot
            con.execute("INSERT INTO schema_migrations VALUES (?, ?)", (version, description))
            con.execute("COMMIT")
        except BaseException:
            con.execute("ROLLBACK")             # a failed migration leaves the schema at the previous version
            raise
        applied.append(version)
    return applied

con = sqlite3.connect(":memory:", isolation_level=None)       # explicit BEGIN/COMMIT, as in the transactions section
print(migrate(con))                             # [1, 2, 3]   a fresh database gets everything
print(migrate(con))                             # []          already up to date
print([r[1] for r in con.execute("PRAGMA table_info(tickets)")])     # ['id', 'employee_id', 'summary', 'closed_on']

# Later, version 4 arrives with a bug. The transaction protects the schema and the record of what ran.
MIGRATIONS.append((4, "broken", "ALTER TABLE tickets ADD COLUMN closed_on TEXT"))     # that column already exists
try:
    migrate(con)
except sqlite3.OperationalError as err:
    print("migration 4 failed:", err)           # migration 4 failed: duplicate column name: closed_on
print(sorted(v for (v,) in con.execute("SELECT version FROM schema_migrations")))      # [1, 2, 3]   version 4 is not recorded
ChangeSafe way on a live table
Add a columnAdd it nullable (or with a constant default), deploy code that writes it, backfill old rows in batches, then add NOT NULL.
Rename or drop a column“Expand and contract”: add the new column, copy and dual-write, switch readers, and only later drop the old one. Never rename in one step while old code still runs.
Add an index (PostgreSQL)CREATE INDEX CONCURRENTLY does not block writes, but cannot run inside a transaction block, so it needs its own migration step.
Add a foreign key or a CHECK to a big tableAdd it NOT VALID, then VALIDATE CONSTRAINT separately (PostgreSQL) so the long check does not hold a heavy lock.

These four are awareness, not exercises. They are also the reason a migration is reviewed like code: the dangerous ones look harmless in a diff.

pgvector.sql (PostgreSQL + pgvector extension)
-- One-time, per database (needs the extension installed on the server; on a managed service it is usually one click or one command).
CREATE EXTENSION vector;

-- A column that holds one embedding per chunk. 384 is the dimension of the embedding MODEL you will choose; it must match exactly.
ALTER TABLE chunks ADD COLUMN embedding vector(384);

-- Vectors are written as text like '[0.1, 0.2, ...]' (your Python client will do this for you).
-- Three distance operators. Smaller = closer. For text embeddings, cosine distance is the usual choice.
--   <->  L2 (Euclidean) distance      <=>  cosine distance      <#>  negative inner product
-- The nearest-neighbour query: ORDER BY distance, LIMIT k. $1 is the question's embedding, from the same model.
SELECT id, body, embedding <=> $1 AS distance
FROM chunks
ORDER BY embedding <=> $1
LIMIT 5;

-- Without an index this scans every row and gives exact results: fine for thousands of chunks, slow for millions.
-- An approximate index trades a little accuracy ("recall") for speed. Two kinds:
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);                       -- usually better recall/speed, slower to build
CREATE INDEX ON chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100); -- faster to build; needs rows present first
-- The operator class (vector_cosine_ops) must match the operator you query with (<=>), or the index is ignored.

The same idea with nothing to install. Three toy chunks with three-number “embeddings” (real ones have hundreds of numbers), stored as JSON text in SQLite; the nearest chunks to a question vector are found by computing cosine distance in Python. That is the exact computation pgvector performs inside the database, and an index is how it avoids doing it for every row.

nearest_chunks.py (Python + SQLite; runs as-is)
import json
import math
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE chunks (id INTEGER PRIMARY KEY, body TEXT NOT NULL, embedding TEXT NOT NULL)")
toy = {                                         # made-up 3-dimensional vectors, for illustration only
    "Badges expire after 90 days": [0.9, 0.1, 0.0],
    "Managers approve requests":   [0.1, 0.9, 0.1],
    "Visitors need an escort":     [0.0, 0.2, 0.9],
}
for body, vector in toy.items():
    con.execute("INSERT INTO chunks (body, embedding) VALUES (?, ?)", (body, json.dumps(vector)))

def cosine_distance(a, b):                      # 0 = same direction, 1 = unrelated, 2 = opposite
    dot = sum(x * y for x, y in zip(a, b))
    return 1 - dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))

question = [0.8, 0.2, 0.1]                      # "how long does a badge last?", embedded by the same model
ranked = sorted((cosine_distance(question, json.loads(emb)), body)
                for body, emb in con.execute("SELECT body, embedding FROM chunks"))
for distance, body in ranked[:2]:               # ORDER BY distance LIMIT 2
    print(round(distance, 4), body)
# 0.0162 Badges expire after 90 days
# 0.6432 Managers approve requests
assert ranked[0][1] == "Badges expire after 90 days"

Comparisons: PostgreSQL vs SQLite, and JSONB vs relational columns

Two choices that come up in every design discussion. Both have an honest answer that is not “always X”.

PostgreSQL versus SQLite

SQLite

A library inside your process. The database is one file. No server, no users, no port, nothing to install: it ships with Python. One writer at a time; many readers.

Flexible typing (an INTEGER column accepts text unless the table is STRICT), a smaller type system, no real timestamptz, foreign keys off until you enable them.

PostgreSQL

A server you connect to over the network. Many clients write at once (MVCC: readers do not block writers). Roles and permissions, replication, backups, extensions (pgvector, full-text search, PostGIS).

Strict types, timestamptz, jsonb, uuid, arrays, EXPLAIN ANALYZE. Needs installing, configuring, upgrading and running by someone.

Pick SQLite for tests, prototypes, command-line tools and anything with one process and one writer; pick PostgreSQL for the system of record behind a service with several users and for anything that needs pgvector. The honest catch is that SQLite’s forgiveness hides bugs that PostgreSQL will surface. On this sheet alone, SQLite accepted a bare column after GROUP BY, a SELECT alias inside WHERE, an ill-typed value in an INTEGER column, and a foreign-key violation until the pragma was on; its LIKE ignored case and it sorted NULLs first. A test suite that runs on SQLite and a production system on PostgreSQL will therefore agree on logic and disagree on the edges. That is why the labs use SQLite (you need nothing installed) and why the real project tests run against a PostgreSQL started for the test run, in Docker or a CI service container.

JSONB versus relational columns

You will be tempted to store each audit record as a blob of JSON because the shapes differ per source. Sometimes that is right. Here is both side by side, and the cost of the flexibility in the executed block.

json_vs_columns.py (Python + SQLite; runs as-is)
import json
import sqlite3

con = sqlite3.connect(":memory:")
# SQLite stores JSON as text. The CHECK uses json_valid to refuse text that is not JSON at all.
con.execute("""CREATE TABLE audit_log (id INTEGER PRIMARY KEY, actor TEXT NOT NULL, action TEXT NOT NULL,
                                       detail TEXT NOT NULL CHECK (json_valid(detail)))""")
ins = "INSERT INTO audit_log (actor, action, detail) VALUES (?, ?, ?)"
con.execute(ins, ("e-902", "request.create", json.dumps({"request_id": 2, "tags": ["urgent", "visitor"], "site": {"id": "BLR-02"}})))
con.execute(ins, ("vendor", "badge.provision", json.dumps({"request_id": 3, "vendor": {"badge_no": "B-77", "door_group": "G4"}})))

# Reaching inside the document: json_extract(...) or the ->> operator (SQLite 3.38+).
print(con.execute("SELECT id, json_extract(detail, '$.site.id'), detail ->> '$.request_id' FROM audit_log ORDER BY id").fetchall())
# [(1, 'BLR-02', 2), (2, None, 3)]      row 2 has no site: a missing key is NULL, not an error

# Searching inside an array: json_each turns the array into rows.
print(con.execute("""SELECT a.id FROM audit_log a
                     WHERE EXISTS (SELECT 1 FROM json_each(a.detail, '$.tags') t WHERE t.value = 'urgent')""").fetchall())   # [(1,)]

# The flexibility has a price: only "is it JSON" is checked, not what is IN it.
try:
    con.execute(ins, ("x", "y", "{not json"))
except sqlite3.IntegrityError as err:
    print(err)                                                      # CHECK constraint failed: json_valid(detail)
con.execute(ins, ("x", "y", json.dumps({"request_id": "two"})))     # accepted: a string where every other row has a number
print(con.execute("SELECT detail ->> '$.request_id' FROM audit_log ORDER BY id").fetchall())   # [(2,), (3,), ('two',)]
# A real column would have refused this: request_id INTEGER NOT NULL REFERENCES access_requests(id).

Fundamentals, short answers

Primary key versus unique key? A primary key is the one unique, never-NULL identifier of a row that other tables reference; a table has one. A unique constraint forbids repeats of some other value (an email), a table can have several, and NULLs are allowed.   DELETE, TRUNCATE, DROP? DELETE removes chosen rows and can be rolled back, logged row by row; TRUNCATE empties the whole table quickly (in PostgreSQL it is transactional but takes a heavy lock); DROP removes the table itself, structure included.   UNION versus UNION ALL? UNION removes duplicate rows and costs a sort or hash; UNION ALL keeps everything and is faster; use UNION ALL unless you need the de-duplication.

Design and behaviour

What is an index and what does it cost? A sorted structure (a B-tree) that lets the database find rows without reading the whole table; the cost is disk space and slower writes, because every INSERT, UPDATE and DELETE must maintain each index.   Normalisation versus denormalisation? Normalise by default so each fact lives once; denormalise deliberately for snapshots, read-heavy reporting or payloads, and own the job of keeping copies in step.   CTE, subquery or temp table? A CTE names a step for readability (and PostgreSQL inlines it when it can); a subquery is the same without the name; a temp table is real storage you can index and reuse across statements.   What is an N+1 query? One query for a list plus one more per item; fix it with a join or a single WHERE id = ANY(...).   Name the isolation levels and what each prevents. Read committed stops dirty reads; repeatable read also stops non-repeatable reads (and in PostgreSQL phantoms); serializable also stops write skew, at the price of retries.   How do you stop two requests booking the last seat? A CHECK constraint plus one atomic UPDATE with WHERE seats_left > 0, or a row lock, or serializable with a retry loop.

Subtly wrong: SELECT employee_id, id, max(starts_on) ... GROUP BY employee_id. SQLite returns an arbitrary id beside the max, PostgreSQL refuses it. Say which tie-break you chose.

Drill — design, performance, safety
access_requests.employee_id is a foreign key. Deleting an employee takes 40 seconds on a big table. Why, and what do you do?

To check that no request still points at the employee, the database must look up requests by employee_id, and PostgreSQL does not index the referencing side of a foreign key automatically, so it does a sequential scan of the whole table. Add CREATE INDEX ON access_requests (employee_id) (CONCURRENTLY on a live table). Verify with EXPLAIN ANALYZE. Follow-up: “what would you choose for ON DELETE?” Not CASCADE for people; keep the audit rows.

EXPLAIN ANALYZE shows Seq Scan on big_requests ... Rows Removed by Filter: 199600 for a query that returned 400 rows, 18 ms. Is that a problem?

It depends on how often it runs and how big the table will get. At 200,000 rows and 18 ms it may be fine; the signal is the ratio (400 kept, 199,600 thrown away) and the growth: at 20 million rows it is 100 times slower. If the query is hot, add an index on the filtered column and re-run EXPLAIN ANALYZE to confirm the plan changed (0.75 ms in my test). Do not add it just because a scan exists.

This code is in a pull request. What is wrong, and what is the fix? cur.execute(f"SELECT * FROM access_requests WHERE reason LIKE '%{term}%' ORDER BY {sort}")

Two injections. term is a value pasted into the SQL, so the fix is a parameter: "... LIKE %s" with (f"%{term}%",). Building the pattern in Python is fine, because it still travels as a parameter. sort is an identifier, and placeholders cannot be identifiers, so it needs an allowlist (if sort not in {"id", "starts_on"}) or psycopg.sql.Identifier. Also SELECT *: name the columns.

An approval writes UPDATE access_requests then INSERT INTO audit_log. The second statement fails and the code catches the exception and returns an error message. What is the state of the data, and what was missing?

Without a transaction (SQLite’s autocommit mode, or a PostgreSQL connection in autocommit) the UPDATE is already permanent: an approved request with no audit row. With a transaction that is not rolled back, the transaction stays open holding locks, and in PostgreSQL every later command fails with “current transaction is aborted”. What was missing: the two writes inside one transaction, with a ROLLBACK (or a with block that does it) on any exception, and the exception re-raised or turned into an error response.

Inside one transaction you run SELECT count(*) FROM access_requests WHERE status = 'pending' twice and get 3, then 4. Name the anomaly, the level you were probably at, and the cheapest fix.

A phantom read (a different set of rows) — a kind of non-repeatable read — at READ COMMITTED, PostgreSQL’s default: each statement sees data committed up to that statement. If the transaction really needs one consistent view (a report), start it at REPEATABLE READ so both counts come from one snapshot; if the code writes based on what it read, be ready to retry serialization failures. For a single query, no change needed.

Which normal form does tickets(id, employee_id, site_id, site_city) violate, and what is the fix?

Third normal form: site_city depends on site_id, a non-key column, not on the ticket’s key. It creates update anomalies (change the city in one row and not another). Move the city into sites, keep only site_id (or even employee_id, from which the site is derived) in tickets. Follow-up: “when would you keep it?” If it must be a snapshot of the city at the time of the ticket.
