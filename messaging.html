Mess­aging.

Kafka, RabbitMQ and the ideas underneath both. This sheet builds the seam from callout 4 of Drawing 00-A: BadgeDesk must never call the slow, flaky vendor access-control API while an employee is waiting. The whole subject reduces to one move — turn a synchronous dependency you do not control into a durable message you do — and then to the bill that move sends you: duplicates, ordering, lag and poison messages.

The seam

One drawing, two halves, the same feature. The top half is what almost everyone builds first. The bottom half is what this sheet exists to teach. Everything after this — partitions, acks, idempotency, dead-letter topics — is a detail of the bottom half.

1
The line that ruins the feature. POST /access-requests calls the vendor inside the request handler. The employee's browser, the Next.js server, the NestJS gateway and the FastAPI worker process are all held open for the duration. On a four-worker Uvicorn process, four simultaneous slow vendor calls take the entire service down — not because the code is wrong but because every worker is parked on a socket owned by somebody else's data centre.
2
The constraint you cannot fix. The vendor's p99 is 30 seconds and roughly 2% of calls return a 5xx. You do not own it, you cannot make it faster, and asking them to is not an engineering answer. Every design on this sheet starts by accepting this number as a fact and asking what shape of system tolerates it.
3
The cost, measured. A 30-second wait is not “slow”, it is a broken feature: browsers, load balancers and API gateways all have their own shorter timeouts, so the user frequently sees a network error while the vendor call is still in flight and may yet succeed. Now BadgeDesk and the vendor disagree about reality, and nothing in the system will notice.
4
The failure path is where the data dies. The vendor 503s, the exception propagates, the transaction rolls back, and the employee gets a 500. The request that a human typed is now gone. There is no retry, no record, no queue — the only durable copy of the intent was in flight in a Python stack frame. This is the specific failure that messaging removes.
5
The synchronous work shrinks to one local write. Insert the access_requests row and insert an outbox row describing the event, in the same Postgres transaction. Both commit or neither does. That is the whole synchronous path: 40 ms, all of it inside your own VPC, against a database you operate. See Sheet 06.
6
The topic is the seam. badge.requests is a durable, replicated, ordered log that the API writes to and the worker reads from. It is the contract boundary: the API's job ends when the event is durable, the worker's job begins when it reads it. Neither service needs the other to be up at the same moment — which is the actual definition of decoupling, and the reason a queue is not just “a buffer”.
7
The slow work moves to a place where slow is allowed. The provisioning-worker still makes the same 30-second call to the same flaky vendor. Nothing got faster. What changed is who waits: a background consumer that can retry on a 1 s / 4 s / 16 s ladder, process 200 messages concurrently, and give up into badge.requests.dlq after three attempts without losing the message or the user's afternoon.
8
The result is a second event, not a silence. The worker publishes badge.provisioned, which the notifier consumes to send the Teams message and the outbound webhook from Sheet 05. Failure is now observable rather than invisible: a vendor outage shows up as consumer lag on a CloudWatch alarm (Sheet 07) and drains automatically when the vendor recovers.
Why this exists

Two services that call each other synchronously are one service with a network in the middle: if either is down, both are down, and availability multiplies downward (99.9% × 99.9% = 99.8%, and the vendor is nowhere near 99.9%). A broker breaks that multiplication by making the handoff durable instead of immediate. You are trading consistency-in-time for availability: after the 202, BadgeDesk has promised the badge will exist, not that it exists yet. Every hard question in this subject — duplicates, ordering, lag, dead letters — is the invoice for that trade.

Red pencil

“We'll just put it on a queue” is not a design. A queue moves the failure, it does not remove it. If you add Kafka and keep returning 200 OK with a fully-populated badge object, you have lied to the client. Asynchronous processing forces three visible changes to the API contract: the status code becomes 202 Accepted, the response carries an identifier and a Location the client can poll, and the resource gains a real state machine (pending → provisioning → active | failed). Interviewers who know this subject ask about the API change, not about Kafka.

Messaging concepts

Broker-agnostic first. Kafka and RabbitMQ disagree about almost everything except this vocabulary, and every interview question worth asking is about the vocabulary rather than the product.

The five nouns

A message system has exactly five moving parts. Learn to say them precisely, because sloppy naming here is the fastest way to sound junior: “we send it to the queue” is ambiguous in Kafka and simply wrong in RabbitMQ.

The two fundamental shapes

Every messaging design is one of these two, or a composition of them. This is not a tuning choice; it determines who is responsible for the work, how you scale, and what happens when you add a second reader next quarter.

Red pencil

Building badge.provisioned as a work queue is the classic mistake. It works on day one because there is only the notifier. Then the audit-reconciler subscribes, and now the two services steal messages from each other: half the notifications vanish and half the audit rows are missing, intermittently, under load. The tell is the naming — a destination whose name is an event in the past tense (badge.provisioned) is a topic with many independent readers; a destination whose name is work to do (badge.requests) is a queue with competing consumers. In Kafka the mechanism is the same log and the difference is entirely whether readers share a group.id; get that wrong and you have silently chosen the other shape.

Delivery guarantees — where the interview lives

A guarantee is not a property of the broker. It is a property of when the acknowledgement happens relative to the side effect. Two lines of code in your consumer, swapped, change the guarantee. Draw this timeline on the whiteboard and you have answered the question before it is finished.

GuaranteeMechanismYou loseYou gainUse it for
At-most-onceAcknowledge before processing (Kafka enable.auto.commit=true at its worst, RabbitMQ autoAck)Messages, silently, on any crashLowest latency, no duplicate logicMetrics samples, cache warmers, click telemetry — anything where one lost point is invisible
At-least-onceAcknowledge after the side effect succeedsUniqueness — you will get duplicatesNo lost work, everEverything in BadgeDesk. This is the default and the correct default.
“Exactly-once”At-least-once delivery plus an idempotent or transactional consumerThroughput, and a table you must maintainExactly-once effect, which is what anybody actually wantedProvisioning a badge, charging money, sending one email

Pick at-least-once and make the consumer idempotent. That single sentence is the answer to most messaging design questions, and the rest of this section is how you earn the right to say it.

Why end-to-end exactly-once delivery is not achievable

This is worth arguing properly, because the phrase is on marketing pages and candidates repeat it.

Consider the smallest possible unit: a consumer reads a message, calls the vendor, and acknowledges. Three things must happen in a fixed order across two machines connected by a network that can drop packets at any instant. Now the consumer calls the vendor and the connection dies before the response arrives. The consumer has no way to know whether the badge was created. It has exactly two options: assume it worked (risk losing the badge) or try again (risk creating two). There is no third option, because the information needed to choose does not exist anywhere in the consumer's process. This is the same impossibility as the Two Generals problem, and no broker feature changes it — the uncertainty is in the side effect, which the broker cannot see.

Interviewers ask

“Kafka advertises exactly-once semantics. What does it actually give you?” Kafka's EOS is real but narrow: with an idempotent producer (sequence numbers per partition, so a retried produce is deduplicated by the broker) and transactions, a consume → transform → produce pipeline that stays inside Kafka can atomically commit its output messages and its input offsets. That covers stream processing — reading access.events and writing a rollup topic. It does not cover calling somebody else's HTTP API, writing to Postgres, or sending an email, because those systems are not participants in Kafka's transaction. So: exactly-once inside Kafka, effectively-once at the edges. Say it in those words.

What people mean when they claim exactly-once is one of exactly two designs:

Design AIdempotent consumer

Deliver at-least-once and make the second delivery a no-op, using a deduplication key derived from the message. Cheap, universal, works against any third party. This is what BadgeDesk does.

Design BTransactional processing

Put the side effect and the offset commit in one transaction. Only possible when both live in the same transactional system — Kafka-to-Kafka, or “write to Postgres and store the offset in the same Postgres transaction”. Elegant, and rarely available.

Idempotent consumers, for real

Idempotent means: applying the operation twice produces the same state as applying it once. Note that this is a property of the whole path, not of your function. If the vendor creates a second badge, your handler being pure does not help. So there are two layers, and you need both.

-- The consumer-side dedupe ledger. One row per (group, message) ever seen.

badgedesk/provisioning_worker/idempotency.py
import psycopg
from datetime import datetime, timedelta, timezone
from psycopg.errors import UniqueViolation

GROUP = "badge-provisioners"
LEASE = timedelta(minutes=5)          # longer than the worst vendor timeout

class Duplicate(Exception):
    """This message is already done, or in flight somewhere else."""

def _lease_live(claimed_at: datetime) -> bool:
    return datetime.now(timezone.utc) - claimed_at < LEASE

def claim(conn: psycopg.Connection, message_id: str) -> None:
    """Take ownership of a message, or raise Duplicate.

    Committed on its own, BEFORE the vendor call - never hold a Postgres
    transaction open across a 30-second third-party HTTP request.
    """
    with conn.transaction():
        try:
            conn.execute(
                "INSERT INTO processed_messages (consumer_group, message_id, status)"
                " VALUES (%s, %s, 'in_progress')",
                (GROUP, message_id),
            )
        except UniqueViolation:
            row = conn.execute(
                "SELECT status, claimed_at FROM processed_messages"
                " WHERE consumer_group = %s AND message_id = %s FOR UPDATE",
                (GROUP, message_id),
            ).fetchone()
            status, claimed_at = row
            if status == "done":
                raise Duplicate(message_id)          # the normal, boring case
            # 'in_progress' means a previous attempt died mid-flight. Only
            # retry once the lease has expired, or two pods race the vendor.
            if _lease_live(claimed_at):
                raise Duplicate(message_id)          # someone else owns it now
            conn.execute(
                "UPDATE processed_messages SET status = 'in_progress',"
                " attempts = attempts + 1, claimed_at = now()"
                " WHERE consumer_group = %s AND message_id = %s",
                (GROUP, message_id),
            )

def finish(conn, message_id: str, status: str = "done") -> None:
    conn.execute(
        "UPDATE processed_messages SET status = %s, finished_at = now()"
        " WHERE consumer_group = %s AND message_id = %s",
        (status, GROUP, message_id),
    )
    conn.commit()

        claim(conn, event["id"])

Red pencil — three ways this goes wrong

1. Deduplicating on the offset. The Kafka offset identifies a position in a partition, not a business fact. Replay the topic into a new consumer group, or re-publish after a bug fix, and every offset is different while every event is the same. Deduplicate on an id the producer generated and put in the envelope. 2. Redis as the only ledger. Redis is a cache: it evicts under memory pressure and a non-persisted restart loses every key, which re-opens the duplicate window exactly when you are already having a bad day. Use Redis for cheap, high-volume, low-stakes dedupe; use Postgres when a duplicate costs money or a physical badge. 3. Checking then acting. if not exists: insert across two statements is a race between two consumer pods. Let the unique constraint decide — insert and catch the violation.

Ordering, and what it costs

Ordering is available, narrow and expensive, and candidates consistently over-buy it. A broker can promise you order within one sequence and nothing more. Kafka's sequence is a partition; RabbitMQ's is a single queue with a single consumer and no requeues.

What ordering costs, concretely:

  • A throughput ceiling per sequence. If all BLR-01 messages must be ordered, they go to one partition, which one consumer thread handles. That site's throughput is now one worker's throughput no matter how many pods you run.
  • Head-of-line blocking. One message that takes 30 seconds, or one poison message being retried, delays every later message for that key. In an ordered queue, a stuck message is an outage for everything behind it.
  • It breaks anyway on retry. Send message A to a dead-letter queue and retry it 16 seconds later and it now arrives after B and C. Any retry ladder plus strict ordering is a contradiction; you get to keep one.

The senior move is to design the consumer so ordering does not matter: make the operations commutative, or carry a version and reject stale updates. Then order becomes a nice-to-have instead of a constraint.

Backpressure and consumer lag

A broker turns a latency problem into a queue-depth problem, and queue depth is the single most useful metric you will ever alarm on. Consumer lag is the log end offset minus the committed offset: how many messages have been published that this group has not finished. Its derivative is what matters — lag of 40 000 that is falling is fine; lag of 900 that is rising is an incident.

In production

The alarm that matters is not “lag > N”, it is “lag is rising for 10 minutes” or, better, time-based lag: how old is the oldest unprocessed message. “We are 14 minutes behind” is a sentence an incident commander can act on; “lag is 41 902” is not, because nobody knows the drain rate. Kafka exposes records-lag-max per consumer; MSK publishes MaxOffsetLag to CloudWatch, where you wire the alarm in Sheet 07. Alarm on lag and on consumer heartbeat — a group with zero lag because every consumer is dead looks perfectly healthy on a lag graph.

Dead letters and the retry ladder

A poison message is one that will never succeed: malformed JSON, a site_id the vendor has never heard of, a schema the consumer cannot parse. Retrying it forever is the classic messaging outage — the consumer never advances, lag climbs to infinity, and the topic stops being processed because of one bad row. The fix is a bounded retry ladder and a terminal destination.

badgedesk/provisioning_worker/retry.py
import random, time, httpx

TRANSIENT = (httpx.TimeoutException, httpx.ConnectError)
MAX_ATTEMPTS, BASE, CAP = 3, 1.0, 60.0

class Permanent(Exception):
    """Do not retry this - straight to the dead-letter topic."""

def backoff(attempt: int) -> float:
    """Full jitter. attempt is 0-based: ~1 s, ~2 s, ~4 s ... capped at 60 s."""
    return min(CAP, BASE * 2 ** attempt) * random.uniform(0.5, 1.5)

def with_retries(fn, *args):
    for attempt in range(MAX_ATTEMPTS):
        try:
            return fn(*args)
        except httpx.HTTPStatusError as e:
            code = e.response.status_code
            if code in (400, 404, 409, 422):        # the vendor says never
                raise Permanent(f"vendor rejected: {code} {e.response.text[:120]}")
            if code == 429:                          # respect their backpressure
                time.sleep(float(e.response.headers.get("Retry-After", 5)))
                continue
            if code < 500:
                raise Permanent(f"unexpected 4xx: {code}")
        except TRANSIENT:
            pass                                     # fall through to the sleep
        if attempt < MAX_ATTEMPTS - 1:
            time.sleep(backoff(attempt))
    raise Permanent(f"still failing after {MAX_ATTEMPTS} attempts")
Red pencil

Two mistakes, both common. Retrying in-process for 21 seconds blocks the partition. Every message behind this one waits, and if the total exceeds max.poll.interval.ms Kafka decides your consumer is dead and rebalances the group out from under you. For anything longer than a couple of seconds, do not sleep — re-publish to a delay topic (or a RabbitMQ TTL queue) and commit the offset. A dead-letter topic nobody reads is a data-loss bug with extra steps. Alarm on badge.requests.dlq having any messages at all, store the original message plus the exception, the stack, the attempt count and the consumer version alongside it, and build the replay tool in the same week you build the DLQ — not after the first incident.

The dual-write problem and the transactional outbox

This is the highest-value topic on the sheet for an SE3 interview, because it is the exact point where “I have used Kafka” separates from “I have designed with Kafka”.

Your handler must do two things: commit a row to Postgres and publish an event to Kafka. Two systems, two networks, no shared transaction. There is no ordering of those two operations that is safe, because the process can die between them — and a distributed transaction across Postgres and Kafka is not a real option (two-phase commit needs both to support it, and it converts two independent availability numbers into one worse one).

import json, time
from confluent_kafka import Producer

producer = Producer({
    "bootstrap.servers": "localhost:9092",
    "acks": "all",                 # every in-sync replica, or it did not happen
    "enable.idempotence": True,    # broker dedupes the producer's own retries
    "linger.ms": 20,               # small batching window: fewer, bigger requests
    "compression.type": "zstd",
})

BATCH = 200

def relay_once(conn) -> int:
    rows = conn.execute(
        "SELECT id, topic, partition_key, event_type, payload, occurred_at"
        "  FROM outbox WHERE sent_at IS NULL"
        "  ORDER BY occurred_at"
        "  LIMIT %s"
        "  FOR UPDATE SKIP LOCKED",   # two relay pods never fight over a row
        (BATCH,),
    ).fetchall()

    for row in rows:
        event_id, topic, key, etype, payload, occurred_at = row
        envelope = {
            "id": str(event_id), "type": etype, "version": 1,
            "occurred_at": occurred_at.isoformat(), "producer": "core",
            "payload": payload,
        }
        producer.produce(
            topic=topic,
            key=key.encode(),                     # ordering + partition placement
            value=json.dumps(envelope).encode(),
            headers=[("event-id", str(event_id)), ("event-type", etype)],
        )
    producer.flush(10)                            # block until brokers acked
    if rows:
        conn.execute("UPDATE outbox SET sent_at = now() WHERE id = ANY(%s)",
                     ([r[0] for r in rows],))
    conn.commit()
    return len(rows)

if __name__ == "__main__":

Interviewers ask

“Doesn't the outbox just move the dual write into the relay?” Yes — and that is the point. The relay's two steps are publish then mark sent, and a crash between them causes a duplicate publish, never a lost event. You have converted an unbounded, invisible, unrecoverable failure (event lost forever, nobody knows) into a bounded, well-understood one (event published twice, handled by the idempotent consumer you already built). Trading loss for duplication is almost always the right trade, because duplication is detectable and loss is not. Follow-up they will ask: “how do you avoid polling?” — Debezium tails the Postgres write-ahead log and publishes outbox inserts with no polling at all, at the cost of running Kafka Connect.

Apache Kafka

The one to learn first. Not because it is simpler — it is not — but because it is free to run locally, it is what the job descriptions ask for, and its model forces you to understand partitions, offsets and consumer groups, which transfer to everything else.

It is a commit log, not a queue

Kafka is a distributed, partitioned, replicated, append-only commit log. Read that as four promises. Append-only: you cannot modify or delete a message, only append. Partitioned: a topic is split into independent logs so it can exceed one machine. Replicated: each partition exists on several brokers. Distributed: those brokers form a cluster with no single writer.

The consequence that changes how you design: reading does not remove anything. A consumer holds a cursor — an offset — and Kafka's only job is to remember where each group's cursor is. Messages leave because retention expires, never because somebody read them. That is why Kafka can do things a queue cannot: add a new consumer group next year and it can read the last seven days from the beginning; a consumer with a bug can be fixed, its offsets reset, and the day replayed.

Brokers, the cluster and KRaft

A broker is one Kafka server process holding some partition replicas on local disk. A cluster is several brokers that agree on metadata: which topics exist, how many partitions each has, and which broker leads each partition. Clients bootstrap by connecting to any broker, asking for metadata, and then talking directly to the leader of each partition they care about — there is no proxy or load balancer in the data path, which is why advertised.listeners must be an address the client can actually reach. Getting that wrong is the number one “Kafka works in the container but not from my laptop” bug.

Historically that metadata lived in ZooKeeper. Since Kafka 3.3 it lives in Kafka itself via KRaft, a Raft quorum of controller nodes. For interviews: know that ZooKeeper is gone, that KRaft removes a whole separate system to operate, and that it made metadata operations and failover materially faster. For the local setup below it means one container instead of two.

Partitions: parallelism, ordering, and the key decision

A partition is simultaneously the unit of parallelism (one partition is consumed by at most one member of a group) and the unit of ordering (records in a partition are strictly ordered by offset; records in different partitions have no defined relative order). Those two facts pull against each other, and resolving the tension is what the partition key is for.

The producer chooses the partition: hash(key) mod partition_count when a key is present, sticky round-robin when it is not. So all records with the same key land in the same partition and are therefore ordered relative to each other. That is the entire mechanism, and every design question about Kafka ordering is really “what did you pick as the key?”

Why BadgeDesk keys on site_id

What it buys: all requests for BLR-01 are processed in submission order by one consumer, so a revoke that follows a grant can never overtake it. It also means one worker holds one site's vendor session and can batch calls per site, and it makes the vendor's own per-site rate limit easy to respect — only one consumer is ever hitting a given site's endpoint. What it costs: one site's throughput is capped at one consumer, and BadgeDesk's traffic is skewed (BLR-01 has 4 000 employees, HYD-01 has 60), so partitions are unevenly loaded — a hot partition. If a single site ever outgrows one consumer, the fix is a composite key such as site_id:employee_id, which restores parallelism and gives up cross-employee ordering within a site. Keying on request_id would spread load perfectly and give up ordering entirely, which is fine only if the consumer is version-aware as in the ordering section.

Red pencil

You can add partitions to a topic but never remove them, and adding them breaks key-to-partition affinity: hash("BLR-01") mod 3 and mod 6 are different partitions, so in-flight ordering for existing keys is lost at the moment you expand and old records stay where they were. Plan partition count up front — a common rule is target throughput divided by per-consumer throughput, then double it for headroom, then check that you are not creating tens of thousands of partitions per cluster. Also: no key means no ordering and no idempotency by key. Producing badge.requests with key=None is a bug that will not show up until two requests for one site race.

Replication, leaders, followers and the ISR

Each partition has a replication factor. One replica is the leader and serves all reads and writes; the others are followers that continuously fetch from the leader. Followers that are caught up form the in-sync replica set (ISR). A write acknowledged with acks=all is on disk on every member of the ISR — and min.insync.replicas sets how small the ISR may get before the leader refuses writes altogether.

Consumer groups and offset commits

A consumer group is identified by group.id, and Kafka guarantees each partition is assigned to exactly one member. The group's committed offsets live in the internal __consumer_offsets topic — which is why offsets survive a pod restart and why two groups reading one topic are completely independent. Same topic, different group.id means fan-out; same group.id means a work queue. That one string is the switch between the two shapes in Drawing 11-B.

How you commit decides your delivery guarantee, exactly as drawn in Drawing 11-C:

  • Auto-commit (enable.auto.commit=true, every 5 s by default) commits offsets for records that poll() has returned to you, whether or not you finished with them. Crash mid-batch and you skip whatever was polled but unprocessed — silent loss. It is also deceptively fine in testing, because a clean shutdown commits.
  • Manual commit after processing (enable.auto.commit=false then commit(msg)) means a crash re-delivers the last batch — duplicates, which you have already made harmless. Note that commit(message=msg) in confluent-kafka commits msg.offset() + 1: the committed offset is the next record to read, not the last one read. Off-by-one here re-processes or skips one message per restart forever.
  • Synchronous or asynchronous. commit(asynchronous=False) costs a round trip per batch and is what you want while learning. In production, commit asynchronously per batch and synchronously once in on_revoke and at shutdown.

Rebalancing — and why yours fired at 3 a.m.

When a member joins, leaves, dies or the partition count changes, the group coordinator reassigns partitions. With the legacy eager assignor the whole group stops consuming for the duration — “stop the world”. The cooperative-sticky assignor revokes only what must move.

Red pencil

Two rebalance traps that cost real incidents. The retry loop that looks like a dead consumer: the 21-second retry ladder from Drawing 11-E plus a 500-record batch is 3 hours between poll() calls. Kafka evicts you, another pod picks up the same partition, both call the vendor, and you get duplicate badges plus an endless rebalance storm. The rolling deploy that rebalances n times: without group.instance.id (static membership) every pod restart triggers a full leave-and-rejoin, so a 6-pod rolling update causes twelve rebalances and a few minutes of stalled consumption. Also always call consumer.close() on SIGTERM — it commits and leaves the group cleanly, turning a 45-second session timeout into an instant reassignment.

Retention and log compaction

Kafka deletes by policy, not by consumption. retention.ms (default 7 days) and retention.bytes delete whole log segments once either limit is exceeded — so a size cap can quietly evict data far younger than your time cap, which is how “we have 30 days of history” becomes 6 hours on a busy topic. cleanup.policy=compact is the other mode: keep the most recent value for every key, forever.

Schema evolution and why a registry exists

A topic is an API with a much longer memory than an HTTP endpoint. A record written today may be read next month by a consumer you have not written, and by a replay of a consumer version you deleted. So the schema is a contract with two directions, and the words matter in interviews:

  • Backward compatible — a new consumer can read old records. Achieved by adding optional fields with defaults. This is the change you make most often.
  • Forward compatible — an old consumer can read new records. Achieved by never removing or renaming a field an old consumer requires, and by consumers ignoring unknown fields.
  • Full — both. What you want on badge.requests, because you cannot deploy the producer and every consumer at the same instant, and because replay makes both directions live at once.

A schema registry (Confluent's, or Apicurio) stores versioned Avro/Protobuf/JSON schemas, gives each one an id that the producer stamps into the first bytes of every message, and rejects a producer whose new schema breaks the configured compatibility rule. That last clause is the real product: it turns “someone renamed a field and the reconciler silently stopped matching rows” into a failed CI build. It also shrinks messages, because the schema is not repeated in every payload the way JSON keys are. For Week 11, produce JSON with an explicit version field in the envelope and treat the registry as a concept you can explain; adding it is Week 12 work if you have time.

badgedesk/provisioning_worker/consumer.py
import json, logging, os, signal, socket
from confluent_kafka import Consumer, Producer, KafkaError, KafkaException, TopicPartition

from .handler import provision
from .retry import Permanent, with_retries

log = logging.getLogger("provisioning-worker")
BROKERS = os.environ["KAFKA_BOOTSTRAP"]          # localhost:9092
TOPIC, DLQ, DONE = "badge.requests", "badge.requests.dlq", "badge.provisioned"

consumer = Consumer({
    "bootstrap.servers": BROKERS,
    "group.id": "badge-provisioners",
    "enable.auto.commit": False,                 # we commit, deliberately
    "auto.offset.reset": "earliest",             # a brand-new group reads history
    "partition.assignment.strategy": "cooperative-sticky",
    "max.poll.interval.ms": 300_000,             # must exceed worst-case handling
    "session.timeout.ms": 45_000,
    "max.poll.records": 50,                      # small batches - see the trap above
    "group.instance.id": os.environ.get("POD_NAME", socket.gethostname()),
})

producer = Producer({
    "bootstrap.servers": BROKERS,
    "acks": "all",
    "enable.idempotence": True,
    "max.in.flight.requests.per.connection": 5,
})

running = True
def stop(signum, frame):
    global running
    running = False                              # finish the message, then leave
signal.signal(signal.SIGTERM, stop)
signal.signal(signal.SIGINT, stop)

def dead_letter(msg, reason: str, attempts: int) -> None:
    """Keep the original bytes. Put the diagnosis in the headers."""
    producer.produce(
        topic=DLQ,
        key=msg.key(),
        value=msg.value(),                       # never a reformatted version
        headers=[
            ("dlq-reason",   reason[:512]),
            ("dlq-attempts", str(attempts)),
            ("src-topic",    msg.topic()),
            ("src-partition", str(msg.partition())),
            ("src-offset",   str(msg.offset())),
            ("worker-version", os.environ.get("GIT_SHA", "dev")),
        ],
    )
    producer.flush(10)
    log.error("dead-lettered %s@%s: %s", msg.partition(), msg.offset(), reason)

def on_revoke(c, partitions):
    """Called before partitions are taken away. Last chance to commit."""
    log.warning("revoking %s", [p.partition for p in partitions])
    try:
        c.commit(asynchronous=False)
    except KafkaException as e:
        log.warning("commit during revoke failed (expected on eviction): %s", e)

def run(conn):
    consumer.subscribe([TOPIC], on_revoke=on_revoke)
    while running:
        msg = consumer.poll(1.0)
        if msg is None:
            continue
        if msg.error():
            if msg.error().code() == KafkaError._PARTITION_EOF:
                continue
            raise KafkaException(msg.error())

        # 1. Parse. Unparseable bytes can never succeed -> straight to the DLQ.
        try:
            event = json.loads(msg.value())
            event_id = event["id"]
        except (json.JSONDecodeError, KeyError, TypeError) as e:
            dead_letter(msg, f"unparseable envelope: {e}", attempts=1)
            consumer.commit(msg, asynchronous=False)
            continue

        # 2. Do the work. with_retries handles 429/5xx; Permanent means stop.
        try:
            badge_id = with_retries(provision, conn, event)
        except Permanent as e:
            dead_letter(msg, str(e), attempts=3)
            consumer.commit(msg, asynchronous=False)   # poison message, move on
            continue
        except Exception:
            # Unknown failure: do NOT commit. Rewind so this partition retries
            # from here on the next poll instead of skipping the record.
            log.exception("unhandled failure at %s@%s", msg.partition(), msg.offset())
            consumer.seek(TopicPartition(msg.topic(), msg.partition(), msg.offset()))
            continue

        # 3. Publish the result, keyed the same way so ordering is preserved.
        if badge_id != "skipped-duplicate":
            producer.produce(
                topic=DONE,
                key=msg.key(),
                value=json.dumps({
                    "id": event_id, "type": "badge.provisioned", "version": 1,
                    "producer": "provisioning-worker",
                    "payload": {"request_id": event["payload"]["request_id"],
                                "site_id": event["payload"]["site_id"],
                                "badge_id": badge_id},
                }).encode(),
            )
            producer.flush(10)                   # durable BEFORE we commit

        # 4. Commit last. commit(message=msg) stores msg.offset() + 1.
        consumer.commit(msg, asynchronous=False)

    consumer.close()                             # commits + leaves the group now
    producer.flush(15)
In production

Step 3 before step 4 is not stylistic. Publishing badge.provisioned and committing the input offset are a dual write, so the order decides which way it fails: publish-then-commit can duplicate the output event (harmless — the notifier is idempotent), while commit-then-publish can lose it entirely (an employee whose badge exists but who is never told). Always order the two so that the failure is a duplicate. For a strictly Kafka-to-Kafka stage you can instead use a Kafka transaction and make both atomic; the moment a vendor HTTP call is in the middle, you are back to ordering the writes by hand.

RabbitMQ

A message broker built around routing rather than storage. Where Kafka asks “which partition does this key belong to?”, RabbitMQ asks “which of my queues should get a copy of this, and under what conditions?” — and answers it with far more flexibility than Kafka can.

The AMQP model: exchange, binding, queue

The single most important sentence about RabbitMQ: a producer never publishes to a queue. It publishes to an exchange with a routing key. The exchange consults its bindings and copies the message into zero, one or many queues. Consumers subscribe to queues. Nothing else in RabbitMQ makes sense until that is automatic.

This is the thing that trips up engineers whose model came from SQS, where you send to a queue URL and that is the whole story. In RabbitMQ, publishing to a routing key with no matching binding is not an error — the message is silently dropped. Zero consumers, zero errors, zero messages. Set mandatory=True and handle the return, or you will debug this for an afternoon.

Acknowledgements and prefetch

RabbitMQ pushes messages to consumers, which is the opposite of Kafka's pull model and the source of both its low latency and its fairness problems. A message is delivered, marked unacknowledged, and held in memory until the consumer sends basic.ack (done), basic.nack/basic.reject (failed — requeue or dead-letter), or dies (the channel closes and every unacknowledged message is requeued automatically). That last behaviour is genuinely excellent: crash a consumer mid-message and the message goes back, at-least-once, with no work from you.

Prefetch (basic_qos(prefetch_count=n)) is how many unacknowledged messages one consumer may hold. The default in most clients is unlimited, and that is a trap:

Red pencil — unbounded prefetch

With no prefetch limit, RabbitMQ shovels the entire queue at whichever consumer connected first. It now holds 80 000 messages in memory, the two other consumers sit idle with nothing to do, and if the greedy one dies you re-deliver 80 000 messages at once. You have accidentally rebuilt a single-threaded consumer with extra latency and a memory leak. Set prefetch_count to roughly (target throughput × processing time) and no higher — for a 30-second vendor call, that is a small number like 10–20, not 1 000. Prefetch 1 is maximally fair and maximally slow (a round trip per message); it is the right choice only when per-message work is long and uneven, which is exactly BadgeDesk's provisioning case.

Durability: three switches, all required

“My messages disappeared when RabbitMQ restarted” is always one of these three being off. They are independent and you need all of them:

  • Durable queue (durable=True) — the queue definition survives a broker restart. Without it the queue itself is gone, along with everything in it.
  • Persistent message (delivery_mode=2) — this individual message is written to disk. A persistent message in a non-durable queue is still lost, and a transient message in a durable queue is still lost. Both, or neither works.
  • Publisher confirms (confirm_delivery()) — the broker tells you it accepted and persisted the message. Without confirms, basic_publish is fire-and-forget over TCP: it returns successfully even when the broker never received the bytes. This is RabbitMQ's acks=all.

Note the cost, because interviewers ask: persistence plus confirms means an fsync in the publish path, which typically takes RabbitMQ from tens of thousands of messages per second to a few thousand. That is still far more than BadgeDesk needs, and the trade is obviously correct for a badge request. It is obviously wrong for telemetry.

Dead-letter exchanges and delayed retry

RabbitMQ has no native “retry this in 5 seconds”. What it has is a queue-level TTL plus a dead-letter exchange, and the composition of those two is the delay mechanism. A message that expires in a TTL queue is dead-lettered onward — so a queue with a 5-second TTL whose dead-letter exchange routes back to the main queue is a 5-second delay line.

Priority queues and quorum queues

Priority queues (x-max-priority) let a message jump the line — genuinely useful and something Kafka simply cannot do, because a log has one order. In BadgeDesk, an emergency revoke (a departing employee's badge) should overtake 3 000 routine grants. The caveats: priority applies only to messages sitting in the queue, so a message already prefetched by a consumer cannot be overtaken (keep prefetch small if priority matters), and a permanently busy high-priority stream starves the low one.

Quorum queues are the modern replicated queue type, using Raft, and are the default choice for anything that must survive a node loss; classic mirrored queues are deprecated. One sentence for an interview: “quorum queues replicate via Raft and trade a little throughput for correct failover, and they are what you should use in production.”

from .retry import Permanent

conn = pika.BlockingConnection(params)
ch = conn.channel()

# --- topology. Declaring is idempotent, so every service declares what it needs.
ch.exchange_declare("x.badge",     exchange_type="topic",  durable=True)
ch.exchange_declare("x.badge.dlx", exchange_type="fanout", durable=True)

ch.queue_declare("q.badge.provision", durable=True, arguments={
    "x-dead-letter-exchange": "x.badge.dlx",     # where rejections go
    "x-max-priority": 5,                          # emergency revokes jump the line
})
ch.queue_bind("q.badge.provision", "x.badge", routing_key="badge.request.#")

ch.queue_declare("q.badge.retry.5s", durable=True, arguments={
    "x-message-ttl": 5_000,                       # expire after 5 s ...
    "x-dead-letter-exchange": "x.badge",          # ... then re-enter the main flow
    "x-dead-letter-routing-key": "badge.request.retry",
})
ch.queue_bind("q.badge.retry.5s", "x.badge.dlx")

ch.queue_declare("q.badge.parked", durable=True)   # terminal. Nobody consumes it.

# --- fairness. Without this, one consumer takes the whole queue.
ch.basic_qos(prefetch_count=20)

def deaths(props) -> int:
    """RabbitMQ appends an x-death entry every time a message is dead-lettered."""
    entries = (props.headers or {}).get("x-death", [])
    return sum(e.get("count", 0) for e in entries)

def on_message(channel, method, props, body):
    try:
        event = json.loads(body)
    except json.JSONDecodeError:
        channel.basic_publish("", "q.badge.parked", body)   # unparseable: park it
        channel.basic_ack(method.delivery_tag)
        return

    try:
        provision(get_conn(), event)                         # idempotent - see above
    except Permanent:
        channel.basic_publish("", "q.badge.parked", body)
        channel.basic_ack(method.delivery_tag)               # ack: do not requeue
        return
    except Exception:
        if deaths(props) >= 3:
            channel.basic_publish("", "q.badge.parked", body)
            channel.basic_ack(method.delivery_tag)
        else:
            # requeue=False sends it to the DLX -> retry.5s -> back here in 5 s.
            # requeue=True would spin at full CPU forever. Never do that.
            channel.basic_nack(method.delivery_tag, requeue=False)
        return

    channel.basic_ack(method.delivery_tag)                   # commit last, as ever

Designing an event

The broker is the easy part. The message is the API, and unlike an HTTP endpoint you cannot deprecate it on Friday — a consumer replaying last month's data is still calling last month's version.

Naming

Three rules, and they are not cosmetic. Past tense for events (badge.requested, badge.provisioned, badge.revoked) because an event is a fact that already happened and cannot be rejected. Domain first, then the thing, then what happened — badge.request.created sorts and wildcard-matches sensibly, while created_badge_request does not. Never name a topic after a consumer. The moment you create notifier.inbox you have coupled the producer to today's consumer list, and the second reader has nowhere to go.

The envelope

Split every message into a fixed envelope that every consumer and every piece of infrastructure can read without knowing the domain, and a payload that only the domain cares about. Then generic tooling — logging, tracing, dead-letter inspectors, replay tools — works for every topic you will ever add.

Event-carrying state transfer versus thin events

Thin event — a notification

{"type":"badge.requested","payload":{"request_id":"req-1"}}

Consumer must call back to GET /access-requests/req-1 for the details. Small messages, no duplicated schema, and the consumer always sees current state.

Cost: you have reintroduced the synchronous coupling you removed. If core is down, the worker cannot process anything — a message it already holds is useless. Plus one HTTP call per message, so 4 000 messages is 4 000 calls, and a replay hammers the API. And the state you fetch is now, not then: a request cancelled since publication reads back as cancelled, which may be right or may hide a bug.

Event-carrying state transfer

The full payload above — employee, site, dates, reason, approver.

Consumer needs nobody. It can provision a badge from the message alone, so it works while core is being deployed, and replay reproduces exactly what was true at the time.

Cost: bigger messages, the schema is now duplicated in every consumer, and the data is a snapshot that can be stale by the time it is read. You need a version field and a rule for what wins.

Default to this for BadgeDesk: the whole point of the seam is that the worker survives core being unavailable. Use thin events only for large payloads — a badge photo goes to S3 and the message carries the key, never the bytes.

Versioning without breaking consumers

You cannot deploy every consumer at once, and replay means old and new payloads coexist forever. So the rules are strict and simple:

  • Additive changes only. Add optional fields with defaults. Never rename, never remove, never change a type, never repurpose a field's meaning — that last one is the worst because nothing breaks loudly.
  • Tolerant reader. Consumers ignore unknown fields. In Pydantic that is the default; make sure you have not set extra="forbid" on an event model, which turns every future producer change into an outage.
  • A breaking change is a new event type or a new topic — badge.requested.v2 or type: "badge.requested" with version: 3 — and the producer emits both for one retention period while consumers migrate. Then you delete the old one, having checked the metric that counts consumption of v1 rather than having asked people.
badgedesk/provisioning_worker/schema.py — a tolerant, versioned reader
from pydantic import BaseModel, Field, ConfigDict

class RequestedV1(BaseModel):
    model_config = ConfigDict(extra="ignore")     # tolerant reader, on purpose
    request_id: str
    employee_id: str
    site_id: str
    starts_on: str
    ends_on: str

class RequestedV2(RequestedV1):
    # v2 added the approval block. Optional, so v1 messages still parse.
    approval: dict | None = None
    reason: str = ""

HANDLERS = {1: RequestedV1, 2: RequestedV2}

def parse(envelope: dict) -> RequestedV1:
    version = envelope.get("version", 1)
    model = HANDLERS.get(version)
    if model is None:
        # A version from the future. Do not guess - park it and alarm.
        raise Permanent(f"unknown envelope version {version}")
    return model.model_validate(envelope["payload"])
Events versus commands — and why mixing them couples services

An event is a statement about the past: badge.provisioned. It has no intended recipient, it cannot be refused, and the publisher does not care who listens or what they do. A command is an instruction for the future: provision this badge. It has exactly one intended handler, it can be rejected, and the sender usually wants to know the outcome. Both travel over the same broker, which is why they get muddled.

The coupling appears the moment you publish a command dressed as an event. If core emits send_teams_message, then core now knows that Teams exists, that the notifier handles it, and that a message should be sent at all — three pieces of downstream knowledge that should not be in the request service. Change the notification policy and you redeploy core. Publish badge.provisioned instead and the notifier decides what to do with it, the reconciler decides separately, and a fourth consumer next year needs no change anywhere upstream.

Commands are still legitimate — badge.requests is honestly a command topic, one producer and one logical handler, and pretending otherwise is worse than naming it accurately. The rule is: commands go to one owner you already depend on; events are broadcast to whoever cares. If you find yourself adding a target_service field, you have written a command and should stop calling it an event.

Drill — messaging fundamentals
Why not just call the vendor API directly from the request handler?

Because their p99 is 30 seconds and 2% of calls fail, and a synchronous call makes those numbers my availability numbers. Every worker in the API is parked on their socket, so their slow day is my outage; and when the call fails the transaction rolls back and the request a human typed is gone with no retry and no record. Writing a row plus an event and returning 202 in 40 ms means the intent is durable in a system I operate, and a background consumer absorbs their latency with retries and a dead-letter topic. The cost is honest: the API now promises the badge will exist, not that it does, so the contract needs 202, a Location to poll, and a real state machine.

At-least-once versus exactly-once — which do you build, and why?

At-least-once, always, plus an idempotent consumer. At-most-once loses messages silently on any crash, which is unacceptable for a badge request. End-to-end exactly-once delivery does not exist: if the network dies after I call the vendor but before the response arrives, I cannot know whether the badge was created, so I must either risk losing it or risk duplicating it. Kafka's exactly-once semantics are real but only cover consume-transform-produce inside Kafka, using the idempotent producer and transactions — they cannot include a third-party HTTP call. So I deliver at-least-once and make the second delivery a no-op, which gives exactly-once effect.

How do you make a consumer idempotent?

Two layers. Mine: a processed_messages table keyed on (consumer_group, message_id) where message_id is the producer-generated envelope id, never the offset. I insert a claim row and let the unique constraint reject the duplicate — never check-then-act, which races between pods. Theirs: an Idempotency-Key header on the vendor call so their side collapses my retries onto one badge. The subtlety is a crash between the claim and the vendor response, which leaves an in_progress row; I use a lease timeout so it can be retried without two pods calling the vendor at once. Redis with SET NX EX works for cheap dedupe, but it evicts and it is not durable, so I use Postgres when a duplicate means a physical badge.

What does the Kafka partition key control?

Three things at once, which is why it is a design decision rather than a config value. Placement: hash(key) mod partitions picks the partition. Ordering: records with the same key are in one partition and therefore strictly ordered relative to each other; across partitions there is no order at all. Distribution: a skewed key gives you a hot partition, whose consumer becomes the bottleneck no matter how many pods you add. BadgeDesk keys on site_id so a revoke can never overtake the grant for the same site and one worker owns a site's vendor session; the cost is that a large site's throughput is capped at one consumer, and the escape hatch is a composite key like site_id:employee_id. Also note you cannot add partitions later without breaking existing key-to-partition affinity.

A consumer dies halfway through a batch. What happens?

Depends entirely on when it committed. With auto-commit, offsets for everything poll() returned may already be committed, so the unprocessed remainder is skipped — silent loss. With manual commit after processing, nothing was committed, so after the session timeout the coordinator reassigns the partition and the new owner re-reads from the last committed offset: every message in that batch is re-delivered, including the ones already done. That is why the handler is idempotent. In RabbitMQ the equivalent is the channel closing, which requeues every unacknowledged message automatically. In both cases the correct fix is not to avoid duplicates but to make them harmless, and to call close() on SIGTERM so a normal deploy commits and leaves the group cleanly instead of waiting out a 45-second timeout.

Why did my consumer group rebalance when I did not deploy anything?

Almost always because a consumer stopped calling poll() for longer than max.poll.interval.ms — usually an in-process retry ladder or one very slow message multiplied by a large max.poll.records. The coordinator declares the member dead, reassigns its partitions, and its eventual commit is rejected, so the work repeats on another pod. Fixes: shrink the batch, move long waits out of the handler by re-publishing to a delay topic instead of sleeping, use the cooperative-sticky assignor so the whole group does not stop, and set group.instance.id for static membership so rolling restarts do not each trigger a full rebalance. The other candidates are a network partition to the coordinator and a broker restart.

Queue or topic — how do you decide?

By asking whether the message is work to be done once or a fact many people may care about. Work goes on a queue with competing consumers: one message, one taker, add consumers for throughput. A fact goes on a topic with independent subscribers: every subscriber gets its own copy and its own position, and adding a subscriber changes nothing for the others. In Kafka both are the same log and the difference is only whether readers share a group.id — which is why getting it wrong is silent. The tell is the name: badge.requests is work, badge.provisioned is a fact. Building a fact as a work queue means two services steal each other's messages and half your notifications disappear intermittently.

What is the outbox pattern, and what problem does it solve?

It solves the dual-write problem: I must commit a row to Postgres and publish an event to Kafka, and there is no shared transaction, so a crash between them leaves the two systems disagreeing with nothing to detect it. Commit-then-publish loses the event; publish-then-commit produces an event for a row that does not exist. So instead I insert the event into an outbox table in the same transaction as the row — both commit or neither does — and a separate relay selects unsent rows with FOR UPDATE SKIP LOCKED, publishes, and marks them sent. The relay still has two steps, but its failure mode is a duplicate publish rather than a lost event, and duplicates are already handled by the idempotent consumer. Log-based CDC with Debezium is the same pattern without polling.

How do you handle a poison message?

Classify first. A permanent failure — unparseable bytes, a 400 or 422 from the vendor, an unknown schema version — can never succeed, so retrying it forever just blocks the partition and drives lag to infinity. It goes straight to badge.requests.dlq with the original bytes untouched plus headers carrying the reason, attempt count, source topic, partition, offset and worker build SHA, and then I commit the offset so the partition advances. A transient failure gets a bounded ladder with exponential backoff and jitter — three attempts, then dead-letter. Two things make this real rather than theatre: an alarm on the DLQ having any depth at all, and a replay script written in the same week, because a dead-letter topic nobody reads is data loss with extra steps.

Kafka or RabbitMQ for BadgeDesk badge provisioning? Defend it.

Kafka, for three specific reasons. Replay: when the provisioning worker has a bug I want to fix it and re-read the last two days, which an acked RabbitMQ message cannot give me. Ordering by key: partitioning on site_id guarantees a revoke never overtakes a grant, which RabbitMQ only achieves with one queue and one consumer. Independent readers: the notifier, the reconciler and later the policy indexer all need the same badge.provisioned stream, and consumer groups make that free. What I give up is real: no per-message priority, so an emergency revoke cannot jump the queue, and no native delayed delivery, so my retry ladder needs a delay topic. If the dominant requirement were complex per-site routing, priorities and delays, RabbitMQ would be the better answer — and if the team had nobody to operate a cluster, managed SQS plus SNS would beat both.
