APIs.

REST, GraphQL and webhooks — the three ways BadgeDesk services talk to each other and to the outside world. The thread running through all three: an API is a promise you make to someone whose code you cannot change. Design is mostly about making promises you can keep while the system underneath changes.

The API is the contract

BadgeDesk has three different API styles, and each one is there for a reason. Being able to say why each boundary uses what it uses is the difference between reciting definitions and designing systems.

1
GraphQL sits at the edge only. A request list screen wants request plus employee name plus site name; a mobile summary wants three fields. Rather than growing a ?include= parameter forever, let the client ask. This is the one place where the client variety justifies the extra machinery.
2
REST between internal services. There are two callers, both ours, and they want boring things: HTTP caching, a URL in a log line, curl in an incident. GraphQL service-to-service buys you nothing here and costs you tooling.
3
Webhooks are inbound because we are not in charge of the timing. A door controller provisions a badge when it provisions it. Polling CCure every thirty seconds to find out would waste 99% of the calls and still be slower.
4
The webhook receiver does almost nothing. Verify the signature, write the event, publish to Kafka, return 202. All real work happens in the worker. If the receiver did the provisioning inline, a slow database would make CCure time out and retry, and now you have duplicates. See Sheet 11.

REST

REST is not “JSON over HTTP”. It is a set of constraints, and the useful ones in practice are: resources have URLs, HTTP verbs mean what they say, and the server does not remember you between calls.

Resources, not remote procedure calls

The most common design mistake is naming URLs after functions. If your endpoints read like method names, you have written RPC and given it a REST-shaped costume.

Do notDoWhy
POST /getAccessRequestsGET /v1/access-requestsA read should be a GET: cacheable, safe to retry, visible in logs and metrics as a read
POST /createRequestPOST /v1/access-requestsThe verb is already in the method. Repeating it in the path adds nothing.
POST /approveRequest?id=42POST /v1/access-requests/42/approveSome operations genuinely are actions. Model them as a sub-resource of the thing they act on.
GET /v1/request/42GET /v1/access-requests/42Collections are plural, consistently. Mixed conventions cost people minutes every day.
GET /v1/employee/1/site/2/requestGET /v1/access-requests?employee_id=1&site_id=2Nest one level at most. Deeper hierarchies encode a relationship that will change.
DELETE /v1/access-requests/42POST /v1/access-requests/42/revokeAudit-relevant records are never really deleted. Say what actually happens.
Why the verbs matter operationally

GET is safe (changes nothing) and idempotent. PUT and DELETE are idempotent but not safe. POST is neither. This is not pedantry — every proxy, CDN, browser, load balancer and retry library in the world reads those properties and acts on them. A GET that mutates data will eventually be fired by a link prefetcher, a crawler or a monitoring probe, and you will have no idea why records changed at 03:00.

Status codes that mean something

Interviewers ask

“What is the difference between 401 and 403?” — 401 means we could not establish who you are: no token, expired token, bad signature; the correct response includes a WWW-Authenticate header and the fix is to authenticate. 403 means we know exactly who you are and you are not allowed; re-authenticating changes nothing. Bonus point: some systems return 404 instead of 403 for resources you may not see, so that the existence of the record is not leaked.

“400 or 422?” — 400 for syntactically broken requests (not valid JSON, a date that is not a date); 422 for well-formed requests that break a business rule (ends_on before starts_on). Plenty of good APIs use 400 for both and that is defensible; what matters is being consistent and saying which you chose.

Idempotency, and why POST needs help

A mobile client submits an access request. The server creates it, then the connection drops before the response arrives. The client retries. Without protection, the employee now has two identical pending requests and an approver has to work out which is real.

services/core/app/api/idempotency.py
import hashlib, json
from fastapi import APIRouter, Header, HTTPException, Response, status

router = APIRouter()
TTL = 60 * 60 * 24            # 24 hours: longer than any client will retry

@router.post("/v1/access-requests", status_code=status.HTTP_201_CREATED)
async def create_access_request(
    payload: AccessRequestCreate,
    response: Response,
    idempotency_key: str | None = Header(default=None, alias="Idempotency-Key"),
    db=Depends(get_db),
    redis=Depends(get_redis),
):
    if idempotency_key is None:
        raise HTTPException(400, "Idempotency-Key header is required")

    # Fingerprint the body too. Reusing one key for a DIFFERENT payload is a
    # client bug, and silently returning the old answer would hide it.
    fingerprint = hashlib.sha256(
        json.dumps(payload.model_dump(mode="json"), sort_keys=True).encode()
    ).hexdigest()
    key = f"idem:{idempotency_key}"

    # SET NX is atomic: exactly one concurrent request can win the claim.
    claimed = await redis.set(
        key, json.dumps({"state": "in-progress", "fp": fingerprint}), nx=True, ex=TTL
    )

    if not claimed:
        stored = json.loads(await redis.get(key))
        if stored["fp"] != fingerprint:
            raise HTTPException(422, "Idempotency-Key reused with a different body")
        if stored["state"] == "in-progress":
            # The first attempt is still running. Tell the client to wait
            # rather than doing the work twice.
            raise HTTPException(409, "request already in progress")
        response.status_code = stored["status"]
        return stored["body"]

    try:
        record = await create_request(db, payload)     # the real work
    except Exception:
        await redis.delete(key)                        # release, so a retry can proceed
        raise

    body = AccessRequestOut.model_validate(record).model_dump(mode="json")
    # Store the response BEFORE returning it. If the process dies here,
    # the retry redoes the work - which is far better than the reverse,
    # where we return a body the client never receives and can never recover.
    await redis.set(key, json.dumps({"state": "done", "status": 201,
                                     "body": body, "fp": fingerprint}), ex=TTL)
    return body
Red pencil

The idempotency key must be generated by the client, once per logical operation, and kept across retries — typically a UUID created when the user taps the button. If the client generates a fresh key on each retry, the mechanism does nothing at all. This is the detail interviewers probe, because it is the one people skip.

Pagination, filtering and sorting

Offset pagination
simple, and wrong at scale
GET /v1/access-requests?limit=50&offset=10000

-- the database must count past 10,000 rows
SELECT * FROM access_requests
ORDER BY created_at DESC
LIMIT 50 OFFSET 10000;

Breaks two ways. It gets slower the deeper you go, because the database walks and discards every skipped row. And if a new request is inserted while the user pages, everything shifts down by one — they see a duplicate on page 2 and miss a row entirely. Fine for an admin screen over a few thousand rows.

Cursor pagination
the one to reach for
GET /v1/access-requests?limit=50
GET /v1/access-requests?limit=50&after=eyJjIjoiMjAyNi0wOC0yN...

-- cursor decodes to (created_at, id); the index does the work
SELECT * FROM access_requests
WHERE (created_at, id) < ('2026-08-27T09:14:02Z', 'ar_7f3a91')
ORDER BY created_at DESC, id DESC
LIMIT 50;

Constant time at any depth, because it seeks straight into the index rather than counting. Stable under inserts. The cost is that you cannot jump to page 47 — which real users never do. Always tie-break on a unique column; created_at alone will skip rows that share a timestamp.

the response envelope — consistent across every collection
{
  "data": [
    { "id": "ar_7f3a91", "employee_id": "e_10422", "site_id": "BLR-01",
      "status": "pending", "starts_on": "2026-09-01", "ends_on": "2026-09-30" }
  ],
  "page": {
    "limit": 50,
    "next": "eyJjIjoiMjAyNi0wOC0yN1QwOToxNDowMloiLCJpIjoiYXJfN2YzYTkxIn0",
    "has_more": true
  }
}

Return the cursor, never a full URL the client must parse, and never a total count on a large table — SELECT count(*) on ten million rows is the query that takes your database down at the worst moment. If the UI needs an approximate figure, use the planner's estimate from pg_class.reltuples and label it as approximate.

Versioning and evolution

The best version is the one you never need. Most changes can be made without a new version at all, if both sides follow one rule: be conservative in what you send, liberal in what you accept.

Safe — ship any timeBackwards compatible

Adding an optional request field with a default. Adding a new field to a response. Adding a new endpoint. Adding a new enum value if clients were told to ignore unknown ones. Relaxing a validation rule.

Breaking — needs a new versionNot compatible

Removing or renaming any response field. Making an optional request field required. Changing a type, including "42" to 42. Changing the meaning of an existing value. Tightening validation. Changing a default.

the deprecation sequence — how the field actually goes away
Week 0   Add the replacement alongside the old field. Both populated. Nothing breaks.
         { "site_id": "BLR-01", "site": { "id": "BLR-01", "name": "Whitefield" } }

Week 1   Announce. Add response headers on every call that touches the old shape:
             Deprecation: true
             Sunset: Wed, 31 Dec 2026 23:59:59 GMT
             Link: <https://badgedesk.example/docs/migrate-site-id>; rel="deprecation"

Week 2+  MEASURE. Log caller identity per deprecated field. You cannot remove
         what you cannot see, and "nobody uses it" is never true.

Month 3  Contact the remaining callers directly. There are always two.

Month 6  Brownout: return 410 Gone for one hour, twice, announced in advance.
         This finds the callers who ignored every email.

Month 7  Remove.

Put the version in the path — /v1/. Header and media-type versioning are more theoretically correct and worse in practice: harder to curl, harder to route at a load balancer, invisible in logs, and impossible to paste into a bug report.

GraphQL

One endpoint, a typed schema, and the client states exactly which fields it wants. It solves a real problem — and it moves several hard problems from the client to your server.

The problem it actually solves

The schema is the contract

services/gateway/src/schema.graphql
enum RequestStatus { PENDING APPROVED REJECTED PROVISIONED REVOKED }

type AccessRequest {
  id:        ID!                 # ! means non-null. The strongest documentation you have.
  status:    RequestStatus!
  startsOn:  Date!
  endsOn:    Date!
  reason:    String!
  employee:  Employee!           # resolved separately - see the N+1 section
  site:      Site!
  approvals: [Approval!]!        # non-null list of non-null items
}

type Site     { id: ID!  name: String!  city: String!  timezone: String! }

type AccessRequestConnection {
  edges:    [AccessRequestEdge!]!
  pageInfo: PageInfo!
}
type AccessRequestEdge { node: AccessRequest!  cursor: String! }
type PageInfo { hasNextPage: Boolean!  endCursor: String }

type Query {
  accessRequest(id: ID!): AccessRequest
  accessRequests(status: RequestStatus, siteId: ID,
                 first: Int = 20, after: String): AccessRequestConnection!
}

# Mutations return a payload type, not a bare object, so that expected
# business failures travel as DATA rather than as top-level errors.
type Mutation {
  approveAccessRequest(input: ApproveInput!): ApproveAccessRequestPayload!
}

input ApproveInput { requestId: ID!  note: String  clientMutationId: String }

union ApproveError = NotFound | NotAuthorised | AlreadyDecided | WindowExpired

type ApproveAccessRequestPayload {
  request: AccessRequest
  errors:  [ApproveError!]!
}
Why mutations return an errors field

GraphQL's top-level errors array is untyped and awkward to handle: it is designed for things going wrong, not for “this request was already approved by someone else”. That is not an exception, it is a normal outcome the UI must render. Putting expected failures in the typed payload means the client gets compile-time knowledge of every case it must handle. Reserve top-level errors for genuine faults.

Resolvers and the N+1 problem

This is the defining GraphQL performance issue, and the question you should expect if GraphQL appears anywhere on your CV.

services/gateway/src/loaders/employee.loader.ts
import DataLoader from 'dataloader';

// One loader instance PER REQUEST. A shared singleton would leak one user's
// data into another user's response through the cache - a real, common bug.
export function createEmployeeLoader(core: CoreClient) {
  return new DataLoader<string, Employee>(async (ids) => {
    const employees = await core.getEmployeesByIds([...ids]);   // one call
    const byId = new Map(employees.map(e => [e.id, e]));

    // CRITICAL: return results in the same order as the requested ids,
    // with a null or Error for misses. DataLoader matches by position.
    return ids.map(id => byId.get(id) ?? new Error(`employee ${id} not found`));
  });
}

@Resolver(() => AccessRequest)
export class AccessRequestResolver {
  @ResolveField(() => Employee)
  employee(@Parent() request: AccessRequest, @Context() ctx: GqlContext) {
    return ctx.loaders.employee.load(request.employeeId);   // batched, deduped
  }
}

Interviewers ask

“Would you use GraphQL for BadgeDesk?” — the answer they want is a decision with a reason attached. Mine: yes at the edge, because a web client and a mobile client want different shapes of the same domain and the alternative is a growing pile of bespoke endpoints; no internally, because there are two known callers and REST gives us caching, plain URLs in logs and curl during an incident. Webhooks

An HTTP callback from a system you do not control. Simple to describe, and full of failure modes that only appear in production.

Push instead of poll

Verifying the signature

services/core/app/api/webhooks.py — every line here matters
import hmac, hashlib, time
from fastapi import APIRouter, Request, Header, HTTPException, status

router = APIRouter()
TOLERANCE = 300      # 5 minutes

@router.post("/webhooks/ccure", status_code=status.HTTP_202_ACCEPTED)
async def receive_ccure_event(
    request: Request,
    signature: str = Header(alias="X-CCure-Signature"),
    delivery_id: str = Header(alias="X-CCure-Delivery"),
    redis=Depends(get_redis),
    producer=Depends(get_kafka_producer),
):
    # 1. The RAW body. Never re-serialise before verifying: a reordered key
    #    or different whitespace produces a different digest, and you will
    #    spend a day on it.
    raw = await request.body()

    # Header format:  t=1756370042,v1=5257a869e7...
    parts = dict(p.split("=", 1) for p in signature.split(","))
    timestamp, provided = parts["t"], parts["v1"]

    # 2. Timestamp check FIRST - a valid old signature is a valid replay.
    if abs(time.time() - int(timestamp)) > TOLERANCE:
        raise HTTPException(400, "signature timestamp outside tolerance")

    expected = hmac.new(
        key=settings.ccure_webhook_secret.encode(),
        msg=f"{timestamp}.".encode() + raw,      # timestamp is INSIDE the digest
        digestmod=hashlib.sha256,
    ).hexdigest()

    # 3. compare_digest, not ==. A normal comparison returns early on the
    #    first differing byte, and that timing difference is enough to
    #    recover the signature byte by byte.
    if not hmac.compare_digest(expected, provided):
        raise HTTPException(401, "invalid signature")

    # 4. Deduplicate. At-least-once delivery means this WILL fire.
    if not await redis.set(f"wh:ccure:{delivery_id}", "1", nx=True, ex=86400):
        return {"status": "duplicate ignored"}       # still a 2xx - do not make it retry

    # 5. Hand off and return. No database writes, no vendor calls, no
    #    email sending on this code path.
    await producer.send("access.provisioned", key=delivery_id, value=raw)
    return {"status": "accepted"}
Red pencil — four ways to get this wrong

Comparing with == leaks the signature through timing. Skipping the timestamp check means a captured request can be replayed forever. Verifying the parsed body rather than the raw bytes fails intermittently and inexplicably. Returning 500 for a duplicate makes the sender retry harder, turning your bug into a self-inflicted denial of service. All four appear in real code; the last two are the ones that get shipped.

How the subtopics connect

One access request, from tap to badge, crossing all three API styles.

In production

Propagate one traceparent header from step 1 and put the trace id in every log line at every step, including the Kafka message headers. When a manager says “I approved this an hour ago and nothing happened”, you paste one id and see exactly which of the ten steps it stopped at. Without it, you are grepping ten services by timestamp. This costs about an hour to add and it is the difference between a five-minute investigation and an afternoon.

Drill book

Answer out loud. If it takes more than 90 seconds, it is not ready.

API design
What actually makes an API RESTful?

The constraints: a uniform interface, statelessness, cacheability, client–server separation, and a layered system. In practice the ones with teeth are that resources have URLs and the HTTP verbs keep their meanings, and that the server holds no client session between calls — which is what lets you put six instances behind a load balancer without sticky sessions. Most “REST” APIs, including good ones, are not fully RESTful because they skip HATEOAS, and that is fine.

Which methods are idempotent, and why does anyone care?

GET, PUT, DELETE, HEAD and OPTIONS are idempotent: doing them twice leaves the same state as doing them once. POST and PATCH are not. It matters because networks fail after the request has arrived but before the response gets back, so retries are unavoidable — and a client library, load balancer or service mesh will retry idempotent methods automatically. For POST you have to supply idempotency yourself with a client-generated key.

Design pagination for ten million access requests.

Cursor-based, on (created_at DESC, id DESC) with a matching composite index, cursor opaque and base64-encoded so clients cannot construct one. Offset pagination degrades linearly with depth and skips or duplicates rows when data is inserted mid-scroll. No total count on a table that size — if the UI needs a figure, use the planner estimate and label it approximate.

How do you version an API without breaking clients?

Prefer not to version: additive changes are safe if clients ignore unknown fields. When a breaking change is unavoidable, add /v2 in the path, run both, and drive migration with Deprecation and Sunset headers plus per-caller metrics on the old shape. Announce, contact the stragglers, run a short brownout returning 410, then remove. Path versioning over header versioning because it survives contact with load balancers, logs and bug reports.

What is the N+1 problem in GraphQL and how do you fix it?

Field resolvers run once per parent object, so a list of twenty requests calls the employee resolver twenty times — twenty-one queries for one screen. The fix is a DataLoader: it collects .load(id) calls made within a single tick of the event loop, deduplicates the ids and issues one batched WHERE id IN (…). Create it per request, never as a singleton, or its cache will leak data between users.

Why is caching harder in GraphQL than REST?

REST caches on the URL, so browsers, CDNs and reverse proxies do it for free. In GraphQL every query is a POST to one URL with the real request in the body, so none of that infrastructure can help. You recover some of it with persisted queries — the client sends a hash, the server holds the text, and it can be a cacheable GET — plus a normalised client cache. That is real work you get for nothing in REST.

Walk through securing an inbound webhook.

Verify an HMAC-SHA256 over the raw body concatenated with the timestamp, using a shared secret, compared in constant time. Reject anything older than about five minutes, so a captured request cannot be replayed. Deduplicate on the provider's delivery id, because delivery is at-least-once. Validate the schema. Then do the minimum — publish to a queue and return 202 — so a slow downstream cannot cause the sender to time out and retry.

A webhook provider says they sent an event and you have no record. What now?

Check their delivery log first for the response we returned: a 4xx means we rejected it and the reason is ours to fix; a 5xx or timeout means we were down and their retries have since expired. That is precisely why the stream is never the only source of truth — a nightly reconciliation job compares our provisioned set against their API and repairs the difference. Then add an alert on the gap so the reconciler finding something is itself a signal.

Should a failed operation ever return HTTP 200?

For REST, no — the status code is the machine-readable outcome, and every proxy, client library, retry policy and dashboard between you and the caller reads it. Returning 200 {"success": false} means your error rate graph is flat during an outage. GraphQL is the documented exception: it returns 200 with an errors array because one response may be partially successful, and that mismatch with HTTP semantics is one of its genuine costs.

How do you rate limit fairly, and what do you return?

Token bucket or sliding window in Redis, keyed by API key or user rather than IP, because IP punishes everyone behind one corporate NAT. Return 429 with Retry-After and the RateLimit-Limit, -Remaining and -Reset headers so a well-behaved client can pace itself instead of hammering. For GraphQL, charge by computed query complexity rather than request count, since one request can be a thousand times more expensive than another.
