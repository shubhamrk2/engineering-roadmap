Data­bases.

PostgreSQL, MongoDB and Redis, plus the relational theory that makes all three make sense. The organising idea: a database is a set of guarantees, and you pick the store whose guarantees match the data. BadgeDesk uses all three because it has three genuinely different kinds of data — not because three is fashionable.

Three stores, three jobs

Every polyglot persistence answer in an interview lives or dies on whether you can justify each store in one sentence. Here are the three sentences.

1
Start relational and stay there until something forces you out. PostgreSQL handles JSON, full-text search, geospatial data, queues and time series adequately. “Adequately” with one store you operate well beats “optimally” across four you operate badly. The burden of proof is on adding a database, not on keeping one.
2
Redis earns its place through atomic primitives, not just speed. SET key value NX EX 86400 in one network round trip is what makes the idempotency scheme on Sheet 05 correct under concurrency. You could do it in Postgres with a unique index — and for BadgeDesk's volume you could argue you should.
3
Mongo is here for genuinely schemaless data. Six controller models, six payload shapes, changing on the vendor's schedule. Note the honest alternative: a jsonb column in Postgres would also work and would remove a whole database from the estate. Be ready to defend the decision either way — that is the actual interview question.

Relational thinking

The schema is the most expensive thing to change and the most valuable thing to get right. Application code is rewritten every few years; the data outlives it.

The BadgeDesk schema

services/core/migrations/0001_initial.sql
CREATE TABLE sites (
  id          text PRIMARY KEY,                    -- 'BLR-01' - natural key, stable
  name        text        NOT NULL,
  city        text        NOT NULL,
  timezone    text        NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()   -- ALWAYS timestamptz, never timestamp
);

CREATE TABLE employees (
  id          text PRIMARY KEY,                    -- 'e_10422' from the HR system
  full_name   text        NOT NULL,
  email       citext      NOT NULL UNIQUE,         -- citext: case-insensitive, still indexed
  manager_id  text        REFERENCES employees(id),-- self-reference, nullable for the CEO
  active      boolean     NOT NULL DEFAULT true,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TYPE request_status AS ENUM
  ('pending','approved','rejected','provisioned','revoked');

CREATE TABLE access_requests (
  id            text PRIMARY KEY,                  -- 'ar_7f3a91'
  employee_id   text NOT NULL REFERENCES employees(id) ON DELETE RESTRICT,
  site_id       text NOT NULL REFERENCES sites(id)     ON DELETE RESTRICT,
  status        request_status NOT NULL DEFAULT 'pending',
  starts_on     date NOT NULL,
  ends_on       date NOT NULL,
  reason        text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),

  -- Constraints are the cheapest tests you will ever write. They hold even
  -- when a migration script, an admin console or a panicking engineer with
  -- psql open is the thing doing the writing.
  CONSTRAINT window_is_sane  CHECK (ends_on >= starts_on),
  CONSTRAINT window_is_short CHECK (ends_on - starts_on <= 365)
);

CREATE TABLE approvals (
  id            bigserial PRIMARY KEY,
  request_id    text NOT NULL REFERENCES access_requests(id) ON DELETE CASCADE,
  approver_id   text NOT NULL REFERENCES employees(id),
  decision      text NOT NULL CHECK (decision IN ('approved','rejected')),
  note          text,
  decided_at    timestamptz NOT NULL DEFAULT now(),

  -- One decision per approver per request. This single line prevents the
  -- double-approve race that application code alone cannot close.
  CONSTRAINT one_decision_per_approver UNIQUE (request_id, approver_id)
);
Why timestamptz, always

timestamp stores a wall-clock reading with no zone, so it is ambiguous the moment two people in different offices look at it — and BadgeDesk spans Bengaluru, Hyderabad and London. timestamptz stores an absolute instant (as UTC) and converts on the way in and out. It is the same eight bytes. There is no scenario in this system where the ambiguous one is correct, and daylight saving turns the mistake into a support ticket twice a year.

Normalisation, and when to stop

FormRule, in plain termsThe violation it removes
1NFOne value per cell; no repeating groupsA site_ids column holding "BLR-01,HYD-01". You now cannot index it, join on it or constrain it.
2NFNon-key columns depend on the whole keyIn a table keyed on (request_id, approver_id), storing request_created_at — it depends on half the key.
3NFNon-key columns depend on nothing but the keyStoring site_city on access_requests. It depends on site_id, which is not the key, so renaming a city means updating a million rows.
BCNF and beyondStricter variants of the same ideaReal but rare. Knowing 3NF exists and why is enough for almost every interview.

Normalise until it hurts, denormalise until it works. Design in 3NF, measure, then denormalise deliberately where a specific query demands it — and write down that the copy exists and what keeps it in step. Denormalisation without that note is how systems start disagreeing with themselves.

In production — a legitimate denormalisation

The approver dashboard shows a count of pending requests per site, on every page load, for every manager. That is a count(*) with a filter across a growing table, run constantly. Keeping a pending_count on sites, updated in the same transaction as the status change, is a correct denormalisation: the source of truth is still access_requests, the copy is maintained transactionally, and a nightly job recomputes it to catch drift. What makes it defensible is the transaction and the reconciliation, not the speed.

Joins

Aggregation, CTEs and window functions

the queries that come up in interviews
-- 1. Aggregate with a filtered count. FILTER beats CASE WHEN and reads better.
SELECT s.id,
       s.name,
       count(*)                                        AS total,
       count(*) FILTER (WHERE r.status = 'pending')     AS pending,
       count(*) FILTER (WHERE r.status = 'provisioned') AS provisioned,
       round(avg(r.ends_on - r.starts_on), 1)           AS avg_days
FROM   sites s
JOIN   access_requests r ON r.site_id = s.id
WHERE  r.created_at >= now() - interval '90 days'
GROUP  BY s.id, s.name
HAVING count(*) > 10          -- HAVING filters GROUPS; WHERE filters ROWS
ORDER  BY pending DESC;

-- 2. Window function: rank each employee's requests without collapsing rows.
--    This is the single most valuable SQL feature to be fluent in.
SELECT id, employee_id, created_at,
       row_number() OVER w                AS n,
       lag(created_at)  OVER w            AS previous_request_at,
       created_at - lag(created_at) OVER w AS gap
FROM   access_requests
WINDOW w AS (PARTITION BY employee_id ORDER BY created_at);

-- 3. "Most recent request per employee" - the classic. Window + filter.
SELECT * FROM (
  SELECT r.*,
         row_number() OVER (PARTITION BY employee_id
                            ORDER BY created_at DESC) AS rn
  FROM   access_requests r
) ranked
WHERE rn = 1;
--   Postgres-specific and faster: SELECT DISTINCT ON (employee_id) *
--   FROM access_requests ORDER BY employee_id, created_at DESC;

-- 4. CTE for readability, and a recursive CTE for the management chain.
WITH RECURSIVE chain AS (
  SELECT id, full_name, manager_id, 1 AS depth
  FROM   employees WHERE id = 'e_10422'
  UNION ALL
  SELECT e.id, e.full_name, e.manager_id, c.depth + 1
  FROM   employees e JOIN chain c ON e.id = c.manager_id
  WHERE  c.depth < 10                    -- always bound the recursion
)
SELECT * FROM chain;

-- 5. Running total - approvals per day and cumulative.
SELECT date_trunc('day', decided_at)::date AS day,
       count(*)                            AS decisions,
       sum(count(*)) OVER (ORDER BY date_trunc('day', decided_at)) AS cumulative
FROM   approvals
GROUP  BY 1
ORDER  BY 1;
Interviewers ask

“WHERE or HAVING?” — WHERE filters individual rows before grouping; HAVING filters the groups afterwards, so it can reference aggregates. Put a condition in WHERE whenever you can, because filtering earlier means grouping less.

“GROUP BY or a window function?” — GROUP BY collapses many rows into one. A window function computes across a set of rows while keeping every row. If the question is “show me each request alongside its rank”, it must be a window.

“What does count(*) do differently from count(col)?” — count(*) counts rows; count(col) counts rows where col is not null. The difference is a real bug when the column is nullable.

Indexes and query plans

Almost every “the database is slow” incident is a missing index, a wrong index, or a query written so the index cannot be used.

Red pencil — ways to make your index unusable

Wrapping the column in a function: WHERE lower(email) = 'a@b.com' cannot use an index on email — you need an expression index on lower(email), or the citext type. Leading wildcards: LIKE '%rao' cannot use a B-tree; use a trigram index. Type mismatches: comparing a text column to an integer forces a cast on every row. Too many indexes: each one is written on every insert, update and delete — an unused index is pure cost. Check pg_stat_user_indexes for ones with idx_scan = 0 and drop them.

And always CREATE INDEX CONCURRENTLY in production. The plain form takes a lock that blocks every write to the table for the duration, which on a large table means an outage.

Transactions, ACID and isolation

The part of databases that is genuinely subtle, and therefore the part interviews focus on.

AAtomicity

All of it or none of it. The approval and the audit row commit together, or neither exists.

CConsistency

Constraints hold at commit. Your CHECK, UNIQUE and foreign keys are never violated by a committed state.

IIsolation

Concurrent transactions do not see each other's half-finished work. How strictly is a setting — see below.

DDurability

Once committed, it survives the machine losing power. Achieved by writing to the WAL and flushing before acknowledging.

write skew in BadgeDesk, and three ways to prevent it
-- RULE: a site must always retain at least one active approver.
-- Two admins simultaneously remove the last two approvers at BLR-01.

-- Transaction A                          -- Transaction B
BEGIN;                                    BEGIN;
SELECT count(*) FROM approvers            SELECT count(*) FROM approvers
WHERE site_id='BLR-01' AND active;        WHERE site_id='BLR-01' AND active;
-- returns 2, so removing one is fine     -- returns 2, so removing one is fine
UPDATE approvers SET active=false         UPDATE approvers SET active=false
WHERE id='ap_1';                          WHERE id='ap_2';
COMMIT;                                   COMMIT;
-- Both succeed at READ COMMITTED and REPEATABLE READ.
-- BLR-01 now has zero approvers. Neither transaction broke the rule alone.

-- FIX 1 - lock the rows you based the decision on:
SELECT count(*) FROM approvers
WHERE site_id='BLR-01' AND active FOR UPDATE;
--   Simple and explicit. Serialises writers on that site only.

-- FIX 2 - SERIALIZABLE, and handle the abort:
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
--   One transaction fails with SQLSTATE 40001. Your code MUST catch it
--   and retry the whole transaction - that is the contract you accept.

-- FIX 3 - make the constraint expressible to the database:
--   Keep a counter column and CHECK (active_approver_count >= 1),
--   updated in the same transaction. The engine enforces it, always.
Red pencil

Never hold a database transaction open across a network call. BEGIN, then a five-second call to CCure, then COMMIT means row locks held for five seconds — and when CCure is slow, connections pile up, the pool exhausts, and the whole service stops. Do the external call outside the transaction, or publish an event and let a consumer do it. This is the most common cause of a database-shaped outage that is not actually the database's fault.

PostgreSQL in practice

Features worth knowing you have

the ones that come up constantly
-- UPSERT. Atomic, no read-then-write race.
INSERT INTO sites (id, name, city, timezone)
VALUES ('BLR-01', 'Whitefield', 'Bengaluru', 'Asia/Kolkata')
ON CONFLICT (id) DO UPDATE
  SET name = EXCLUDED.name, city = EXCLUDED.city;
--   ON CONFLICT DO NOTHING is the idempotent-insert idiom.

-- RETURNING - get the generated row back without a second query.
UPDATE access_requests SET status = 'approved', updated_at = now()
WHERE id = 'ar_7f3a91' AND status = 'pending'      -- optimistic guard
RETURNING id, status, updated_at;
--   Zero rows returned means someone else already decided it. Handle that
--   instead of blindly reporting success.

-- JSONB for the vendor payload we do not control.
ALTER TABLE access_requests ADD COLUMN vendor_meta jsonb NOT NULL DEFAULT '{}';
CREATE INDEX idx_vendor_meta ON access_requests USING gin (vendor_meta);
SELECT * FROM access_requests
WHERE vendor_meta @> '{"controller": {"model": "CC-9000"}}';
--   -> returns jsonb, ->> returns text. Mixing them up is a rite of passage.

-- Partial index: index only the rows anyone queries.
CREATE INDEX idx_pending ON access_requests (site_id, created_at DESC)
WHERE status = 'pending';
--   Tiny, hot, always in memory. 3% of the rows, 3% of the size.

-- Full-text search, without adding Elasticsearch.
CREATE INDEX idx_reason_fts ON access_requests
  USING gin (to_tsvector('english', reason));
SELECT * FROM access_requests
WHERE to_tsvector('english', reason) @@ plainto_tsquery('english', 'server room audit');

-- Row-level security - the tenant filter the application cannot forget.
ALTER TABLE access_requests ENABLE ROW LEVEL SECURITY;
CREATE POLICY site_isolation ON access_requests
  USING (site_id = current_setting('app.current_site', true));

Connection pooling

A PostgreSQL connection is an operating-system process using several megabytes. Two hundred application instances each holding ten idle connections will exhaust max_connections and the server will spend its time context-switching rather than answering queries.

the two layers, and what each is for
# Layer 1 - in-process pool. Reuses connections within one service instance.
engine = create_async_engine(
    settings.database_url,
    pool_size=10,           # steady-state connections per instance
    max_overflow=5,         # burst headroom
    pool_timeout=3,         # fail fast rather than queue forever behind a slow query
    pool_recycle=1800,      # pre-empt the proxy closing idle connections
    pool_pre_ping=True,     # cheap liveness check; avoids "server closed the connection"
)

# Layer 2 - PgBouncer in front of the database, in TRANSACTION mode.
#   Hundreds of client connections multiplexed onto a few server ones.
#   The catch: in transaction mode, session state does not persist between
#   statements, so prepared statements, SET, advisory locks and LISTEN/NOTIFY
#   break. Set prepare_threshold=0 (asyncpg) or use statement_cache_size=0.

# Sizing, roughly:  pool_size x instances must stay under max_connections
#   10 x 20 instances = 200, against max_connections = 300. Leave room for
#   migrations, your psql session and the monitoring agent - the connection
#   you cannot get is always the one you need during an incident.

MongoDB

Documents instead of rows. The model genuinely fits some data — and the design decision that matters is not “SQL or NoSQL”, it is embed or reference.

the access_events collection, and an aggregation pipeline
// The document we actually store: whatever the controller sent, verbatim,
// wrapped in a few fields WE control and can index.
{
  _id: ObjectId("..."),
  siteId: "BLR-01",
  employeeId: "e_10422",
  eventType: "door.granted",
  occurredAt: ISODate("2026-08-27T09:14:02.331Z"),
  controller: { model: "CC-9000", firmware: "4.2.1" },
  raw: { /* vendor payload, shape varies, never queried by us */ }
}

// Indexes: same rules as PostgreSQL, same leftmost-prefix behaviour.
db.access_events.createIndex({ siteId: 1, occurredAt: -1 })
db.access_events.createIndex({ employeeId: 1, occurredAt: -1 })
db.access_events.createIndex({ occurredAt: 1 }, { expireAfterSeconds: 60*60*24*400 })
//   A TTL index: events self-delete after ~13 months, matching the retention
//   policy. No cron job, no cleanup script that everyone forgets to monitor.

// Aggregation pipeline: denials per site per day, last 30 days.
db.access_events.aggregate([
  { $match: {                                    // ALWAYS first - it uses the index
      eventType: "door.denied",
      occurredAt: { $gte: new Date(Date.now() - 30*24*3600*1000) } } },
  { $group: {
      _id: { site: "$siteId",
             day:  { $dateToString: { format: "%Y-%m-%d", date: "$occurredAt" } } },
      denials:   { $sum: 1 },
      employees: { $addToSet: "$employeeId" } } },
  { $project: {
      _id: 0, site: "$_id.site", day: "$_id.day",
      denials: 1, distinctEmployees: { $size: "$employees" } } },
  { $sort: { denials: -1 } },
  { $limit: 20 },
])

// Explain works here too, and you should use it:
db.access_events.find({ siteId: "BLR-01" }).explain("executionStats")
//   Look for stage: "IXSCAN". "COLLSCAN" means no index was used.
The honest position on MongoDB

Mongo has had multi-document ACID transactions since 4.0, so “NoSQL has no transactions” is out of date — but they carry real cost and are not the idiomatic path, and if you find yourself needing them everywhere, the data was relational and you chose wrong. Its genuine strengths are a flexible schema for data whose shape you do not control, straightforward horizontal sharding, and a document model that maps neatly onto objects. Its genuine weakness is that it makes joins and cross-entity invariants awkward, which is most business software. For BadgeDesk it holds exactly one collection, and that is the right amount.

services/core/app/cache.py — cache-aside with stampede protection
import json, random

async def get_site(site_id: str, redis, db) -> dict:
    key = f"site:{site_id}"

    if cached := await redis.get(key):
        return json.loads(cached)

    # Only one caller rebuilds. The rest wait briefly and re-read.
    lock = f"lock:{key}"
    if await redis.set(lock, "1", nx=True, ex=5):
        try:
            site = await db.fetch_site(site_id)
            # Jittered TTL: 300 to 360 seconds, so a batch of keys created
            # together does not expire together.
            await redis.set(key, json.dumps(site), ex=300 + random.randint(0, 60))
            return site
        finally:
            await redis.delete(lock)

    await asyncio.sleep(0.05)
    if cached := await redis.get(key):
        return json.loads(cached)
    return await db.fetch_site(site_id)      # last resort: never fail on cache trouble
sliding-window rate limiting with a sorted set
async def allow(redis, api_key: str, limit: int = 100, window: int = 60) -> bool:
    key, now = f"rl:{api_key}", time.time()
    pipe = redis.pipeline()                  # one round trip, executed atomically
    pipe.zremrangebyscore(key, 0, now - window)   # drop entries outside the window
    pipe.zadd(key, {f"{now}:{uuid4()}": now})     # record this request
    pipe.zcard(key)                               # how many in the window
    pipe.expire(key, window)                      # so idle keys disappear
    _, _, count, _ = await pipe.execute()
    return count <= limit
# A fixed-window counter is simpler but allows 2x the limit across a boundary:
# 100 requests at 11:59:59 and 100 more at 12:00:00 both "pass".

Interviewers ask

“SQL or NoSQL for this?” is a trap when answered as a preference. Answer with the access patterns: what are the reads, what are the writes, what invariants must hold, and what is the scale? For BadgeDesk, requests and approvals must never disagree and are always queried relationally → PostgreSQL. Door events have no cross-entity invariants, arrive in six shapes and are queried by aggregation → a document store or a jsonb column. Then say what would change your mind: at a hundred times the event volume, the aggregation pipeline stops being adequate and this becomes a column store such as ClickHouse.

How the subtopics connect

One approval, touching all three stores, with the guarantee each one provides.

Drill book

Databases carry more interview weight than anything else on this set. Answer out loud.

Databases
Explain ACID with a concrete example.

Approving a request updates access_requests, inserts into approvals and inserts an outbox row. Atomicity: all three or none — never an approval row with the request still pending. Consistency: the unique constraint and the check on the date window hold at commit. Isolation: a concurrent approver does not see my half-finished work. Durability: once committed, a power cut cannot undo it, because the write-ahead log was flushed before the commit was acknowledged.

What is an index, and what does it cost?

A separate sorted structure — usually a B-tree — mapping column values to row locations, so a lookup is three or four page reads instead of scanning the table. The cost is space, plus write amplification: every insert, update and delete must maintain every affected index. That is why an unused index is worse than no index, and why you check pg_stat_user_indexes for ones with zero scans.

You have an index on (site_id, status, created_at). Which queries use it?

Anything filtering on a leftmost prefix: site_id alone; site_id and status; all three. A query on status alone cannot use it, because the index is sorted by site_id first — like looking for everyone with a given first name in a phone book ordered by surname. Order the columns with equality predicates first and range predicates last, since a range stops later columns from narrowing the scan.

The same query is fast in staging and slow in production. Why?

Most often data volume and distribution: the planner chose a sequential scan because staging has ten thousand rows and production has ten million, or statistics are stale so the estimates are wrong. Run EXPLAIN (ANALYZE, BUFFERS) on both and compare estimated against actual rows. Other candidates: a missing index that was created by hand in staging, parameter sniffing on a prepared statement, lock contention, or the working set no longer fitting in the buffer cache.

What are the isolation levels and what does each prevent?

Read Uncommitted allows dirty reads — and PostgreSQL does not implement it, treating it as Read Committed. Read Committed, the Postgres default, prevents dirty reads; each statement sees a fresh snapshot, so non-repeatable and phantom reads remain possible. Repeatable Read takes one snapshot for the whole transaction, preventing both. Serializable additionally prevents write skew by aborting transactions that could not have occurred in any serial order — which means your code must catch SQLSTATE 40001 and retry.

What is a deadlock and how do you avoid it?

Two transactions each hold a lock the other needs, so neither can proceed; PostgreSQL detects the cycle after about a second and aborts one with 40P01. The main prevention is acquiring locks in a consistent order — sort the ids before locking — plus short transactions, no external calls while holding locks, and a statement_timeout. You still retry, because deadlocks are a normal condition rather than a bug.

How do you add a NOT NULL column to a table with fifty million rows, with no downtime?

Add it nullable with a default — on PostgreSQL 11 and later that is metadata only and instant. Backfill in batches of a few thousand keyed on the primary key, committing between batches so you never hold a long transaction or bloat the table. Add a CHECK (col IS NOT NULL) NOT VALID, then VALIDATE CONSTRAINT, which takes only a share lock. Finally set NOT NULL, which can now use the validated constraint instead of rescanning.

How would you cache the site directory, and how do you invalidate it?

Cache-aside in Redis keyed site:{id}, TTL around five minutes with jitter so keys do not expire in lockstep. On write, commit to Postgres first and then DEL the key — delete rather than update, because writing a new value races with a concurrent rebuild and can leave a stale entry with a fresh TTL. Guard the rebuild with a short lock so a popular key expiring does not stampede the database.

Why can you not write to a database and a message queue atomically?

They are separate systems with separate commit protocols, so any ordering leaves a window: commit first and the process can die before publishing; publish first and the transaction can roll back after the event is out. Two-phase commit solves it in theory and is operationally miserable. The practical answer is the transactional outbox — insert the event into an outbox table inside the same transaction, then have a relay read that table and publish, marking rows as sent. Delivery becomes at-least-once, so consumers must be idempotent.

When would you actually reach for MongoDB over PostgreSQL?

When the shape genuinely varies and is not under your control — six door controller vendors emitting six payloads that change with firmware releases — and when there are no invariants spanning entities, so you never need a transaction across documents. Also when you know you will shard on a clear key. I would say honestly that a jsonb column in Postgres covers the same case at BadgeDesk's scale and removes a database from the estate; the argument for Mongo gets stronger with volume and with a team already operating it.

What does N+1 look like at the database layer and how do you find it?

One query for a list, then one more per row for a related entity — typically an ORM lazily loading a relationship inside a loop. You find it by logging query counts per request and alerting when the count scales with result size, or with pg_stat_statements showing an enormous call count for a trivial query. Fix it with a join, an eager-loading hint such as selectinload, or a batched WHERE id IN (…) — the same fix as the GraphQL DataLoader on Sheet 05.
