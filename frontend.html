What the browser actually does

Six stages between the first byte and a pixel the employee can click. Every performance problem you will ever debug is one of these stages being blocked, repeated, or done at the wrong time.

1
HTML arrives first and streams. The parser builds the DOM incrementally as bytes arrive, which is why a server-rendered page can show content before the whole response has downloaded. It is also why the order of tags in <head> matters so much.
2
The render tree is DOM × CSSOM, minus the invisible. CSS is render-blocking by design: the browser refuses to paint until it knows the styles, because painting unstyled content and then restyling looks worse than waiting. This is why a huge stylesheet delays everything.
3
Layout is the expensive one. It computes the geometry of every box. Changing a property that affects geometry — width, top, font-size — forces a re-layout of a whole subtree. Changing transform or opacity does not, which is why animations should use those two and almost nothing else.
4
Composite happens on the GPU. Layers are moved and blended without touching layout or paint. A 60 fps animation is one that only ever reaches this stage.
5
A plain <script src> in the head is a parser stop sign. The browser must assume the script might call document.write, so it halts DOM construction. defer keeps document order and runs after parsing; async runs the moment it lands, in any order. Use defer unless the script is genuinely independent.
6
Hydration is React re-doing on the client what the server already did. It walks the server HTML, builds the component tree in memory and attaches listeners. Until it finishes, the page is a photograph. Server components (later on this sheet) exist largely to shrink this step.
Why this is the first section

Interviewers rarely ask “explain the critical rendering path”. They ask “this page feels slow, how would you investigate?” The only way to answer that well is to know which of the six stages you are talking about. Open DevTools → Performance on any site and find these stages in the flame chart before you move on.

HTML that means something

The BadgeDesk request form is the highest-risk markup in the product: it is where an employee enters dates that determine physical building access. It has to be correct, keyboard-usable and screen-reader-usable, and none of that comes from a <div>.

Semantic elements are behaviour, not decoration

Every semantic element ships with keyboard handling, focus behaviour, an accessibility role and browser defaults. When you rebuild one out of <div>s you inherit the obligation to reimplement all four, and you will forget at least two.

Red pencil

Client-side validation is a convenience, never a control. required, min and maxlength improve the experience for honest users and stop nobody else — anyone can curl your endpoint. Every rule in this form is duplicated in Pydantic on the server, and the server is the one that counts. If an interviewer hears you describe validation without saying “and again on the server”, that is a mark against you.

CSS

Four ideas carry ninety per cent of real CSS work: the box model, the cascade, flexbox and grid. Everything else is vocabulary you can look up.

The box model

web/app/globals.css — the four lines every project starts with
*, *::before, *::after { box-sizing: border-box; }
body { margin: 0; }
img, svg, video { display: block; max-width: 100%; }
input, button, select, textarea { font: inherit; }   /* forms do NOT inherit by default */

The cascade, specificity and inheritance

When two rules target the same element, the winner is decided in this order: importance, then origin, then specificity, then document order. Specificity is a three-part score, compared left to right.

Flexbox and grid

The decision is one question: are you laying out along one axis or two? A toolbar, a row of chips, a card's header — one axis, use flex. A page skeleton, a data table layout, a gallery — two axes, use grid.

Pick Tailwind for BadgeDesk web. It is a product UI built quickly by a small number of people, where consistency of spacing and colour matters more than elegant stylesheets, and where deleting a component should delete its styles. Pick plain CSS when you are writing something long-lived and document-shaped — which is exactly why this study site is hand-written CSS.

Red pencil — @apply

The moment Tailwind feels repetitive, the tempting fix is @apply to bundle utilities into a class. That reinvents the stylesheet you were trying to avoid, and you now have both problems. The correct fix is to extract a component — a React <RequestCard> — so the classes appear once because the markup appears once. Reserve @apply for genuinely global primitives such as a base button in a design system.

React

One sentence to hold on to: your component is a function that turns state into a description of UI, and React's job is to make the screen match that description. Everything else is detail.

Render and commit

State, and why updates look asynchronous

web/components/ApprovalPanel.tsx
function ApprovalPanel({ request }: { request: AccessRequest }) {
  const [status, setStatus] = useState(request.status);
  const [count, setCount] = useState(0);

  function handleApprove() {
    setStatus('approved');
    console.log(status);        // still 'pending' - `status` is this render's value

    // Both of these read the SAME stale count, so it only goes up by one.
    setCount(count + 1);
    setCount(count + 1);        // count is 1, not 2

    // The updater form reads the latest queued value. This gives 2.
    setCount(c => c + 1);
    setCount(c => c + 1);
  }

  // State is a snapshot. Each render has its own `status` and `count`
  // constants that never change. React re-runs the function to give
  // you new ones. Nothing is mutated in place.
  return (
    <button onClick={handleApprove} disabled={status !== 'pending'}>
      {status === 'pending' ? 'Approve' : `Already ${status}`}
    </button>
  );
}
Interviewers ask

“Why does setCount(count + 1) twice only increment once?” Because count is a constant captured by this render, and both calls compute from the same value. React batches the updates and the last one wins. The updater form setCount(c => c + 1) queues a function that receives the latest pending value, so the two compose. Follow-up they will ask: “when would you reach for the updater form by default?” — whenever the next state derives from the previous one.

Lists and the key rule

useEffect, done properly

An effect synchronises your component with something outside React: a subscription, a timer, a browser API, an analytics call. It is not a lifecycle hook and it is not the place to fetch data in a modern app.

web/hooks/useDoorEvents.ts — a legitimate effect
// Synchronising with something outside React: a live event stream.
function useDoorEvents(siteId: string) {
  const [events, setEvents] = useState<DoorEvent[]>([]);

  useEffect(() => {
    const source = new EventSource(`/api/sites/${siteId}/door-events`);
    source.onmessage = (e) => setEvents(prev => [JSON.parse(e.data), ...prev]);

    return () => source.close();   // runs before the next siteId, and on unmount
  }, [siteId]);

  return events;
}
Red pencil — the stale closure

An effect captures the variables from the render it was created in. With [] as the dependency array, that capture is permanent, so an interval created on mount will read the mount-time value of status forever, no matter how many times the user clicks approve. The lint rule react-hooks/exhaustive-deps exists to catch exactly this. When you find yourself deleting a dependency to stop a loop, the dependency is not the problem — the effect is doing something it should not.

useMemo, useCallback, useRef and context

Next.js

React that runs in two places. The App Router's whole design is about deciding, per component, whether it runs on the server, in the browser, or both.

Server components versus client components

web/app/requests/page.tsx — server component
// No 'use client' - this is a server component by default.
// It is an async function, and it runs on the server only.
import { ApproveButton } from './ApproveButton';

export default async function RequestsPage({
  searchParams,
}: { searchParams: { status?: string } }) {
  // Called directly. No API route, no useEffect, no loading state.
  // The service token never reaches the browser.
  const res = await fetch(
    `${process.env.GATEWAY_URL}/access-requests?status=${searchParams.status ?? 'pending'}`,
    { headers: { authorization: `Bearer ${process.env.SERVICE_TOKEN}` },
      next: { revalidate: 30, tags: ['requests'] } },
  );
  const requests: AccessRequest[] = await res.json();

  return (
    <ul className="grid gap-4">
      {requests.map(r => (
        <li key={r.id} className="rounded border border-slate-700 p-4">
          <h3>{r.site_id} &middot; {r.employee_id}</h3>
          <p>{r.starts_on} to {r.ends_on}</p>
          {/* only THIS is interactive, so only THIS is a client component */}
          <ApproveButton requestId={r.id} />
        </li>
      ))}
    </ul>
  );
}
web/app/requests/ApproveButton.tsx — client component + server action
'use client';
import { useTransition } from 'react';
import { approveRequest } from './actions';

export function ApproveButton({ requestId }: { requestId: string }) {
  const [pending, startTransition] = useTransition();

  return (
    <button
      disabled={pending}
      onClick={() => startTransition(() => approveRequest(requestId))}
      className="bg-amber-500 px-4 py-2 disabled:opacity-50"
    >
      {pending ? 'Approving...' : 'Approve'}
    </button>
  );
}
web/app/requests/actions.ts — the mutation runs on the server
'use server';
import { revalidateTag } from 'next/cache';

export async function approveRequest(requestId: string) {
  // Authorisation is checked HERE. A server action is a public endpoint -
  // treat it exactly like one. Never trust that only your button calls it.
  const session = await requireSession();
  if (!session.roles.includes('manager')) throw new Error('forbidden');

  await fetch(`${process.env.GATEWAY_URL}/access-requests/${requestId}/approve`, {
    method: 'POST',
    headers: { authorization: `Bearer ${process.env.SERVICE_TOKEN}` },
  });

  revalidateTag('requests');    // the list above re-fetches, no client state needed
}
Red pencil

A server action compiles down to an HTTP endpoint with a generated URL. Anyone can call it with any arguments. Every check you would put on a REST handler — authentication, authorisation, input validation — belongs inside the action itself, not in the component that calls it. “Only my button calls this” is not a security model.

Server state is not client state

The distinction that separates a mid-level frontend answer from a senior one. Most React “state management” pain is caused by storing a copy of the server's data in the client and then trying to keep the copy honest.

In production

Move the filter and page number into the URL and three bugs disappear at once: the back button starts working, a manager can paste “the pending list for BLR-01” into chat, and a refresh no longer dumps them back to page one. Frontend fundamentals
Is the virtual DOM faster than manipulating the DOM directly?

No. Hand-written, perfectly targeted DOM updates will always beat it, because the virtual DOM adds a diffing step on top of the same final operations. What it buys is a programming model: you describe the UI for a given state and never write the update logic yourself. React trades a little speed for a large reduction in a whole class of bug.

Why must list keys be stable, and what breaks with the array index?

React matches elements between renders by key to decide what to reuse, move or create. With index keys, inserting at the top shifts every item's key, so React keeps each position's DOM node and component state and only swaps the text — a checkbox ticked on row two stays on row two even though a different request is now there. With a stable id, React inserts one node and leaves the rest untouched.

Controlled or uncontrolled inputs — when would you use each?

Controlled means React state is the source of truth and the input's value comes from it; use it when you need to validate as the user types, disable submit conditionally, or derive one field from another. Uncontrolled leaves the value in the DOM and you read it on submit; use it for simple forms, file inputs, and anything where re-rendering on every keystroke is wasted work. With server actions, uncontrolled forms have become the reasonable default again.

What does an effect's cleanup function actually run for?

It runs before every re-execution of the effect, and once more on unmount — not only on unmount, which is the common misunderstanding. Its job is to undo whatever the effect set up: close the EventSource, clear the interval, remove the listener, abort the fetch. Strict Mode in development deliberately mounts, unmounts and remounts to surface effects whose cleanup is missing or wrong.

What can a server component not do, and why?

No state, no effects, no event handlers, no browser APIs — it runs once on the server and its output is serialised HTML plus an RSC payload, so there is nothing to attach a listener to and no place to keep state between interactions. In exchange it can await a database query directly, read secrets safely, and use heavy dependencies that never reach the browser.

What is hydration, and what is a hydration mismatch?

Hydration is React walking the server-rendered HTML in the browser, rebuilding its component tree and attaching event listeners so the page becomes interactive. A mismatch is when the markup React produces on the client differs from what the server sent — typically caused by Date.now(), Math.random(), reading localStorage, or a locale-dependent format during render. React warns and re-renders that subtree, costing you the performance you server-rendered for.

Two rules both set the colour. Which wins?

Compare specificity as three numbers — IDs, then classes and attributes and pseudo-classes, then elements and pseudo-elements — left to right. One ID beats any number of classes. If the scores tie, the rule that appears later in the stylesheet wins. Inline styles beat all selectors, and !important beats inline. Reaching for either of the last two is a sign the architecture needs fixing.

Flexbox or grid?

One axis, sized by content: flex — toolbars, chip rows, a card's internal stack. Two axes, sized by the container: grid — page skeletons, galleries, anything where things must line up in both directions. They compose: a grid page layout whose cells contain flex rows is the normal arrangement.

The BadgeDesk request page feels slow on a mid-range phone. How do you investigate?

Measure before guessing. Open DevTools Performance with CPU throttling and record a load; look at where the time sits in the six stages of the rendering path. Check whether the delay is network (waterfall, blocking scripts and fonts), main-thread JavaScript (a large hydration bundle), or layout thrash. On a Next.js app the usual answer is too much marked 'use client', so push the boundary lower and let the static parts stay server-rendered.
