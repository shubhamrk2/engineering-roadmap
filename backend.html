What a backend service actually is

A process holding a listening socket. Everything a framework does happens between the kernel handing you a byte stream and you handing back a byte stream. Here is one real request, with the clock running.

1
Three round trips happen before a single line of your code runs. DNS, then the TCP three-way handshake, then the TLS handshake. On a warm connection all three cost zero because the browser reuses an existing socket — which is exactly why Connection: keep-alive and HTTP/2 matter, and why a service that closes connections aggressively feels slow for reasons that never appear in your application logs.
2
The load balancer is the first thing that can make you disappear. It picks a pod that is passing its readiness probe. If your process is up but cannot reach Postgres, you want it taken out of rotation here rather than returning 500s — that is the whole point of the readiness/liveness split covered later on this sheet and used in anger on Sheet 09.
3
Middleware runs for every request, including the ones that 404. It is the only place you can attach a request id, start a timer or set CORS headers on responses your handler never produced. Put cheap things here. Anything that touches the database belongs in a dependency, not in middleware, because middleware cannot easily return a typed error body.
4
The dependency tree is resolved per request, in order, before your handler is called. Settings, then a database session, then the current user decoded from the token, then a role check. If require_role raises 403, the handler never runs and the session is still closed correctly. This ordering is what makes authorisation reliable instead of something you remember to write at the top of each function.
5
The bar is the whole lesson. Your framework, your router, your dependency injection and your business logic together cost 13 ms. One unindexed query costs 140 ms. Every “is FastAPI faster than Express” argument is an argument about the 13, and you have not yet looked at the 140. Query tuning is Sheet 06.
6
Serialisation is not free and is not automatic. Turning ORM rows into a response model validates every field, converts dates to ISO-8601 strings and drops anything not declared. That last part is a security control, not a formatting detail — it is why the response model is mandatory, argued in full below.

The process and worker model

“How many concurrent requests can this hold?” has a different answer in each of the three runtimes on this sheet, and the answer is not about language speed. It is about what a request occupies while it waits.

Interviewers ask

“Your FastAPI service has 4 workers and a pool of 10 connections. How many requests can it serve at once?” Two numbers, and the honest answer names both: it can accept thousands, because an awaiting coroutine costs kilobytes; it can have at most 40 touching the database at once, because 4 × 10 is the real ceiling. Requests past 40 queue at the pool, latency climbs, and the symptom looks like a slow database when it is actually a small pool.

Why this exists

Every framework on this sheet is solving the same four problems: match a URL to a function, get structured data out of an untrusted byte stream, give the function the things it needs (a database session, the current user) without hard-coding them, and turn the return value plus any exception into a correct HTTP response. FastAPI solves them with type hints, Express with a callback chain, NestJS with decorators and a container. Same four problems.

FastAPI — building the core service

The source of truth for BadgeDesk. Python, async, typed end to end. The whole framework is one idea executed relentlessly: your type hints are the API contract, the validator, the documentation and the dependency graph, all at once.

Red pencil

The most common FastAPI codebase in the wild is one 1,400-line main.py with the database connection as a module-level global. It works until you write your first test, at which point you discover that importing the module opens a connection and there is no seam to replace it. The layout above exists so that every external thing enters through a dependency, and dependencies can be swapped.

Path, query and body parameters

FastAPI reads the function signature and decides where each argument comes from, so you never parse a request object by hand. A name that appears in the route path ("/{request_id}") is a path parameter and is always required. A parameter annotated with a Pydantic model is the JSON body. Everything else is a query parameter, required if it has no default and optional if it does. Wrap any of them in Annotated[T, Path(…)], Annotated[T, Query(…)] or Annotated[T, Body(…)] to add constraints — ge, le, min_length, pattern, an alias when the wire name differs from the Python name — and every one of those constraints appears in the generated OpenAPI schema. All three kinds appear in the endpoints below.

Pydantic v2, and why the response model is not optional

Two models per resource, always. AccessRequestCreate is what a client may send; AccessRequestOut is what you promise to return. They are deliberately different objects, because the set of fields a client may set and the set you may reveal are different sets.

app/schemas/access_request.py
from datetime import date, datetime
from typing import Annotated, Generic, Literal, TypeVar
from pydantic import BaseModel, ConfigDict, Field, model_validator

SiteId = Annotated[str, Field(pattern=r"^[A-Z]{3}-\d{2}$", examples=["BLR-01"])]
Status = Literal["pending", "approved", "rejected"]

class AccessRequestCreate(BaseModel):
    # extra="forbid" turns a typo in the client into a 422 instead of a silent no-op.
    model_config = ConfigDict(extra="forbid")

    site_id: SiteId
    starts_on: date
    ends_on: date
    reason: Annotated[str, Field(min_length=10, max_length=500)]

    @model_validator(mode="after")
    def dates_make_sense(self) -> "AccessRequestCreate":
        if self.ends_on < self.starts_on:
            raise ValueError("ends_on must not be before starts_on")
        if (self.ends_on - self.starts_on).days > 90:
            raise ValueError("access may not be requested for more than 90 days")
        return self

class AccessRequestOut(BaseModel):
    # from_attributes lets Pydantic read an ORM object, not just a dict.
    model_config = ConfigDict(from_attributes=True)

    id: str
    employee_id: str
    site_id: str
    starts_on: date
    ends_on: date
    status: Status
    reason: str
    created_at: datetime

T = TypeVar("T")

class Page(BaseModel, Generic[T]):
    items: list[T]
    next_cursor: str | None = None
    total: int | None = None      # None when the count would cost a full scan
Why the response model is not optional

Three separate jobs, and you lose all three if you return a raw dict or an ORM object. One — it is a filter. Your AccessRequest ORM row also carries internal_risk_score, reviewer_notes and the employee's home address. With response_model=AccessRequestOut, anything not declared is dropped before it reaches the socket, so adding a column to the table can never leak it through the API. Without one, it ships the day the migration runs. Two — it is the contract. It generates the OpenAPI schema, which generates the TypeScript client the web app on Sheet 03 imports. Three — it is a test. If the handler returns a row with status="aproved", serialisation raises in your CI rather than corrupting the frontend three days later.

from typing import Annotated
from fastapi import APIRouter, BackgroundTasks, Depends, Query, Response, status

from app.api.deps import CurrentUser, DbSession, require_role
from app.schemas.access_request import (
    AccessRequestCreate, AccessRequestOut, ApprovalIn, Page, Status,
)
from app.services import access_requests as svc

router = APIRouter(prefix="/access-requests", tags=["access-requests"])

@router.post(
    "",
    response_model=AccessRequestOut,
    status_code=status.HTTP_201_CREATED,
    responses={409: {"description": "An overlapping request for this site already exists"}},
)
async def create_access_request(
    body: AccessRequestCreate,          # the JSON body
    db: DbSession,                      # injected
    user: CurrentUser,                  # injected
    response: Response,
    background: BackgroundTasks,
) -> AccessRequestOut:
    """Create a pending request for the calling employee."""
    created = await svc.create(db, body, employee_id=user.employee_id)
    response.headers["Location"] = f"/access-requests/{created.id}"   # 201 must say where
    background.add_task(svc.emit_created_metric, created.id)          # best-effort only
    return created

@router.get("", response_model=Page[AccessRequestOut])
async def list_access_requests(
    db: DbSession,
    user: CurrentUser,
    status_filter: Annotated[Status | None, Query(alias="status")] = None,
    site_id: Annotated[str | None, Query(pattern=r"^[A-Z]{3}-\d{2}$")] = None,
    limit: Annotated[int, Query(ge=1, le=100)] = 25,
    cursor: Annotated[str | None, Query(description="Opaque cursor from the last page")] = None,
) -> Page[AccessRequestOut]:
    """Managers see their reports' requests; everyone else sees their own."""
    return await svc.list_for(db, viewer=user, status=status_filter,
                              site_id=site_id, limit=limit, cursor=cursor)

    "/{request_id}/approve",

)

    body: ApprovalIn,
    db: DbSession,
    user: CurrentUser,
) -> AccessRequestOut:
    return await svc.approve(db, request_id, approver=user, note=body.note)
app/services/access_requests.py — where the domain rules live
from sqlalchemy.exc import IntegrityError

from app.repositories import access_requests as repo
from app.core.errors import Conflict, Forbidden, NotFound

async def create(db, body, *, employee_id: str):
    # A unique partial index in Postgres does the real enforcement; this check
    # exists to give a good message. The index is what survives a race.
    if await repo.overlapping_exists(db, employee_id, body.site_id,
                                     body.starts_on, body.ends_on):
        raise Conflict("an overlapping request for this site is already pending")
    try:
        return await repo.insert(db, body, employee_id=employee_id)
    except IntegrityError as exc:                 # two requests arrived at once
        raise Conflict("an overlapping request for this site is already pending") from exc

async def approve(db, request_id: str, *, approver, note: str | None):
    row = await repo.get_for_update(db, request_id)   # SELECT ... FOR UPDATE
    if row is None:
        raise NotFound(f"access request {request_id} does not exist")
    if row.manager_id != approver.employee_id:
        raise Forbidden("only the requester's manager may approve")
    if row.status != "pending":
        # 409, not 400: the request was valid, the resource state was wrong.
        raise Conflict(f"request is already {row.status}")
    return await repo.set_approved(db, row, approver.employee_id, note)
Interviewers ask

“What status code do you return when someone creates a duplicate?” 409 Conflict. 400 means the request was malformed — it was not. 422 means the body failed validation — it did not. 409 means “your request is well formed and permitted, but the current state of the resource refuses it.” The follow-up is always “what if the client retries after a timeout and the first call actually succeeded?” — that is an idempotency key, and it lives on Sheet 05.

Validation errors and the 422 body

When a body fails a Pydantic model, FastAPI never calls your handler. It returns 422 Unprocessable Entity with a machine-readable list of every failure — not the first one, all of them, which is what lets a form highlight three fields at once.

Dependency injection, in depth

A dependency is a callable whose result FastAPI computes before your handler and passes in. That sounds small. It is the single most important feature of the framework, because it turns “things my handler needs from the outside world” into a graph the framework owns — and anything the framework owns, you can replace.

app/api/deps.py
from functools import lru_cache
from typing import Annotated, AsyncIterator, Callable

import jwt
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

from app.core.settings import Settings
from app.db.models import Employee

bearer = HTTPBearer(auto_error=False)

@lru_cache                      # built once per worker process, not per request
def get_settings() -> Settings:
    return Settings()

SettingsDep = Annotated[Settings, Depends(get_settings)]

@lru_cache
def _sessionmaker(dsn: str) -> async_sessionmaker[AsyncSession]:
    engine = create_async_engine(
        dsn,
        pool_size=10,           # steady-state connections PER WORKER
        max_overflow=5,         # burst headroom
        pool_timeout=3,         # fail fast rather than pile up
        pool_pre_ping=True,     # survive a database failover
        pool_recycle=1800,      # beat a proxy that culls idle connections
    )
    return async_sessionmaker(engine, expire_on_commit=False)

async def get_db_session(s: SettingsDep) -> AsyncIterator[AsyncSession]:
    """One transaction per request. Code after `yield` runs on the way out even
    if the handler raised, which is why cleanup is never forgotten."""
    async with _sessionmaker(str(s.database_dsn))() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise

DbSession = Annotated[AsyncSession, Depends(get_db_session)]

async def get_current_user(
    creds: Annotated[HTTPAuthorizationCredentials | None, Depends(bearer)],
    settings: SettingsDep,
    db: DbSession,
) -> Employee:
    if creds is None:
        raise HTTPException(401, "missing bearer token",
                            headers={"WWW-Authenticate": "Bearer"})
    try:
        claims = jwt.decode(
            creds.credentials, settings.jwt_public_key,
            algorithms=["RS256"],        # a fixed allow-list. See the trap below.
            audience="badgedesk-core", issuer="badgedesk-gateway",
        )
    except jwt.PyJWTError as exc:
        raise HTTPException(401, "invalid token") from exc
    employee = await db.get(Employee, claims["sub"])
    if employee is None or not employee.active:
        raise HTTPException(401, "unknown or disabled employee")
    employee.roles = claims.get("roles", [])
    return employee

CurrentUser = Annotated[Employee, Depends(get_current_user)]

def require_role(role: str) -> Callable:
    """A dependency FACTORY: called at import time, returns the real dependency."""
    async def checker(user: CurrentUser) -> None:
        if role not in user.roles:
            raise HTTPException(403, f"requires role: {role}")
    return checker
In production

Notice pool_size=10 is per worker. Four gunicorn workers on three pods is 4 × 3 × 15 = 180 possible connections against an RDS instance whose max_connections may be 200 — and the reconciler and the worker also need some. The classic production incident is scaling pods for throughput and taking the database down instead. Either put PgBouncer in front, or do the multiplication every time you change a replica count.

Async endpoints, and the trap inside one

Declare a handler async def and it runs on the event loop. Declare it plain def and FastAPI runs it in a thread pool so it cannot block the loop. Both are correct; mixing them up is not.

Wrong — blocking inside async
freezes every request on this worker
import requests, time

@router.get("/sites/{site_id}/policy")
async def policy(site_id: str):
    # requests is synchronous. This parks the
    # ENTIRE event loop for 800 ms - every other
    # in-flight request on this worker stalls.
    r = requests.get(f"{VENDOR}/p/{site_id}",
                     timeout=2)
    time.sleep(0.1)          # same bug, smaller
    return r.json()

Symptom: p99 latency collapses under load while CPU sits at 8%. Drawing 02-B on Sheet 02 is the same lesson one layer down.

Right — two valid fixes
await it, or push it to a thread
import anyio, httpx

@router.get("/sites/{site_id}/policy")
async def policy(site_id: str, client: HttpDep):
    r = await client.get(f"/p/{site_id}")   # awaits
    return r.json()

# When the library has no async version at all:
@router.post("/badges/{id}/render")
async def render(id: str):
    return await anyio.to_thread.run_sync(
        blocking_pdf_render, id)   # off the loop

# Or simply drop the `async` - FastAPI will run a
# plain `def` handler in its own thread pool.

Rule: if a handler is async def, every call inside it must be awaitable or provably instant.

Red pencil

The blocking call that catches everyone is the database driver. psycopg2 and plain SQLAlchemy sessions are synchronous; asyncpg and sqlalchemy.ext.asyncio are not. An async def handler using a sync session looks fine in development with one user and falls over at twenty. Check the driver, not the ORM.

Middleware, CORS and consistent error bodies

Middleware wraps every request, including 404s and 500s. Exception handlers turn your domain errors into one predictable JSON shape so the frontend has exactly one error branch to write.

app/main.py
import httpx, time, uuid
from contextlib import asynccontextmanager

from fastapi import FastAPI, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import JSONResponse

from app.api.routers import access_requests, health
from app.core.errors import BadgeDeskError
from app.core.logging import log, request_id_var
from app.api.deps import get_settings

@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup: open shared clients ONCE, not per request
    app.state.http = httpx.AsyncClient(timeout=httpx.Timeout(2.0, connect=1.0))
    yield
    # shutdown: uvicorn calls this after it stops accepting new connections
    await app.state.http.aclose()

def create_app() -> FastAPI:
    s = get_settings()
    app = FastAPI(title="BadgeDesk core", version="1.4.0", lifespan=lifespan)

    app.add_middleware(
        CORSMiddleware,
        allow_origins=s.cors_origins,        # ["https://badgedesk.example.com"]
        allow_credentials=True,              # NEVER combine this with allow_origins=["*"]
        allow_methods=["GET", "POST", "PATCH"],
        allow_headers=["authorization", "content-type", "x-request-id"],
        max_age=600,                         # cache the preflight for 10 minutes
    )

    @app.middleware("http")
    async def observability(request: Request, call_next):
        rid = request.headers.get("x-request-id") or str(uuid.uuid4())
        token = request_id_var.set(rid)      # every log line below inherits it
        started = time.perf_counter()
        try:
            response = await call_next(request)
        finally:
            request_id_var.reset(token)
        ms = (time.perf_counter() - started) * 1000
        response.headers["x-request-id"] = rid
        log.info("request", extra={"method": request.method,
                                   "path": request.url.path,
                                   "status": response.status_code,
                                   "duration_ms": round(ms, 1)})
        return response

    @app.exception_handler(BadgeDeskError)
    async def domain_error(request: Request, exc: BadgeDeskError):
        return JSONResponse(
            status_code=exc.status_code,
            content={"error": {"code": exc.code, "message": str(exc),
                               "request_id": request_id_var.get()}},
        )

    @app.exception_handler(RequestValidationError)
    async def validation_error(request: Request, exc: RequestValidationError):
        # Reshape FastAPI's default 422 into the SAME envelope as everything else.
        return JSONResponse(
            status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
            content={"error": {"code": "validation_failed",
                               "message": "the request body is not valid",
                               "fields": exc.errors(),
                               "request_id": request_id_var.get()}},
        )

    app.include_router(access_requests.router, prefix="/v1")
    app.include_router(health.router)         # unversioned, never behind auth
    return app

app = create_app()
Red pencil — CORS is not a security feature

CORS is a browser rule about which origins may read a response. It stops nothing else: curl, Postman, a server and a mobile app all ignore it completely. Setting allow_origins=["*"] to make an error go away, and then relying on “only our frontend calls this”, is two mistakes at once. Also note that allow_credentials=True with "*" is rejected by browsers outright — if that combination silently “works” in your setup, something is echoing the origin back and you have effectively disabled CORS.

Background tasks vs a real queue

BackgroundTasks runs a coroutine after the response is sent, in the same process. That is the entire feature, and both the strength and the disqualifier are in that sentence.

QuestionBackgroundTasksKafka / a real queue
Survives a pod restart mid-task?No. The work is gone, silently.Yes. The message is still on the topic.
Retries on failure?No. It logs and dies.Yes, with backoff and a dead-letter topic.

Getting this wrong in either direction is a real cost. Using BackgroundTasks to call the badge vendor means a rolling deploy silently drops provisioning for everyone mid-request; standing up Kafka to increment a counter is a week of infrastructure for a line of code. SQLAlchemy 2.0 async and the repository

app/repositories/access_requests.py
from datetime import date, datetime, timezone
from sqlalchemy import select, func
from sqlalchemy.ext.asyncio import AsyncSession

from app.db.models import AccessRequest

async def overlapping_exists(db: AsyncSession, employee_id: str, site_id: str,
                             starts_on: date, ends_on: date) -> bool:
    stmt = (
        select(func.count())
        .select_from(AccessRequest)
        .where(
            AccessRequest.employee_id == employee_id,
            AccessRequest.site_id == site_id,
            AccessRequest.status == "pending",
            AccessRequest.starts_on <= ends_on,      # classic overlap test:
            AccessRequest.ends_on >= starts_on,      # A.start <= B.end AND A.end >= B.start
        )
    )
    return bool((await db.execute(stmt)).scalar_one())

async def page(db: AsyncSession, *, employee_ids: list[str], status: str | None,
               site_id: str | None, limit: int, after_created_at: datetime | None):
    stmt = select(AccessRequest).where(AccessRequest.employee_id.in_(employee_ids))
    if status:
        stmt = stmt.where(AccessRequest.status == status)
    if site_id:
        stmt = stmt.where(AccessRequest.site_id == site_id)
    if after_created_at:                       # keyset pagination, not OFFSET
        stmt = stmt.where(AccessRequest.created_at < after_created_at)
    stmt = stmt.order_by(AccessRequest.created_at.desc()).limit(limit + 1)
    rows = list((await db.execute(stmt)).scalars())
    has_more = len(rows) > limit
    return rows[:limit], has_more

async def get_for_update(db: AsyncSession, request_id: str) -> AccessRequest | None:
    # Row lock held until this request's transaction commits, so two managers
    # clicking Approve at the same instant cannot both win.
    stmt = select(AccessRequest).where(AccessRequest.id == request_id).with_for_update()
    return (await db.execute(stmt)).scalar_one_or_none()
Why keyset pagination and not OFFSET

LIMIT 25 OFFSET 10000 makes Postgres produce 10,025 rows and throw 10,000 away, so page 400 is 400× slower than page 1. Worse, if a row is inserted between requests every subsequent page shifts and the user sees a duplicate. A cursor over (created_at, id) is O(log n) on every page and stable under inserts. Node + Express — building the notifier

Express gives you almost nothing and gets out of the way. That is simultaneously why it is still everywhere and why every Express codebase past 5,000 lines looks different from every other one.

The middleware chain, and the branch nobody draws

An Express app is an array of functions. Each gets (req, res, next) and must do exactly one of three things: send a response, call next(), or call next(err). Forget all three and the request hangs until the client times out — no error, no log, nothing.

notifier/src/app.js
import express from 'express';
import helmet from 'helmet';
import cors from 'cors';
import { randomUUID } from 'node:crypto';
import { webhooksRouter } from './routes/webhooks.js';
import { log } from './log.js';

export function createApp() {
  const app = express();

  app.use(helmet());
  app.use(cors({ origin: process.env.CORS_ORIGIN?.split(',') ?? [] }));

  // The raw body is needed to verify the vendor's HMAC signature, so keep a copy
  // BEFORE json() consumes the stream. Doing this after parsing is impossible.
  app.use(express.json({
    limit: '256kb',
    verify: (req, _res, buf) => { req.rawBody = buf; },
  }));

  app.use((req, res, next) => {
    req.id = req.header('x-request-id') ?? randomUUID();
    res.setHeader('x-request-id', req.id);
    const t0 = process.hrtime.bigint();
    res.on('finish', () => {
      const ms = Number(process.hrtime.bigint() - t0) / 1e6;
      log.info({ requestId: req.id, method: req.method, path: req.originalUrl,
                 status: res.statusCode, durationMs: +ms.toFixed(1) }, 'request');
    });
    next();                       // forget this line and the request hangs forever
  });

  app.use('/webhooks', webhooksRouter);

  // 404 is just the middleware that runs when no route matched.
  app.use((req, res) => res.status(404).json({
    error: { code: 'not_found', message: `no route for ${req.method} ${req.path}` },
  }));

  // Error handler LAST, and with exactly four parameters.
  app.use((err, req, res, _next) => {
    const status = err.status ?? 500;
    if (status >= 500) log.error({ requestId: req.id, err }, 'unhandled');
    res.status(status).json({
      error: { code: err.code ?? 'internal_error',
               message: status >= 500 ? 'internal error' : err.message,
               requestId: req.id },
    });
  });

  return app;
}

The async error trap

Express 4 — the bug
the request never completes
router.post('/vendor', async (req, res) => {
  const event = await parseVendorEvent(req.body);
  // If this rejects, Express 4 does NOT catch it.
  // The promise rejection is unhandled, next(err)
  // is never called, the error middleware never
  // runs, and res is never written to.
  await forwardToCore(event);
  res.status(202).json({ accepted: true });
});

Symptom: UnhandledPromiseRejection in the logs (if you are lucky), a client that times out after 30 s, and a socket held open until then.

The two fixes
wrap it, or upgrade
// Fix 1 - a five-line wrapper, Express 4.
export const ah = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

router.post('/vendor', ah(async (req, res) => {
  const event = await parseVendorEvent(req.body);
  await forwardToCore(event);
  res.status(202).json({ accepted: true });
}));

// Fix 2 - Express 5 (npm i express@5). A rejected
// promise returned by a handler is forwarded to
// next(err) for you. Delete the wrapper.

Either way, add process.on('unhandledRejection', ...) so the next one is loud instead of silent.

Interviewers ask

“How does Express know a function is error-handling middleware?” By fn.length === 4. It literally inspects the declared parameter count. Which means app.use((err, req, res) => {}) is registered as ordinary middleware, gets called with (req, res, next), and your “error handler” silently starts handling successful requests. You must keep the unused fourth parameter.

export const validate = (schemas) => (req, _res, next) => {
  try {
    // Reassign: from here on req.body is the PARSED, coerced, trusted value.
    if (schemas.body)  req.body  = schemas.body.parse(req.body);
    if (schemas.query) req.query = schemas.query.parse(req.query);
    if (schemas.params) req.params = schemas.params.parse(req.params);
    next();
  } catch (err) {

        status: 400, code: 'validation_failed',
        fields: err.issues.map(i => ({ path: i.path, message: i.message })),
      }));
    } else next(err);
  }
};

  event_id: z.string().uuid(),
  type: z.enum(['badge.activated', 'badge.revoked', 'badge.failed']),
  badge_id: z.string(),
  request_id: z.string().regex(/^req-\d+$/),
  occurred_at: z.coerce.date(),
});

function signatureIsValid(req) {
  const header = req.header('x-vendor-signature') ?? '';
  const expected = createHmac('sha256', process.env.VENDOR_WEBHOOK_SECRET)
    .update(req.rawBody)                 // the raw bytes, not JSON.stringify(req.body)
    .digest('hex');
  const a = Buffer.from(header, 'utf8');
  const b = Buffer.from(expected, 'utf8');
  // Constant-time compare: `a === b` leaks the secret one byte at a time.
  return a.length === b.length && timingSafeEqual(a, b);
}

// INBOUND: the vendor tells us a badge went live.
webhooksRouter.post('/vendor', ah(async (req, res, next) => {
  if (!signatureIsValid(req)) {
    return next(Object.assign(new Error('bad signature'),
                              { status: 401, code: 'bad_signature' }));
  }
  const event = VendorEvent.parse(req.body);

  // Answer FAST. The vendor will retry if we take longer than 5 s, and a retry
  // storm from a slow receiver is a self-inflicted outage.
  res.status(202).json({ accepted: true, eventId: event.event_id });

  // Then do the work. event_id makes the downstream call idempotent, so the
  // vendor's inevitable duplicate delivery is harmless.
  queueMicrotask(() => handleVendorEvent(event).catch(
    (err) => log.error({ err, eventId: event.event_id }, 'vendor event failed')));
}));

// OUTBOUND: tell core, then tell the human.
async function handleVendorEvent(event) {
  await postToCore(`/v1/access-requests/${event.request_id}/provisioned`, {
    badge_id: event.badge_id,
    occurred_at: event.occurred_at.toISOString(),
    idempotency_key: event.event_id,
  });
  await sendTeamsCard({
    title: 'Badge ready',
    text: `Badge ${event.badge_id} is active for ${event.request_id}.`,
  });
}

const sleep = (ms) => new Promise(r => setTimeout(r, ms));

export async function postToCore(path, body, { attempts = 3 } = {}) {
  let lastErr;
  for (let i = 0; i < attempts; i++) {
    try {
      const res = await fetch(`${process.env.CORE_URL}${path}`, {
        method: 'POST',
        headers: { 'content-type': 'application/json',
                   'authorization': `Bearer ${await serviceToken()}` },
        body: JSON.stringify(body),
        signal: AbortSignal.timeout(2000),   // 2 s per ATTEMPT, not per call
      });
      if (res.status >= 500) throw new Error(`core ${res.status}`); // retryable
      if (!res.ok) return res;               // 4xx: our fault, retrying cannot help
      return res;
    } catch (err) {
      lastErr = err;
      // Exponential backoff with full jitter: 0-200 ms, 0-400 ms, 0-800 ms.
      // Without jitter every retrying client returns at the same instant and
      // knocks the service over exactly as it recovers.
      await sleep(Math.random() * 200 * 2 ** i);
    }
  }
  throw lastErr;
}

Graceful shutdown

notifier/src/server.js
import { createApp } from './app.js';
import { log } from './log.js';

const server = createApp().listen(5000, () => log.info('notifier on :5000'));
server.keepAliveTimeout = 65_000;   // must exceed the load balancer's idle timeout
server.headersTimeout   = 66_000;   // or you will see random 502s under keep-alive

let shuttingDown = false;

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  log.info({ signal }, 'draining');

  // 1. Fail readiness immediately so the load balancer stops sending new work.
  //    Kubernetes needs a few seconds to notice; keep serving during that window.
  global.__ready = false;
  await new Promise(r => setTimeout(r, 5000));

  // 2. Stop accepting connections; the callback fires when the last one closes.
  server.close(async () => {
    await Promise.allSettled([pool.end(), redis.quit()]);
    log.info('drained cleanly');
    process.exit(0);
  });

  // 3. Hard deadline. Must be shorter than terminationGracePeriodSeconds (30 s)
  //    or Kubernetes SIGKILLs you mid-write.
  setTimeout(() => { log.error('forced exit'); process.exit(1); }, 20_000).unref();
}

process.on('SIGTERM', () => shutdown('SIGTERM'));   // what Kubernetes sends
process.on('SIGINT',  () => shutdown('SIGINT'));    // what Ctrl-C sends
process.on('unhandledRejection', (err) => { log.error({ err }, 'unhandled'); });
In production

The five-second sleep before server.close() looks wrong and is the most important line in the file. When Kubernetes terminates a pod it sends SIGTERM and removes the endpoint at the same time, asynchronously. If you stop accepting instantly, every request the load balancer already routed in that window gets a connection reset — visible to users as intermittent 502s on every single deploy. Fail the readiness probe, wait, then drain. Probes are on Sheet 09.

NestJS — building the gateway

Express with structure and a dependency-injection container, expressed in TypeScript decorators. If FastAPI is “your types are the framework”, NestJS is “your classes are the framework”.

Why it exists

Take the Express app above and give it to six engineers for a year. import {
  CanActivate, ExecutionContext, Injectable, UnauthorizedException, ForbiddenException,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { JwtService } from '@nestjs/jwt';
import { ConfigService } from '@nestjs/config';

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly jwt: JwtService,
              private readonly config: ConfigService) {}

  async canActivate(ctx: ExecutionContext): Promise<boolean> {
    const req = ctx.switchToHttp().getRequest();
    const [scheme, token] = (req.headers.authorization ?? '').split(' ');
    if (scheme !== 'Bearer' || !token) throw new UnauthorizedException('missing token');
    try {
      req.user = await this.jwt.verifyAsync(token, {
        publicKey: this.config.getOrThrow('JWT_PUBLIC_KEY'),
        algorithms: ['RS256'],       // an allow-list, so `alg: none` is rejected
        issuer: 'badgedesk-gateway',
        audience: 'badgedesk-gateway',
      });
    } catch {
      throw new UnauthorizedException('invalid or expired token');
    }
    return true;                     // false would give a bare 403 with no message
  }
}

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    // Read the @Roles('manager') metadata off the method, falling back to the class.
    const required = this.reflector.getAllAndOverride<string[]>('roles', [
      ctx.getHandler(), ctx.getClass(),
    ]);
    if (!required?.length) return true;          // no @Roles = no role requirement

    const { user } = ctx.switchToHttp().getRequest();
    const ok = required.some((r) => user?.roles?.includes(r));
    if (!ok) throw new ForbiddenException(`requires one of: ${required.join(', ')}`);
    return true;
  }
}

Password hashing

from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError, VerificationError

# Deliberately slow and memory-hard. ~80 ms and 64 MB per verify makes an
# offline GPU attack on a stolen dump economically painful. Tune with
# `argon2-cli benchmark` on the target hardware, not by guessing.
ph = PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4)

def hash_password(plain: str) -> str:
    # The salt is generated per password and stored INSIDE the returned string:
    # $argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$hash...
    return ph.hash(plain)

def verify_password(stored_hash: str, plain: str) -> bool:
    try:
        ok = ph.verify(stored_hash, plain)
    except (VerifyMismatchError, VerificationError):
        return False
    if ph.check_needs_rehash(stored_hash):
        # Parameters were raised since this user last logged in. Upgrade silently.
        save_new_hash(ph.hash(plain))
    return ok

# Never: md5, sha1, sha256, or "sha256 with a salt". Fast hashes are the wrong
# tool - a modern GPU does billions of sha256 per second. bcrypt is acceptable
# (cost >= 12); argon2id is the current default recommendation.
Red pencil — the alg: none attack

The JWT header declares its own algorithm, and some libraries used to trust it. An attacker edits the payload to {"sub":"e-001","roles":["admin"]}, sets the header to {"alg":"none"}, drops the signature and sends it. A verifier that reads alg from the token and dispatches on it says “no algorithm, nothing to check” and lets it through. The variant that still catches people: a service verifying an RS256 token where the attacker re-signs with HS256 using the public key as the HMAC secret — which is public. Always pass an explicit allow-list (algorithms=["RS256"] in PyJWT, algorithms: ['RS256'] in @nestjs/jwt) and always verify iss, aud and exp as well. A token that is valid but was minted for a different audience is not valid for you.

Interviewers ask

“JWT or server-side sessions?” Sessions are a random id in a cookie plus state in Redis: revocation is a DEL, but every request needs a lookup. JWTs are self-contained: verification is local and free, which is what lets the gateway and the core both check a token without a shared database — but you cannot un-issue one, so a fired employee stays authorised until exp. The real answer is the hybrid in Drawing 04-G: short access tokens so the window is 15 minutes, plus a server-side record of refresh tokens so logout and revocation actually work.

Health and readiness are not the same endpoint

The distinction matters because the two answers cause opposite actions. Liveness answers “is this process wedged and in need of a restart?” — a failure kills the pod. Readiness answers “should this instance receive traffic right now?” — a failure removes it from the load balancer and leaves it running. Wire the database check into liveness and a thirty-second database blip restarts every pod you own simultaneously, turning a small outage into a total one.

app/api/routers/health.py
import asyncio, time
from fastapi import APIRouter, Response, status
from sqlalchemy import text

from app.api.deps import DbSession, RedisDep

router = APIRouter(tags=["ops"])
BOOTED_AT = time.time()

@router.get("/healthz", include_in_schema=False)
async def liveness() -> dict:
    """Checks nothing external. If the event loop can answer, the process is alive.
    A dependency check here means a database blip restarts every pod at once."""
    return {"status": "ok", "uptime_s": round(time.time() - BOOTED_AT)}

@router.get("/readyz", include_in_schema=False)
async def readiness(db: DbSession, redis: RedisDep, response: Response) -> dict:
    checks: dict[str, str] = {}

    async def probe(name: str, coro, timeout: float) -> None:
        started = time.perf_counter()
        try:
            # A readiness probe without a timeout is how one slow dependency
            # hangs the probe, which the platform then reads as "not ready".
            await asyncio.wait_for(coro, timeout=timeout)
            checks[name] = f"ok in {(time.perf_counter() - started) * 1000:.0f}ms"
        except asyncio.TimeoutError:
            checks[name] = f"timeout after {timeout}s"
        except Exception as exc:
            checks[name] = f"error: {type(exc).__name__}"

    # SELECT 1 proves the pool can hand out a connection AND the server answers.
    # `SELECT 1` is not a real query - it is deliberately the cheapest possible one.
    await probe("postgres", db.execute(text("SELECT 1")), timeout=1.0)
    await probe("redis", redis.ping(), timeout=0.5)

    healthy = all(v.startswith("ok") for v in checks.values())
    response.status_code = (status.HTTP_200_OK if healthy
                            else status.HTTP_503_SERVICE_UNAVAILABLE)
    return {"ready": healthy, "checks": checks, "version": "1.4.0"}

In production

Retries without a budget are how a small failure becomes an outage. Three services in a chain each retrying three times is 27 calls to the thing that is already struggling. Retry only idempotent operations, only on 5xx and connection errors (never on 4xx — the answer will not change), cap total attempts across the chain, use exponential backoff with jitter, and put a circuit breaker in front of anything known to be flaky. The badge vendor is known to be flaky; that is why it is behind Kafka on Sheet 11 and not on the request path at all.

Drill — the request path
Walk me through everything that happens between the TCP socket and your handler function.

The kernel completes the handshake and accept() hands the server a file descriptor. The ASGI or HTTP server reads bytes, parses the request line, headers and body into a structure, and hands it to the application. Middleware runs in registration order — CORS, request id, timing. The router matches method and path to a function, extracting path parameters. Dependencies resolve in order: settings, a database session, the decoded user, the role check. Parameters are coerced and validated; a failure short-circuits to 422 without calling the handler. Only then does your code run. On the way out the return value is serialised through the response model, middleware unwinds in reverse, and the bytes go back on the same socket. Follow-up: “where would you add a timeout?” — on every outbound call inside the handler, and at the server for the request as a whole.

In FastAPI, when should a handler be async def and when plain def?

async def when everything inside it is awaitable — httpx, asyncpg, an async SQLAlchemy session. Plain def when the work is blocking and there is no async version, because FastAPI runs plain functions in a thread pool where blocking is harmless. The failure case is the mix: a blocking call inside an async def parks the entire event loop, so every other request being served by that worker stalls too. The symptom is p99 latency collapsing while CPU sits near idle.

How does dependency injection make a service testable? Be specific.

Because the handler never constructs its collaborators, it only declares them. The framework owns the graph, so a test can replace any node. In FastAPI, app.dependency_overrides[get_db_session] swaps in a session bound to a transaction that is rolled back after the test, and get_current_user becomes a lambda returning a fake manager — no token minting, no auth server. In NestJS the equivalent is Test.createTestingModule with { provide: CoreHttpClient, useValue: mock }. Without DI the alternative is monkey-patching module globals, which is order-dependent and leaks between tests.

What status code do you return when a client creates something that already exists?

409 Conflict. 400 is for a malformed request and 422 for one that failed validation; this request was well formed and permitted, and the current state of the resource refused it. Return a body naming the conflicting resource so the client can act. Follow-up: “what if it was a retry of a request that actually succeeded?” — then it should be 200 or 201 with the original resource, keyed off an Idempotency-Key header. Sheet 05.

Where do you put a timeout, and what number do you choose?

On every outbound call without exception: HTTP clients, database statements, cache reads, queue publishes. The number comes from the chain, not from taste — each layer's timeout must be shorter than its caller's, so browser 30 s, gateway 10 s, core 5 s, vendor 2 s. If a downstream timeout exceeds the upstream one, the caller has already given up while you still hold a worker slot, a connection and a socket for an answer nobody will read. Separate the connect timeout from the read timeout; a connect that takes a second means the host is gone.

How do you deploy a new version without dropping in-flight requests?

On SIGTERM, first fail the readiness probe and keep serving for about five seconds, because Kubernetes removes the endpoint asynchronously and the load balancer needs time to notice. Then stop accepting new connections and let in-flight requests finish. Then close the database pool, the Redis client and flush the queue producer. Then exit, with a hard deadline shorter than terminationGracePeriodSeconds. Skipping the first step is what causes intermittent 502s on every deploy — the classic symptom that looks random and is not.

JWT or server-side sessions?

Sessions store state server-side and the cookie holds only an opaque id: revocation is instant, but every request costs a lookup and all services need the session store. JWTs are self-contained, so verification is a local signature check — that is what lets the gateway and the core both authorise without a shared database — but you cannot un-issue one. Use both: a 15-minute access token so a stolen one expires quickly, and a refresh token whose jti is recorded in Redis so logout and revocation genuinely work.

Why is the response model important? Is it not just documentation?

It does three jobs. It filters: fields not declared on the model never reach the socket, so adding internal_risk_score to the table cannot leak it through the API. It is the contract: it generates the OpenAPI schema that generates the frontend's typed client. And it validates outbound data, so a handler returning a bad status string fails in CI rather than corrupting the UI. Drop it and you have chosen to make every future database migration a potential data-exposure incident.

Your FastAPI service has 4 workers and pool_size=10. How many concurrent requests can it handle?

Two different numbers. It can hold thousands of connections, because a coroutine awaiting a socket costs kilobytes. But at most 40 can be executing a query at once, because the pool is per worker. Past that, requests block at pool_timeout and latency climbs while the database looks idle. Multiply by replicas before you scale: 3 pods is 120 connections, and the worker and the reconciler need some of max_connections too.

Why does a thrown error inside an Express async handler not reach your error middleware?

Express 4 calls the handler and ignores the promise it returns. A rejection therefore becomes an unhandled rejection rather than a call to next(err), so the error middleware never runs, no response is written, and the client hangs until it times out. Fix it with a wrapper — const ah = fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next) — or upgrade to Express 5, which forwards rejected promises automatically. Also remember error middleware is identified by having exactly four parameters.
