Git, Docker, GitHub Actions and Kubernetes — the machinery that turns a commit on your laptop into a running process serving employees. The idea underneath all four: make the path from change to production so short and so boring that shipping stops being an event.

Commit to production

The whole week on one drawing. Each stage exists to catch a specific class of problem as cheaply as possible — and the order is deliberate: the fastest checks run first.

1
Fast checks first, and the human last. A reviewer should never be the one who discovers a formatting problem or a failing test — that wastes the scarcest resource in the pipeline. If the whole pull request run takes more than about ten minutes, people stop waiting for it and start merging on hope.
2
Squash merges keep main readable. One commit per change, each one revertable in a single command, each one bisectable. The messy exploration stays in the pull request where it belongs.
3
Tag images with the commit SHA, never latest. Then any running container can be traced back to the exact source that built it, and a rollback is a redeploy of a known tag rather than a rebuild you hope produces the same thing.
4
One manual gate, at the last possible moment. Everything before it is automatic. The gate exists so a person chooses when production changes, not whether the code is good — the pipeline already answered that.

Git

Most Git confusion disappears once you know what the objects are. It is not a diff tool; it is a content-addressed store of snapshots, with movable labels pointing into it.

The object model

Merge or rebase

the working rule, and the commands that get you out of trouble
# RULE: rebase your own unpushed work to keep it tidy. Merge anything shared.
#       Never rebase a branch other people have based work on.

git pull --rebase                 # replay your local commits on top of origin
git rebase -i HEAD~4              # squash, reword, drop before opening a PR

# --- Recovery. Almost nothing in Git is truly lost for 90 days. ---
git reflog                        # every position HEAD has held, including
                                  # "lost" commits after a bad reset or rebase
git reset --hard HEAD@{3}         # go back to where you were three moves ago

git restore --source=HEAD~2 app/main.py    # one file, from an old commit
git revert a1b2c3d                # a NEW commit undoing an old one - the only
                                  # safe undo for something already pushed
git cherry-pick a1b2c3d           # take one commit from another branch

git bisect start
git bisect bad                    # this commit is broken
git bisect good v1.2.0            # this one was fine
                                  # Git binary-searches; ~10 steps for 1000 commits
git bisect run pytest tests/test_approval.py    # or automate it entirely

# --- The one command that destroys work permanently ---
git clean -fd                     # deletes untracked files. No reflog. No undo.
Interviewers ask

“You pushed a secret to main. What do you do?” — rotate the secret first, before touching Git, because the push may already have been mirrored, cached by a scanner or cloned. Then rewrite history with git filter-repo or BFG, force-push, and tell everyone with a clone to re-clone. Rewriting without rotating protects nothing, and that is the half of the answer most candidates give.

Docker

A container is not a small virtual machine. It is a normal process on the host kernel, with namespaces limiting what it can see and cgroups limiting what it can use.

services/core/Dockerfile — multi-stage, non-root, small
# ---------- stage 1: build ----------
FROM python:3.12-slim AS builder
WORKDIR /app

# Dependencies first, so this layer survives source changes.
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---------- stage 2: runtime ----------
FROM python:3.12-slim AS runtime

# A non-root user. Without this, a container escape starts as root on the host.
RUN useradd --create-home --uid 10001 appuser
WORKDIR /app

# Only the installed packages come across - not pip's cache, not build tools,
# not the compiler that needed to exist to build a wheel.
COPY --from=builder /install /usr/local
COPY --chown=appuser:appuser ./app ./app

USER appuser
EXPOSE 8000

# Distinct from the Kubernetes probes below, but useful for Compose and ECS.
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8000/healthz')"

# Exec form, not shell form. Shell form wraps the process in /bin/sh, which
# does not forward SIGTERM, so your container is killed rather than shut down.
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

# Single stage:  1.1 GB, runs as root, ships gcc and pip's cache.
# Multi-stage:    180 MB, runs as appuser, nothing but runtime dependencies.
RuleWhy it matters
Pin base image tags, ideally by digestpython:3.12-slim changes underneath you. @sha256:... makes the build reproducible.
Write a .dockerignoreWithout it, .git, node_modules and .env are sent to the daemon — slow builds, and secrets baked into layers.
Never COPY a secretDeleting it in a later layer does not remove it; the earlier layer still contains it and anyone can extract it. Use build secrets or inject at runtime.
One process per containerThe orchestrator restarts containers, not processes inside them. Two processes means one can die invisibly.
Log to stdout and stderrThe platform collects streams. Writing to a file inside a container means the logs vanish with it.
Handle SIGTERMYou get a grace period to finish in-flight requests. Ignore it and you drop requests on every single deploy.
Scan in CItrivy image fails the build on a critical CVE. Cheaper than finding it in production.

GitHub Actions

The pipeline in Drawing 09-A, as code that lives beside the code it builds.

.github/workflows/core.yml
name: core

on:
  pull_request:
    paths: ["services/core/**", ".github/workflows/core.yml"]
  push:
    branches: [main]

concurrency:
  # A new push cancels the in-progress run for the same branch. Without this
  # you queue five runs of a branch you have already fixed.
  group: core-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env: { POSTGRES_PASSWORD: test, POSTGRES_DB: test }
        options: >-
          --health-cmd pg_isready --health-interval 5s --health-retries 10
        ports: ["5432:5432"]
      redis:
        image: redis:7-alpine
        ports: ["6379:6379"]

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip                      # restores ~/.cache/pip between runs

      - run: pip install -r services/core/requirements.txt -r requirements-dev.txt
      - run: ruff check services/core     # fastest check first
      - run: mypy services/core
      - run: pytest services/core -q --cov=app --cov-fail-under=80
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/test
          REDIS_URL: redis://localhost:6379

  build:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      id-token: write                     # for OIDC - see Sheet 07
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111122223333:role/badgedesk-deploy
          aws-region: ap-south-1
      - uses: aws-actions/amazon-ecr-login@v2

      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          context: services/core
          push: true
          tags: ${{ steps.ecr.outputs.registry }}/badgedesk-core:${{ github.sha }}
          cache-from: type=gha            # layer cache across runs
          cache-to: type=gha,mode=max

      - uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ steps.ecr.outputs.registry }}/badgedesk-core:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: "1"                  # fail the build, do not just warn

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging                  # automatic
    steps:
      - run: aws ecs update-service --cluster badgedesk-staging \
               --service core --force-new-deployment

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production               # protected: requires an approver
    steps:
      - run: aws ecs update-service --cluster badgedesk-prod \
               --service core --force-new-deployment
Red pencil — Actions security

Never use pull_request_target with a checkout of the pull request head: that runs untrusted code from a fork with access to your repository secrets, and it is the standard supply-chain attack on CI. Pin third-party actions to a full commit SHA rather than a tag, because a tag can be moved. Set permissions explicitly at the top of every workflow, since the default token is more powerful than most jobs need. And never interpolate ${{ github.event.issue.title }} or any other user-controlled value directly into a run: block — that is shell injection with extra steps.

Kubernetes

A control loop that continuously moves the cluster's actual state towards the desired state you declared. Every object makes more sense once you see it that way.

infra/k8s/provisioning-worker.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: provisioning-worker
spec:
  replicas: 3
  selector:
    matchLabels: { app: provisioning-worker }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1            # one extra pod during rollout
      maxUnavailable: 0      # never drop below 3 healthy - zero downtime
  template:
    metadata:
      labels: { app: provisioning-worker }
    spec:
      serviceAccountName: provisioning-worker      # IRSA - maps to an IAM role
      containers:
        - name: worker
          image: 1111.dkr.ecr.ap-south-1.amazonaws.com/worker:a1b2c3d
          ports: [{ containerPort: 8080 }]

          # Requests are what the scheduler reserves. Limits are the hard cap.
          # No requests means the scheduler is guessing, and your pod is the
          # first one evicted when a node runs short.
          resources:
            requests: { cpu: 100m, memory: 256Mi }
            limits:   { cpu: 500m, memory: 512Mi }

          # THREE PROBES, THREE DIFFERENT QUESTIONS:
          startupProbe:      # "has it finished booting?" - protects slow starts
            httpGet: { path: /healthz, port: 8080 }
            failureThreshold: 30
            periodSeconds: 2
          readinessProbe:    # "should it receive traffic?" - failing removes it
            httpGet: { path: /readyz, port: 8080 }   # checks DB and Kafka
            periodSeconds: 5
          livenessProbe:     # "is it wedged?" - failing RESTARTS the container
            httpGet: { path: /healthz, port: 8080 }  # cheap and local ONLY
            periodSeconds: 10

          envFrom:
            - configMapRef: { name: worker-config }
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef: { name: worker-secrets, key: db-password }

      terminationGracePeriodSeconds: 45   # longer than your longest request
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: provisioning-worker }
spec:
  minAvailable: 2                          # a node drain cannot take all three
  selector:
    matchLabels: { app: provisioning-worker }
the kubectl you will actually type
kubectl get pods -w                          # watch a rollout live
kubectl describe pod worker-7d4b             # EVENTS at the bottom - read these first
kubectl logs -f deploy/provisioning-worker   # follow across all pods
kubectl logs worker-7d4b --previous          # logs from the crashed instance

kubectl rollout status deploy/provisioning-worker
kubectl rollout undo   deploy/provisioning-worker    # instant, no rebuild
kubectl rollout restart deploy/provisioning-worker   # pick up a new ConfigMap

kubectl exec -it worker-7d4b -- sh           # inside the container
kubectl port-forward svc/provisioning-worker 8080:80
kubectl top pods                             # actual CPU and memory usage

#   ImagePullBackOff  - wrong tag, or the node's role cannot read ECR
#   CrashLoopBackOff  - it starts and dies. Check logs --previous.
#   Pending           - nothing will fix itself. describe it: usually the
#                       requests exceed any node's free capacity
#   OOMKilled         - it exceeded its memory limit. Raise it, or fix the leak.

DevOps
Merge or rebase — when do you use each?

Rebase your own unpushed branch to keep the history linear and readable before opening a pull request. Merge anything shared, because rebasing rewrites commits into new objects and anyone who has based work on the old ones now has a conflicting copy. In short: rebase private history, merge public history. For merging into main, squash so that each change is one revertable, bisectable commit.

You deleted a branch with unpushed commits. Are they gone?

Almost certainly not. The commit objects still exist and the reflog still records where HEAD has been, so git reflog finds the SHA and git branch recovered <sha> brings it back. Unreachable objects survive until garbage collection, roughly ninety days by default. The genuine exception is git clean, which removes untracked files that were never in Git at all — nothing recovers those.

Is a container a lightweight VM?

No. A VM virtualises hardware and runs its own kernel; a container is ordinary processes on the host kernel, isolated by namespaces (what it can see) and constrained by cgroups (what it can use). That is why containers start in milliseconds, why the image contains no kernel, and why a Linux container needs a Linux kernel underneath — which on Windows is what WSL2 provides.

Your Docker builds take five minutes on every commit. Why?

Almost always instruction order: COPY . . sitting above the dependency install, so any source change invalidates the install layer and everything below it. Move the manifest copy and install above the source copy. Then add a .dockerignore so the build context is not sending .git and node_modules, use multi-stage so build tools never reach the final image, and enable a registry or GitHub Actions layer cache in CI.

Explain liveness, readiness and startup probes.

Startup asks “has it finished booting?” and suspends the other two until it passes, which protects slow-starting applications from being killed. Readiness asks “should this pod receive traffic?” and failing it removes the pod from the Service without restarting it — this is what makes zero-downtime rollouts work. Liveness asks “is this process wedged?” and failing it restarts the container. Never check a database in liveness: a database blip then restarts every pod simultaneously and turns a blip into an outage.

What actually happens during kubectl apply of a new image tag?

The Deployment's pod template changes, so a new ReplicaSet is created for that version. Governed by maxSurge and maxUnavailable, it scales the new one up and the old one down: each new pod must pass its readiness probe before it receives traffic and before the next old pod is removed. The old ReplicaSet is kept at zero replicas, which is why kubectl rollout undo is instant — it simply scales it back up.

How do you deploy with zero downtime?

Four things together. Correct readiness probes so traffic only reaches pods that can serve. maxUnavailable: 0 so capacity never dips. Graceful shutdown — handle SIGTERM, stop accepting new work, finish in-flight requests, with terminationGracePeriodSeconds longer than the longest request. And backwards-compatible database migrations, because during the rollout both versions are running against the same schema. The last one is the one people forget, and it is the one that causes the outage.

What are the four DORA metrics and why do they matter?

Deployment frequency, lead time for change, change failure rate, and time to restore service. They matter because they measure the system rather than the individual, and because the counter-intuitive finding is that speed and stability rise together — teams that deploy often have lower failure rates, since small changes are easier to verify and to reverse. If asked how you would improve a team's delivery, these give you a structure rather than opinions.

How do you handle secrets in CI/CD?

Do not store them where you can avoid it: OIDC federation lets GitHub Actions assume an AWS role with no stored credentials, and the trust policy pins it to one repository and branch. For what remains, use the platform's encrypted secret store, never .env in the repository, and inject at runtime rather than baking into an image — a secret in an image layer is permanent even if a later layer deletes it. Add secret scanning in pre-commit and in CI, and rotate on a schedule so that rotation is routine rather than an emergency.

A pod is in CrashLoopBackOff. Walk through your debugging.

kubectl describe pod first, and read the Events at the bottom — they usually name it outright. Then kubectl logs --previous for the output of the instance that died, since the current one may not have got far enough to log. The common causes are a missing environment variable or secret, a failing liveness probe with too short a threshold, an OOMKilled status meaning the memory limit is too low, or a dependency that is not reachable from that namespace. Check the image tag too — ImagePullBackOff looks similar and is a completely different problem.
