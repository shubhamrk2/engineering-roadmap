Three things must agree

Terraform is not a deployment tool and it is not a wrapper around the AWS CLI. It is a reconciliation loop over three separate pictures of your infrastructure. Learn this one drawing and you can debug Terraform for the rest of your career without reading a single blog post.

1
Your configuration is desired state, not instructions. A .tf file is a description of the end result: “there is a VPC with this CIDR, and four subnets in it.” You never write “create a VPC”. Terraform decides whether creating is what is needed. This is the single largest mental shift coming from shell scripts.
2
State is a cache with authority. It maps each address in your config (aws_vpc.main) to a real resource ID (vpc-0f3a1c9e) plus a full snapshot of that resource's attributes. Without it, Terraform cannot tell “create this” from “this already exists and is correct”. It is not a log and it is not a backup — it is the index.
3
The cloud is the only picture that is actually true, and it is the one Terraform looks at least often. It changes without asking you: an autoscaler resizes something, AWS deprecates a default, a colleague fixes an outage at 02:00 in the console.
4
plan is a three-way diff and it writes nothing. First it refreshes: for every resource in state, it calls the API and updates its snapshot. Then it compares that refreshed state against your configuration and prints what it would take to close the gap. Running plan a hundred times costs you a hundred sets of API calls and nothing else.
5
apply is the reconciliation. It walks the dependency graph, calls create/update/delete APIs in order, and after each resource succeeds it writes the new state. Two writes per resource, in effect: one to the cloud, one to state. An apply that dies halfway leaves both half-done — and that is fine, because the next plan just diffs again.
6
Drift is a change to picture 3 that pictures 1 and 2 never heard about. The next plan refreshes, notices the security group is wider than state remembers, and offers to narrow it back — silently undoing the 02:00 fix. This is why “who has console write access in prod” is a Terraform question, not just a security question.
7
Three failure shapes, and you will hit all three. Someone deleted a resource by hand, so state is stale and Terraform recreates it. Someone created a resource by hand, so apply collides with it and you must import. Or two people applied at once and the state file now describes a system that never existed. Locking prevents the third; nothing prevents the first two except discipline.
Interviewers ask

“What does terraform plan actually do?” The weak answer is “it shows you what will change.” The answer that lands: “It refreshes the state file against the live API, then diffs the refreshed state against my configuration, then prints the ordered set of create, update, replace and destroy operations needed to close the gap. It takes no write locks on the cloud and changes nothing — but it does read every resource in state, so on a large workspace it is slow and it does hit API rate limits.”

Declarative versus imperative, concretely

The difference is not syntax. It is who owns the decision about what to do. In the imperative version you own it, so you must handle every starting condition. In the declarative version the tool owns it, so you only describe the destination.

Imperative — you write the steps
scripts/create-reports-bucket.sh
#!/usr/bin/env bash
set -euo pipefail
B=badgedesk-prod-audit-reports

# Does it already exist? You must ask, and handle both answers.
if aws s3api head-bucket --bucket "$B" 2>/dev/null; then
  echo "exists, skipping create"
else
  aws s3api create-bucket --bucket "$B" \
    --create-bucket-configuration LocationConstraint=ap-south-1
fi

# Is versioning already on? Turning it on twice is fine here,
# but you have no idea whether it was on before you ran this.
aws s3api put-bucket-versioning --bucket "$B" \
  --versioning-configuration Status=Enabled

aws s3api put-public-access-block --bucket "$B" \
  --public-access-block-configuration \
  "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"

# And there is no way to answer "what does this script
# believe the bucket looks like right now?"
Declarative — you write the destination
data.tf
resource "aws_s3_bucket" "reports" {
  bucket = "badgedesk-prod-audit-reports"
}

resource "aws_s3_bucket_versioning" "reports" {
  bucket = aws_s3_bucket.reports.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_public_access_block" "reports" {
  bucket                  = aws_s3_bucket.reports.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# No `if`. No ordering. No "does it exist".
# `plan` answers "what is different"; the graph
# answers "in what order".

Which and when: use declarative IaC for anything that persists — networks, databases, roles, buckets, clusters. Keep imperative scripts for genuinely one-shot operations that have no desired end state: rotating a key today, running a backfill, taking a manual snapshot before a risky migration.

The language

HCL has about eight constructs. This section is all of them, in the order you will meet them, with the two that cause real damage — count and lifecycle — given proper space.

Providers, and why you pin versions

A provider is a plugin that translates HCL into API calls. terraform init downloads it. The terraform block is the only place in the language that cannot use variables — it is read before anything is evaluated.

envs/prod/00-provider.tf
terraform {
  required_version = "~> 1.10"          # 1.10.x only. Not 1.11.
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.60"               # 5.60 up to but excluding 6.0
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}

provider "aws" {
  region = var.region

  # Applied to every resource that supports tags. Do this once, here,
  # not on 60 individual resources.
  default_tags {
    tags = {
      Project     = "badgedesk"
      Environment = var.environment
      ManagedBy   = "terraform"
      Repo        = "badgedesk-infra"
    }
  }
}

# A second provider instance for a different region, addressed by alias.
provider "aws" {
  alias  = "us_east_1"
  region = "us-east-1"                  # ACM certs for CloudFront live here
}
Why you pin, and why you commit the lock file

~> 5.60 means “any 5.x at or above 5.60”. Without it, a colleague running init next Tuesday gets provider 6.0, which renames an argument, and their plan proposes to replace your production database. terraform init writes .terraform.lock.hcl with the exact versions and their checksums — commit that file, exactly like package-lock.json. It is what makes CI and your laptop produce the same plan. Upgrade deliberately with terraform init -upgrade, in its own PR, where the plan is the review.

Resources, addresses, and data sources

A resource block says “this thing exists and I own it”. Its address is type.name — the first string is fixed by the provider, the second is a label you choose that must be unique in the module. That address is the key in the state file, the thing you type in state mv, and the thing that appears in every plan.

resource, data, and the difference between them
# Terraform CREATES, UPDATES and DELETES this. Address: aws_vpc.main
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true
  tags                 = { Name = "badgedesk-${var.environment}" }
}

# Terraform only READS this. It is looked up on every plan and never changed.
# Use data sources for things someone else owns: shared accounts, AMIs,
# the account id, a certificate the platform team manages.
data "aws_caller_identity" "current" {}

data "aws_availability_zones" "available" {
  state = "available"
}

data "aws_ssm_parameter" "vendor_api_host" {
  name = "/platform/access-control/host"     # owned by the platform team
}

output "account_id" {
  value = data.aws_caller_identity.current.account_id
}

# Referencing an attribute of another resource does two things:
#   1. substitutes the value at apply time
#   2. creates an edge in the dependency graph
resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.main.id                   # <- both, from one expression
}
Red pencil — renaming is not free

Changing resource "aws_vpc" "main" to resource "aws_vpc" "core" does not rename anything in AWS. Terraform sees one address disappear and a new one appear, so the plan is destroy the VPC and create another one. The label is part of the identity. If you must rename, add a moved block (shown in the state section) or use terraform state mv; never just edit the label and apply.

Variables, locals and outputs

Three different jobs that beginners mix up. Variables are the module's inputs — things a caller sets. Locals are named expressions to stop repeating yourself; they are computed, not settable. Outputs are the module's return values.

envs/prod/variables.tf
variable "region" {
  description = "AWS region. BadgeDesk is Mumbai; BLR-01 and HYD-01 are both in-country."
  type        = string
  default     = "ap-south-1"
}

variable "environment" {
  description = "dev | staging | prod. Drives sizing, backups and deletion protection."
  type        = string                        # no default: must be supplied

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be one of dev, staging, prod."
  }
}

variable "vpc_cidr" {
  type    = string
  default = "10.20.0.0/16"

  validation {
    condition     = can(cidrnetmask(var.vpc_cidr))
    error_message = "vpc_cidr must be a valid IPv4 CIDR block."
  }
}

# Object types make bad input a plan-time error rather than an apply-time one.
variable "db" {
  type = object({
    instance_class    = string
    allocated_storage = number
    multi_az          = bool
  })
  default = {
    instance_class    = "db.t4g.micro"
    allocated_storage = 20
    multi_az          = false
  }
}

variable "vendor_api_token" {
  type      = string
  sensitive = true       # redacted in plan output and in the CLI. NOT in state.
}
envs/prod/locals.tf
locals {
  name = "badgedesk-${var.environment}"

  azs = slice(data.aws_availability_zones.available.names, 0, 2)

  # A map, not a list. The keys become part of the resource address,
  # so they must be stable for the life of the infrastructure.
  public_subnets = {
    a = { cidr = cidrsubnet(var.vpc_cidr, 8, 0), az = local.azs[0] }
    b = { cidr = cidrsubnet(var.vpc_cidr, 8, 1), az = local.azs[1] }
  }

  private_subnets = {
    a = { cidr = cidrsubnet(var.vpc_cidr, 8, 10), az = local.azs[0] }
    b = { cidr = cidrsubnet(var.vpc_cidr, 8, 11), az = local.azs[1] }
  }

  is_prod = var.environment == "prod"
}

for_each versus count — the one that will bite you

Both create several copies of a resource. They differ in what the copies are named, and that naming decides whether a small edit is a one-resource change or a cascade.

the same four subnets, both ways
# count - indexed by position. Avoid for collections that change.
resource "aws_subnet" "private" {
  count             = length(var.private_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.private_cidrs[count.index]
  availability_zone = local.azs[count.index % length(local.azs)]
}
# addresses: aws_subnet.private[0] [1] [2]

# for_each over a map - keyed by a name you control. Almost always right.
resource "aws_subnet" "private" {
  for_each          = local.private_subnets
  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value.cidr
  availability_zone = each.value.az
  tags              = { Name = "${local.name}-private-${each.key}", Tier = "private" }
}
# addresses: aws_subnet.private["a"] ["b"]

# for_each also accepts a SET of strings, where the key is the value itself
resource "aws_ssm_parameter" "site_policy" {
  for_each = toset(["BLR-01", "BLR-02", "HYD-01"])
  name     = "/badgedesk/sites/${each.key}/policy"
  type     = "String"
  value    = jsonencode({ max_days = 30 })
}
# addresses: aws_ssm_parameter.site_policy["BLR-01"] ...

# The one legitimate use of count: a conditional single resource.
resource "aws_nat_gateway" "main" {
  count         = local.is_prod ? 1 : 0        # dev saves $32/month
  allocation_id = aws_eip.nat[0].id
  subnet_id     = aws_subnet.public["a"].id
}
Red pencil — for_each keys must not be computed

for_each keys become resource addresses, so Terraform must know them at plan time. Key a for_each off something that only exists after apply — an ARN, a generated id, a random_id.result — and you get “the for_each value depends on resource attributes that cannot be determined until apply”. The fix is always the same: key off something you wrote down yourself (a site code, an environment name, a subnet letter) and put the computed value in each.value, not in the key.

Expressions, functions and dynamic blocks

There is no standard library to learn. About a dozen functions cover everything you will write this week.

the functions you actually use
# String interpolation and templating
name        = "badgedesk-${var.environment}-audit"
bucket_path = "reports/${formatdate("YYYY-MM-DD", timestamp())}/summary.json"

# Networking maths - never hand-calculate a CIDR again
cidrsubnet("10.20.0.0/16", 8, 10)      # "10.20.10.0/24"
cidrhost("10.20.10.0/24", 1)           # "10.20.10.1"

# Collections
toset(["BLR-01", "BLR-02"])            # list -> set, drops order and duplicates
slice(local.all_azs, 0, 2)             # first two AZs
merge(local.base_tags, { Tier = "private" })
lookup(local.sizes, var.environment, "db.t4g.micro")   # with a default
coalesce(var.override_host, data.aws_ssm_parameter.vendor_api_host.value)
flatten([for s in aws_subnet.private : s.id])

# Encoding - jsonencode is how you write IAM policies and Lambda env vars
jsonencode({ max_days = 30, sites = ["BLR-01"] })
filebase64sha256("${path.module}/build/audit-reconciler.zip")

# Guards
can(cidrnetmask(var.vpc_cidr))         # true/false instead of an error
try(var.db.multi_az, false)

# Conditionals and comprehensions

by_site        = { for r in var.requests : r.site_id => r.id... }   # group by key

dynamic blocks generate nested blocks from a collection. Use them sparingly — they are the fastest way to make a Terraform file unreadable — but they are the only option when a provider models something as repeated blocks rather than a list argument.

dynamic — when a nested block must repeat
locals {
  report_lifecycle = {
    expire-old-reports  = { days = 400, prefix = "reports/" }
    expire-temp-exports = { days = 7,   prefix = "tmp/" }
  }
}

resource "aws_s3_bucket_lifecycle_configuration" "reports" {
  bucket = aws_s3_bucket.reports.id

  dynamic "rule" {
    for_each = local.report_lifecycle
    content {
      id     = rule.key                  # <block label>.key
      status = "Enabled"
      filter {
        prefix = rule.value.prefix       # <block label>.value
      }
      expiration {
        days = rule.value.days
      }
    }
  }
}

lifecycle — three seatbelts

lifecycle in anger
resource "aws_db_instance" "core" {
  identifier = "${local.name}"
  # ... engine, size, credentials ...

  lifecycle {
    # 1. Refuse to destroy this, ever, from any plan. A `destroy` that
    #    touches it fails with an error instead of dropping your Postgres.
    #    Removing this line is a deliberate, reviewable commit.
    prevent_destroy = true

    # 2. Do not diff these attributes. AWS rotates the password out from
    #    under us and the maintenance window drifts; we do not care.
    ignore_changes = [
      password,
      engine_version,          # patch upgrades applied by AWS
    ]
  }
}

resource "aws_security_group" "core" {
  name_prefix = "${local.name}-core-"     # not `name` - see below
  vpc_id      = aws_vpc.main.id

  lifecycle {
    # 3. When a change forces replacement, make the NEW one before
    #    destroying the old one. Without this, replacing a security group
    #    fails: AWS will not delete one that still has ENIs attached,
    #    and the ENIs cannot move until the replacement exists.
    create_before_destroy = true
  }
}
Red pencil — ignore_changes as a rug

ignore_changes does not fix drift, it hides it. Adding ignore_changes = [tags] because a plan is noisy means that from now on nobody — including you at 03:00 — can see tag drift on that resource. Use it only where another system legitimately owns the field: an autoscaler owning desired_count, AWS owning a rotated password, a deployment pipeline owning an image tag. And never reach for ignore_changes = all; at that point the resource is not managed, and you should say so out loud.

The dependency graph

You never specify order. Terraform builds a directed acyclic graph from your references and walks it, creating up to ten resources in parallel by default and destroying in exactly reverse order.

terminal — look at your own graph
terraform graph | dot -Tsvg > graph.svg     # needs graphviz; big but readable

# The far more useful daily version - what depends on what, in the plan
terraform plan -out=tfplan
terraform show -json tfplan | jq -r '
  .resource_changes[] | "\(.change.actions[0])  \(.address)"'
# create  aws_subnet.private["b"]
# update  aws_s3_bucket_lifecycle_configuration.reports
# replace aws_db_subnet_group.core
In production

depends_on is for real ordering that references cannot see: the log group above, an IAM policy that must exist before a service assumes the role, a NAT gateway that needs the internet gateway attached first even though it only references the EIP. It is not a fix for “my apply failed once”. Every unnecessary depends_on serialises a branch of the graph and makes your apply slower, and on a module it forces the entire module to wait for the entire target.

State

The file at the centre of Drawing 10-A. Understand what is in it, where it must live, and what to do when it is wrong, and you have covered most of what senior engineers actually get asked about Terraform.

What is actually in the file

JSON. A serial number, a lineage id, your outputs, and one entry per resource instance holding its real identifier, a full snapshot of every attribute, and the list of addresses it depended on.

Red pencil — state contains your secrets, in plain text

Look at password above. Terraform stores every attribute it manages, including generated passwords, private keys, and the plaintext of any aws_secretsmanager_secret_version you create. sensitive = true only redacts CLI output; it does nothing to the file. So the state file is a credentials file and must be treated as one: never in Git, never in a public bucket, encrypted at rest, versioned, and with a bucket policy that lists the handful of roles allowed to read it. The corollary: it is better to have Terraform create an empty secret and let the application write the value, or reference a secret created outside Terraform with a data source, than to have Terraform generate every credential.

Remote state and locking

The default backend writes terraform.tfstate next to your files. That is fine for one person learning and untenable for two people. Two laptops each holding their own copy of the truth means the second apply silently deletes what the first one built.

envs/prod/00-provider.tf — the S3 backend
terraform {
  backend "s3" {
    bucket = "badgedesk-tfstate"          # versioning ON, public access BLOCKED,
    key    = "prod/infra.tfstate"         # SSE-KMS, and a bucket policy that
    region = "ap-south-1"                 # lists exactly who may read it
    encrypt = true

    # Terraform 1.10+: locking via a conditional-write .tflock object in S3.
    use_lockfile = true

    # Before 1.10 you needed a DynamoDB table with a "LockID" string
    # partition key, and this line instead:
    # dynamodb_table = "badgedesk-tfstate-locks"
  }
}
In production

Locks get stranded: someone's laptop sleeps mid-apply, or CI is cancelled between acquiring the lock and releasing it. Terraform prints the lock id and tells you to run terraform force-unlock 4f2b…. Before you do, find the human. Force-unlocking a lock that is genuinely still held is how you get the corruption the lock existed to prevent. And enable S3 versioning on the state bucket on day one — it is the only undo you have.

Operating on state

terminal — the five state commands worth knowing
# What does Terraform think it owns?

# aws_db_instance.core

terraform state mv 'aws_subnet.private[0]' 'aws_subnet.private["a"]'

# Read-only drift check: refresh state, show what changed in the cloud,
# and do not propose to change anything back.
terraform plan -refresh-only

Prefer moved blocks to state mv where you can. They are code, so they get reviewed, and they run for everyone including CI — nobody has to remember to type a command.

You built Sheet 07 by clicking. Those resources exist and Terraform has never heard of them. Importing is how you take them over without deleting and rebuilding.

# the import id is - a bucket name, an instance id, an ARN, sometimes a

terminal — the import loop
# Step 2: let Terraform write the matching config for you.
terraform plan -generate-config-out=generated.tf

# Step 3: read generated.tf. It is verbose and includes computed fields
# you must delete. Move the parts you want into data.tf, keep the arguments
# that describe intent, drop the ones AWS filled in.

# Step 4: plan until it says "no changes". THIS IS THE WHOLE JOB.
terraform plan
# Plan: 2 to import, 0 to add, 0 to change, 0 to destroy.

terraform apply       # records them in state, changes nothing in AWS

# The older imperative form still works and is handy for one-offs:
terraform import 'aws_s3_bucket.reports' badgedesk-prod-audit-reports
Red pencil — and never edit state by hand

Two rules. First: an import is not finished until plan reports no changes. If you apply while the plan still shows ~ 14 to change, you have just reverted a year of console tweaks on live infrastructure. Second: do not open the state file in an editor. Every field you might want to change has a command — state mv, state rm, import, taint/-replace. Hand-editing breaks the serial and lineage bookkeeping and turns a recoverable mess into an unrecoverable one.

The workflow

Six commands, one of which matters. Everything in this section is about reading plan output properly, because that is the skill that stops you destroying a database.

init, fmt, validate, plan, apply, destroy

terminal — the loop you will run fifty times this week
terraform init            # download providers, configure the backend, write the
                          # lock file. Re-run after changing providers or backend.
terraform fmt -recursive  # canonical formatting. Run it on save; CI checks it.
terraform validate        # syntax and type checking only. No API calls, no creds.

terraform plan -out=tfplan          # save the plan so apply cannot drift from it
terraform apply tfplan              # apply EXACTLY that plan, no second prompt

terraform apply                     # or: plan and prompt in one step, for dev
terraform destroy                   # reverse dependency order. Read it first.

terraform output -raw db_endpoint   # a value, unquoted, for a shell pipeline
terraform show                      # human-readable dump of current state

# Useful flags
terraform plan  -detailed-exitcode  # 0 no change, 1 error, 2 changes pending
terraform apply -lock-timeout=120s  # wait for a colleague instead of failing
terraform apply -parallelism=5      # be kinder to API rate limits
Why -out=tfplan is not optional in CI

terraform apply with no argument plans again and then asks. In CI, where the approval step happens minutes or hours after the plan a human reviewed, that means you approve one plan and apply a different one. Saving the plan and applying the file makes the artefact you reviewed the artefact that runs. The catch: the plan file contains state, so it contains secrets — if you upload it as a CI artefact it needs the same protection as the state bucket.

Red pencil — -/+ means it will not be the same thing afterwards

-/+ is destroy then create. Every attribute that was “known after apply” the first time will be a different value: a new ARN, a new endpoint DNS name, a new IP, an empty disk. For a subnet group that is survivable; for an aws_db_instance it is your production database gone, and for an EBS volume it is data gone. Find the # forces replacement comment — Terraform always tells you which single attribute caused it — and decide whether you meant it. The usual culprits are name, availability_zone, subnet_id and anything the cloud cannot change without rebuilding.

The defence is prevent_destroy = true on anything that holds data. With it set, the plan refuses outright rather than helpfully offering to proceed:

Targeting, and why it is a smell

terminal — -target and -replace
# Apply only part of the graph. Terraform prints a warning every time,
# because the resulting state is not what your configuration describes.
terraform apply -target='module.network.aws_subnet.private["b"]'

# Force one resource to be recreated without changing any code.
# The modern replacement for `terraform taint`.
terraform apply -replace='aws_lambda_function.audit'

-target is a recovery tool, not a workflow. It exists for exactly two situations: unwinding a half-failed apply, and breaking a genuine chicken-and-egg cycle on the very first apply of a new account. If you find yourself typing it routinely, the real problem is that your root module is too big — split it, so that the blast radius of one apply is a thing you actually want to change together. An interviewer who hears “we always use -target” will ask why, and the honest answer is always architectural.

Terraform has already created or modified some resources. They are recorded

There is no rollback and you should not want one. The subnet and the subnet group exist and are recorded; only the database change failed. locals {
  # Keys "a" and "b" become part of the resource address forever.
  # Never derive them from something that can reorder.
  public = {
    for i, az in var.azs : substr(az, -1, 1) => {
      az   = az
      cidr = cidrsubnet(var.cidr, 8, i)
    }
  }

  private = {
    for i, az in var.azs : substr(az, -1, 1) => {
      az   = az
      cidr = cidrsubnet(var.cidr, 8, i + 10)
    }
  }

  nat_keys = var.single_nat_gateway ? [keys(local.public)[0]] : keys(local.public)
}

# network

A two-AZ VPC for BadgeDesk: public subnets with an internet gateway, private
subnets behind NAT, and one route table per private subnet.

| Name               | Type         | Default | Description                        |
|--------------------|--------------|---------|------------------------------------|

Red pencil — why workspaces are the wrong tool for prod

Workspaces isolate state and nothing else. The consequences bite in order: the backend block is shared, so dev state and prod state sit in the same bucket under the same permissions; the provider block is shared, so you cannot put prod in a separate AWS account without a conditional; the code is shared, so “prod is bigger” becomes terraform.workspace == "prod" ? "db.r6g.large" : "db.t4g.micro" sprinkled across ten files; and the current workspace is invisible — it is a piece of CLI state, not something in the diff. The failure mode is famous and it is exactly what you think: you forget to run terraform workspace select and apply a dev change to prod. A directory has none of these properties, and a wrong directory is visible in the shell prompt, the PR, and the CI job name.

In production — the artefact boundary

Notice what the Lambda block does not do: it does not zip your Python. Building an artefact inside Terraform means every plan depends on a build, the hash changes when it should not, and two engineers get different plans from the same commit. The pipeline on Sheet 09 builds the zip once, uploads it to the artefact bucket under an immutable key, and passes the version and hash in as variables. Terraform owns the function; the pipeline owns the code. That line is the subject of the last drawing on this sheet.

Terraform in CI/CD

The point of putting infrastructure in Git is the pull request. This pipeline makes plan a review artefact and makes apply something only main can do, with a human in the loop and no long-lived AWS keys anywhere.

on:
  pull_request:
    paths: ['envs/**', 'modules/**', '.github/workflows/terraform.yml']

  TF_VERSION: 1.10.5
  TF_IN_AUTOMATION: 'true'

jobs:
  plan:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: envs/prod
    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - name: fmt
        run: terraform fmt -check -recursive -diff
        working-directory: .            # check the whole repo, not just this env

      # A role with READ-ONLY IAM permissions. It can refresh state and plan;
      # it cannot create, modify or delete anything.
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/badgedesk-terraform-plan
          aws-region: ap-south-1

      - run: terraform init -input=false
      - run: terraform validate

      - uses: terraform-linters/setup-tflint@v4
      - run: tflint --recursive --format compact
        working-directory: .

      - name: checkov
        uses: bridgecrewio/checkov-action@master
        with:
          directory: envs/prod
          framework: terraform
          soft_fail: false              # a public S3 bucket fails the build

      - name: plan
        id: plan
        run: |
          terraform plan -input=false -lock-timeout=120s \
            -no-color -out=tfplan | tee plan.txt

      - name: comment the plan on the PR
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const body = fs.readFileSync('envs/prod/plan.txt', 'utf8');
            await github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: '### Terraform plan (prod)\n```\n'
                    + body.slice(-60000) + '\n```',
            });

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: prod          # <- the approval gate. Reviewers set in repo settings.
    defaults:
      run:
        working-directory: envs/prod
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - uses: aws-actions/configure-aws-credentials@v4

          role-to-assume: arn:aws:iam::123456789012:role/badgedesk-terraform-apply
          aws-region: ap-south-1

      - run: terraform init -input=false
      # Re-plan rather than passing tfplan between jobs: a plan file contains
      # state, so uploading it as an artefact means uploading your secrets.
      - run: terraform plan -input=false -lock-timeout=300s -out=tfplan
      - run: terraform apply -input=false -auto-approve tfplan

Interviewers ask

“How does your pipeline authenticate to AWS?” The answer that ends the topic: “GitHub OIDC. The workflow requests a short-lived OIDC token, AWS STS exchanges it for temporary credentials via a role whose trust policy is scoped to our repository and the main ref. Two-machine rule

Install Terraform on your personal laptop — winget install Hashicorp.Terraform or tfenv in WSL2. On the corporate laptop with no admin rights: download the terraform_*_windows_amd64.zip, unzip a single binary into %LOCALAPPDATA%\bin and add that to your user PATH — no installer needed. In production — the test that decides

Drill — Terraform
What is the state file and why does Terraform need one at all?

It is a JSON map from the addresses in my configuration to the real resource IDs in the cloud, plus a full snapshot of each resource's attributes and its dependencies. Terraform needs it because a cloud API cannot answer “is this my VPC, the one called aws_vpc.main?” — there is no field for that. Without state, every plan would either try to create everything again or would have to discover and match resources heuristically. It is also what makes destroy possible in the correct order, and what records the metadata AWS does not store, such as generated passwords. Follow-up they will ask: “so what happens if you delete it?” — Terraform forgets it owns anything and the next plan proposes to build a second copy of your entire environment.

Two engineers run terraform apply at the same time. What happens?

With locking configured, the first writes a lock — a conditional .tflock object in S3, or a conditional PutItem in DynamoDB — and the second's conditional write fails, so it blocks and retries until -lock-timeout expires. Without locking, both read serial 118, both compute a plan against it, both apply, and both write serial 119. The loser's resources now exist in AWS but are absent from state: orphaned, billed for, invisible to Terraform. Recovery means restoring an earlier state version from the bucket and importing what was lost. Follow-up: “what if the lock is stuck?” — terraform force-unlock <id>, but only after confirming with a human that no apply is actually running.

count versus for_each — which and why?

for_each over a map or set, almost always. With count the resource address is a list index, so removing an element in the middle shifts every element after it: Terraform sees [1]'s attributes change and [2] disappear, and it destroys and recreates real infrastructure to reindex a list. With for_each the address is a stable key I chose, so removing one entry destroys exactly one resource. I use count only for zero-or-one conditionals like count = local.is_prod ? 1 : 0. Follow-up: “how do you migrate an existing count resource?” — moved blocks, or terraform state mv per instance, then confirm the plan is empty before applying.

How do you bring an existing, hand-created resource under Terraform?

Write an import block with the target address and the provider's import id, then run terraform plan -generate-config-out=generated.tf to get a starting configuration. Trim the generated file down to the arguments that express intent, and iterate on plan until it reports zero changes — that is the actual work, and it is where you discover the four settings someone changed in the console two years ago. Only then apply, which writes state and touches nothing in the cloud. The dangerous mistake is applying while the plan still shows changes, because you then revert live configuration you never intended to.

How do you handle secrets with Terraform?

Starting from the fact that state stores every managed attribute in plain text, so sensitive = true protects the terminal, not the file. So: the state backend is encrypted, versioned, private and readable by a handful of roles — it is a credentials store and is treated like one. Terraform creates the secret container (the Secrets Manager secret, its rotation schedule, the IAM policy granting access) and where possible not the value; the application reads the secret at runtime by ARN rather than receiving it through an environment variable Terraform set. Values that must be supplied come from the pipeline's OIDC-derived credentials or a data source, never from a committed tfvars file. Follow-up: “where do the AWS credentials for Terraform itself come from?” — OIDC, short-lived, two roles, one read-only.

What is drift and how do you detect it?

Drift is a change made to the real cloud that neither the configuration nor the state file knows about — almost always a human in the console during an incident. I detect it with terraform plan -refresh-only -detailed-exitcode on a nightly schedule; exit code 2 means something changed and the job alerts. That matters because the next ordinary apply would quietly revert it. The organisational half of the answer is more important than the technical half: remove console write access in production so an emergency fix has to be a fast-tracked PR, and if a console change is unavoidable, require a same-day PR that codifies it.

Would you use Terraform to deploy your application?

No. The test is “does it change on every deploy?” An image tag or a Lambda zip changes hourly; a VPC changes quarterly. If Terraform owns the image tag then every deploy is an infrastructure apply, every plan diff is noise nobody reads carefully, and a routine deploy can pick up an unrelated pending infrastructure change. Terraform creates the ECS service, the EKS cluster, the Lambda function, the IAM role and the bucket; the application pipeline pushes the artefact and updates the running version. The grey area is Kubernetes: I will use the Terraform Kubernetes and Helm providers for cluster singletons like namespaces, cert-manager and the ingress controller, but not for application workloads, because Argo CD or the app's own pipeline reconciles those continuously and two controllers fighting over one object is a bad Tuesday.

Your plan shows -/+ on the production database. Walk me through the next sixty seconds.

I stop and find the # forces replacement comment, because Terraform always names the single attribute responsible. Then I decide whether I intended a rebuild — usually I did not; usually I changed a name, an availability zone or a subnet, which the cloud cannot alter in place. I do not apply. In the longer term, anything holding data carries lifecycle { prevent_destroy = true } so the plan errors instead of politely offering to drop the database, and the CI plan comment means a second person sees the -/+ before I do. Follow-up: “how would you actually make that change?” — create the new resource alongside, migrate data, cut over, then remove the old one, in separate applies.
