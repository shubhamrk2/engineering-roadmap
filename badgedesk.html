How to read this set

Six conventions. Learn them once and every sheet after this reads the same way.

Convention 01Colour means something

Cyan is a synchronous request or a data read — something waits for it. Brass is asynchronous: an event, a job, the thing you act on. Red pencil is the failure path and the trap that ends interviews.

Convention 02Numbered callouts

Circled numbers in a drawing map one-to-one onto the numbered notes directly beneath it. Read the drawing, then the notes, then the drawing again.

Convention 03One system throughout

Every example belongs to BadgeDesk. When Sheet 06 indexes a table, it is the same table Sheet 04 queries and Sheet 07 backs up.

Convention 04Ask / Trap / Ship panels

Interviewers ask is what gets asked out loud. Red pencil is the mistake that costs you the round. In production is what the answer looks like when real money is on it.

Convention 05Sign-off boxes

Tick a box and it is saved in this browser. The title block bottom-right tracks the whole set. Do not tick until you have typed the code yourself.

Convention 06Keyboard

/ searches the sheet index. [ and ] move to the previous and next sheet. Every code block has a copy button.

Why one product instead of twenty tutorials

The gap between SE2 and SE3 is almost never syntax. It is whether you can hold a whole system in your head and reason about what breaks when one piece is slow, down or lying to you. Tutorials teach pieces. This set teaches one system from six angles, which is the same skill an interviewer is probing when they ask “so what happens if the badge vendor takes thirty seconds to respond?”

The system you are building

BadgeDesk: an employee requests access to a building, a manager approves it, a badge gets provisioned in the physical access-control system, and a nightly job proves the two sides still agree. Small enough to finish, big enough to need every technology on your list.

1
The synchronous spine. A browser hits Next.js, which renders on the server and calls a NestJS gateway, which calls the FastAPI core. Four hops, one user waiting. Every millisecond here is a millisecond the employee stares at a spinner — which is exactly why the slow work is pushed off this path at callout 4.
2
The trust boundary. The dashed rectangle is a VPC: the gateway, the core and all three databases have no public IP. Only the load balancer in front of Next.js does. Identity is external — Entra ID says who the human is, IAM says what the machine may touch. Sheets 07 and 08.
3
Three databases, three different jobs. Postgres holds facts that must be correct and related (a request belongs to an employee, an approval belongs to a request). Redis holds facts you can afford to lose (cached site policy, rate-limit counters, idempotency keys). Mongo holds documents whose shape changes per vendor (raw audit events). Picking the wrong one of these three is the single most common design-interview failure. Sheet 06.
4
The seam. Provisioning a badge means calling a vendor system that is slow and sometimes down. So the API does not call it. The API writes a row, publishes an event to Kafka and returns 202 Accepted in 40 ms. Workers do the slow part, retry, and give up into a dead-letter topic after three attempts. This one decision is what “designing for failure” means. Sheet 11.
5
The outside world. Four consumers, four different integration shapes: a flaky vendor REST API, outbound webhooks, object storage, and an LLM with a vector index over the access-policy documents. Sheets 05, 07 and 12.
6
The platform. Terraform creates the AWS account contents. GitHub Actions tests each commit, builds one Docker image and rolls it onto EKS. CloudWatch tells you when it went wrong. Nothing above this band exists without this band. Sheets 09 and 10.
Interviewers ask

“Walk me through what happens when a user clicks Request Access.” If you can narrate Drawing 00-A end to end — naming the protocol at each hop, what is stored where, what happens when the vendor is down, and how you would know — you have just passed most of a system-design round. Come back and re-narrate this drawing at the end of every week.

Why the constraint is worth keeping even if you can afford it

Knowing that a NAT Gateway is $32 a month, that an EKS control plane bills whether or not a pod is scheduled, and that an unattached Elastic IP is charged because it is unattached, is not penny-pinching — it is the same knowledge that makes you useful on a team with a cloud budget. “How would you make this architecture cheaper?” is a standard system-design follow-up, and the candidates who answer it well are the ones who have personally paid for a mistake. Better to learn it on a $10 budget than on someone else’s $10,000 one.

The weekly rhythm

Sixteen hours a week is the target. Spread it like this, because the distribution matters more than the total — recall is built by returning to material, not by staring at it longer.

Red pencil

The failure mode for this plan is not laziness, it is tutorial drift: watching a 9-hour course at 1.75×, feeling productive, and retaining nothing. Video is for unblocking, not for learning. The rule for every sheet: you may not watch a video until you have tried the thing and got stuck. The resource lists exist to rescue you, not to schedule you.

Where the SE3 bar actually is

Interviewers are not checking whether you know a framework. They are checking which column you answer from. Use this to decide when a topic is done.

AreaSE2 answer (not enough)SE3 answer (the bar)
Languages“I use Python and JavaScript.”Explains why a Python service uses async for I/O but threads do nothing for CPU work, and why TypeScript's types vanish at runtime.
Frontend“I use React with useEffect.”Knows which state is server state and which is client state, and can say what a server component costs you.
Backend“I built REST endpoints.”Designs for retries: idempotency keys, timeouts, the difference between 400, 409, 422 and 503.

Two laptops, one workflow

A corporate laptop will fight you: no admin rights, a TLS-inspecting proxy, blocked package registries, Docker Desktop licensing. Plan around it instead of discovering it in Week 8.

Personal laptop — the build machine

Full admin. Install everything natively plus WSL2. Docker Desktop, Node, Python, Java, AWS and Azure CLIs, Terraform, a local Kafka in Compose, a real cloud account with a billing alarm.

Do here: anything that needs Docker, Kubernetes, Kafka, cloud deploys, the Saturday block.

Corporate laptop — the practice machine

Assume no admin. Use user-scope installs (winget in user mode, nvm-windows portable, Python from the Store, portable JDK), configure the proxy CA for npm and pip, and use Podman or Rancher Desktop if Docker Desktop is not licensed.

Do here: reading sheets, katas, SQL against a local Postgres, LeetCode-style drills, the Friday drill session. Never store personal cloud credentials here.

Keep the two in sync with one Git repository and a .env.example file. Full command-by-command instructions, including the proxy and no-admin workarounds, are on Sheet 01 — Machine Setup.

How to use the resource lists

Every sheet ends each subtopic with a short list. They are chosen for density, not popularity.

Rule 01One primary, one rescue

Pick a single primary source per topic and finish it. Everything else on the list is for when you are stuck on one specific thing.

Rule 02Watch at 1× with your hands on the keys

If you are not typing, you are watching television. Pause every time the instructor runs something and run it yourself first.

Rule 03Docs beat video for reference

Video is good for “why” and for a first pass. For “what are the arguments to this function”, the official docs are faster and correct.
