Interviewers ask — and you answer in your own words first

“You are stuck. What do you do?”

Attempt it, then open.

Say so, calmly, and make the stuck-ness smaller: “I am not sure how to do X efficiently; let me first do it the slow way so we have something correct.” Then shrink the input to a tiny example and trace it by hand. A brute-force answer that works beats a clever one that does not. If a library call is the gap, say “I would normally check the docs for the exact signature; here is what I expect it to do.” Follow-up: “Can you do it faster?” Name the bottleneck (the nested loop), then the data structure that removes it (a dict or set lookup).

Problem 1 — group anagrams (strings and dicts)

Prompt: “Given a list of words, group the ones that are anagrams of each other.” Clarify: case-sensitive? Does order within a group matter? What about an empty list?

p1_anagrams.py
from collections import defaultdict

def group_anagrams(words):
    groups = defaultdict(list)                 # key -> list of words with that key
    for w in words:
        key = "".join(sorted(w.lower()))       # anagrams share the same sorted letters
        groups[key].append(w)
    return list(groups.values())               # dicts keep insertion order in Python 3.7+

result = group_anagrams(["listen", "Silent", "enlist", "badge", "gabed", "x"])
print(result)       # [['listen', 'Silent', 'enlist'], ['badge', 'gabed'], ['x']]
assert result == [["listen", "Silent", "enlist"], ["badge", "gabed"], ["x"]]
assert group_anagrams([]) == []
assert group_anagrams(["a", "A"]) == [["a", "A"]]    # the case decision, stated and tested

Say: “Time O(n · k log k) for n words of length k, because of the sort; space O(n · k). If k is large I could use a 26-slot letter count as the key to get O(n · k).” Follow-up they ask: “Why defaultdict and not a plain dict?” It removes the create-if-missing step; with a plain dict you would write setdefault(key, []).append(w).

Problem 2 — parse key=value text with repeats and bad input (parsing)

Prompt: “Parse site=BLR-01; tag=a; tag=b; bad; empty= into a dict. Repeated keys become lists. Report entries you could not parse.”

p2_parse_kv.py
def parse_kv(text):
    """Return (values, rejected). Repeated keys collect into a list."""
    values, rejected = {}, []
    for chunk in text.split(";"):
        chunk = chunk.strip()
        if not chunk:
            continue                              # trailing ';' or double ';;'
        if "=" not in chunk:
            rejected.append(chunk)
            continue
        key, value = chunk.split("=", 1)          # split ONCE: the value may contain '='
        key, value = key.strip(), value.strip()
        if not key:
            rejected.append(chunk)
            continue
        if key in values:
            if not isinstance(values[key], list):
                values[key] = [values[key]]       # promote the first value to a list
            values[key].append(value)
        else:
            values[key] = value
    return values, rejected

got, bad = parse_kv("site=BLR-01; tag=a; tag=b; bad; empty=")
print(got, bad)     # {'site': 'BLR-01', 'tag': ['a', 'b'], 'empty': ''} ['bad']
assert got == {"site": "BLR-01", "tag": ["a", "b"], "empty": ""} and bad == ["bad"]
assert parse_kv("") == ({}, [])
assert parse_kv("q=a=b;;")[0] == {"q": "a=b"}     # '=' inside a value survives
assert parse_kv("=x")[1] == ["=x"]                # empty key is rejected
assert parse_kv("t=1;t=2;t=3")[0] == {"t": ["1", "2", "3"]}

You must be able to explain this line: split("=", 1). Without the 1, a value containing = (a URL, a base64 string) is cut into three parts and unpacking raises ValueError. Follow-up: “What would you change if the file is 2 GB?” Stream it line by line (a generator) instead of holding the text; the function body stays the same.

Problem 3 — two-sum: brute force, then a dict (complexity talk)

Prompt: “Return the indices of two numbers that add up to target.” Always say the slow answer first; it proves you understand the problem and gives the interviewer something to push on.

p3_two_sum.py
def two_sum_slow(nums, target):               # O(n^2): check every pair
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):     # j starts after i: never pair an item with itself
            if nums[i] + nums[j] == target:
                return (i, j)
    return None

def two_sum(nums, target):                    # O(n) time, O(n) space
    seen = {}                                 # value -> index where we saw it
    for i, n in enumerate(nums):
        need = target - n
        if need in seen:                      # O(1) average lookup
            return (seen[need], i)
        seen[n] = i                           # store AFTER checking, so [3] with target 6 does not match itself
    return None

for fn in (two_sum_slow, two_sum):
    assert fn([2, 7, 11, 15], 9) == (0, 1)
    assert fn([3, 3], 6) == (0, 1)            # duplicates
    assert fn([3], 6) is None                 # one item cannot pair with itself
    assert fn([], 1) is None
    assert fn([1, 2, 3], 99) is None
print("both agree")

Follow-up: “What if the list is sorted?” Two pointers from each end, O(n) time and O(1) space. “What if there are many valid pairs?” Ask which one is wanted; if all, collect them and mind duplicates. More on patterns: the DSA sheet.

Problem 4 — a small class with a rule (classes)

Prompt: “Design a BadgePool: assign a free badge to an employee, release it, and never hand the same badge to two people.” Class questions test state, invariants and error handling; they rarely need inheritance.

p4_badge_pool.py
class PoolEmpty(Exception):
    """Raised when no badge is free. A named error lets callers handle exactly this case."""

class BadgePool:
    def __init__(self, badge_ids):
        self._free = list(dict.fromkeys(badge_ids))   # drop duplicates, keep order
        self._assigned = {}                           # employee_id -> badge_id

    def assign(self, employee_id):
        if employee_id in self._assigned:             # asking twice must be safe (idempotent)
            return self._assigned[employee_id]
        if not self._free:
            raise PoolEmpty(f"no free badge for {employee_id}")
        badge = self._free.pop(0)
        self._assigned[employee_id] = badge
        return badge

    def release(self, employee_id):
        badge = self._assigned.pop(employee_id, None)
        if badge is None:
            return False                              # releasing twice is a no-op, not a crash
        self._free.append(badge)
        return True

    def free_count(self):
        return len(self._free)

pool = BadgePool(["b-1", "b-2", "b-1"])              # duplicate id in the input
assert pool.free_count() == 2
assert pool.assign("e-1") == "b-1"
assert pool.assign("e-1") == "b-1"                   # same employee, same badge, no second badge used
assert pool.free_count() == 1
assert pool.assign("e-2") == "b-2"
try:
    pool.assign("e-3")
except PoolEmpty as err:
    print("caught:", err)                            # caught: no free badge for e-3
else:
    raise AssertionError("expected PoolEmpty")
assert pool.release("e-1") is True and pool.release("e-1") is False
assert pool.assign("e-3") == "b-1"                   # the released badge is reusable

Follow-up they ask: “Is this thread-safe?” No: two threads can both pass the if not self._free check. Say so, then say you would add a lock (threading.Lock) in one process, or a database row lock or unique constraint across processes. Naming the limit honestly beats claiming it is safe.

Problem 5 — merge overlapping intervals (sorting)

Prompt: “Given booking windows as (start, end), merge the overlapping ones.” Clarify: do touching intervals like (1,3) and (3,5) merge? (Here: yes.)

p5_intervals.py
def merge_intervals(intervals):
    merged = []
    for start, end in sorted(intervals):                 # sorted() returns a new list: input untouched
        if merged and start <= merged[-1][1]:            # overlaps or touches the last merged window
            merged[-1] = (merged[-1][0], max(merged[-1][1], end))   # max: the new one may sit inside it
        else:
            merged.append((start, end))
    return merged

assert merge_intervals([(1, 3), (2, 6), (8, 10), (15, 18)]) == [(1, 6), (8, 10), (15, 18)]
assert merge_intervals([(1, 3), (3, 5)]) == [(1, 5)]       # touching
assert merge_intervals([(1, 10), (2, 3)]) == [(1, 10)]     # contained: why max() is needed
assert merge_intervals([]) == []
data = [(5, 6), (1, 2)]
assert merge_intervals(data) == [(1, 2), (5, 6)] and data == [(5, 6), (1, 2)]
print("ok")

Say: “Sorting dominates: O(n log n); the pass is O(n). Space O(n) for the output.” The classic bug is writing merged[-1][1] = end instead of max(...), which shrinks (1,10) when (2,3) follows. Your third assertion exists to catch exactly that.

Problem 6 — totals from messy CSV (files and error handling)

Prompt: “Sum hours per site from this CSV. Some rows are bad. Count them, do not crash.”

p6_csv_totals.py
import csv
import io

DATA = """request_id,site,hours
req-1,BLR-01,4
req-2,HYD-01,abc
req-3,BLR-01,2.5
,BLR-02,1
req-5,BLR-01,
"""

def hours_by_site(text):
    totals, bad = {}, 0
    for row in csv.DictReader(io.StringIO(text)):   # csv handles quotes and commas inside fields
        try:
            hours = float(row["hours"])             # ValueError for 'abc', for '' too
        except (TypeError, ValueError):
            bad += 1
            continue
        if not row["request_id"]:
            bad += 1
            continue
        totals[row["site"]] = totals.get(row["site"], 0) + hours
    return totals, bad

totals, bad = hours_by_site(DATA)
print(totals, bad)          # {'BLR-01': 6.5} 3
assert totals == {"BLR-01": 6.5} and bad == 3
assert hours_by_site("request_id,site,hours\n") == ({}, 0)    # header only

Follow-up: “Why not line.split(',')?” A quoted field such as "Bengaluru, Block A" contains a comma; csv parses quotes correctly. “How do you open a real file?” with open(path, newline="", encoding="utf-8") as f: and pass f to DictReader.

Problem 7 — safe lookup in nested JSON (dicts and lists)

Prompt: “Write get_path(obj, "a.b.0.c", default) that walks dict keys and list indexes and returns default on any miss.” Typical for API-response handling.

p7_get_path.py
def get_path(obj, path, default=None):
    cur = obj
    for part in path.split("."):
        if isinstance(cur, dict) and part in cur:
            cur = cur[part]
        elif isinstance(cur, list) and part.isdigit() and int(part) < len(cur):
            cur = cur[int(part)]
        else:
            return default                      # any miss: wrong type, missing key, index too big
    return cur

doc = {"items": [{"id": "req-1", "meta": {"site": "BLR-01"}}, {"id": "req-2"}], "total": 0}
assert get_path(doc, "items.0.meta.site") == "BLR-01"
assert get_path(doc, "items.1.meta.site", "n/a") == "n/a"     # missing key
assert get_path(doc, "items.5.id") is None                    # index out of range, no IndexError
assert get_path(doc, "total") == 0                            # a falsy value is still a value
assert get_path(doc, "total.x", "d") == "d"                   # walking into an int
assert get_path(doc, "") is None                              # '' splits to [''] which is a miss
print("ok")

You must be able to explain: why the checks are part in cur and int(part) < len(cur) rather than a bare cur[part] in a try/except or a truthiness test. Membership checks separate “the key is missing” from “the key holds 0 or None”; the assertion on total == 0 proves a falsy value is returned, not replaced by the default.

Interviewers ask

“What is the time complexity of looking something up in a Python list versus a set?”

Attempt it, then open.

List membership (x in lst) scans: O(n). Set and dict membership hashes the key: O(1) on average, O(n) in a pathological collision case, which I would mention but not dwell on. That is why “have I seen this?” inside a loop should use a set: it turns an O(n squared) program into O(n). Follow-up: “What is the cost?” Memory, and the items must be hashable (a list cannot go in a set; a tuple can).

Bad answers: “sets are faster” with no number; saying a dict lookup is always O(1) with no “average”; not knowing lists are scanned.

FROM requests
WHERE status = 'approved'

FROM employees e
LEFT JOIN requests r ON r.employee_id = e.id

-- Problem 3: ROW_NUMBER numbers rows inside each partition; keep number 1.
-- The second ORDER BY column (id) breaks ties so the result is deterministic.
SELECT employee_id, id, created_on
FROM (SELECT r.*, ROW_NUMBER() OVER (PARTITION BY employee_id ORDER BY created_on DESC, id DESC) AS rn
      FROM requests r)
WHERE rn = 1
ORDER BY employee_id;
-- [('e-1','req-2','2027-03-03'), ('e-2','req-4','2027-03-02'), ('e-3','req-6','2027-03-05'), ('e-4','req-7','2027-03-05')]

-- Problem 4: DENSE_RANK keeps ties together. Ops has Asha 2, Ravi 2, Isha 0: ranks 1, 1, 2.
SELECT dept, name, n
FROM (SELECT e.dept, e.name, COUNT(r.id) AS n,
             DENSE_RANK() OVER (PARTITION BY e.dept ORDER BY COUNT(r.id) DESC) AS rk
      FROM employees e LEFT JOIN requests r ON r.employee_id = e.id
      GROUP BY e.id)
WHERE rk <= 2
ORDER BY dept, n DESC, name;
-- [('Finance','Meera',2), ('Finance','Kabir',1), ('Ops','Asha',2), ('Ops','Ravi',2), ('Ops','Isha',0)]
-- Three Ops rows for "top two": that is the tie decision. ROW_NUMBER would drop Ravi or Asha arbitrarily.

-- Problem 5: SUM(...) OVER (ORDER BY ...) is a running total; the aggregate inside is the per-day count.
SELECT created_on, COUNT(*) AS n, SUM(COUNT(*)) OVER (ORDER BY created_on) AS running
FROM requests
GROUP BY created_on
ORDER BY created_on;
-- [('2027-03-01',1,1), ('2027-03-02',2,3), ('2027-03-03',1,4), ('2027-03-04',1,5), ('2027-03-05',2,7)]
Interviewers ask

“What is the difference between ROW_NUMBER, RANK and DENSE_RANK?”

Attempt it, then open.

All three number rows within an ordered partition. ROW_NUMBER gives every row a unique number even on ties (1, 2, 3), so which tied row comes first is arbitrary unless you add a tie-breaker. RANK gives tied rows the same number and then skips (1, 1, 3). DENSE_RANK gives tied rows the same number and does not skip (1, 1, 2). Use ROW_NUMBER to pick exactly one row per group, DENSE_RANK for “top N values including ties”. Follow-up: “Why a subquery around the window function?” Window functions are evaluated after WHERE and GROUP BY, so you cannot filter on rn in the same level; you filter in the outer query.

Bad answers: describing all three as “ranking” with no tie example; choosing ROW_NUMBER for “top two scores” without noticing ties.

REST API questions

Interviewers use REST questions to find out whether you have been bitten by a real integration. The strongest answers name a failure (a retry that created two records) and the mechanism that prevents it. Background: the HTTP sheet and the FastAPI sheet.

Drill — REST fundamentals (attempt, then open)
What does it mean for an HTTP method to be idempotent, and which ones are?

Making the same request once or many times leaves the server in the same final state. GET, PUT, DELETE, HEAD and OPTIONS are defined as idempotent; POST is not, and PATCH is not guaranteed to be. It says nothing about the response being identical: a second DELETE may return 404 while the state (gone) is the same. Follow-up: “How do you make a POST safe to retry?” An idempotency key, shown next. Bad answer: “idempotent means it returns the same response.”

PUT versus PATCH versus POST?

POST creates (or triggers an action) and the server picks the id. PUT replaces the whole resource at a known URL, so repeating it is harmless. PATCH changes some fields; whether repeating it is safe depends on the operation (“set status to approved” is; “add 1 to a counter” is not). Follow-up: “What if two clients PATCH the same record?” Last write wins unless you add optimistic concurrency, an ETag with If-Match or a version field, so the second client gets 412 or 409 instead of silently overwriting.

401 versus 403 versus 404, and 400 versus 422?

401: I do not know who you are (missing or invalid credentials). 403: I know who you are and you are not allowed. 404: it does not exist, and sometimes deliberately returned instead of 403 so you cannot probe what exists. 400: the request is malformed. 422: well-formed but fails validation (FastAPI uses 422 for body validation errors by default). Teams differ on 400 versus 422; consistency matters more than the choice. Follow-up: “What does the client do on each?” 401: refresh the token and retry once. 403, 400, 422: do not retry; fix the request. 429 and 5xx: retry with backoff.

Offset versus cursor pagination: which would you use, and why?

Offset (?page=3) is simple but skips or repeats rows when data is inserted between requests, and gets slow on big tables because the database walks past all the skipped rows. Cursor (keyset) pagination returns an opaque cursor encoding the last seen key and asks for rows after it: stable under inserts and fast with an index. I use cursors for feeds and anything that changes; offset is acceptable for small, static, admin-style lists that need “jump to page 7”. Follow-up: “What is the cost of cursors?” No random page access, and the sort key must be unique (add the id as a tie-breaker).

The vendor API is slow and flaky. How do you call it from your service?

Set explicit connect and read timeouts (never the default of none). Retry only what is safe: idempotent operations, or POSTs carrying an idempotency key; retry on timeouts, 429 and 5xx, not on 4xx. Back off exponentially with jitter and honour Retry-After. Cap total attempts and total time. Put the call behind a queue so the user is not waiting, and keep a dead-letter path for what exhausts its retries. Follow-up: “What if the vendor processed the request but the response was lost?” That is exactly why the key exists: the retry returns the original result instead of creating a second one.

Webhooks versus polling?

Webhooks push events to you when something changes: low latency, no wasted calls, but you must expose an endpoint, verify signatures, and cope with duplicates, out-of-order delivery and downtime (providers usually retry, so you will see the same event more than once). Polling is simple and under your control but wasteful and slow. In practice: use webhooks for speed, plus a periodic reconciliation poll to catch what was lost. Follow-up: “How do you verify a webhook?” HMAC signature over the raw body with a shared secret, a timestamp to limit replay, and a constant-time comparison.

Idempotency key, in code

The server remembers the first result for each key. A retry with the same key and the same body replays that result; the same key with a different body is a client bug and is rejected. You must be able to explain why the body fingerprint is stored.

rest_idempotency.py
import hashlib
import json

class RequestsApi:
    def __init__(self):
        self.created = []                     # the "database"
        self.keys = {}                        # idempotency key -> (body fingerprint, saved response)

    def post_request(self, key, body):
        fingerprint = hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()
        if key in self.keys:
            saved_fingerprint, saved_response = self.keys[key]
            if saved_fingerprint != fingerprint:
                return 422, {"error": "idempotency key reused with a different body"}
            return 200, saved_response        # replay: no second record
        record = {"id": f"req-{len(self.created) + 1}", **body}
        self.created.append(record)
        response = {"created": record}
        self.keys[key] = (fingerprint, response)
        return 201, response

api = RequestsApi()
body = {"employee_id": "e-902", "site_id": "BLR-01"}
status1, r1 = api.post_request("key-A", body)
status2, r2 = api.post_request("key-A", body)           # the client timed out and retried
print(status1, status2, len(api.created))               # 201 200 1
assert (status1, status2, len(api.created)) == (201, 200, 1) and r1 == r2
assert api.post_request("key-A", {"employee_id": "e-1", "site_id": "X"})[0] == 422
assert api.post_request("key-B", body)[0] == 201 and len(api.created) == 2   # new key, new request
Red pencil — what this demo does not prove

It is single-threaded. Two simultaneous requests with the same key can both pass the if key in self.keys check and create two records. In production the key is stored with a unique constraint (an atomic insert), or taken under a lock, and the saved response is written in the same transaction as the record. Say this unprompted; it is the follow-up. I did not test concurrency here.

Cursor pagination and why offset breaks

rest_pagination.py
import base64
import json

def encode(last_id):                               # opaque to the client: they must not parse or build it
    return base64.urlsafe_b64encode(json.dumps({"after": last_id}).encode()).decode()

def decode(cursor):
    return json.loads(base64.urlsafe_b64decode(cursor.encode()))["after"]

def cursor_page(items, limit=3, cursor=None):
    after = decode(cursor) if cursor else 0
    batch = [it for it in items if it["id"] > after][: limit + 1]   # SQL: WHERE id > :after ORDER BY id LIMIT :limit+1
    has_more = len(batch) > limit                                    # fetch one extra to know whether another page exists
    batch = batch[:limit]
    return batch, (encode(batch[-1]["id"]) if has_more else None)

def offset_page(items, offset, limit=3):
    return items[offset: offset + limit]

items = [{"id": i} for i in range(1, 8)]
p1, cur = cursor_page(items)
o1 = offset_page(items, 0)
items.insert(0, {"id": 0})                          # a new row arrives between page 1 and page 2

p2, cur = cursor_page(items, cursor=cur)
o2 = offset_page(items, 3)
print([i["id"] for i in p1], [i["id"] for i in p2])    # [1, 2, 3] [4, 5, 6]
print([i["id"] for i in o1], [i["id"] for i in o2])    # [1, 2, 3] [3, 4, 5]   (3 appears twice)
assert [i["id"] for i in p2] == [4, 5, 6]
assert [i["id"] for i in o2] == [3, 4, 5]
last, cur = cursor_page(items, cursor=cur)
assert [i["id"] for i in last] == [7] and cur is None
Offset (?page=2)
Simple. Allows jumping to page 7. Repeats or skips rows when data changes between requests; cost grows with the offset.
Cursor (?after=abc)
Stable under inserts and deletes; cost stays flat with an index. No random page access; needs a unique sort key.

Pick: cursor for anything that changes while people read it or that grows large; offset only for small, mostly static lists.

Verifying a webhook

rest_webhook_signature.py
import hashlib
import hmac
import time

SECRET = b"demo-secret-not-a-real-key"           # synthetic. Real secrets come from a secret store, never source.

def sign(body, timestamp):
    message = f"{timestamp}.".encode() + body        # bind the timestamp into the signature
    return hmac.new(SECRET, message, hashlib.sha256).hexdigest()

def verify(body, timestamp, signature, now=None, tolerance=300):
    now = time.time() if now is None else now
    if abs(now - timestamp) > tolerance:             # an old, replayed request is rejected
        return False
    return hmac.compare_digest(sign(body, timestamp), signature)   # constant-time compare

body = b'{"event_id": "evt-1", "type": "badge.provisioned"}'
ts = 1_700_000_000
sig = sign(body, ts)
assert verify(body, ts, sig, now=ts + 10)
assert not verify(body + b" ", ts, sig, now=ts + 10)             # body tampered with
assert not verify(body, ts, sig, now=ts + 10_000)                # too old: replay
assert not verify(body, ts, "0" * 64, now=ts + 10)               # wrong signature
print("webhook checks ok")

Why compare_digest? An ordinary == returns as soon as one character differs, so response time leaks how many leading characters were right. A constant-time comparison does not. Why the raw body? If you parse the JSON and re-serialise it, whitespace and key order change and the signature no longer matches. Verify the bytes you received.

Interviewers ask

“Your service consumes a queue with at-least-once delivery. A message is delivered twice. What happens, and how do you stop the harm?”

Attempt it, then open.

The handler runs twice. If it sends an email or creates a record, the user gets two. The fix is to make the handler idempotent: give each message a stable id (or derive a business key such as request_id + action), and record “processed” in the same transaction as the effect, with a unique constraint, so the second delivery finds the row and does nothing. For effects outside my database (an email, a vendor call), pass the same id as an idempotency key to the vendor, or accept that a rare duplicate is possible and say so. Follow-up: “Why not just mark processed first?” If the process dies between marking and acting, the work is lost forever; that trades a duplicate for a silent drop, which is usually worse.

Bad answers: “use a queue that guarantees exactly-once”; “it will not happen”; checking a variable in memory.

“How would you rate-limit a public endpoint?”

Attempt it, then open.

Pick the key (API key, user id, or IP as a weak fallback), the algorithm and the numbers. A sliding window or token bucket per key; the lab’s SlidingWindowLimiter is the single-process version. Drill — RAG questions (attempt, then open)
The assistant gives a confident wrong answer. How do you debug it?

Split the system at the retrieval boundary. Step 1: for that question, were the right chunks retrieved? If not, it is a retrieval problem: chunking, embedding model, missing keyword search, a filter excluding the document, or the document never indexed. If the right chunks were retrieved and the answer is still wrong, it is a generation problem: the prompt, too many distracting chunks, contradictory sources, or the model ignoring context; then tighten the instruction to answer only from the sources and cite, and test refusal. Either way, add the failing question to the golden set so it can never regress silently. Follow-up: “How do you find out the document was never indexed?” Log ingestion results per document id and check the count against the source.

How do you choose chunk size?

It is a trade-off, and I would measure it rather than quote a number. Small chunks retrieve precisely but lose context; large chunks keep context but dilute the embedding and cost more tokens per question. Start with a few hundred tokens with some overlap, split on natural boundaries (headings, paragraphs) rather than a fixed character count, then compare recall@k on a golden set for two or three sizes. Follow-up: “What if answers span two chunks?” Overlap, retrieve neighbouring chunks, or index parent sections with child chunks.

How do you evaluate a RAG system without a research team?

Write 30 to 50 real questions with the document and passage that answers each, including some that should be refused. Measure retrieval alone (did the right passage appear in the top k?), then answers: is every claim supported by a cited passage, and did it refuse the unanswerable ones? Start by hand-grading; an LLM-as-judge can scale it later, but calibrate it against your human grades first or you are measuring the judge. Keep the set and scores in version control. Follow-up: “Your score went up. Is it better?” Only if it did not go down on the questions that used to pass; look at per-question changes, not just the average.

How do you stop users seeing documents they should not?

Store access metadata (group, tenant, classification) with each chunk at ingestion and filter on the caller’s identity in the retrieval query, before anything reaches the model. Filtering afterwards, or trusting the model not to mention it, is not access control. Keep the permissions in sync: when a document’s access changes, re-index or update the metadata. Follow-up: “What if permissions change after indexing?” Treat that as a freshness requirement with its own deadline and a test, not an afterthought.

RAG versus fine-tuning?

RAG supplies knowledge at question time from documents you control: fresh, citable, and access-controlled. Fine-tuning changes behaviour or style (format, tone, a narrow task) and is a poor way to store changing facts, because you cannot cite or easily update or delete them. For “answer from our documents”, start with RAG. Consider fine-tuning only after you have an evaluation set showing prompt and retrieval improvements are exhausted. Follow-up: “Can you combine them?” Yes, but earn the complexity with measurements first.

Evaluation in code: recall@k and MRR

You must be able to explain these two numbers. Recall@k: of the questions, in what fraction does the right passage appear in the top k results? MRR (mean reciprocal rank): the average of 1/rank of the first right passage, so finding it first counts more than finding it fifth.

def recall_at_k(results, k):
    """results: list of (ranked_passage_ids, correct_passage_id). Fraction with the answer in the top k."""
    if not results:
        return 0.0
    hits = sum(1 for ranked, correct in results if correct in ranked[:k])
    return hits / len(results)

def mean_reciprocal_rank(results):
    if not results:
        return 0.0
    total = 0.0
    for ranked, correct in results:
        if correct in ranked:
            total += 1 / (ranked.index(correct) + 1)       # rank 1 -> 1.0, rank 2 -> 0.5, rank 4 -> 0.25
    return total / len(results)

Drill — agents (attempt, then open)
How do you stop an agent doing something harmful?

Layers, none of which depends on the model behaving. (1) Least privilege: the tools run with the calling user’s permissions, or a narrow service account; read tools and write tools are separate. (2) An allow-list of tools and schema validation on every argument in code. (3) Approval for any write or irreversible action, showing the exact parameters. (4) Hard limits: maximum steps, tokens, time and spend per request. (5) Audit log of every proposed and executed action. (6) Treat tool output and retrieved text as untrusted input, since it can carry injected instructions. Follow-up: “Is a system prompt saying ‘never delete’ enough?” No. A prompt is a request, not a control; enforcement lives in code.

What is the difference between a workflow and an agent?

In a workflow, your code decides the sequence and the model fills in steps (classify, extract, draft). In an agent, the model decides the sequence at runtime by choosing tools in a loop. Workflows are more predictable and cheaper; agents handle open-ended tasks. Many production systems are workflows with one small agentic step. Follow-up: “Which did you build?” Answer from your own project, honestly, including if the answer is “a workflow, because the steps were known”.

Your agent loops, calling the same tool repeatedly. What do you do?

Immediately: a step cap and a repeated-call check so it stops and reports, rather than burning budget. Diagnose from the trace: is the tool returning an error the model cannot interpret, is the result identical each time (the model sees no progress), or is the tool description ambiguous? Fix the tool’s error messages and description first, then the prompt. Add the case to a regression set. Follow-up: “Why not raise the step limit?” That hides the cause and raises the cost of every future failure.

How do you design tools for a model?

Few, with clear names and one job each; descriptions that say when to use and when not to; strict JSON schemas with enums where possible; outputs that are small, structured and include enough to decide the next step; and error messages that tell the model what to change (“site_id must be one of BLR-01, BLR-02, HYD-01”). Make write tools idempotent, so a repeated call is harmless. Follow-up: “What makes a tool dangerous?” Breadth: a tool that runs arbitrary SQL or shell commands gives the model more authority than your validation can check.

A bounded loop with an allow-list and approval

agent_guards.py
def get_status(request_id):
    return {"request_id": request_id, "status": "approved"}

def revoke_badge(request_id):
    return {"request_id": request_id, "revoked": True}

TOOLS = {"get_status": get_status, "revoke_badge": revoke_badge}
WRITE_TOOLS = {"revoke_badge"}                      # anything that changes the world needs approval

def run_agent(model, approve, max_steps=4):
    history, audit = [], []
    for _ in range(max_steps):                      # guard 1: a hard step limit
        action = model(history)
        if "final" in action:
            audit.append(("final", action["final"]))
            return action["final"], audit
        name, args = action["tool"], action["args"]
        if name not in TOOLS:                       # guard 2: allow-list, checked in code
            result = {"error": f"unknown tool {name}"}
        elif name in WRITE_TOOLS and not approve(name, args):    # guard 3: human approval for writes
            result = {"error": "approval denied"}
        else:
            try:
                result = TOOLS[name](**args)
            except TypeError:                       # guard 4: bad arguments become an error the model can read
                result = {"error": "bad arguments"}
        audit.append((name, args, result))          # guard 5: everything is recorded
        history.append((action, result))
    return "stopped: step limit reached", audit

def scripted(*actions):                             # a fake model that replays a fixed script
    it = iter(actions)
    return lambda history: next(it)

# approved path
model = scripted({"tool": "get_status", "args": {"request_id": "req-1"}},
                 {"tool": "revoke_badge", "args": {"request_id": "req-1"}},
                 {"final": "Revoked req-1."})
answer, audit = run_agent(model, approve=lambda n, a: True)
assert answer == "Revoked req-1." and audit[1][2] == {"request_id": "req-1", "revoked": True}

# approval denied: the write never ran
model = scripted({"tool": "revoke_badge", "args": {"request_id": "req-1"}}, {"final": "Not revoked."})
answer, audit = run_agent(model, approve=lambda n, a: False)
assert audit[0][2] == {"error": "approval denied"}

# invented tool and a loop that never ends
model = scripted({"tool": "delete_everything", "args": {}}, *[{"tool": "get_status", "args": {"request_id": "r"}}] * 10)
answer, audit = run_agent(model, approve=lambda n, a: True, max_steps=3)
assert answer == "stopped: step limit reached" and len(audit) == 3
assert audit[0][2] == {"error": "unknown tool delete_everything"}
print("guards ok")

Drill — MCP (attempt, then open)
What is MCP and what problem does it solve?

The Model Context Protocol is an open protocol for connecting AI applications to tools and data in a standard way, instead of writing a custom integration for every pairing of application and system. An MCP server exposes capabilities; an AI application (the host) runs a client that connects to it. The main server-side primitives are tools (actions the model can request), resources (data the application can read) and prompts (reusable templates). Messages are JSON-RPC 2.0, over standard input/output for local servers or HTTP for remote ones. The specification changes between versions, so I would check the current one before relying on a detail. Follow-up: “Why not just call the REST API?” You can; MCP standardises discovery (tools/list) and invocation so any compliant host can use the same server, and gives you one place to apply descriptions, validation and auth.

How would you secure an MCP server that can change records?

Authenticate the caller and run each operation with that user’s permissions, not a shared super-account. Expose few, narrow tools; separate read from write; mark and require confirmation for destructive ones; validate every argument server-side; make write operations idempotent; rate-limit; log each call with the user and parameters. Treat anything the server returns, and anything a model sends, as untrusted: tool output can carry injected instructions. For remote servers use the transport’s authorisation mechanism rather than inventing one, per the current specification. Follow-up: “Who is responsible for confirmation: the server or the host?” Both should assume the other might not: the host shows approvals, and the server still enforces permissions.

Tool, resource or prompt: how do you choose?

If the model should decide to do something or fetch something on demand, it is a tool. If the application should attach data as context (a file, a record), it is a resource. If it is a reusable, user-selected template for an interaction, it is a prompt. In practice most integrations are tools, and the common mistake is exposing one huge, general tool instead of several small ones with clear descriptions.

Reference design 2 — a vendor integration that survives failure

Prompt: “Our system must create badges in a vendor’s access-control API. The API is slow, rate-limited and sometimes loses responses. Design it.” This is your home ground; the failure paths are what impress.

You must be able to explain the outbox. If the service saved the state and then called the vendor, a crash between the two loses the call; if it called first, a crash loses the state. Writing the state and an outbox row in one database transaction means either both exist or neither, and a worker delivers the outbox rows afterwards, retrying until done.

vendor_integration_sim.py
class RateLimited(Exception):
    def __init__(self, retry_after):
        self.retry_after = retry_after

class VendorDown(Exception):
    pass

class FakeVendor:
    """Stands in for the vendor. Idempotent by key. A script says how each call misbehaves."""
    def __init__(self, script=()):
        self.badges = {}                         # idempotency key -> badge record
        self.calls = 0
        self._script = list(script)

    def provision(self, key, employee_id):
        self.calls += 1
        step = self._script.pop(0) if self._script else None
        if step == "429":
            raise RateLimited(retry_after=2)
        if step == "503":
            raise VendorDown("503 from vendor")
        if key not in self.badges:               # the effect happens at most once per key
            self.badges[key] = {"badge_id": f"b-{len(self.badges) + 1}", "employee_id": employee_id}
        if step == "lost_response":
            raise TimeoutError("response lost")  # it worked, but the caller never finds out
        return self.badges[key]

def provision_with_retry(vendor, key, employee_id, sleep, attempts=5):
    last = None
    for n in range(attempts):
        try:
            return vendor.provision(key, employee_id)
        except RateLimited as err:
            last, wait = err, err.retry_after    # obey the vendor when it tells us
        except (VendorDown, TimeoutError) as err:
            last, wait = err, min(2 ** n, 30)    # otherwise exponential, capped (add jitter in production)
        if n < attempts - 1:
            sleep(wait)                          # no pointless sleep after the final failure
    raise last                                   # out of attempts: surface the last error

def process_outbox(outbox, vendor, sleep):
    dead_letter = []
    for row in outbox:
        if row["status"] != "pending":
            continue
        try:
            badge = provision_with_retry(vendor, row["key"], row["employee_id"], sleep)
            row["status"], row["badge_id"] = "done", badge["badge_id"]
        except (RateLimited, VendorDown, TimeoutError):
            row["status"] = "failed"
            dead_letter.append(row["key"])       # alert a human; replay later with the SAME key
    return dead_letter

def reconcile(ours, theirs):                     # id -> value on each side
    return {"missing_in_theirs": sorted(k for k in ours if k not in theirs),
            "missing_in_ours": sorted(k for k in theirs if k not in ours),
            "mismatched": sorted(k for k in ours if k in theirs and ours[k] != theirs[k])}

def apply_event(state, seen, event):
    """Apply a webhook event at most once, and never let an older event overwrite a newer one."""
    if event["id"] in seen:
        return "duplicate"                              # the vendor retried: same id, do nothing
    current = state.get(event["entity"])
    if current is not None and current["version"] >= event["version"]:
        seen.add(event["id"])                           # remember it, but do not apply: it is stale
        return "stale"
    state[event["entity"]] = {"status": event["status"], "version": event["version"]}
    seen.add(event["id"])                               # in a real system: same transaction as the update
    return "applied"

Enterprise-integration scenario questions

This is where your three-plus years carry real weight. Answer each with the same shape: what is the failure, how do I detect it, what is safe to retry, and how do I know it ended up correct. Keep examples generic; never name an employer, client or their data.

Drill — integration scenarios (attempt, then open)
“The vendor API starts returning 429s.”

429 means I am sending faster than the vendor allows, so retrying harder makes it worse. Honour Retry-After if present; otherwise back off exponentially with jitter. Reduce my own concurrency (a limiter in front of the client, sized to the documented quota) so I do not trigger 429s in the first place, and spread bursts through a queue. Check whether a single noisy caller or a bulk job is responsible, and whether the quota is per key, per tenant or global. Measure the 429 rate as a metric with an alert. Follow-up: “Can you retry a POST?” Only with an idempotency key or after confirming the first attempt did not take effect.

“A nightly file arrives twice.”

First, define identity: a file is the same delivery if it has the same business key (feed name plus business date) and the same content hash. Record each processed file in a ledger with a unique constraint on that key. Same key and same hash: skip and log “duplicate”. Same key but a different hash: that is a correction, not a duplicate; do not silently load it or skip it, flag it for review or apply by a stated rule. Underneath, make the load itself idempotent (upsert by record id), so even a reprocess is harmless. Follow-up: “What if the first run died halfway?” Record completion only after the load commits, and make the load resumable or all-or-nothing in one transaction.

“A large file is split into chunks, encrypted, transferred and reassembled. How do you know the result is correct?”

Send a manifest alongside the chunks: file id, number of chunks, each chunk’s size and checksum, and a checksum of the whole. The receiver confirms every chunk is present and valid before reassembling, verifies the whole-file checksum after, and uses authenticated encryption so tampering or corruption fails decryption rather than yielding garbage. Handle duplicates (same chunk twice), out-of-order arrival (sequence numbers) and partial delivery (do not publish until complete; clean up abandoned partials). Make delivery of the final package idempotent. This is a generic design; apply it to your own experience only as far as you actually built it. Follow-up: “Where do the keys live?” In a managed secret or key store, never in code or in the same place as the data.

“The webhook arrives before the record it refers to exists.”

Do not drop it and do not fail the handler forever. Acknowledge quickly, store the event, and retry processing later with a bounded delay, or park it until the creating event arrives; alternatively fetch the record from the source when the event arrives. Set a limit, after which it goes to a dead-letter queue and an alert, because an event that never resolves is a data problem someone needs to see. Follow-up: “Why not return 500 and let the vendor retry?” You hand your retry policy to the vendor, whose schedule and limits you do not control, and repeated failures may get your endpoint disabled.

“The vendor renames a field without warning.”

Detect it at the boundary: validate every inbound payload against the shape you expect and fail loudly, with the payload id, instead of writing nulls into your database. Keep the raw payload for a short, access-controlled period so you can replay after a fix. Isolate vendor shapes in one adapter layer, so a rename is a one-file change. Add a contract test that runs against a recorded sample of the vendor’s response, and monitor the validation-failure rate. Follow-up: “Should you accept both names?” Temporarily, in the adapter, during the transition, with a date to remove the old one.

“Two systems disagree about a record. Which is right?”

Not a question to answer by guessing: first establish which system is the system of record for that field, then find how they diverged (a lost event, a manual edit, a bug) using timestamps and logs. Fix the record by the owner’s rule, fix the cause, and add the case to the reconciler so it is detected next time. If no owner is defined, that is the real finding, and a design decision for the people who own the process. Follow-up: “Do you auto-correct?” Only for categories with a written rule and a way to undo; report the rest.

import hashlib

def ingest(ledger, store, feed, business_date, content, parse):
    """Return 'processed', 'duplicate' or 'conflict'. The ledger maps (feed, business_date) -> content hash."""
    key = (feed, business_date)
    digest = hashlib.sha256(content).hexdigest()
    if key in ledger:
        return "duplicate" if ledger[key] == digest else "conflict"   # same name and date, different bytes: a human decides
    staged = {}
    for record_id, value in parse(content):
        staged[record_id] = value                        # build first: a bad row raises before anything is written
    store.update(staged)                                 # upsert by id: reprocessing is harmless
    ledger[key] = digest                                 # record completion LAST (same transaction in a real database)
    return "processed"

def parse(content):
    for line in content.decode().splitlines():
        record_id, value = line.split(",")
        yield record_id, value

Drill — deep-dive follow-ups (attempt, then open)
“What alternative did you consider, and why did you reject it?”

Name a real alternative and tie the rejection to a requirement, not a taste: “I considered polling the vendor every minute instead of webhooks; I rejected it because the vendor’s rate limit would have used most of our quota, but I kept a nightly poll as the reconciliation check.” If you honestly did not consider one, say so and say what you would consider now. Follow-up: “Would you decide the same today?” An answer that includes one thing you would change is stronger than “yes”.

“What was the hardest bug?”

Choose a bug where you can narrate the method: symptom, how you reproduced it, the hypothesis you disproved first, the root cause, the fix, and the test or alert that now guards it. Follow-up: “How did you know it was fixed?” The failing test you wrote first now passes, and you watched the metric.

“What would break at 100x the load?”

Estimate before answering: where is the first bottleneck? “What would you do differently?”

Pick something real and specific, not a humble-brag: “I would have written the reconciliation report before the retry logic, because it would have shown me the duplicate problem sooner.” Then show you have acted on it. Avoid “nothing” (no reflection) and “everything” (no judgement).

Behavioural questions and the STAR structure

STAR keeps an answer from rambling: Situation, Task, Action, Result, plus one line on what you learned. Spend most of your time on the Action, in the first person, because that is the only part that tells the interviewer anything about you.

Eight prompts follow. For each, write your own answer from a real event before you open the block; the blocks show what the interviewer is probing, a skeleton, and the usual bad answer. I have not written your stories: they must be true, and they must be yours.

Drill — eight behavioural prompts
1. Tell me about a conflict with a colleague or stakeholder.

Probing: can you disagree about the problem without making it personal, and do you resolve it or avoid it? Skeleton: two people wanted different things for a stated reason; you sought to understand their constraint first (what you asked); you proposed a way to decide (data, a small trial, an escalation path); the outcome, including what you conceded. Bad answer: a story where the other person was simply wrong and you were right, or “I do not really have conflicts”.

2. Tell me about a time you failed.

Probing: honesty, ownership, and whether you change. Skeleton: a real failure with real cost, your specific mistake (not “the requirements changed”), how you found out, what you did to limit the damage, and a concrete practice you adopted that you can show. Bad answer: a disguised strength (“I work too hard”), blaming others, or a failure so small it costs nothing.

3. Tell me about a time the requirements were ambiguous.

Probing: do you stall, guess silently, or reduce ambiguity? Forward-deployed roles weight this heavily. Skeleton: what was unclear; the questions you asked and of whom; the smallest thing you built or showed to get a real reaction; the assumptions you wrote down and had confirmed; the outcome. Bad answer: “I just figured it out” with no description of how, or building the whole thing on an unconfirmed guess.

4. Tell me about a time you had to learn something quickly.

Probing: how you learn, and whether you can tell learning from pretending. This is your story: Python and applied AI in months, alongside a job. Skeleton: the deadline; your method (read the docs, build a small thing, write tests that mark you, ask for review); the evidence of progress (a repository, a test count, a mock result); what you still cannot do. Bad answer: “I learn fast” with no method or evidence, or claiming mastery in weeks.

5. Tell me about something you owned end to end.

Probing: do you follow through after the interesting part, into operations and users? Skeleton: the goal and who relied on it; what you did beyond building (monitoring, documentation, on-call, user feedback); a thing that went wrong after launch and how you handled it; what happened to it afterwards. Bad answer: describing a team project in “we” so the ownership cannot be seen, or ending at launch.

6. Tell me about a time you disagreed with your lead.

Probing: respectful candour, and whether you commit after a decision. Skeleton: the decision and your concern (a risk, with a reason); how you raised it (privately, with evidence or a small test, an alternative offered); the decision made; whether you committed and how it turned out, including if you were wrong. Bad answer: “I went along with everything” or “I proved them wrong and they thanked me”.

7. A client gives you a vague requirement. What do you do?

Probing: customer-facing problem solving; the core of a forward-deployed interview. Skeleton: ask what decision or outcome the requirement serves and who will use it; ask for an example of a good result and a bad one; restate it in writing and get it confirmed; propose a thin first slice that can be shown within days; agree what is explicitly out of scope; check back early. Bad answer: asking for a complete specification before doing anything, or building quietly for a month.

8. Tell me about a mistake you made in production.

Probing: calm under pressure, blameless analysis, prevention. Skeleton: what broke and who was affected; how it was detected (ideally not by a customer); the order you did things in (contain, then diagnose, then fix); the communication you sent; the root cause stated without blame; the safeguard you added. Bad answer: “I have never broken production”, or a story with no impact so nothing was at stake. Confidential details stay out: describe the pattern, not the client.

Drill — mixed round
Walk me through how you would run a 20-minute coding round.

Clarify (inputs, edge cases, bad data), write two or three examples including an edge case, state the approach and its complexity, code in small named functions while narrating decisions, then run my own examples and trace one by hand, and finish with complexity and one improvement. If stuck, solve the slow way first. Follow-up: “Why examples before code?” They become the tests, and they expose misunderstandings while they are cheap.

Your solution is O(n squared). How do you improve it?

Find what the inner loop is doing: usually searching for something. Replace the search with a dict or set lookup (O(1) average), or sort and use two pointers, or use a heap if only the top k matter. Say the trade-off: extra memory for speed. Confirm the new version against the old on the same examples. Follow-up: “What if memory is tight?” Sort in place and use two pointers, accepting O(n log n) time.

Write a query for the latest request per employee. What if two share a timestamp?

ROW_NUMBER() OVER (PARTITION BY employee_id ORDER BY created_on DESC, id DESC) in a subquery, keep rn = 1. The second ORDER BY column is the tie-breaker; without it the choice among equal timestamps is arbitrary and may change between runs. Follow-up: “Without window functions?” Join to a subquery of MAX(created_on) per employee, which returns both rows on a tie, so I would still need a tie rule.

How do you make a POST endpoint safe to retry?

An idempotency key chosen by the client, stored with the saved response and a fingerprint of the request body, in the same transaction as the effect and under a unique constraint. A retry with the same key and body replays the saved response; the same key with a different body is rejected. Keys expire after a stated period. Follow-up: “Two identical requests arrive simultaneously.” The unique constraint makes one insert win; the other waits or receives the winner’s result.

Describe how you would design a RAG assistant for internal policies. Out loud, ten minutes.

Requirements and clarifying questions; components (ingestion, index with vectors, keywords and access metadata, retrieval with rerank, generation with citations and refusal, evaluation harness); one document in and one question through; failure points (stale index, bad chunks, retrieval miss, permissions leak, injection through documents, vendor outage); evaluation (golden set, recall@k, groundedness, refusal); security (filter before the model, untrusted content, minimal logging); cost (tokens per answer, caching, top-k); scale (what breaks at 10x and 100x). The test is that you covered all eight parts, in order, with the failure paths drawn.

When would you not build an agent?

When the steps are known (use a workflow), when one lookup answers it (use a single call), when actions are irreversible and unreviewed, when latency or cost is tight, or when I cannot evaluate success. An agent is justified for open-ended, multi-step tasks with varying tools and a human reviewing the output, and even then with an allow-list, approval for writes, step and spend limits, and an audit log.

The vendor returns 429s during your nightly sync. What now?

Slow down rather than retry harder: honour Retry-After, back off with jitter, reduce concurrency to the documented quota, and spread the work through a queue. Make writes idempotent so retries are safe, set an overall deadline, send exhausted items to a dead-letter queue with an alert, and let the reconciler close any gap the next night. Measure the 429 rate. Follow-up: “What if the quota is genuinely too low?” Ask the vendor for a higher one with numbers, and batch or filter what you request.

A customer says the assistant is wrong. First three actions?

One, collect concrete examples with the question, the answer and the expectation. Two, reproduce and locate the failure: retrieval, source quality, permissions, generation, or an unreasonable expectation. Three, add the examples to the evaluation set and tell the customer in plain words what I found, what I will change and when I will re-measure. I would not change the prompt blindly or promise perfection.

Describe a bug you found by reasoning rather than guessing.

How do you say “I don’t know” in an interview without losing the room?

Boundary, adjacent knowledge, plan: “I do not know that. I do know the related thing, which suggests this; here is how I would confirm.” Then reason aloud from what you do know. Do not bluff, do not invent an API, and do not go silent. A calm “I do not remember the exact name; I expect…” is a normal engineering sentence.
