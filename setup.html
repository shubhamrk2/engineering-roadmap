What you are installing and why

Not a shopping list. A topology: two machines with deliberately different capabilities, joined by exactly one thing they both trust — a Git repository. Read the drawing before you type anything, because the boundary in the middle is the part people get wrong.

1
Admin rights are the whole difference. On the personal machine you can enable the VirtualMachinePlatform Windows feature, install to C:\Program Files, register a Windows service and run a hypervisor. On the corporate machine you can do none of those, which rules out WSL2 unless IT has already enabled it, rules out Docker Desktop’s service, and forces every install into %LOCALAPPDATA%. Establish which of those you actually have on day one — run the two probe commands in §3 before you plan anything.
2
WSL2 is not “Linux emulation”. It is a real Linux kernel in a lightweight Hyper-V virtual machine, sharing your Windows filesystem over a network protocol. That last clause is the important one: code kept under /mnt/c is reached over 9p and is roughly 10× slower to stat, which is fatal for npm install, pytest collection and file watchers. Keep every repository in the Linux home directory. Drawing 01-B is the whole story.
3
Real cloud accounts, real spend, on the personal machine only. You cannot learn Sheet 07 against a simulator. You need an account with MFA on the root user, an IAM Identity Center admin user you actually log in as, and a $10 budget alarm wired up before you create your first NAT Gateway. Corporate cloud tenants are for corporate work; never point your learning Terraform at one.
4
All five data services come from one Compose file. PostgreSQL 16, Redis 7, MongoDB 7, Kafka in KRaft mode and kafka-ui. You never install a database on the host, on either machine. One file, checked into the repo, is what makes the two laptops equivalent from Week 01 onwards — and it is the same file Sheet 06 and Sheet 11 assume you already have.
5
The proxy is a man in the middle, by design. It terminates your TLS connection, inspects the plaintext, then makes its own connection onwards and hands you a certificate it signed itself with the corporate root CA. Your tools reject it because that CA is not in their bundle. Every one of SELF_SIGNED_CERT_IN_CHAIN, CERTIFICATE_VERIFY_FAILED and unable to get local issuer certificate is the same event seen through three different libraries. §3 fixes all three properly, and explains why strict-ssl=false is not a fix.
6
The red line is a policy, not a suggestion. A corporate laptop is monitored, backed up, subject to DLP scanning and can be remotely wiped or forensically imaged. Personal long-lived AWS keys on it are a real incident with your name on it, and a personal SSH key there is compromised the moment the disk is imaged. Two identities, two key pairs, one repository.
7
The repository is the only shared state. Not a USB stick, not OneDrive, not a zip file in email. Both machines clone the same repo, both run the same docker compose up -d, both have a .env derived from the committed .env.example and never committed themselves. When something works on one machine and not the other, the diff is either in .env or in the toolchain — and the verification script in §7 tells you which in ten seconds.
Why this sheet exists at all

Setup is the most-skipped and most-expensive sheet in the set. The failure mode is not that you cannot install Node; it is that you install it four different ways over twelve weeks, end up with three Pythons on PATH, discover in Week 08 that your corporate laptop cannot reach Terraform’s registry, and lose a Saturday block to it. Six hours here buys back roughly twenty over the twelve weeks. Do not start Week 01 until the script in §7 prints a version for every line on both machines.

Personal laptop — the full install

Full admin, so do it properly once. Everything in this section is personal machine only unless it says otherwise. Budget two hours, most of which is downloads.

winget, PowerShell 7 and Windows Terminal

winget ships with Windows 11 and is the one install mechanism you should use for Windows-side software. It writes to the registry properly, supports upgrades, and gives you a reproducible list you can commit. Start by getting a decent shell, because you will be living in it.

PowerShell (Admin) — personal laptop
# Confirm winget exists and is recent. Anything below 1.6 is worth upgrading.
winget --version                       # v1.9.25180

# The shell and the terminal first.
winget install --id Microsoft.PowerShell        --source winget
winget install --id Microsoft.WindowsTerminal   --source winget

# Then the always-on tools. --silent skips the installer UI.
winget install --id Git.Git                     --silent
winget install --id GitHub.cli                  --silent
winget install --id Microsoft.VisualStudioCode  --silent
winget install --id 7zip.7zip                   --silent

# Keep everything current, in one command, once a fortnight.
winget upgrade --all --include-unknown

# Export the exact set so you can rebuild this machine, or seed the corporate one.
winget export -o $HOME\badgedesk-winget.json --include-versions

Two habits worth forming now. Search before you install — package IDs are exact and near-misses are common (Python.Python.3.12, not python3). And prefer the winget source over msstore, because Store packages are sandboxed in ways that break native build tooling.

WSL2 in detail — and where your code must live

WSL2 gives you a real Linux kernel on the same machine as Windows, booting in about a second and sharing memory dynamically with the host. It is not a compatibility layer; there is an actual Hyper-V virtual machine with a Microsoft-built kernel underneath. Understanding that is what makes the filesystem rule obvious rather than arbitrary.

PowerShell (Admin) — personal laptop
# One command now does the lot: enables the VirtualMachinePlatform and WSL Windows
# features, downloads the kernel, and installs the default distribution.
wsl --install

# Pin the default before installing anything, so nothing lands on WSL1.
wsl --set-default-version 2

# See what is offered, then take the one this set assumes.
wsl --list --online
wsl --install --distribution Ubuntu-24.04

# The kernel is updated separately from Windows Update. Do this now and monthly.
wsl --update
wsl --version
# WSL version: 2.3.26.0
# Kernel version: 6.6.87.2-1
# WSLg version: 1.0.65
# Windows version: 10.0.26200.1742

wsl --status
# Default Distribution: Ubuntu-24.04
# Default Version: 2

# If an existing distro is on version 1, convert it. Takes a few minutes.
wsl --list --verbose
#   NAME            STATE           VERSION
# * Ubuntu-24.04    Running         2
wsl --set-version Ubuntu-24.04 2

Two configuration files matter. /etc/wsl.conf lives inside the distribution and configures that distribution; %USERPROFILE%\.wslconfig lives on Windows and configures the virtual machine itself. Enabling systemd is worth doing on day one, because Docker CE, PostgreSQL packages and anything else that ships a unit file expect it.

/etc/wsl.conf — inside Ubuntu, edit with sudo
[boot]
systemd=true                 # so `systemctl` works; needed for Docker CE in §3

[interop]
enabled=true
appendWindowsPath=true       # keeps code.exe and winget on PATH inside Linux

[automount]
enabled=true
options="metadata,umask=0022,fmask=0011"
                             # metadata lets chmod work on /mnt/c. Without it every
                             # Windows file looks like 0777 and git sees phantom
                             # permission changes on every status.

[user]
default=you                  # the Linux user, not your Windows account name

[network]
generateHosts=true
generateResolvConf=true      # set to false only if you hand-manage DNS for a VPN
C:\Users\you\.wslconfig — on the Windows side
[wsl2]
memory=8GB                   # cap it. The default is 50% of RAM and Kafka will take it.
processors=4
swap=4GB
localhostForwarding=true     # localhost:5432 on Windows reaches the VM's 5432
nestedVirtualization=true    # required if you want kind or minikube inside WSL
vmIdleTimeout=60000
Ubuntu 24.04 — first ten minutes inside the distro
sudo apt-get update && sudo apt-get upgrade -y
sudo apt-get install -y build-essential curl git unzip ca-certificates \
                        pkg-config libssl-dev zip

mkdir -p ~/code && cd ~/code          # every repository lives here. No exceptions.

# Prove which filesystem you are on before you trust a benchmark.
df -hT ~/code   | tail -1              # /dev/sdc  ext4   1006G  ...  /
df -hT /mnt/c   | tail -1              # C:\       9p     476G   ...  /mnt/c

# Apply the wsl.conf changes: a full shutdown, not a reboot of the distro.
exit
PowerShell — the command you will use constantly
wsl --shutdown              # stops the VM. Next `wsl` starts it fresh with new config.
wsl -d Ubuntu-24.04         # back in
wsl --terminate Ubuntu-24.04  # stop one distro only

# Back the whole distro up before doing anything drastic. This is your undo button.
wsl --export Ubuntu-24.04 D:\backups\ubuntu-2404-week00.tar
wsl --import Ubuntu-Restored D:\wsl\ubuntu-restored D:\backups\ubuntu-2404-week00.tar
Red pencil — three WSL2 mistakes that cost a day each

Cloning into /mnt/c. Everything works, everything is slow, and you blame the framework. Letting a repo sit inside a OneDrive-synced folder. OneDrive rewrites file timestamps and locks files mid-build, so node_modules and .venv produce random EPERM and EBUSY errors. Installing Node and Python on both Windows and inside WSL and then not knowing which one a terminal is using. Pick one side per language — this set assumes Linux-side for everything except the editor — and check with which -a node whenever something behaves oddly.

Git identity, an SSH key, and proving it works

Configure Git once inside WSL and once on Windows if you will ever use it there. The line-ending setting differs between the two and is the most common source of a diff that shows every line as changed.

Ubuntu (WSL) — git configuration worth having
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"      # match a verified GitHub email
git config --global init.defaultBranch main
git config --global pull.rebase true                  # linear history, no merge noise
git config --global fetch.prune true                  # drop deleted remote branches
git config --global core.editor "code --wait"
git config --global diff.colorMoved zebra
git config --global rerere.enabled true               # remembers conflict resolutions

# Line endings. THIS DIFFERS BY MACHINE:
git config --global core.autocrlf input               # inside WSL / Linux
# On Windows-native Git instead:   git config --global core.autocrlf true

git config --global --list | sort
Ubuntu (WSL) — one key for this machine only
# ed25519, not RSA. Smaller, faster, and what GitHub recommends.
ssh-keygen -t ed25519 -C "you@personal-laptop-2026-08" -f ~/.ssh/id_ed25519
# Enter passphrase: use one. The agent will remember it for the session.

eval "$(ssh-agent -s)"          # Agent pid 1487
ssh-add ~/.ssh/id_ed25519

cat ~/.ssh/id_ed25519.pub
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIH... you@personal-laptop-2026-08

# Paste that into GitHub -> Settings -> SSH and GPG keys -> New SSH key,
# titled "personal laptop (WSL) 2026-08". Or do it from the CLI:
gh auth login                   # choose SSH, let it upload the key for you
gh ssh-key add ~/.ssh/id_ed25519.pub --title "personal laptop (WSL) 2026-08"

# The test. Anything other than this line means the key is not registered.
ssh -T git@github.com
# Hi you! You've successfully authenticated, but GitHub does not provide shell access.

# Keep the agent alive across shells:
printf '%s\n' 'eval "$(ssh-agent -s)" >/dev/null' 'ssh-add -q ~/.ssh/id_ed25519 2>/dev/null' >> ~/.bashrc
Interviewers ask

“What actually happens when you git push over SSH?” The client opens TCP 22 to github.com, both sides negotiate a session key, the server sends its host key which your client checks against ~/.ssh/known_hosts (that is the “authenticity of host” prompt), then you prove you hold the private key matching a public key on the account — the private key never leaves your machine. Only then does git-receive-pack run on the far side. If port 22 is blocked, as it often is on a corporate network, HTTPS on 443 or ssh.github.com:443 is the way round; see §3.

Why a virtual environment at all

Two BadgeDesk services will disagree about a dependency version within six weeks — provisioning-worker wants an older httpx than core does. A venv is just a directory with its own site-packages and a pyvenv.cfg pointing at a base interpreter; activating it puts that directory first on PATH. Installing into the system Python instead is how you end up with an unreproducible machine and a Dockerfile that works only for you. On Debian and Ubuntu, pip install outside a venv now refuses outright with error: externally-managed-environment — that error is the packaging system doing you a favour.

Red pencil — docker vs docker-compose

docker-compose with a hyphen is Compose v1, written in Python, end-of-life since July 2023. It reads version: "3.8" at the top of the file and has different networking defaults. Compose v2 is a Go plugin invoked as docker compose, and the version: key is now obsolete — leaving it in produces a warning on every command. Every Compose invocation on this set is docker compose.

Red pencil — never aws configure with long-lived keys

Why every tool suddenly cannot verify a certificate

This is the single biggest time-sink on a corporate machine, and almost nobody explains it properly. Your employer runs a proxy that decrypts your HTTPS traffic to inspect it, then re-encrypts it with a certificate it signs itself. Windows trusts that signature because IT installed the root certificate. Node, Python and Git do not use the Windows trust store — they each ship their own list of trusted authorities, and the corporate root is not on any of them.

1
The proxy is not attacking you — this is standard corporate data-loss prevention. It is indistinguishable from a man-in-the-middle attack at the protocol level, which is exactly why your tools complain. The fix is to tell each tool that this particular authority is expected.
2
The browser working proves nothing. Chrome and Edge read the Windows store, so the web is fine while npm install fails. If someone tells you “the network is fine, the site loads”, this drawing is your answer.
step 1 — export the corporate root certificate
# Find it. The name varies - look for your company in the subject.
Get-ChildItem Cert:\LocalMachine\Root |
  Where-Object { $_.Subject -match 'MegaCorp|Zscaler|Netskope|Blue Coat|Forcepoint' } |
  Format-List Subject, Thumbprint, NotAfter

# Export it as PEM (Base-64), which is what npm, pip and git all want.
$dst = "$env:USERPROFILE\.certs\corp-root.pem"
New-Item -ItemType Directory -Force -Path (Split-Path $dst) | Out-Null

Get-ChildItem Cert:\LocalMachine\Root |
  Where-Object { $_.Subject -match 'MegaCorp' } |

    "-----BEGIN CERTIFICATE-----"
    [Convert]::ToBase64String($_.RawData, 'InsertLineBreaks')
    "-----END CERTIFICATE-----"

Red pencil

Every search result for these errors suggests npm config set strict-ssl false, pip --trusted-host pypi.org or git config http.sslVerify false. IAM Identity Center is advertised as a free service, and it is — but it provisions two customer-managed KMS keys, at $1/month each, in us-east-1 and us-west-2 regardless of your chosen region. Drill book

Setup questions come up in interviews more than people expect, because they reveal whether you understand the machine or only follow instructions.

Environment and tooling
What is WSL2, and how is it different from WSL1?

WSL2 runs a real Linux kernel inside a lightweight, managed Hyper-V virtual machine, so system calls are genuinely Linux system calls. WSL1 was a translation layer that mapped Linux calls onto the Windows kernel — faster for files on C:, but incomplete, and it could not run Docker. The trade-off in WSL2 is the filesystem boundary: files inside the VM are fast, files on /mnt/c cross a 9p network share and are dramatically slower.

Is a container a lightweight virtual machine?

No. A virtual machine virtualises hardware and runs its own kernel. A container is just processes on the host kernel, isolated with namespaces and limited with cgroups. That is why containers start in milliseconds and a VM takes tens of seconds, and also why a Linux container needs a Linux kernel — which is exactly what WSL2 is providing on your Windows laptop.

Why does npm install fail with a certificate error on your work laptop but the browser works fine?

A corporate proxy terminates TLS and re-signs traffic with its own root certificate. Chrome and Edge read the Windows certificate store, where IT installed that root, so browsing works. Node, Python and Git each ship their own bundled certificate authority list, which does not include it. The fix is to export the corporate root and point NODE_EXTRA_CA_CERTS, REQUESTS_CA_BUNDLE and http.sslCAInfo at it — not to disable verification.

Why should Node be installed with nvm or fnm rather than the installer?

Different projects pin different Node majors, and the installer gives you one global version owned by root. A version manager keeps Node in your home directory, so global installs never need elevation, and lets you switch per project with a .nvmrc. On a machine with no admin rights it is the only approach that works at all.

What goes in .env and what goes in .env.example?

.env.example is committed and lists every variable the application needs, with safe placeholder or local-development values, so a new clone runs immediately. .env holds real values and is git-ignored. The rule is that the names of your secrets are documentation and belong in the repository; the values never do.

You committed an API key. What do you do, in order?

Rotate the key first — assume it is already compromised, because the push may have been mirrored, cached or scraped within seconds. Only then clean history with git filter-repo or BFG and force-push, and tell anyone who has cloned it. Rewriting history without rotating is the common mistake, and it protects nothing.

Two containers in the same Compose file cannot talk over localhost. Why?

Each container has its own network namespace, so localhost inside a container means that container. On a Compose network they reach each other by service name — postgres:5432, kafka:19092. localhost:5432 only works from the host, because of the published port mapping.
