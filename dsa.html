The drill loop

Four steps per problem. The order is the whole point — every one of them is a thing an interviewer will actually watch you do.

1
Open a problem and read only section 1. It has the statement, the constraints, two worked examples and the edge cases — everything you would get on the platform and nothing else. Give it ten minutes on paper before you touch a keyboard. If you cannot start, that is data: it means you do not recognise the pattern yet, and that is what section 2 is for.
2
Press Reveal approach. You get a ladder, not an answer: brute force first with its complexity, then better, then optimal. Read the brute force even when you already saw the optimal — interviewers almost always want the naive solution stated and costed before you improve it, and “I would start with the O(n²) and then improve it” is a scoring sentence.
3
Type the optimal version in Java and in JavaScript from memory, then compare against section 4. Section 5 lists the differences that actually bite for that specific problem — integer overflow, sort comparators, string immutability. Typing it is what moves it from recognised to recallable.
4
Set the problem to Attempted or Solved. Attempted is not a failure state, it is a queue: it is the list you re-run next week. Progress is stored in this browser's localStorage alongside the sign-offs from every other sheet.
Why this exists

A solutions repository is a reference, not a training tool — the answer is on screen before you have had a thought. This sheet takes the same 369 C++ solutions and reconstructs the question from each one, so the material can be used the way it will be tested. The original C++ is still there, untouched, in section 3.

Reading the constraints

The constraint line tells you the complexity you are allowed to spend. Work that out before you design anything — it eliminates most of the wrong approaches for free.

Interviewers ask

“What is the time complexity?” is rarely the real question. The real question is “can you justify it?” Say where the work happens, not just the letter: “the outer loop runs n times, and each iteration does an O(1) hash lookup, so O(n) time and O(n) extra space for the map.” Naming the space cost without being asked is the part most candidates forget.

The pattern catalogue

Most of the 369 problems are a small number of ideas wearing different clothes. Every problem page is tagged with its patterns, and the search box filters on those tags.

The tags you will see most

Linear scanTwo pointers

One index from each end, or a slow/fast pair. Turns an O(n²) pair hunt into O(n) when the data is sorted or when order does not matter.

Linear scanSliding window

Expand right, shrink left, keep an invariant true. The answer is the best window you ever held.

PrecomputePrefix sum

Range sums in O(1) after an O(n) pass. Paired with a hash map it answers “how many subarrays sum to K”.

PrecomputeHash map

Trade space for time. The single most common way to delete an inner loop.

DivideBinary search

On a sorted array, or on the answer itself when you can test “is X feasible?” monotonically.

StructureMonotonic stack

Next greater, previous smaller, largest rectangle. Each element is pushed and popped once, so O(n).

StructureHeap

Top-K and streaming medians without sorting everything. O(n log k) instead of O(n log n).

RecursionPick / not-pick

The subsequence skeleton. Every subset, combination and knapsack question is this tree with different pruning.

RecursionBacktracking

Place, recurse, undo. The undo is the part people forget, and it is where the bug always is.

OverlapDynamic programming

Recursion with a memo, then a table, then rolling arrays. Always derive it in that order.

GraphsBFS / DFS

Shortest path on an unweighted graph is BFS. Connectivity, cycles and components are DFS or union-find.

BitsXOR tricks

Self-cancelling: a XOR a is 0. Finds the unpaired element, and drives the prefix-XOR subarray counts.

Red pencil

Recognising the pattern is not solving the problem. The failure mode in a real interview is announcing “this is a sliding window” and then fumbling the shrink condition for fifteen minutes. The tag gets you to the right family; the invariant is what you have to be able to state precisely. For every window problem, say out loud what must remain true inside the window before you write the loop.

Three languages, one algorithm

Every problem page carries the original C++ plus Java and JavaScript versions of the optimal approach. These are the differences that change whether your code is correct, not just whether it is idiomatic.

Integer overflow

C++ int and Java int are both 32-bit and both wrap silently on overflow. JavaScript has no integer type at all — every number is a double, exact only up to 2⁵³. The same expression can be wrong in three different ways.

Java — wraps silently at 2³¹
Overflow.java
int lo = 2_000_000_000, hi = 2_000_000_100;
int mid = (lo + hi) / 2;        // -147483598  <- wrapped, negative
int ok  = lo + (hi - lo) / 2;   // 2000000050  <- correct

// The same trap in a sum:
int[] a = {1_500_000_000, 1_500_000_000};
int bad  = a[0] + a[1];         // -1294967296
long good = (long) a[0] + a[1]; //  3000000000
JavaScript — exact only to 2⁵³
overflow.js
let lo = 2000000000, hi = 2000000100;
let mid = (lo + hi) / 2;          // 2000000050  <- fine, no wrap
let half = Math.floor((lo + hi) / 2);

// But precision dies past Number.MAX_SAFE_INTEGER:
9007199254740992 === 9007199254740993;  // true  <- both are 2**53
// Use BigInt when a product can exceed 2**53:
BigInt(3037000500) * BigInt(3037000500); // 9223372037000250000n

Write lo + (hi - lo) / 2 in all three languages even where it is not required. It costs nothing and it is the version an interviewer is watching for.

Sorting

This is the single most common silent wrong answer when a C++ or Java solution is translated to JavaScript.

sorting.js — the default comparator is lexicographic
[10, 9, 100, 1].sort();               // [1, 10, 100, 9]   <- string order
[10, 9, 100, 1].sort((a, b) => a - b); // [1, 9, 10, 100]  <- numeric

// Sorting pairs by second key, then first:
const pairs = [[1, 5], [2, 3], [3, 5]];
pairs.sort((x, y) => x[1] - y[1] || x[0] - y[0]);

// sort() mutates in place and returns the same array.
// Copy first when the caller still needs the original:
const sorted = [...nums].sort((a, b) => a - b);
Sorting.java — the boxing trap
int[] a = {10, 9, 100, 1};
Arrays.sort(a);                       // fine, ascending primitives

// There is no comparator overload for int[]. To sort descending you must box:
Integer[] b = {10, 9, 100, 1};
Arrays.sort(b, Collections.reverseOrder());

// Subtraction comparators overflow. Use the built-in:
Arrays.sort(b, (x, y) -> Integer.compare(x, y));   // safe
// Arrays.sort(b, (x, y) -> x - y);                // wrong near MIN_VALUE

List<Integer> list = new ArrayList<>(List.of(3, 1, 2));
Collections.sort(list);
Red pencil

Two Java traps that cost real interviews. First, list.remove(2) on a List<Integer> removes the element at index 2, not the value 2 — you need list.remove(Integer.valueOf(2)). Second, Integer objects compared with == only work by accident for values in −128…127, because that range is cached. Use .equals() or unbox to int.

Strings and characters

Java — immutable, so build with a builder
Strings.java
// s += c inside a loop is O(n^2): each += copies the whole string.
StringBuilder sb = new StringBuilder();
for (char c : s.toCharArray()) sb.append(c);
String out = sb.reverse().toString();

// char arithmetic works because char is a 16-bit integer:
int idx = s.charAt(i) - 'a';          // 0..25
char back = (char) ('a' + idx);

// Mutating in place needs a char[]:
char[] cs = s.toCharArray();
cs[0] = 'X';
String changed = new String(cs);
JavaScript — immutable too, and no char type
strings.js
// Building with += is optimised by modern engines, but an array join
// is the predictable choice and matches the Java shape:
const parts = [];
for (const c of s) parts.push(c);
const out = parts.reverse().join('');

// There is no char: s[i] is a one-character string.
const idx = s.charCodeAt(i) - 97;          // 'a' is 97
const back = String.fromCharCode(97 + idx);

// s[i] - 'a' does NOT work; it is NaN.
// Mutating in place needs an array:
const cs = [...s];
cs[0] = 'X';
const changed = cs.join('');

In production

arr.shift() being O(n) is not a trivia question. A BFS over 10⁵ nodes written with shift() is O(n²) and will time out on the platform and stall a real queue consumer the same way. In BadgeDesk's provisioning-worker the same mistake — treating a list as a queue — is what turns a retry backlog into an outage.

Drill — complexity and trade-offs
You have an O(n²) solution and the interviewer says nothing. What do you do?

State it yourself: “this is O(n²) time, O(1) space — the repeated work is that I rescan the suffix for every index. If I trade O(n) space for a hash map I can drop it to O(n).” Then ask whether they want the optimisation. Volunteering the cost and naming the specific repeated work is what separates a candidate who memorised a solution from one who understands it. The follow-up is nearly always “so what is the space cost of that map, and does it matter here?”

When is an O(n log n) solution better than an O(n) one?

When the O(n) solution needs O(n) extra memory you do not have, when n is small enough that constants dominate — sorting 50 elements beats building a hash map — or when the sort gives you something else you need, like ordered output. Big-O describes growth, not runtime. Follow-up: “at what n does the crossover happen?” Answer honestly: you would measure it, but it is usually in the hundreds.

What is amortised complexity, and where have you relied on it today?

The average cost per operation across a sequence, even though one individual operation may be expensive. A dynamic array's push is amortised O(1): most pushes are O(1), and the occasional resize copies n elements, but the doubling means those copies total O(n) across n pushes. A monotonic stack relies on the same argument — a single element can trigger many pops, but each element is pushed and popped at most once, so the whole pass is O(n), not O(n²).

Your recursive solution passes the samples and fails the large case. First three checks?

Stack depth — roughly 10⁴ frames in Java and JavaScript, so a recursion of depth 10⁵ dies; convert to an explicit stack or an iterative form. Missing memoisation — if the same arguments recur, you are exponential. Integer overflow in an accumulator, which is silent in Java and a precision loss in JavaScript. Check those before touching the logic, because the logic is probably fine.

Explain why binary search on the answer works.

It needs a predicate that is monotonic: if X is feasible then every value on one side of X is also feasible. You are not searching the input, you are searching the range of possible answers and asking a yes/no feasibility question at each midpoint. “Minimum capacity to ship in D days” is the standard example — if capacity C works, C+1 works, so you binary search C and the check is a linear simulation. Cost is O(n log(range)).

How do you know a greedy algorithm is correct?

You have to argue it, usually with an exchange argument: take any optimal solution, show you can swap in the greedy choice without making it worse, and conclude the greedy choice is safe. If you cannot make that argument, the problem is probably DP. Saying “greedy feels right here” is the wrong answer even when the code passes — the interviewer is testing whether you know the difference between a heuristic and a proof.

Walk me from a recursive solution to an O(1)-space DP.

Four steps, always in this order. Write the recursion and state the parameters that change. Add a memo keyed on exactly those parameters — that alone kills the exponential blowup. Convert to a table by filling the states in dependency order, which removes the call stack. Then notice the table only reads the previous row or two, and keep just those. Doing it in this order means each step is mechanical; jumping straight to the tabulation is where people get the base cases wrong.

Why is a hash map's O(1) lookup a lie, and when does it matter?

It is O(1) expected, not worst case. With adversarial keys that all collide it degrades to O(n) per lookup, making a scan O(n²). Java's HashMap mitigates this by turning long buckets into balanced trees, giving O(log n) worst case. It matters when keys are attacker-controlled — a real denial-of-service vector — and in competitive settings where anti-hash tests exist. In an interview, saying “O(1) average, O(n) worst case with collisions” is the complete answer.

What is the difference between BFS and Dijkstra, and when does BFS stop working?

BFS finds the shortest path when every edge costs the same, because the first time it reaches a node it has used the fewest edges. Add non-uniform positive weights and that stops holding, so you need Dijkstra — a priority queue that always expands the cheapest known node. Add negative weights and Dijkstra breaks too, because a settled node can later be improved; that is Bellman-Ford. Knowing which assumption each algorithm rests on is the actual question.

You cannot see the optimal solution and there are ten minutes left. What now?

Write the brute force, correctly, and say what you are doing: “I will get a correct O(n²) version down first so we have something working, then optimise.” A correct slow solution scores; a half-written clever one does not. Then narrate where the waste is. Most interviewers will hint once you have shown a working baseline, and taking a hint well is itself a positive signal.
