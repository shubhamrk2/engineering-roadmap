The BadgeDesk policy assistant

One concrete thing to build: employees ask “can I get weekend access to the BLR-01 server room?” and get an answer grounded in the actual access policy documents, with citations. Every technique on this sheet appears in it.

1
Chunking is where most RAG quality is won or lost. Split a policy in the middle of the sentence that names the exception and the assistant will confidently tell an employee the opposite of the rule. Chunk on semantic boundaries — headings, clauses — not on a fixed character count, and overlap so a boundary never destroys context.
2
Retrieve broadly, then rerank narrowly. Vector search is fast and approximate; a cross-encoder reranker actually reads the query and each candidate together and is far more accurate but too slow to run over the whole corpus. Twenty then five gives you most of the accuracy for a fraction of the cost. This two-stage shape is the single highest-value improvement over naive RAG.
3
Citations are not decoration. They are how a user verifies the answer, how you debug a wrong one, and how you avoid the assistant being an unaccountable oracle about building access. If the model cannot cite it, the model should not say it.

Red pencil

Never let a model output be the authorisation decision. In BadgeDesk the assistant explains the policy and tells the employee what to request; the approval itself goes through the deterministic flow on Sheet 05, with the unique constraint on Sheet 06 behind it. “The LLM said yes” is not an access control model, and an interviewer will absolutely push on this if you build anything that touches permissions.

Prompt engineering

Less mystical than it sounds. It is specification writing: be explicit about role, task, constraints, format and what to do when uncertain.

The part people skip: evaluation

Prompt work without measurement is superstition. Build a file of 30 to 50 real questions with expected answers before you tune anything, then score every change against it. Measure retrieval separately from generation — if the right chunk was never retrieved, no amount of prompt wording will save the answer. That separation is the single most useful diagnostic habit in this whole discipline, and being able to describe it is what makes an AI answer sound like engineering rather than enthusiasm.

Embeddings and vector databases

pgvector — a vector database you already operate
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE policy_chunks (
  id          bigserial PRIMARY KEY,
  document_id text        NOT NULL,
  section_id  text        NOT NULL,        -- 'AP-4.2', used in citations
  site_id     text,                        -- NULL means it applies globally
  content     text        NOT NULL,
  embedding   vector(1536) NOT NULL,
  token_count int         NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now()
);

-- HNSW for approximate nearest neighbour. vector_cosine_ops must match the
-- operator used in the query, or the index is silently ignored.
CREATE INDEX ON policy_chunks
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- Ordinary B-tree indexes for the metadata filter - this is why keeping
-- vectors in Postgres is pleasant: it is still just SQL.
CREATE INDEX ON policy_chunks (site_id, document_id);

-- Retrieval with a hard access-control filter applied BEFORE similarity.
-- The employee must never be able to retrieve a chunk they may not read,
-- and that is a WHERE clause, not a prompt instruction.
SELECT section_id, content, 1 - (embedding <=> $1) AS similarity
FROM   policy_chunks
WHERE  (site_id = $2 OR site_id IS NULL)
ORDER  BY embedding <=> $1        -- <=> is cosine distance
LIMIT  20;

Making RAG actually work

services/assistant/retrieval.py — the improvements that matter
async def retrieve(question: str, employee: Employee) -> list[Chunk]:
    # 1. Query expansion. Employees ask "can I get in on Saturday"; the policy
    #    says "out-of-hours access". One cheap small-model call bridges that.
    expanded = await expand_query(question)          # gpt-4o-mini, temperature 0

    # 2. Hybrid: vector for meaning, BM25 for exact terms like site codes.
    vector_hits  = await vector_search(expanded, employee.site_ids, limit=20)
    keyword_hits = await bm25_search(question,   employee.site_ids, limit=20)

    # 3. Reciprocal rank fusion - combines two rankings without needing the
    #    scores to be on a comparable scale. Simple, and hard to beat.
    fused = reciprocal_rank_fusion([vector_hits, keyword_hits], k=60)

    # 4. Rerank with a cross-encoder. Reads query and chunk TOGETHER, so it is
    #    far more accurate than comparing two independently computed vectors.
    reranked = await rerank(question, fused[:20])
    top = reranked[:5]

    # 5. A relevance floor. Returning weak chunks invites a confident wrong
    #    answer; returning nothing lets the model say "I cannot find that",
    #    which is the better outcome.
    top = [c for c in top if c.score > 0.35]

    # 6. Order for attention: best first, second-best LAST.
    return interleave_for_attention(top)

Production concerns

ConcernWhat good looks like
EvaluationA golden set of 30–50 questions with expected answers, scored on every change. Retrieval measured separately with recall@k, generation with faithfulness and citation accuracy.
Cost controlPer-user and per-day spend caps enforced in code, a hard max_tokens, semantic caching of repeated questions, and a small model for classification and expansion.
LatencyStream the response so time-to-first-token is what users feel. Run retrieval and reranking concurrently where possible. Set aggressive timeouts — a 30-second answer is a failed answer.
ObservabilityLog prompt, retrieved chunk ids, model, token counts, cost, latency and the answer for every call. Without this you cannot debug a bad answer a user reports tomorrow.
FallbackThe provider will have outages and rate limits. Have a second provider or a degraded path that returns the retrieved policy extracts with no generated summary.
PrivacyNever send names, employee ids or badge numbers to a third-party API. Redact before the call and re-insert after. Check the provider's data-retention terms.
VersioningPrompts live in the repository and are versioned like code. A prompt change is a deploy, with the evaluation suite as its test.

Corporate policy almost certainly forbids sending internal documents to a public LLM API, and this sheet is personal-laptop work for that reason. Practise with a corpus you invent yourself. Which models to pull, and what your GPU can hold

Check your VRAM first — it decides everything. On Windows, nvidia-smi reports it in the top-right of the table.

Subtract what the desktop already holds. Windows, a browser and Teams take 600–800 MB before Ollama starts, so a 4 GB card has roughly 3.4 GB usable — budget against that number, not the sticker one.

Red pencil — “shared GPU memory” is not more VRAM

Task Manager reports dedicated GPU memory and shared GPU memory, the latter usually half your system RAM. It is tempting to add them together. Do not. Shared GPU memory is ordinary system RAM reached over PCIe — useful to a game spilling textures, useless here. Ollama splits a model by layer: some layers run on the GPU in dedicated VRAM, the remainder run on the CPU in system RAM, and it sizes that split against dedicated VRAM alone. If a CUDA allocation does spill into shared memory, throughput collapses further than a clean CPU offload would, because every weight access now crosses PCIe on the critical path. Plan against dedicated VRAM minus what the desktop is holding, and set NVIDIA Control Panel → Manage 3D settings → CUDA - Sysmem Fallback Policy → Prefer No Sysmem Fallback so an oversized model fails loudly instead of silently running at two tokens a second. Your system RAM still matters — it holds the CPU-offloaded layers — so 16 GB makes a 7B model merely slow where 8 GB makes it thrash.

Red pencil — the dimension mismatch that silently breaks retrieval

The schema in §4 declares embedding vector(1536), which is text-embedding-3-small’s width. nomic-embed-text produces 768 dimensions. If you swap the embedding model without changing the column, Postgres rejects the insert — which is the good outcome. The bad outcome is swapping models after ingestion and querying a table embedded with a different model: no error, just quietly meaningless similarity scores. This is Drawing 12-D’s “embedding mismatch” failure, and it is the single most common RAG bug. Change the column, then re-embed everything.

Why building against a local model makes you better at this

A frontier model hides sloppy retrieval. Give gpt-4o twelve mediocre chunks and it will still produce a plausible answer, so you never learn whether your chunking worked. A 7B model has no such slack: if the right chunk is not in the context, the answer is visibly wrong. Building the pipeline against a weak model forces the retrieval to be genuinely good, and retrieval — not the model — is what you are actually being hired to get right. Swap in a paid model at the end and everything gets better for free.

AI engineering
What is RAG and why use it instead of fine-tuning?

Retrieval-augmented generation retrieves relevant documents at query time and puts them into the prompt, so the model answers from supplied context rather than memorised weights. Prefer it when facts change, when you must cite sources, when access control matters per user, and when you need a wrong answer to be traceable to a specific document. Fine-tuning is for behaviour and format — tone, structure, a domain vocabulary — not for facts, because retraining is slow, expensive, and produces a model that cannot tell you where an answer came from.

What is an embedding?

A fixed-length vector of floats representing the meaning of a piece of text, positioned so that semantically similar texts sit close together. Closeness is measured with cosine similarity. This is what lets a query about “getting in on Saturday” retrieve a policy about “out-of-hours access” despite sharing no keywords — and it is also why exact identifiers retrieve badly, which is why you add keyword search alongside.

Your RAG system gives a confidently wrong answer. How do you debug it?

Split retrieval from generation first, because they fail differently. Look at what was retrieved: if the correct chunk is not there, it is a retrieval problem — chunking, embedding model mismatch, missing keyword matching, or too aggressive a metadata filter. If the correct chunk was in the prompt and the answer still contradicts it, it is generation — conflicting chunks, the key one buried in the middle of a long context, or a prompt that does not insist on grounding. Logging retrieved chunk ids per request is what makes this a five-minute investigation.

How would you chunk a policy document?

On semantic boundaries — headings, numbered clauses — rather than a fixed character count, targeting roughly 300 to 800 tokens with 10 to 20 per cent overlap so a boundary never splits a rule from its exception. Prepend the document title and section number to each chunk so it carries its own context and can be cited. Store the section id as metadata for citations and filtering. Then test it: the chunking strategy is a parameter you tune against your evaluation set, not a decision you make once.

What is prompt injection and can you prevent it?

Untrusted content — a retrieved document, a user message, a web page — containing text that the model treats as instructions, because a model sees one undifferentiated token stream and cannot reliably distinguish your instructions from data that resembles them. There is no complete fix through prompting. The defence that actually holds is architectural: least privilege, so the assistant simply cannot reach data or actions the user is not entitled to. Everything else — delimiting untrusted content, validating output, requiring human confirmation for state changes, controlling who can write to the indexed corpus — is defence in depth.

How do you control cost?

Measure first: log prompt and completion tokens on every call, because output is typically three to five times the price of input and average prompt size drifts upward silently. Then cap max_tokens, retrieve five chunks rather than twenty, route classification and query expansion to a small model, cache semantically similar questions, and enforce per-user and per-day spend limits in code rather than trusting a dashboard. Streaming does not reduce cost but it changes what users perceive, which often removes the pressure to use a bigger model.

How do you test something non-deterministic?

Not with string equality. Build a golden set of representative questions with expected answers and score each change against it: recall@k for retrieval, and for generation either an LLM-as-judge rubric or assertions on properties — does it cite a valid section, does it refuse when the answer is absent, does it stay within length. Pin temperature to zero for reproducibility while accepting it is not guaranteed identical. Treat the evaluation suite as the test suite for prompts, and run it in CI when a prompt changes.

When should you not use an LLM?

When the task is deterministic and a rule or a database query would do it — deciding whether an access window is valid is arithmetic, not a language problem. When you need guaranteed correctness or auditability of the decision itself. When latency budgets are tight. When the data cannot leave your network and you cannot run a local model. And when the failure mode is unacceptable: an authorisation decision must never depend on a probabilistic system, which is exactly why the BadgeDesk assistant explains policy and never grants access.
